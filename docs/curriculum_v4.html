Block A — 기반 설계
IT 인프라와 블록체인의 충돌 지점
"이 시스템이 기존 IT 인프라와 부딪히는 지점이 정확히 어디인가?"
3시간 (180분)
선행 연결 선행 CH01에서 비가역성·공개키 암호화·트랜잭션 구조를 개념으로 배웠다면, 이 세션에서는 그 특성들이 금융사 기존 IT(패치 가능한 서버, AD 권한 관리, 즉시 응답 시스템)와 정확히 어디서 충돌하고 어떻게 설계로 해소하는지 봅니다.
1부 · 00:00~00:50
블록체인이 기존 IT와 다른 4가지 지점
  • 배포 후 수정 불가 — 버그 발견 시 어떤 선택지가 있고 각각 비용이 얼마인가
  • 연산·저장 비용 발생 — 온체인에 뭘 올리고 뭘 빼야 하는가
  • 서명 키 = 권한 — 키 유출 시 피해 범위와 즉시 대응 방법
  • 트랜잭션 확정 지연 — 실시간 응답이 필요한 서비스에서 어떻게 처리하는가
2부 · 00:50~01:20
설계 결정 문서로 "왜 이렇게 만들었나" 읽기
  • 블록체인 연결을 추상화한 이유 — 나중에 체인을 바꿔도 비즈니스 로직이 그대로인 구조
  • 외부 결제 파트너를 교체 가능하게 만든 이유 — 사업 환경 변화에 코드가 따라가는 방법
  • 설계 결정 4종 → 각각 어느 코드 위치에서 구현됐는지 직접 추적
실습

선행 연결 선행 CH02에서 로컬 노드를 설치하고 개인키로 지갑을 만들어봤다면, 이 세션에서는 그 노드를 금융기관 내부망에 실제로 연결할 때 신뢰 경계와 접근 제어를 어떻게 설계하는지 봅니다.

블록체인 노드를 내부망에 연결하는 방법
  • 내부망과 외부 노드 사이에 신뢰 경계를 어디에 긋는가

  • RPC와 WebSocket 중 언제 무엇을 선택하는가

1부 · 00:00~00:35
온체인 이벤트가 DB에 도착하기까지

2부 · 01:15~01:45
노드가 꺼진 사이에 발생한 이벤트 복구하기
  • 마지막 처리 블록 번호를 DB에 저장해야 하는 이유
  • 누락 구간을 1,000 블록 단위로 나눠 순차 스캔하는 방법
  • 복구 완료 후 실시간 구독으로 전환하는 흐름
실습
실시간 Issued 이벤트 수신 + 노드 재시작 후 Missed 복구 확인
ChainEventListener.start() → Issued 이벤트 실시간 콘솔 수신
노드 종료 → NFT 발행 → 노드 재시작 → Missed Event 복구 확인
lastProcessedBlock이 DB에 정확히 기록되는지 검증
핵심: 구독은 실시간만 처리한다. queryEvents가 빈 구간을 메운다. 이 두 가지가 동시에 있어야 "단 하나도 놓치지 않는다"고 말할 수 있다.

1부 · 00:00~00:30
Webhook이 Core Banking에 안전하게 전달되려면
  • 위변조 — 서명으로 출처를 확인하고 타이밍 공격을 차단하는 방법
  • 중복 처리 — 같은 요청이 두 번 와도 한 번만 처리되는 구조
  • 전달 실패 — 재시도가 자동으로 일어나고 포기 후 어디로 가는가
2부 · 01:10~02:10
재시도 실패 시 데이터가 사라지지 않는 구조

  • 최대 재시도 초과 시 실패 큐로 이동하는 흐름
  • 실패 큐가 쌓이면 어떤 알람이 발생하고 어떻게 수동 재처리하는가
실습 3종
HMAC 서명 실험 + IdempotencyGuard 테스트 + RetryHandler 백오프 확인
