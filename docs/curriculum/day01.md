## 1부: 교보생명 IT 구조와 블록체인의 충돌 (00:20~01:00)

### 1-1. 교보생명이 현재 운영하는 시스템의 특성 (15분)

**토킹포인트:**

> "금융 IT 시스템에는 몇 가지 공통된 특성이 있습니다. 첫째, 데이터는 수정될 수 있습니다. DB의 보험 계약 레코드는 담당자가 실수로 덮어쓸 수 있습니다. 둘째, 신뢰의 근거는 교보생명이라는 기관입니다. 계약서에 도장을 찍은 법인이 보증합니다. 셋째, 내부망과 외부망은 철저히 분리됩니다. ISMS-P 인증이 요구하는 구조입니다."

현재 교보생명 IT 구조 (일반화):
```
[고객 모바일 앱]
      ↓ HTTPS
[API Gateway / WAF]        ← 외부망
━━━━━━━━━━━━━━━━━━━━━━━━━━━  DMZ
[Internal API Server]      ← 내부망
      ↓
[Core Banking System]
      ↓
[보험 계약 DB / 원장]
```

**이 구조에서 "불변성"은 어떻게 보장되는가?**
- DB 트랜잭션 + 감사 로그
- 접근 제어 (특정 계정만 수정 가능)
- 백업 및 감사

### 1-2. 블록체인이 이 구조와 부딪히는 지점 (25분)

**토킹포인트:**

> "블록체인 노드 하나를 교보생명 인프라에 넣는다고 생각해보세요. 노드는 외부 피어와 통신해야 합니다. 근데 내부망에 있으면 외부와 통신이 안 됩니다. 그렇다고 외부망에 노드를 두면 내부 시스템과 직접 통신이 안 됩니다. 여기서 첫 번째 충돌이 생깁니다."

**충돌 지점 4가지:**

**충돌 1 — 네트워크 위치**
- 블록체인 노드: 외부 피어와 P2P 통신 필요
- 교보 내부망: 외부 직접 통신 차단
- → 해결: DMZ에 노드 배치 + 방화벽 규칙 설계 (Day 02)

**충돌 2 — 이벤트 전달**
- 기존 시스템: DB 트리거, 메시지 큐 등 내부 이벤트
- 블록체인: 이벤트를 "보내주지" 않는다. 직접 구독해야 한다.
- → 해결: ChainEventListener + Webhook (Day 03/04)

**충돌 3 — 키 관리**
- 기존 시스템: 서비스 계정 + DB 패스워드
- 블록체인: 프라이빗 키 (잃으면 복구 불가, 노출되면 자산 탈취)
- → 해결: HSM/KMS, VASP 어댑터 (Day 08)

**충돌 4 — 규제 준수**
- ISMS-P: 내부망 시스템 전수 감사
- 블록체인 노드: 기존 감사 도구로 커버 안 됨
- → 해결: ISMSChecklist 코드화 (Day 08)

### 1-3. 왜 직접 구현을 해야 하는가 (5분)

**토킹포인트:**

> "시중에 블록체인 SaaS가 있습니다. 버튼 하나로 NFT를 발행해주는 서비스도 있어요. 그런데 교보생명이 그걸 쓸 수 있을까요? 그 서비스가 내일 망하면? 계약이 끝나면? 고객 데이터가 외부 서버에? ISMS-P는? 결국 금융기관은 핵심 인프라를 직접 소유해야 합니다. 이 레포가 그 첫 번째 버전입니다."

## 2부: 이 프로젝트의 전체 로드맵 (01:40~02:20)

### 2-1. Phase 1~4 구조 (20분)

**토킹포인트:**

> "이 레포의 `docs/architecture/overview.md`를 보면 Phase가 4개입니다. 오늘부터 9일은 Phase 1만 다룹니다. 근데 코드 안에 Phase 2/3/4 파일이 이미 있어요. 왜일까요?"

```
blockchain/src/
├── phase1/  KyoboNFT.sol        ← 9일 동안 다루는 것
├── phase2/  KRWStablecoin.sol   ← 빈 파일
└── phase3/  SecurityToken.sol   ← 빈 파일
```

> "Phase 2/3 파일이 지금 존재한다는 것은, 이 구조가 Phase 2로 확장될 것을 처음부터 고려했다는 뜻입니다. 나중에 Phase 2 개발자가 와도 구조를 바꾸지 않고 이 자리에 채워넣기만 하면 됩니다."

**Phase별 핵심:**

| Phase | 무엇을 | 왜 지금은 아닌가 |
|---|---|---|
| 1 | 행동 보상 NFT | 지금 시작 |
| 2 | KRW 스테이블코인 | VASP 인가 필요 |
| 3 | STO | 금융위 가이드라인 대기 |
| 4 | VASP 내재화 | 교보 직접 인가 취득 후 |

### 2-2. 추상화 레이어가 왜 중요한가 (20분)

**토킹포인트:**

> "`IChainAdapter` 인터페이스를 보세요. EVM이든 XRP Ledger든 이 인터페이스를 구현합니다. issuer-service는 체인이 뭔지 모릅니다. 그냥 `adapter.sendTransaction()`을 호출할 뿐이에요."

```typescript
// issuer-service 입장
const receipt = await this.deps.chainAdapter.sendTransaction({...});
// EVMAdapter인지 XRPLAdapter인지 모른다
```

> "VASP도 마찬가지입니다. 지금은 외부 VASP를 씁니다. 나중에 교보가 직접 VASP 인가를 받으면 `KyoboVASPAdapter`로 교체합니다. 위 코드는 한 줄도 안 바꿉니다."

**핵심 개념: 인터페이스 = 미래의 교체 가능성을 지금 보장하는 계약**
