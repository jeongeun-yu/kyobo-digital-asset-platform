# 블록체인과 기업 내부망 사이의 DMZ: 커스터디 시스템 게이트웨이 아키텍처

> 금융기관이 블록체인을 도입할 때 가장 먼저 맞닥뜨리는 질문은 기술 선택이 아닙니다. "어떻게 내부 시스템을 안전하게 연결할 것인가"입니다.

## 왜 DMZ가 필요한가

은행이나 보험사의 코어 시스템(원장, 자산 DB)은 인터넷과 직접 연결될 수 없습니다. 그런데 이더리움 메인넷은 퍼블릭 인터넷 위에 있습니다. 이 두 세계를 연결하려면 완충 구역이 필요합니다. 이것이 DMZ(Demilitarized Zone)입니다.

DMZ 없이 내부망에서 블록체인 RPC에 직접 접속하면:

- 내부 IP와 트랜잭션 패턴이 외부 서비스에 노출됩니다
- 퍼블릭 RPC 서비스(Infura, Alchemy)가 다운되면 전체 시스템이 멈춥니다
- 방화벽 정책이 복잡해지고 감사 추적이 어려워집니다

DMZ를 두면 내부망은 DMZ하고만 통신하고, 인터넷과는 절대 직접 닿지 않습니다.

```
인터넷 (퍼블릭 블록체인)  <-->  DMZ  <-->  내부망 (코어 시스템)
```

---

## 전체 아키텍처 구조

3개 구역으로 나뉩니다.

**외부망 (퍼블릭 블록체인)**

이더리움 메인넷과 RPC 엔드포인트, 스마트컨트랙트 이벤트 로그가 여기 있습니다.

**DMZ (게이트웨이 레이어)**

5개 구성요소가 내부-외부 중계를 담당합니다: Private RPC Node, Gateway Server, Webhook Receiver, Redis Streams, Transaction Dispatcher.

**내부망 (코어 시스템)**

자산 원장, 승인 워크플로우, MPC 키 관리, HSM, Hot/Cold 지갑이 여기 있습니다.

---

## 데이터 흐름 1: 블록체인 이벤트 수신 (외부 → 내부)

블록체인에서 이벤트가 발생했을 때 내부 시스템에 전달되는 흐름입니다.

```
[이더리움 메인넷]
      |
      | 스마트컨트랙트 이벤트 발생
      v
[Webhook Receiver]  <-- DMZ 경계
      |
      | 수신 즉시 큐에 적재
      v
[Redis Streams]
      |
      | Consumer가 메시지 꺼내서 처리
      v
[Core System]  <-- 내부망 경계
      |
      | 비즈니스 로직 처리
      v
[감사 로그 DB]
```

**핵심 설계 원칙**: Webhook Receiver는 이벤트를 받는 즉시 Redis Streams에 적재하고 응답합니다. 직접 처리하지 않습니다. 이유는 아래에서 설명합니다.

---

## 데이터 흐름 2: 트랜잭션 제출 (내부 → 블록체인)

내부에서 승인된 트랜잭션을 블록체인에 제출하는 흐름입니다.

```
[Core System]  <-- 내부망
      |
      | 트랜잭션 생성 + 승인 워크플로우 완료
      v
[Redis Streams]
      |
      | Transaction Dispatcher가 꺼냄
      v
[Transaction Dispatcher]  <-- DMZ
      |
      | 서명 완료된 트랜잭션 전달
      v
[Gateway Server]
      |
      | 유일한 외부 통신 채널
      v
[Private RPC Node]
      |
      v
[이더리움 메인넷]
```

---

## DMZ 구성요소 상세

### Private RPC Node

퍼블릭 RPC 서비스를 쓰지 않고 DMZ 안에 전용 노드를 운영합니다.

**퍼블릭 RPC 사용 시 문제점**

| 항목 | 퍼블릭 RPC | Private RPC Node |
|---|---|---|
| 트랜잭션 데이터 노출 | 외부 서비스에 모두 노출 | 내부에서만 처리 |
| 서비스 의존성 | Infura/Alchemy 장애 시 중단 | 자체 운영으로 독립 |
| SLA 보장 | 외부 정책에 종속 | 직접 관리 |
| 감사 추적 | 불가 | 모든 요청 로깅 가능 |

노드가 단일 장애점이 되지 않도록 Active-Standby 이중화 구성이 필요합니다.

---

### Gateway Server

내부망과 블록체인 사이의 **유일한 통신 채널**입니다. 방화벽은 Gateway를 통하지 않는 모든 블록체인 통신을 차단합니다.

Gateway에서 처리하는 것들:

- 인증 및 접근 제어 (내부 시스템만 접근 가능)
- 요청/응답 로깅 (감사 추적)
- Rate Limiting (과도한 트랜잭션 제출 방지)
- 트랜잭션 형식 검증

---

### Webhook Receiver

블록체인 이벤트를 HTTP로 수신하는 엔드포인트입니다.

**중요한 설계 결정**: Receiver는 이벤트를 받는 즉시 Redis Streams에 넣고 `200 OK`를 반환합니다. 처리 로직을 여기서 실행하지 않습니다.

왜냐하면 처리 중 오류가 나면 이벤트를 다시 보내달라고 요청할 방법이 없기 때문입니다. 이벤트는 이미 발생했고, 블록체인은 재전송을 보장하지 않습니다.

---

### Redis Streams (메시지 큐)

DMZ의 핵심입니다. 수신과 처리를 분리합니다.

**Redis Streams를 쓰는 이유**

| 시나리오 | 큐 없이 직접 처리 | Redis Streams |
|---|---|---|
| Consumer 서버 재시작 | 재시작 중 수신된 이벤트 유실 | 큐에 남아있어 재시작 후 이어서 처리 |
| 처리 실패 | 유실 | Dead Letter Queue로 이동, 수동 재처리 |
| 트래픽 폭증 | 처리 서버 과부하 | 큐가 완충 역할, 처리 속도에 맞게 소비 |
| 감사 추적 | 처리 이력 없음 | 모든 메시지 이력 보관 |

**Consumer 설계 원칙 — 멱등성(Idempotency)**

같은 메시지가 두 번 처리돼도 결과가 동일해야 합니다. 네트워크 오류로 인한 중복 처리를 피할 수 없기 때문입니다.

구현 방법: `txHash + logIndex`를 복합 유니크 키로 DB에 저장하고, 처리 전에 이미 처리된 메시지인지 확인합니다.

```
메시지 수신
    |
    v
[이미 처리된 txHash+logIndex인가?]
    |
    Yes --> 스킵 (중복)
    No  --> 처리 진행 --> 완료 후 DB에 기록
```

**처리 상태 머신**

```
PENDING --> PROCESSING --> PROCESSED
                |
                v
             FAILED --> (재시도 후) --> Dead Letter Queue
```

---

### Transaction Dispatcher

내부 승인이 완료된 트랜잭션을 블록체인에 제출합니다.

**Nonce 관리가 핵심**

이더리움에서 각 계정의 트랜잭션은 순서(Nonce)가 있습니다. Dispatcher가 여러 트랜잭션을 동시에 제출할 때 Nonce를 잘못 관리하면:

- 같은 Nonce가 두 번 나오면 하나가 무시됩니다
- Nonce에 빈 구멍이 생기면 이후 트랜잭션이 전부 대기합니다

해결: Dispatcher 내에서 Nonce를 직렬로 관리하고, 트랜잭션 제출 전 Lock을 획득합니다.

**트랜잭션 상태 추적**

```
SUBMITTED --> PENDING(Mempool) --> CONFIRMED(n blocks) --> FINALIZED
                                        |
                                        v
                                     REORGED --> 재제출
```

Reorg(체인 재조직) 발생 시 이미 처리한 것으로 표시된 트랜잭션이 취소될 수 있습니다. Confirmation Depth를 설정해 충분한 블록이 쌓인 후에만 최종 확정 처리합니다.

## 장애 시나리오별 대응

| 장애 | 영향 범위 | 대응 |
|---|---|---|
| Private RPC Node 다운 | 트랜잭션 제출 불가 | Standby 노드로 자동 전환 |
| Webhook Receiver 다운 | 이벤트 수신 중단 | 재시작 후 블록 커서부터 이벤트 재수집 |
| Redis Streams 다운 | 전체 파이프라인 중단 | Redis Cluster 또는 Sentinel 이중화 |
| Consumer 다운 | 처리 중단 (수신은 계속) | 재시작 후 미처리 메시지 자동 재개 |
| Transaction Dispatcher 다운 | 제출 중단 (승인은 계속) | 재시작 후 PENDING 상태 트랜잭션 재제출 |

---

## 정리

DMZ 아키텍처의 핵심 원칙은 세 가지입니다.

**1. 단일 통신 경로**: Gateway Server를 통하지 않는 블록체인 통신은 없습니다. 이것이 감사 추적과 접근 제어의 기반입니다.

**2. 수신과 처리 분리**: Webhook Receiver는 받기만 하고, Redis Streams가 완충합니다. 이것이 이벤트 유실 방지의 기반입니다.

**3. 멱등성 보장**: 같은 이벤트가 두 번 처리돼도 안전한 설계. 이것이 분산 시스템 신뢰성의 기반입니다.

이 세 원칙이 지켜진 시스템은 개별 구성요소가 장애를 겪어도 전체 데이터 정합성을 유지할 수 있습니다.
