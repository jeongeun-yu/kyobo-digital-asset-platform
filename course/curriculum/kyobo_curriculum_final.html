  • Pub/Sub vs Queue vs Streams 비교 — Pub/Sub: 재수신 불가 / 단순 Queue: 영구 저장 없음 / Streams: 영구 저장 + Consumer Group + 재처리

S9이벤트 소비자 처리 순서 불변 규칙과 At-least-once 설계 원리1h
강의 55분
  • At-least-once 의미 — 최소 1번 처리 보장, 중복 가능. Exactly-once는 분산 시스템에서 사실상 불가 → 멱등성이 필수인 이유
  • 잘못된 처리 순서 케이스 1 — XACK 먼저 → DB 처리 실패 → 메시지 PEL에서 제거됨 → 영구 유실
  • 잘못된 처리 순서 케이스 2 — DB 커밋 먼저 → XACK 실패 → 재시작 후 재수신 → 멱등성 없으면 holdings +2
  • 올바른 처리 순서 — 멱등성 확인(ON CONFLICT DO NOTHING) → DB 트랜잭션(LedgerService 포함) → 트랜잭션 커밋 → XACK
  • XACK 실패 케이스 대응 — 재시작 후 PEL 재수신 → 멱등성 체크에서 이미 처리됨 감지 → XACK만 재실행
  • DB와 XACK 원자성 불가 문제 — Redis-DB 간 2PC 불가. 멱등성이 유일한 현실적 보정 수단
  • Consumer 인스턴스 확장 시 안전성 — 멱등성 + Consumer Group으로 중복 처리 없는 수평 확장 가능
