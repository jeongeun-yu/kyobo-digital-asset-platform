SLIDE 01

표지 — 발행 정책 서비스 + 조건 판단 Strategy

0:00

안녕하세요. M5 스물여덟 번째 세션입니다. 지난 S27에서 우리는 사용자의 지갑 주소를 DB에 등록하고 조회하는 user_wallet_mapping 테이블과 서비스 레이어를 완성했죠. 오늘은 그 다음 단계로 넘어갑니다. 지갑을 알았으면 이제 NFT를 실제로 발행해야 하는데, 발행하기 전에 두 가지 질문에 먼저 답해야 합니다. 첫째, "이 이벤트는 어떤 NFT를 몇 개나 발행해야 하는가?"—이게 오늘 전반부에서 다룰 발행 정책입니다. 둘째, "이 사용자가 정말로 발행 조건을 만족하는가?"—이게 오늘 후반부에서 다룰 조건 검증입니다.

이 두 질문에 답하는 방식이 어떤 아키텍처 패턴을 쓰느냐에 따라 코드의 유지보수성이 하늘과 땅 차이가 납니다. 오늘 우리는 첫 번째 질문에는 DB 기반 정책 테이블을 사용하고, 두 번째 질문에는 GoF의 Strategy 패턴을 사용합니다. 세션이 끝날 때쯤이면 여러분은 새로운 이벤트 타입이 추가될 때 코드를 한 줄도 바꾸지 않아도 되는 구조가 왜 가능한지 이해하게 될 것입니다.

오늘 핵심 메시지: "정책은 DB에, 조건 검증 로직은 Strategy 클래스에." 이 두 곳을 분리함으로써 비즈니스 팀이 정책을 바꿔도 코드 배포 없이 대응 가능하다.

잠깐 배경을 설명하겠습니다. 왜 M5가 중요한가? 우리가 만들고 있는 시스템은 교보생명이 고객에게 NFT를 발행하는 플랫폼입니다. 교보생명이라는 대형 금융사에서 블록체인 기반 NFT를 도입한다는 것은 단순한 실험이 아닙니다. 실제 규제 환경에서 감사 추적이 가능해야 하고, 잘못 발행된 NFT는 컴플라이언스 문제로 이어질 수 있습니다. 그래서 M5의 아키텍처가 단순히 "동작하는 코드"를 넘어서 "검증 가능하고, 감사 가능하고, 확장 가능한" 설계를 지향합니다. 여러분이 배우는 것은 장난감 프로젝트가 아니라 실제 금융 서비스에 준하는 수준의 설계 사고입니다. 이 관점을 항상 유지하면서 세션을 따라와주세요.

목차

3:00

오늘 세션의 구성을 먼저 전체적으로 보겠습니다. 크게 세 파트로 나뉩니다. 1부는 발행 정책 설계 — issuance_policies 테이블 스키마부터 IssuancePolicyService의 getPolicy 메서드, 그리고 정책이 없을 때 던지는 NoPolicyError까지입니다. 2부는 조건 검증의 Strategy 패턴 — EventConditionChecker 인터페이스 정의, 세 가지 구체 전략 클래스 구현, 그리고 이것들을 조율하는 EventConditionService 작성입니다. 3부는 실습 — 실제로 코드를 작성하고 테스트를 돌려봅니다.

특히 오늘 세션에서 제가 강조하고 싶은 것은 false positive와 false negative 개념입니다. 블록체인 NFT 발행은 한번 기록되면 되돌릴 수 없습니다. 그래서 조건 검증에서 어떤 실수를 더 경계해야 하는지를 오늘 명확하게 정립하고 갑니다.

S27 복습 — 지갑 매핑

6:00

지난 세션을 빠르게 복습하겠습니다. S27에서 우리가 만든 건 user_wallet_mapping 테이블입니다. userId와 walletAddr의 일대일 매핑을 저장하고, vasp_type으로 외부 지갑인지 교보 내부 지갑인지를 구분하며, verified 플래그로 KYC 인증 완료 여부를 관리했죠. 서비스 레이어에서는 getWalletAddress(userId)를 호출하면 해당 사용자의 지갑 주소를 반환하고, 없으면 WalletNotFoundError를 던지도록 설계했습니다.

오늘 우리가 만들 IssuancePolicyService는 getWalletAddress 다음에 호출됩니다. 즉, "지갑 주소를 알았다 → 이제 어떤 NFT를 발행할지 정책을 조회한다"라는 순서입니다. 그러고 나서 조건을 검증하고, 조건이 충족되면 실제로 발행을 시작합니다. 오늘은 그 중 정책 조회와 조건 검증까지 완성합니다.

user_wallet_mapping — userId(VARCHAR 64) ↔ walletAddr(VARCHAR 42) 일대일 매핑 테이블. vasp_type은 EXTERNAL(사용자 개인 지갑) 또는 KYOBO(교보 커스터디 지갑)를 구분.
SLIDE 02

발행 전에 답해야 할 두 가지 질문

10:00

핵심 질문을 하나 드리겠습니다. 여러분이 이벤트 기반 NFT 발행 시스템을 설계한다고 가정해보세요. 현재 이벤트 타입이 세 가지 있습니다. FIRST_PURCHASE는 첫 구매를 하면 tokenId 1001번 NFT를 1개 발행, ANNUAL_REVIEW는 연간 리뷰 완료 시 tokenId 1002번 NFT를 1개 발행, VIP_UPGRADE는 VIP 등급 달성 시 tokenId 1003번 NFT를 3개 발행하는 식입니다.

이걸 코드로 표현하면 어떻게 쓰시겠어요? 아마 if-else나 switch문을 쓰시겠죠. "eventType이 FIRST_PURCHASE이면 tokenId=1001, amount=1..." 이런 식으로요. 그런데 이 방식의 문제가 뭔지 아시나요? 내년에 이벤트 타입이 10개로 늘어나면 어떻게 됩니까? 그리고 마케팅팀이 VIP_UPGRADE의 발행량을 3개에서 5개로 바꾸고 싶다면요? 코드를 열고, 수정하고, 테스트하고, 배포해야 합니다. 이게 작은 시스템에서는 별 문제 없어 보이지만, 운영 환경에서는 매우 큰 부담입니다.

오늘 우리는 이 문제를 DB 기반 정책 테이블로 해결합니다. 코드 배포 없이 DB 레코드만 수정해서 정책을 바꿀 수 있는 구조를 만들겠습니다.

질문 유도: "현재 코드에 이벤트 타입별 if-else가 있다면, 이벤트가 추가될 때마다 배포가 필요합니다. 이게 진짜 문제가 되는 상황은 언제일까요?" — 수강생에게 물어보고 잠깐 대기
SLIDE 03

두 질문의 역할 — 왜 분리하는가

15:00

발행 정책이란 "이 이벤트가 발생하면 어떤 NFT를, 몇 개, 언제부터 언제까지 발행하는가"를 정의하는 규칙 집합입니다. 다시 말해 이벤트 타입과 발행 규격 사이의 매핑 테이블이라고 보면 됩니다.

우리 시스템에서 정책은 다섯 가지 속성을 갖습니다. event_type은 이 정책을 어떤 이벤트에 적용할지 결정하는 키입니다. 예를 들어 "FIRST_PURCHASE"나 "ANNUAL_REVIEW" 같은 문자열이 들어옵니다. token_id는 발행할 NFT의 종류를 나타냅니다. ERC-1155에서 tokenId가 같으면 같은 종류의 NFT입니다. amount는 한 번의 이벤트에서 몇 개를 발행할지입니다. valid_from과 valid_to는 이 정책이 유효한 기간입니다. 예를 들어 프로모션 기간에만 특별 NFT를 발행하고 싶을 때 valid_from, valid_to를 설정합니다.

핵심은 이 정책이 DB에 저장된다는 점입니다. 코드에 하드코딩하는 것이 아니라요. 그러면 비즈니스 팀이 직접 DB 레코드를 수정해서 정책을 바꿀 수 있고, 코드 배포 없이 즉시 반영됩니다. 이것이 DB 기반 정책 설계의 핵심 가치입니다.

발행 정책(Issuance Policy) — 이벤트 타입별로 어떤 NFT(tokenId)를 몇 개(amount) 발행할지, 언제부터 언제까지(valid_from ~ valid_to) 유효한지를 정의한 DB 레코드.
SLIDE 04

발행 정책 서비스 — DB 기반 관리 (1/4)

실제 PDF 슬라이드 04번에 해당한다. 안티패턴 코드 — 이벤트 타입을 if-else로 하드코딩한 초기 구현을 보여준다. event_type이 추가될 때마다 코드를 수정·배포해야 하는 문제를 시각화하는 슬라이드다.

SLIDE 05

발행 정책 서비스 — DB 기반 관리 (2/4)

20:00

스키마를 보겠습니다. issuance_policies 테이블에는 일곱 개 컬럼이 있습니다. id는 BIGSERIAL Primary Key. event_type은 VARCHAR(64) NOT NULL UNIQUE — 이벤트 타입 하나에 정책이 하나라는 1대1 제약입니다. token_id는 NUMERIC — 이더리움의 uint256 범위를 커버하기 위해 BIGINT 대신 NUMERIC을 씁니다. amount는 NUMERIC NOT NULL DEFAULT 1. valid_from과 valid_to는 TIMESTAMPTZ — 타임존 포함 타임스탬프입니다. created_at은 TIMESTAMPTZ NOT NULL DEFAULT NOW().

NoPolicyError 클래스를 살펴보겠습니다. 이것은 Error를 상속하는 커스텀 에러입니다. 코드를 보면 이렇습니다. class NoPolicyError extends Error { constructor(eventType: string) { super("No active policy for event: " + eventType); this.name = "NoPolicyError"; } }

왜 그냥 throw new Error(...)를 쓰지 않고 커스텀 에러 클래스를 만들까요? 세 가지 이유가 있습니다. 첫째, 에러 타입으로 구분이 가능합니다. 상위 레이어에서 catch할 때 if (err instanceof NoPolicyError)로 이 에러만 선별해서 처리할 수 있습니다. 만약 일반 Error를 쓴다면 에러 메시지 문자열을 파싱해야 하는데, 이건 매우 brittle한 코드입니다. 둘째, 에러의 의도가 코드에서 드러납니다. NoPolicyError라는 이름 자체가 "발행 정책이 존재하지 않는다"는 도메인 맥락을 전달합니다. 셋째, 테스트에서 명확하게 assert할 수 있습니다. expect(() => service.getPolicy("UNKNOWN")).rejects.toThrow(NoPolicyError)처럼요.

실무에서는 이런 커스텀 에러들을 errors 디렉토리에 모아두고, HTTP 핸들러 레이어에서 에러 타입별로 HTTP 상태 코드를 매핑합니다. NoPolicyError는 404 Not Found에 매핑하면 적절합니다.

커스텀 에러 클래스 설계의 추가 고려사항을 말씀드립니다. 실무에서는 에러 클래스에 추가 속성을 넣는 경우가 많습니다. NoPolicyError에 eventType 속성을 추가하면 catch 블록에서 어떤 이벤트 타입에 정책이 없는지 바로 알 수 있습니다. 이것이 메시지 문자열을 파싱하는 것보다 훨씬 안전합니다. 또한 에러 클래스에 HTTP 상태 코드를 직접 담는 패턴도 있습니다. class NoPolicyError extends Error { statusCode = 404; } 이렇게 하면 글로벌 에러 핸들러에서 instanceof 체크 없이 e.statusCode로 응답 코드를 결정할 수 있습니다.

에러 로깅 전략도 중요합니다. NoPolicyError는 예상 가능한 비즈니스 에러입니다. 이런 에러는 ERROR 레벨로 로깅하면 불필요한 알람 노이즈가 됩니다. WARN 레벨이나 INFO 레벨이 적절합니다. 반면 DB 연결 실패나 예상치 못한 예외는 ERROR 레벨로 로깅해야 합니다. 에러의 심각도에 맞는 로그 레벨을 사용하는 것이 운영 관점에서 매우 중요합니다. 알람이 너무 자주 울리면 팀이 알람에 무감각해지는 "알람 피로" 현상이 발생합니다. 비즈니스 에러와 시스템 에러를 구분해서 로깅 수준을 달리하는 습관을 들이세요.

supports()와 check() — 메서드 계약

78:00

supports()와 check() 두 메서드의 계약을 다시 한번 정리하겠습니다. supports()는 동기 메서드입니다. boolean을 즉시 반환합니다. 이건 중요합니다. supports()가 비동기라면 EventConditionService가 await를 기다려야 하고, 전략을 탐색하는 과정이 복잡해집니다. 전략이 자신의 담당 이벤트 타입을 아는 것은 런타임 I/O가 필요 없는 순수 로직이므로 동기로 충분합니다.

check()는 비동기 메서드입니다. Promise<boolean>을 반환합니다. 이건 실제로 외부 서비스를 호출하거나 DB를 조회해야 할 수 있기 때문입니다. ActivityService에 HTTP 요청을 날리거나, DB에서 쿠폰 상태를 조회하거나 하는 I/O 작업이 포함됩니다. 그래서 비동기여야 합니다.

이 두 메서드의 타입 시그니처를 인터페이스에 정확하게 명시하는 것이 중요합니다. 구현 클래스가 실수로 check()를 동기로 구현하거나, supports()를 async로 만들면 타입 시스템이 잡아줄 수 있도록요. TypeScript의 타입 시스템을 믿고, 인터페이스를 명확하게 정의하세요.

internal/apps/issuer-service/src/services/EventConditionService.ts
interface EventConditionChecker { supports(eventType: string): boolean; // 동기! check(ctx: EvaluationContext): Promise<boolean>; // 비동기! } // supports가 async이면 컴파일 에러는 없지만 불필요한 Promise wrapper 발생

Strategy 패턴 — 설계 철학 깊게 보기

Strategy 패턴을 조금 더 깊이 들여다보겠습니다. 이 패턴이 왜 GoF(Gang of Four) 패턴 중에서도 가장 자주 쓰이는지 이해하면, 앞으로 유사한 문제를 만났을 때 자연스럽게 이 패턴을 떠올릴 수 있습니다.

Strategy 패턴의 핵심 아이디어는 "행동(behavior)을 객체로 캡슐화하는 것"입니다. 전통적으로 행동은 메서드 안에 if-else나 switch로 표현되었습니다. Strategy 패턴은 이 행동 자체를 별도의 클래스 — 전략 클래스 — 로 만들어서 교환 가능하게 만듭니다. 컨텍스트(EventConditionService)는 어떤 전략을 사용할지 알지 못하고, 단지 전략에게 "실행해라"고 위임합니다. 이것이 위임(delegation) 패턴입니다.

Strategy 패턴을 쓰기에 적합한 상황은 다음과 같습니다. 첫째, 행동이 런타임에 교환되어야 할 때. 우리 경우 이벤트 타입에 따라 다른 전략이 선택됩니다. 둘째, 여러 클래스가 행동만 다를 때. ActivityStrategy, CouponStrategy, PremiumStrategy는 모두 "조건 검증"을 하지만 방법이 다릅니다. 셋째, 조건부 분기를 제거하고 싶을 때. switch문 대신 전략 선택으로 대체합니다. 넷째, 알고리즘을 독립적으로 변경하고 싶을 때. 한 전략의 내부 로직을 바꿔도 다른 전략에 영향 없습니다.

Strategy 패턴이 맞지 않는 상황도 있습니다. 행동의 변형이 단 두세 가지이고 앞으로도 늘어날 가능성이 없다면 오버엔지니어링입니다. 그냥 if-else 두 줄이 더 명확합니다. "단순함을 먼저, 복잡함은 나중에"라는 YAGNI(You Aren't Gonna Need It) 원칙을 기억하세요. 우리 시스템에서 이벤트 타입이 앞으로 계속 늘어날 것이 확실하기 때문에 Strategy 패턴이 적합한 것입니다. 확장 가능성이 불분명한 상황에서 미리 Strategy 패턴을 도입하는 것은 복잡성만 늘립니다.

Strategy 패턴과 함께 자주 쓰이는 패턴들을 언급하겠습니다. Factory 패턴과의 조합: EventConditionServiceFactory가 적절한 전략들의 배열을 주입해서 EventConditionService를 생성합니다. 팩토리가 전략 선택의 책임을 집니다. Builder 패턴과의 조합: 복잡한 컨텍스트 객체를 EvaluationContextBuilder로 구성합니다. Decorator 패턴과의 조합: 전략에 공통적인 전처리/후처리 — 예를 들어 결과 캐싱이나 로깅 — 를 Decorator로 감쌀 수 있습니다. 이런 패턴들의 조합이 실제 복잡한 비즈니스 시스템을 구성합니다.

YAGNI(You Aren't Gonna Need It) — 지금 당장 필요하지 않은 것을 미리 만들지 말라는 원칙. 확장 가능성이 명확할 때만 Strategy 패턴을 도입하고, 지금 당장 두세 가지 케이스만 있다면 단순한 if-else가 더 좋은 코드다.

반면 거대한 switch문 구조에서는 EventConditionService.ts를 반드시 열어야 합니다. 기존 코드에 손을 대는 순간 리그레션 버그가 생길 위험이 생깁니다. 테스트를 다시 전부 돌려야 하고, 기존 기능이 망가지지 않았는지 검증해야 합니다. Strategy 패턴은 이 위험을 제거합니다.

OCP 실증: 새 이벤트 타입 추가 시 수정 파일 = 0개, 추가 파일 = 1개(Strategy 클래스) + DB INSERT 1건. 기존 전략들의 단위 테스트는 전혀 영향받지 않는다.

OCP 심화 질문 — 자주 나오는 질문들

OCP 설명이 끝날 때쯤이면 항상 비슷한 질문들이 나옵니다. 미리 답을 준비했습니다.

Q1: "Strategy 패턴으로 OCP를 지키면 코드가 너무 많아지지 않나요?" 맞습니다. 파일이 늘어납니다. 하지만 각 파일이 하나의 책임만 가집니다. 200줄짜리 switch문 하나보다, 20줄짜리 전략 파일 10개가 이해하고 테스트하고 유지보수하기 훨씬 쉽습니다. "파일이 많으면 복잡하다"는 것은 오해입니다. 파일이 많아도 각각이 단순하면 시스템 전체는 오히려 단순합니다. 복잡도는 파일 수가 아니라 각 단위의 의존 관계와 책임의 복잡도에서 옵니다.

Q2: "새 이벤트 타입을 추가할 때 DI 컨테이너도 수정해야 하지 않나요? 그것도 코드 변경이 아닌가요?" 예, DI 등록은 수정해야 합니다. 하지만 DI 등록 코드는 "설정 코드"입니다. 비즈니스 로직이 담긴 EventConditionService나 기존 전략 클래스들은 수정하지 않습니다. OCP는 "어떤 코드도 수정하면 안 된다"는 것이 아니라 "기존 동작하는 핵심 코드를 수정하지 않고 확장할 수 있어야 한다"는 것입니다. DI 설정 파일을 수정하는 것은 OCP 위반이 아닙니다.

Q3: "모든 if-else를 Strategy 패턴으로 바꿔야 하나요?" 절대 아닙니다. 두 개의 분기만 있고 앞으로 늘어날 가능성이 없다면 if-else가 더 명확합니다. Strategy 패턴은 분기가 늘어날 것이 예상될 때, 각 분기의 로직이 복잡할 때, 각 분기를 독립적으로 테스트해야 할 때 도입하세요. 패턴 자체가 목적이 아니라 패턴이 해결하는 문제가 있을 때 도입하는 것입니다. 필요 없는 곳에 패턴을 쓰면 "과도한 엔지니어링(over-engineering)"이 됩니다. 좋은 개발자는 패턴을 많이 쓰는 사람이 아니라, 패턴이 필요한 상황과 불필요한 상황을 구분할 줄 아는 사람입니다.

Q4: "EventConditionService에 strategies를 주입할 때 순서가 중요한가요?" supports()로 찾는 로직에서 배열의 첫 번째 매칭을 사용한다면 순서가 중요합니다. 하나의 이벤트 타입에 두 전략이 supports() true를 반환하면 먼저 나온 전략이 선택됩니다. 이는 잠재적 버그입니다. 더 안전한 설계는 초기화 시점에 중복 지원 전략이 있는지 검사하고, 있으면 에러를 던지는 것입니다. 또는 Map 레지스트리 패턴을 사용해서 이벤트 타입당 하나의 전략만 등록되도록 강제합니다.

패턴 도입 기준: 문제가 있고 → 패턴이 그 문제를 해결하고 → 패턴 도입의 비용(복잡성 증가)이 이득(유연성)보다 작을 때. 문제 없이 패턴 먼저 도입하는 것은 오버엔지니어링이다.

false positive vs false negative

90:00

자 이제 오늘 세션에서 제가 가장 강조하고 싶은 개념입니다. false positive와 false negative. 통계학·의학에서 나온 개념인데 우리 시스템에 그대로 적용됩니다.

먼저 정의부터 하겠습니다. 조건 검증의 결과는 true(조건 충족) 또는 false(조건 미충족)입니다. 실제 상태와 우리 시스템의 판단이 일치하면 올바른 판단이고, 불일치하면 오류입니다. false positive는 실제로는 조건을 만족하지 않는데 우리 시스템이 "만족했다"고 판단하는 경우입니다. 발행해선 안 되는데 발행이 일어납니다. false negative는 실제로는 조건을 만족하는데 우리 시스템이 "만족하지 않았다"고 판단하는 경우입니다. 발행받아야 할 사람이 발행을 못 받습니다.

질문입니다. 어떤 오류가 더 심각할까요? 잠깐 생각해보세요. 정답은 false positive입니다. 왜냐고요? 다음 슬라이드에서 자세히 설명드립니다.

false positive — 실제로는 음성(조건 미충족)인데 양성(조건 충족)으로 판단. 발행해선 안 되는데 발행 발생. / false negative — 실제로는 양성(조건 충족)인데 음성(조건 미충족)으로 판단. 발행받아야 하는데 못 받음.

false positive가 더 위험한 이유

96:00

false positive가 왜 더 위험한지 설명하겠습니다. 두 시나리오를 비교해보겠습니다.

시나리오 A: false negative 발생. 실제로 FIRST_PURCHASE 조건을 만족한 사용자가 NFT를 받지 못했습니다. 어떻게 복구합니까? 나중에 조건을 다시 검증해서 발행합니다. 이벤트를 재처리하거나, CS팀이 수동으로 발행을 처리하거나, 배치 프로세스로 누락 케이스를 처리합니다. 불편하지만 복구 가능합니다.

시나리오 B: false positive 발생. FIRST_PURCHASE 조건을 만족하지 않은 사용자에게 NFT가 발행됐습니다. 이미 블록체인에 민팅 트랜잭션이 기록됐습니다. 이걸 어떻게 복구합니까? 블록체인 트랜잭션은 취소할 수 없습니다. NFT를 소각할 수는 있지만 "발행됐다"는 사실 자체는 블록체인에 영원히 남습니다. 감사 추적에 이상한 기록이 생기고, 컴플라이언스 문제가 생길 수 있고, 사용자 불만이 발생할 수 있습니다.

결론: 시스템 오류가 발생했을 때 — 외부 서비스 타임아웃, 데이터 불일치, 예외 상황 — 우리는 false negative 방향으로 실패해야 합니다. "확인하지 못했으면 발행하지 않는다." 이것이 안전한 실패(fail safe) 원칙입니다.

블록체인 특성상 false positive의 결과(잘못된 발행)는 되돌릴 수 없다. 조건 검증 코드에서 불확실한 상황 — 외부 API 타임아웃, DB 오류, 예외 — 은 반드시 false(발행 거부)로 처리해야 한다.

false positive·negative — 실제 사고 사례와 시스템 설계

false positive가 더 위험하다고 했는데, 이 원칙이 실제로 적용된 사례들을 살펴보겠습니다. 이 사례들이 우리 시스템 설계에 어떤 교훈을 주는지 이야기합니다.

사례 1 — 항공 안전 시스템. 항공기의 엔진 화재 경보 시스템은 어떻게 설계할까요? false positive(실제 화재 없는데 경보 울림)는 불필요한 비상 착륙과 승객 불편을 초래합니다. false negative(실제 화재인데 경보 안 울림)는 항공기 추락으로 이어질 수 있습니다. 이 경우 false negative가 훨씬 더 위험합니다. 그래서 항공 경보 시스템은 false positive를 감수하고 false negative를 최소화하도록 설계됩니다. 의심스러우면 경보를 울립니다.

사례 2 — 암 진단 검사. 암 스크리닝 검사는 어떻게 설계할까요? false positive(암이 없는데 있다고 판정)는 불필요한 추가 검사와 환자의 불안을 초래합니다. false negative(암이 있는데 없다고 판정)는 암을 놓쳐서 치료 기회를 잃습니다. 암 스크리닝에서도 false negative가 더 위험합니다. 그래서 스크리닝 검사는 민감도(sensitivity)를 높여서 false negative를 최소화합니다. false positive가 늘어나더라도요. 이후 추가 검사로 false positive를 걸러냅니다.

사례 3 — 우리 NFT 발행 시스템. 이제 우리 맥락입니다. false positive(발행해선 안 되는데 발행) vs false negative(발행받아야 하는데 못 받음). 앞서 설명했듯 블록체인 특성상 false positive는 취소가 어렵습니다. false negative는 나중에 보정 가능합니다. 따라서 우리 시스템은 "불확실하면 발행하지 않는다"는 보수적 설계를 채택합니다. 항공 안전과 반대 방향입니다. 도메인의 특성에 따라 어떤 방향의 오류가 더 허용 가능한지가 달라집니다.

이 원칙을 우리 코드에 어떻게 반영했는지 정리하겠습니다. 첫째, check() 메서드가 외부 서비스 호출에 실패하면 에러를 상위로 전파합니다. 상위에서는 에러를 "조건 미충족"으로 처리합니다. 즉 false negative 방향으로 실패합니다. 둘째, ActivityService 같은 외부 서비스의 응답이 불명확할 때도 false를 반환합니다. 셋째, 멱등성 체크(findPending)가 실패하면 발행을 진행하지 않습니다. 이 모든 설계가 "불확실하면 발행하지 않는다"는 한 가지 원칙에서 나옵니다. 이 원칙을 팀 전체가 공유하고 있어야 합니다. 구현 순간 순간에 "이게 false positive 위험이 있는가?"를 자문하는 습관이 시스템의 신뢰성을 만듭니다.

민감도(Sensitivity) vs 특이도(Specificity) — 민감도는 실제 양성을 얼마나 잘 잡는지(false negative를 줄이는 능력). 특이도는 실제 음성을 얼마나 잘 걸러내는지(false positive를 줄이는 능력). 우리 시스템은 특이도를 높여서 false positive를 최소화한다.

정책에서 token_id를 반환하는데, 이 tokenId는 어디서 오는 값일까요? 이건 ERC-1155 표준에서 아이디어를 가져옵니다. ERC-1155에서 tokenId는 NFT의 "종류"를 나타냅니다. 같은 tokenId를 가진 NFT들은 서로 같은 종류입니다. 예를 들어 tokenId=1001은 "교보 첫 구매 NFT", tokenId=1002는 "연간 리뷰 완료 NFT" 같은 식으로 미리 정의됩니다.

그렇다면 tokenId는 어떻게 결정됩니까? 두 가지 방법이 있습니다. 첫 번째는 그냥 증가하는 정수 1, 2, 3...를 쓰는 방법. 단순하지만 확장성이 떨어지고, 서로 다른 종류의 NFT 간 충돌 위험이 있습니다. 두 번째는 비트 인코딩을 쓰는 방법. tokenId 안에 여러 의미를 압축해서 넣습니다. 예를 들어 상위 64비트에 productCode, 하위 64비트에 eventCode를 넣는 방식입니다. 이 방법을 쓰면 tokenId 자체가 의미를 가집니다. 어떤 상품의 어떤 이벤트인지 tokenId만 봐도 알 수 있습니다.

오늘 세션에서는 tokenId를 정책 테이블에서 직접 설정하는 방식을 씁니다. 운영팀이 DB 레코드에 tokenId를 입력하면 그것이 발행 시 사용됩니다. 비트 인코딩은 S30에서 자세히 다룹니다.

tokenId — ERC-1155 토큰 타입 식별자 (2/2)

107:00

tokenId 비트 인코딩은 S30에서 상세히 다루겠습니다. 지금은 개념만 맛보기로 보겠습니다. ERC-1155 표준에서 tokenId는 uint256입니다. 256비트의 정수입니다. 이 넓은 공간을 구조적으로 활용할 수 있습니다. 우리 시스템에서는 tokenId를 (productCode << 64n) | BigInt(eventCode)로 인코딩합니다. 즉 tokenId의 상위 비트에 상품 코드를 넣고, 하위 비트에 이벤트 코드를 넣습니다.

예를 들어 productCode가 1이고 eventCode가 1이면 tokenId = (1n << 64n) | 1n입니다. 이 tokenId를 보면 즉시 "상품 1번의 이벤트 1번"임을 알 수 있습니다. 디코딩은 역연산으로 가능합니다. productCode = tokenId >> 64n, eventCode = tokenId & ((1n << 64n) - 1n).

이 방식의 장점은 tokenId만으로 NFT의 맥락을 즉시 파악할 수 있다는 점입니다. 또한 productCode 범위, eventCode 범위를 미리 정의하면 각 범위가 충돌하지 않음을 수학적으로 보장할 수 있습니다. S30에서 실제로 구현해보겠습니다.

테스트 가능한 코드 — Strategy 패턴이 주는 선물

소프트웨어 품질에서 테스트 가능성(testability)은 매우 중요한 지표입니다. 테스트하기 어려운 코드는 대부분 설계가 잘못된 코드입니다. Strategy 패턴이 우리 코드를 어떻게 테스트하기 쉽게 만드는지 구체적으로 살펴보겠습니다.

Strategy 패턴 이전 — 거대한 switch문 방식을 생각해봅시다. EventConditionService 안에 ActivityService, CouponService, MemberService가 직접 주입됩니다. 이 서비스를 테스트하려면 세 개의 외부 서비스를 모두 mock해야 합니다. 단순히 ActivityService 로직만 테스트하고 싶어도 CouponService와 MemberService mock도 설정해야 합니다. 이건 불필요한 복잡성입니다. 게다가 테스트가 이 세 서비스의 구체적인 구현에 강하게 결합됩니다. 나중에 ActivityService의 인터페이스가 바뀌면 EventConditionService 테스트도 바꿔야 합니다.

Strategy 패턴 이후를 보겠습니다. WalkingConditionChecker 테스트에는 ActivityService만 mock합니다. CouponConditionChecker 테스트에는 CouponService만 mock합니다. EventConditionService 테스트에는 EventConditionChecker mock 배열만 있으면 됩니다. 각 테스트가 자신의 관심사에만 집중합니다. 이것이 단일 책임 원칙이 테스트에서도 적용되는 방식입니다.

실제 테스트 코드로 확인해보겠습니다. EventConditionService 단위 테스트: const mockStrategy: EventConditionChecker = { supports: jest.fn().mockReturnValue(true), check: jest.fn().mockResolvedValue(true) }. const service = new EventConditionService([mockStrategy]). const result = await service.evaluate(ctx). expect(result).toBe(true). expect(mockStrategy.supports).toHaveBeenCalledWith(ctx.eventType). expect(mockStrategy.check).toHaveBeenCalledWith(ctx). 이 테스트에서 ActivityService, CouponService, MemberService의 흔적은 전혀 없습니다. EventConditionService의 "오케스트레이션" 로직만 테스트합니다. 테스트가 명확하고 빠르며 외부 의존 없이 실행됩니다.

테스트 커버리지 관점에서도 이야기하겠습니다. Strategy 패턴으로 설계된 코드는 각 전략 클래스별로 독립적인 단위 테스트를 가질 수 있습니다. 커버리지를 높이기 위해 모든 케이스를 하나의 거대한 테스트 파일에 담지 않아도 됩니다. WalkingConditionChecker 테스트 파일에서는 activity 관련 케이스만, CouponConditionChecker 테스트에서는 coupon 관련 케이스만 다룹니다. 테스트 파일도 단일 책임 원칙을 따릅니다. 이렇게 설계된 테스트 스위트는 실패 시 어느 전략에서 실패했는지 즉시 파악할 수 있고, CI에서 병렬 실행이 자연스럽습니다.

테스트 가능성은 설계 품질의 지표다. "이 코드를 단위 테스트하려면 무엇을 mock해야 하는가?"를 자문해보라. 필요한 mock이 적을수록 설계가 좋다. Strategy 패턴은 각 전략을 최소한의 mock으로 테스트 가능하게 만든다.

S28 심화 — 실무에서 Strategy 패턴 운용

실습이 끝났으니 실무에서 Strategy 패턴을 운용할 때 마주치는 현실적인 문제들을 짚고 넘어가겠습니다. 첫 번째 현실: 전략 클래스가 너무 많아질 때의 관리입니다. 처음에는 세 개의 전략으로 시작했지만 서비스가 성장하면서 이벤트 타입이 수십 개가 될 수 있습니다. 이 경우 전략 파일도 수십 개가 되는데, 이걸 어떻게 관리할까요? 몇 가지 방법이 있습니다. 첫째는 이벤트 카테고리별로 디렉토리를 만드는 것입니다. strategies/activity/, strategies/coupon/, strategies/premium/ 처럼요. 둘째는 전략 파일 네이밍 컨벤션을 통일하는 것입니다. *.condition.strategy.ts처럼요. 셋째는 README나 전략 레지스트리 문서를 유지하는 것입니다. 어떤 이벤트 타입을 어떤 전략이 담당하는지 한눈에 볼 수 있는 문서가 있으면 신규 팀원이 적응하기 훨씬 쉬워집니다.

두 번째 현실: 전략 간 공통 로직 처리입니다. WalkingConditionChecker와 CouponConditionChecker가 둘 다 ActivityService를 호출한다면? 중복 코드가 생깁니다. 이런 경우 추상 기반 클래스를 만들어서 공통 로직을 담을 수 있습니다. abstract class BaseConditionStrategy implements EventConditionChecker { constructor(protected activitySvc: ActivityService) {} abstract supports(eventType: string): boolean; abstract check(ctx: EvaluationContext): Promise<boolean>; }. 공통 헬퍼 메서드를 기반 클래스에 두고 구체 클래스가 상속합니다. 다만 너무 많은 것을 기반 클래스에 넣으면 Strategy 패턴의 독립성이 깨질 수 있습니다. 상속 트리가 깊어지면 코드 이해가 어려워집니다. 공통 로직이 진짜 많을 때만 기반 클래스를 도입하세요.

세 번째 현실: 성능 최적화입니다. supports()를 배열 전체를 순회해서 찾는 방식은 전략이 많을수록 선형 탐색이 됩니다. 전략이 100개이면 평균 50번 supports()를 호출합니다. 대부분의 경우 이건 문제가 아닙니다. supports()가 단순한 배열 lookup이라 매우 빠르니까요. 하지만 최적화가 필요하다면 Map으로 이벤트 타입을 키로 전략을 값으로 저장하는 레지스트리 패턴을 쓸 수 있습니다. EventConditionService 생성 시 strategies.forEach(s => s.getSupportedTypes().forEach(t => this.registry.set(t, s))). evaluate 시에는 this.registry.get(eventType)으로 O(1) 탐색이 됩니다. 이 최적화는 전략이 수십 개 이상일 때 고려하세요.

네 번째 현실: 전략 테스트의 독립성입니다. Strategy 패턴의 큰 장점 중 하나가 각 전략을 독립적으로 테스트할 수 있다는 점입니다. 이걸 최대한 활용하세요. WalkingConditionChecker 테스트 파일에는 ActivityService만 mock하고, CouponConditionChecker 테스트에는 CouponService만 mock합니다. 전략 간 의존이 없으므로 테스트도 독립적입니다. CI에서 테스트를 병렬로 실행하면 전체 테스트 시간을 줄일 수 있습니다. Jest에서 --runInBand 옵션을 제거하면 기본적으로 워커를 사용해서 병렬 실행합니다. 이것도 Strategy 패턴이 가져다주는 간접적인 이점입니다.

전략 레지스트리 패턴 — Map<string, EventConditionChecker>를 사용해서 이벤트 타입을 키로 전략을 O(1)에 조회하는 최적화. 전략 수가 많을 때 선형 탐색보다 효율적. 초기에는 단순한 배열 탐색으로 시작하고, 전략이 많아질 때 도입하는 점진적 최적화가 바람직하다.

IssuanceRequest — 상태 흐름

22:00

IssuanceStatus는 비즈니스 관점에서 발행 요청이 어떤 단계에 있는지를 나타냅니다. 네 가지 값이 있습니다. REQUESTED — 발행 요청이 접수되었지만 블록체인에 아직 제출되지 않은 상태. SUBMITTED — 블록체인에 제출 완료, 결과를 기다리는 중. CONFIRMED — 블록체인에서 최종 확인됨. FAILED — 어느 단계에서든 실패가 발생함.

이 상태는 최종 사용자에게 보여주는 상태입니다. "당신의 NFT 발행 요청은 현재 블록체인 확인 대기 중입니다(SUBMITTED)" 같은 메시지를 보여줄 때 이 상태를 씁니다. 비즈니스 팀이 대시보드에서 모니터링하는 것도 이 상태입니다.

중요한 것은 CONFIRMED와 FAILED가 터미널 상태라는 점입니다. 한번 CONFIRMED가 되면 다시 SUBMITTED나 REQUESTED로 돌아갈 수 없습니다. FAILED도 마찬가지입니다. 이 터미널 상태 불변 규칙을 코드로 어떻게 강제하는지 곧 보겠습니다.

IssuanceStatus — REQUESTED(접수) → SUBMITTED(제출됨) → CONFIRMED(확인됨) 또는 FAILED(실패). CONFIRMED와 FAILED는 터미널 상태로 한번 진입하면 다른 상태로 전이할 수 없다.

선행 개념 정리 (2/9) — TxStatus DDL

34:00

TxStatus는 블록체인 트랜잭션 자체의 상태입니다. REQUESTED, SUBMITTED, PENDING, MINED, CONFIRMED, FINALIZED 여섯 단계입니다. MintStatus와 비슷해보이지만 가장 하위 레이어에서 체인 TX를 직접 추적하는 상태입니다.

PENDING은 TxStatus에만 있고 MintStatus에는 없습니다. PENDING은 "트랜잭션이 mempool에 있지만 아직 채굴자가 선택하지 않은 상태"입니다. 이 상태는 수분에서 수시간이 걸릴 수 있고, 가스 가격이 너무 낮으면 영원히 PENDING에 머무를 수도 있습니다. MintStatus에서는 이 세부 사항을 추상화해서 SUBMITTED와 MINED 사이에 PENDING을 포함시킵니다.

TxStatus가 별도로 존재하는 이유는 각 레이어가 자신의 관심사에만 집중하기 위해서입니다. 비즈니스 로직(IssuanceStatus)은 체인 TX의 세부 사항을 알 필요가 없습니다. 원장 레이어(MintStatus)는 체인 TX를 약간 추상화해서 표현합니다. 그리고 가장 하위 레이어(TxStatus)만 체인 TX 상태를 정밀하게 추적합니다. 이것이 레이어 분리입니다.

TxStatus의 PENDING은 mempool 대기 상태 — 채굴자가 아직 이 TX를 블록에 포함시키지 않음. 가스 전쟁(gas war)이나 네트워크 혼잡 시 수분~수시간이 될 수 있다. MintStatus는 이를 추상화하여 SUBMITTED→MINED로 표현한다.

선행 개념 정리 (8/9) — 세 Status를 한 흐름으로

40:00

세 Status 레이어가 어떻게 연결되는지 이해하는 것이 오늘 세션의 핵심입니다. 방향은 아래에서 위입니다. TxStatus가 변하면 MintStatus에 영향을 주고, MintStatus가 변하면 IssuanceStatus에 영향을 줍니다. 그 반대는 없습니다. IssuanceStatus가 변한다고 해서 MintStatus나 TxStatus가 변하지 않습니다.

구체적인 예를 들겠습니다. TxStatus가 FINALIZED 되면 → Mint 서비스가 Webhook을 통해 우리 시스템에 알립니다 → 우리 시스템은 MintStatus를 FINALIZED로 업데이트하고 → IssuanceStatus를 CONFIRMED로 업데이트합니다. 전체 흐름은 체인 이벤트에서 시작해서 비즈니스 상태까지 올라옵니다.

왜 이런 방향이어야 할까요? 블록체인이 최종 진실 소스(source of truth)이기 때문입니다. 체인에서 실제로 트랜잭션이 확인되어야 비즈니스 상태가 "확인됨"이 될 수 있습니다. 우리 애플리케이션이 임의로 IssuanceStatus를 CONFIRMED로 바꾼다고 해서 실제로 NFT가 발행된 것이 아닙니다. 체인의 상태가 최종 결정자입니다.

하위 레이어 캡슐화 — "하위 레이어가 세부사항을 캡슐화한다"는 말은, 상위 레이어(IssuanceStatus)가 TxStatus의 세부 전이(PENDING, MINED 등)를 직접 알 필요 없이, 하위 레이어(MintStatus)가 이를 추상화해서 상위에 단순한 신호만 전달한다는 의미다.

상태 전이 불변 조건

46:00

상태 전이 불변이란 무엇인지 명확히 하겠습니다. 이미 터미널 상태(CONFIRMED 또는 FAILED)에 있는 IssuanceRequest를 다른 상태로 전이시킬 수 없다는 규칙입니다. 예를 들어 issuance_status가 이미 CONFIRMED인 레코드에 updateStatus(SUBMITTED)를 호출하면 에러를 던져야 합니다.

왜 이 불변이 중요합니까? 블록체인에서 이미 CONFIRMED된 발행을 "다시 SUBMITTED로 되돌린다"는 것은 말이 안 됩니다. 블록체인에는 이미 민팅 트랜잭션이 영구히 기록됐습니다. 만약 Webhook이 중복으로 두 번 도착해서 두 번 처리된다면? 첫 번째에서 CONFIRMED, 두 번째에서 다시 CONFIRMED 시도. 두 번째는 무시해야 합니다. 이 불변 규칙이 없으면 Webhook 중복 처리가 상태를 엉망으로 만들 수 있습니다.

구현 방법은 updateStatus() 메서드 내에서 현재 상태를 먼저 조회하고, 이미 터미널 상태면 에러를 던지는 것입니다. 또는 DB에서 UPDATE issuance_requests SET issuance_status = $1 WHERE id = $2 AND issuance_status NOT IN ('CONFIRMED', 'FAILED')처럼 WHERE 조건으로 걸 수도 있습니다. DB 레벨에서 걸면 레이스 컨디션도 방지할 수 있습니다.

터미널 상태(CONFIRMED/FAILED)에서의 전이 시도는 에러로 처리해야 한다. DB UPDATE의 WHERE 조건에 "issuance_status NOT IN ('CONFIRMED','FAILED')"를 추가하면 단일 쿼리로 불변을 보장할 수 있다.

상태 기계(State Machine) 패턴 관점에서 보는 IssuanceStatus

IssuanceStatus의 상태 전이를 상태 기계(State Machine) 패턴의 관점에서 바라보겠습니다. 상태 기계는 시스템이 취할 수 있는 유한한 상태들과, 한 상태에서 다른 상태로의 전이 규칙을 형식적으로 정의하는 모델입니다. IssuanceStatus가 정확히 이 모델에 해당합니다.

형식적으로 정의하면 이렇습니다. 상태 집합 S = {REQUESTED, SUBMITTED, CONFIRMED, FAILED}. 초기 상태 S0 = REQUESTED. 터미널 상태 집합 T = {CONFIRMED, FAILED}. 유효 전이 집합: (REQUESTED → SUBMITTED), (SUBMITTED → CONFIRMED), (SUBMITTED → FAILED). 이것이 전부입니다. 다른 전이는 모두 금지입니다. REQUESTED에서 CONFIRMED로 바로 가거나, CONFIRMED에서 SUBMITTED로 역행하는 것은 불법 전이입니다.

이걸 코드로 어떻게 강제할까요? 가장 단순한 방법은 updateStatus() 메서드에서 현재 상태와 목표 상태를 검사하는 것입니다. 유효 전이 맵을 정의합니다. const VALID_TRANSITIONS: Record<IssuanceStatus, IssuanceStatus[]> = { REQUESTED: ['SUBMITTED'], SUBMITTED: ['CONFIRMED', 'FAILED'], CONFIRMED: [], FAILED: [] }. updateStatus(id, newStatus)를 호출할 때 현재 상태를 조회하고, VALID_TRANSITIONS[currentStatus].includes(newStatus)가 false이면 InvalidTransitionError를 던집니다.

이 방식의 장점은 상태 전이 규칙이 코드에 명시적으로 표현된다는 점입니다. 새로운 팀원이 VALID_TRANSITIONS 맵을 보면 어떤 전이가 허용되는지 즉시 이해합니다. 상태 전이 로직이 분산되지 않고 한 곳에 집중됩니다. 단위 테스트도 명확합니다. 허용된 전이는 성공, 금지된 전이는 에러를 확인하면 됩니다. 이 패턴은 주문 처리(ORDER_PLACED → PAYMENT_PENDING → CONFIRMED/REFUNDED), KYC 검증(PENDING → IN_REVIEW → APPROVED/REJECTED) 등 다양한 비즈니스 도메인에서 활용됩니다.

XState 같은 상태 기계 라이브러리를 사용하면 상태 전이를 더 선언적으로 관리할 수 있습니다. 하지만 라이브러리 없이도 VALID_TRANSITIONS 맵 패턴으로 충분히 관리 가능합니다. 라이브러리 도입은 상태가 복잡해지고(10개 이상), 병렬 상태나 히스토리 상태가 필요할 때 고려하세요. 오늘 우리 시스템에서는 단순한 맵으로 충분합니다.

internal/apps/issuer-service/src/services/IssuanceRequestRepository.ts
유효 전이 맵 패턴: const VALID = { REQUESTED: ['SUBMITTED'], SUBMITTED: ['CONFIRMED','FAILED'], CONFIRMED: [], FAILED: [] }; function updateStatus(current, next) { if (!VALID[current].includes(next)) throw new InvalidTransitionError(current, next); }

상태 기계 관련해서 한 가지 더 이야기합니다. 상태 전이 이벤트 소싱(Event Sourcing)입니다. 현재 우리 설계는 issuance_status 컬럼을 업데이트하는 방식입니다. 이걸 "현재 상태를 저장하는 방식(State-based)"이라고 합니다. 반대로 "상태 변화 이벤트를 저장하는 방식(Event-sourced)"이 있습니다. 상태 변화 이력 — REQUESTED_AT, SUBMITTED_AT, CONFIRMED_AT — 을 모두 별도 테이블에 저장하고, 현재 상태는 이벤트들을 재생(replay)해서 계산합니다. Event Sourcing의 장점은 완전한 감사 추적입니다. 언제 어떤 상태가 됐는지, 왜 됐는지를 모두 기록할 수 있습니다. 금융 시스템에서 특히 중요합니다. 단점은 복잡성과 성능입니다. 현재 상태를 구하려면 이벤트들을 모두 재생해야 하기 때문입니다. 스냅샷을 주기적으로 만들어서 성능을 보완합니다. 교보 시스템에서 Event Sourcing 도입은 여러분이 실무에서 고려해볼 수 있는 흥미로운 방향입니다.

issueOne() 파이프라인 — 자주 나오는 질문들

issueOne() 6단계 파이프라인에 대해 수강생들이 자주 하는 질문들을 정리했습니다.

Q1: "6단계를 하나의 DB 트랜잭션으로 묶으면 안 되나요?" 좋은 질문입니다. 4단계(create)와 6단계(submitIssuance) 사이에 블록체인 호출이 있기 때문에 DB 트랜잭션으로 묶을 수 없습니다. DB 트랜잭션은 빠르게 커밋되어야 하고, 외부 I/O 중간에 열려 있으면 안 됩니다. 블록체인 호출이 수초에서 수십 초가 걸릴 수 있으므로 DB 커넥션을 그 동안 잡고 있으면 커넥션 풀이 고갈됩니다. 해결책은 4단계를 먼저 커밋하고, 6단계를 별도 작업으로 처리하는 것입니다. 4단계가 성공했지만 6단계가 실패하면 IssuanceRequest는 REQUESTED 상태로 남습니다. 이걸 복구하는 것이 reconciliation 프로세스입니다.

Q2: "3단계 findPending이 REQUESTED와 SUBMITTED를 모두 조회하는 이유는?" REQUESTED는 아직 블록체인에 제출되지 않았지만 이미 접수된 요청입니다. 이 요청이 진행 중이므로 새 요청을 막아야 합니다. SUBMITTED는 블록체인에 제출됐지만 아직 확인 대기 중입니다. 마찬가지로 진행 중입니다. CONFIRMED와 FAILED는 완료된 요청입니다. 이미 완료된 이벤트에 대해 같은 사용자가 다시 발행을 요청하는 것은 허용할 수도, 금지할 수도 있습니다. 비즈니스 정책에 따라 다릅니다. FIRST_PURCHASE는 딱 한 번만 받아야 하므로 CONFIRMED도 조회 대상에 포함할 수 있습니다.

Q3: "5단계 provision에서 지갑 주소를 매번 DB에서 조회해야 하나요? 캐싱하면 안 되나요?" 캐싱 가능합니다. Redis 같은 인메모리 캐시를 사용해서 userId → walletAddress 매핑을 캐싱하면 DB 부담을 줄일 수 있습니다. TTL(Time-To-Live)은 적절하게 설정하세요. 사용자가 지갑 주소를 변경할 수 있다면 TTL이 짧아야 합니다. 변경이 드물다면 TTL을 길게 설정해도 됩니다. 단, 캐시가 있으면 캐시 무효화(invalidation) 로직도 구현해야 합니다. 지갑 주소가 변경될 때 캐시를 지워야 합니다. 캐싱을 도입할 때는 "캐시 일관성"을 항상 고려하세요.

Q4: "issueOne()을 여러 클라이언트가 동시에 호출하면 어떻게 되나요?" 3단계 findPending과 4단계 create 사이에 레이스 컨디션이 있을 수 있습니다. 두 클라이언트가 동시에 같은 userId + eventType으로 findPending을 호출하면 둘 다 null을 얻습니다. 둘 다 4단계로 진행해서 두 개의 IssuanceRequest를 생성하려 합니다. Webhook 보안 — 출처 검증과 서명

Webhook 핸들러를 구현할 때 보안을 빠뜨리면 안 됩니다. 우리 /api/mint-webhook 엔드포인트가 공개된 인터넷에 노출되어 있다면, 누구나 이 엔드포인트에 POST 요청을 보내서 IssuanceRequest 상태를 임의로 변경할 수 있습니다. 악의적인 공격자가 "CONFIRMED" 상태로 Webhook을 위조하면 실제로 블록체인에서 확인되지 않은 발행이 우리 시스템에서 CONFIRMED로 처리될 수 있습니다.

Webhook 보안의 핵심은 요청이 정말로 Mint 서비스에서 온 것인지 검증하는 것입니다. 가장 일반적인 방법은 HMAC 서명 검증입니다. Mint 서비스와 미리 공유한 비밀 키(secret key)가 있습니다. Mint 서비스는 Webhook 요청 본문을 이 비밀 키로 HMAC-SHA256 해시를 계산하고, 이를 X-Webhook-Signature 헤더에 담아 보냅니다. 우리 Webhook 핸들러는 같은 방식으로 해시를 계산해서 헤더의 값과 비교합니다. 같으면 정상 요청, 다르면 거부합니다.

Node.js에서 HMAC 검증 코드입니다. const crypto = require('crypto'). function verifyWebhookSignature(body: string, signature: string, secret: string): boolean { const expected = crypto.createHmac('sha256', secret).update(body).digest('hex'); return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature)); }. timingSafeEqual을 사용하는 이유는 타이밍 공격(timing attack)을 방지하기 위해서입니다. 일반 문자열 비교(===)는 첫 번째 다른 문자에서 즉시 false를 반환하기 때문에 비교 시간이 달라집니다. 공격자가 응답 시간의 미세한 차이를 분석해서 서명을 역산할 수 있습니다. timingSafeEqual은 항상 일정한 시간이 걸리므로 이 공격을 방지합니다.

Webhook 보안의 추가 레이어로 IP 화이트리스팅이 있습니다. Mint 서비스의 IP 주소 범위만 허용하는 방화벽 규칙이나 미들웨어를 추가합니다. 이건 HMAC 서명과 함께 사용하면 이중 보호가 됩니다. IP 화이트리스팅만 쓰면 IP 스푸핑에 취약하고, HMAC만 쓰면 비밀 키가 유출될 위험이 있습니다. 둘을 함께 쓰는 것이 defense-in-depth(심층 방어) 원칙입니다. 금융 시스템인 교보 플랫폼에서는 이 두 가지를 모두 적용하는 것을 강력히 권장합니다.

Webhook 엔드포인트를 서명 검증 없이 공개하면 공격자가 임의로 발행 상태를 변경할 수 있다. HMAC 서명 검증은 Webhook 보안의 최소 요건이다. timingSafeEqual을 반드시 사용해서 타이밍 공격을 방지하라.

시나리오 1 — 6단계 submitIssuance 직후 서버가 죽었다. txHash를 받았지만 DB에 SUBMITTED로 업데이트하기 전에 서버가 재시작됐습니다. 이 경우 IssuanceRequest는 여전히 REQUESTED 상태입니다. 하지만 블록체인에는 트랜잭션이 이미 제출됐습니다. 이 불일치를 어떻게 해결합니까? 복구 프로세스가 필요합니다. REQUESTED 상태이면서 일정 시간이 지난 IssuanceRequest를 찾아서 mintRequestId로 Mint 서비스에 현재 상태를 조회합니다. 이미 SUBMITTED 이상이면 우리 상태를 동기화합니다. 이런 reconciliation 프로세스는 실무 시스템에서 필수입니다.

시나리오 2 — Webhook이 두 번 이상 도착했다. Webhook 발송 시스템은 at-least-once 전달을 보장하기 위해 같은 Webhook을 중복 발송할 수 있습니다. 우리 시스템이 첫 번째 Webhook에서 CONFIRMED로 업데이트하고, 두 번째 Webhook에서 또 CONFIRMED로 업데이트 시도합니다. 터미널 상태 불변 규칙으로 두 번째는 무시됩니다. 이것이 멱등성 처리의 핵심입니다. Webhook 핸들러는 반드시 멱등해야 합니다.

시나리오 3 — Webhook이 전혀 오지 않는다. 네트워크 문제나 Mint 서비스 장애로 Webhook이 도착하지 않을 수 있습니다. 이 경우 IssuanceRequest는 영원히 SUBMITTED 상태로 남습니다. 이를 방지하기 위해 타임아웃 기반 polling을 별도 워커로 구현합니다. SUBMITTED 상태이면서 일정 시간이 경과한 IssuanceRequest를 찾아서 Mint 서비스에 직접 상태를 조회합니다. 이것이 능동적 폴링(active polling) 전략입니다. Webhook은 수동적(passive) 전략이고, polling은 능동적(active) 전략입니다. 신뢰할 수 있는 시스템은 둘 다 사용합니다.

시나리오 4 — 블록체인 재구성(reorg) 발생. 이더리움에서는 드물지만 체인 재구성이 발생할 수 있습니다. CONFIRMED로 업데이트했는데 재구성으로 그 블록이 orphan이 되면? 이 경우 Mint 서비스가 새로운 Webhook을 보내서 상태가 FAILED로 변경될 수 있습니다. 터미널 상태인 CONFIRMED에서 FAILED로의 전이 — 이걸 허용해야 할까요? 이건 매우 어려운 설계 질문입니다. 일반적으로 재구성은 극히 드문 일이고, 교육용 시스템에서는 고려하지 않아도 됩니다. 하지만 실제 금융 서비스에서는 재구성 처리 정책을 명확히 해야 합니다.

분산 시스템의 두 가지 보장 방식: at-most-once(한 번만 실행, 누락 가능) vs at-least-once(반드시 실행, 중복 가능). 블록체인 발행 시스템은 at-least-once + 멱등성 처리로 "exactly-once" 효과를 달성한다. 중복 발행이 누락 발행보다 더 위험하므로 멱등성이 핵심이다.

이런 엣지 케이스들이 실무에서는 모두 발생할 수 있습니다. 교육 수준에서는 "이런 문제가 있다"는 인식만 갖고 넘어가도 됩니다. 하지만 실제 서비스를 구축할 때는 각각에 대한 처리 전략을 문서화하고 구현해야 합니다. M5에서 배운 IssuanceStatus 상태 기계, 터미널 상태 불변, 멱등성 설계가 이런 엣지 케이스들을 처리하기 위한 기반이 됩니다. 이 기반을 잘 이해하고 있으면 엣지 케이스가 발생했을 때 어디를 수정해야 하는지, 어떤 추가 로직이 필요한지 판단하는 것이 훨씬 쉬워집니다. 아키텍처를 이해한다는 것은 그것이 왜 그 형태인지를 아는 것이고, 그 이해가 있어야 새로운 문제에 유연하게 대응할 수 있습니다.

그런데 실제로는 그렇게 할 수 없습니다. 왜냐하면 블록에는 다른 트랜잭션들도 있기 때문입니다. 우리 트랜잭션만 블록을 독점할 수 없습니다. 또한 Gas 추정치가 실제보다 낮을 수 있어서 안전 마진이 필요합니다. 그래서 600의 약 17% 버퍼를 두어 500으로 CHUNK_SIZE를 정합니다. 이것이 CHUNK_SIZE=500의 근거입니다.

즉, 1,000명에게 발행할 때 첫 번째 청크(1~500번)를 처리하고, 두 번째 청크(501~1000번)를 처리하는 방식입니다. 각 청크 내에서는 Promise.all로 병렬 처리합니다. 청크 간은 순차 처리합니다.

블록 Gas 한도 — 하나의 블록에 포함될 수 있는 전체 Gas의 합계 상한. 현재 이더리움 메인넷 기준 약 30M Gas. 민팅 TX 하나 ≈ 50K Gas이면 블록당 최대 600개 이론적 한계. 실용적 CHUNK_SIZE = 500 (17% 버퍼).

17%라는 버퍼는 어디서 왔을까요? 여러 요소를 고려한 경험적 수치입니다. 첫째, Gas 추정치가 실제보다 낮을 수 있습니다. 컨트랙트 상태에 따라 실제 Gas 소비가 달라질 수 있습니다. 둘째, 블록에는 다른 트랜잭션도 있어서 우리 트랜잭션만 들어가지 않습니다. 셋째, 가스 가격 급등 시 채굴자 우선순위 등 예측 불가한 요소들이 있습니다. 10~20% 버퍼가 일반적인 관행입니다.

물론 이 계산은 단순화된 것입니다. 실제로는 컨트랙트 오디터나 블록체인 개발자와 함께 정밀한 Gas 프로파일링을 해야 합니다. 하지만 오늘 교육 맥락에서는 이 계산 방식이 CHUNK_SIZE=500이라는 숫자가 근거 없는 마법이 아니라 Gas 수학에서 나온 것임을 이해하는 것이 중요합니다.

Promise.all vs Promise.allSettled (1/2)

58:00

청크 내 병렬 처리에서 Promise.all과 Promise.allSettled 중 어떤 것을 써야 할까요? 먼저 차이를 이해해야 합니다.

Promise.all(promises)은 배열의 모든 Promise가 resolve되면 모든 결과를 배열로 반환합니다. 하지만 하나라도 reject되면 즉시 전체가 reject됩니다. "All or Nothing"입니다. 배치 발행에서 Promise.all을 쓰면 500명 중 한 명이라도 실패하면 전체 청크가 실패로 처리됩니다. 499명의 성공이 날아갑니다.

Promise.allSettled(promises)는 배열의 모든 Promise가 resolve되든 reject되든 완료될 때까지 기다립니다. 결과는 각 Promise의 상태와 값을 담은 객체 배열입니다. { status: 'fulfilled', value: ... } 또는 { status: 'rejected', reason: ... }. 이걸 쓰면 499명이 성공하고 1명이 실패해도 499명의 성공을 그대로 유지할 수 있습니다.

배치 발행에서는 당연히 Promise.allSettled를 써야 합니다. 한 명의 실패가 다른 사람의 NFT 발행을 막으면 안 됩니다. 실패는 실패로 기록하고, 성공은 성공으로 유지하면서 전체를 계속 진행합니다. 이것이 PARTIAL_FAILURE 처리의 기반입니다.

배치 처리에서 Promise.all 사용 금지 — 한 건의 실패가 전체 청크를 실패시킨다. 반드시 Promise.allSettled를 사용해서 개별 성공/실패를 독립적으로 처리해야 한다.

PARTIAL_FAILURE는 배치 작업의 일부 항목이 실패한 상태입니다. 예를 들어 1,000명 중 950명 성공, 50명 실패. BulkJob.status = PARTIAL_FAILURE, success_count = 950, fail_count = 50이 됩니다.

PARTIAL_FAILURE를 어떻게 처리해야 할까요? 세 가지 선택이 있습니다. 첫째, 운영팀이 수동으로 실패한 50명에 대해 재처리. 둘째, 자동 재시도 — retryFailedChunks를 호출해서 실패한 항목들만 재시도. 셋째, 무시 — 실패를 기록만 하고 넘어감(비추천). 가장 좋은 방법은 둘째, 자동 재시도입니다. 이어서 retryFailedChunks를 설명하겠습니다.

PARTIAL_FAILURE 상태의 BulkJob을 어떻게 추적합니까? failed_user_ids 컬럼에 실패한 userId 목록을 JSON 배열로 저장하거나, 별도의 bulk_job_failures 테이블을 만들어서 실패 항목을 저장합니다. 후자가 정규화된 방식으로 더 유연합니다. retryFailedChunks는 이 실패 목록을 읽어서 재시도합니다.

부분 실패 허용 정책 (2/2)

retryFailedChunks 메서드를 보겠습니다. 이 메서드는 PARTIAL_FAILURE 상태의 BulkJob에서 실패한 userId 목록을 가져와서 다시 청크 처리를 합니다. 로직은 이렇습니다. 1. PARTIAL_FAILURE인 BulkJob의 실패 목록을 조회합니다. 2. 이 목록을 다시 chunk 함수로 청크 분할합니다. 3. 청크별로 Promise.allSettled 처리합니다. 4. 성공한 것은 BulkJob의 success_count를 증가시키고 fail_count를 감소시킵니다. 5. 모든 재시도가 성공하면 BulkJob.status = COMPLETED. 아직 실패가 남으면 PARTIAL_FAILURE 유지.

재시도 횟수는 제한해야 합니다. 무한 재시도는 무한 루프가 될 수 있습니다. maxRetries를 설정하고, maxRetries를 초과하면 해당 항목을 PERMANENT_FAILURE로 마킹하고 운영팀에 알림을 보냅니다. 이런 재시도 전략을 Exponential Backoff와 함께 사용하면 더 좋습니다. 실패 후 즉시 재시도보다 잠깐 기다린 후 재시도하는 것이 일시적 네트워크 문제 등에 더 효과적입니다.

retryFailedChunks의 핵심: 실패 항목만 재처리한다. 이미 CONFIRMED된 성공 항목은 재처리하면 안 된다 — findPending이 DuplicateIssuanceError를 던지겠지만, 의도치 않은 중복 시도 자체를 막아야 한다.
EXTRA

배치 처리 아키텍처 — 큐 기반 vs 동기 처리

BulkIssueService를 for 루프 + Promise.allSettled로 구현했습니다. 이 방식은 간단하고 이해하기 쉽지만, 대용량 배치에서 한계가 있습니다. 더 강건한 아키텍처인 큐 기반 배치 처리를 소개하고, 우리 방식과 비교하겠습니다.

현재 우리 방식의 한계를 먼저 이해합시다. BulkIssueService.bulkIssue()가 실행되는 동안 API 서버가 이 처리를 직접 담당합니다. 처리가 완료될 때까지 워커 스레드가 묶입니다. 서버가 재시작되면 진행 중인 배치가 중단됩니다. 병렬로 여러 배치가 실행되면 서버 리소스가 빠르게 고갈됩니다. 수십만 명의 배치라면 수시간이 걸릴 수 있는데, API 서버가 그 동안 계속 점유됩니다.

큐 기반 아키텍처는 이 문제를 해결합니다. 배치 요청을 받으면 개별 발행 작업들을 메시지 큐(예: Redis Streams, RabbitMQ, AWS SQS)에 넣습니다. 별도의 워커 프로세스들이 큐에서 메시지를 가져와서 처리합니다. API 서버는 큐에 넣는 역할만 하고 즉시 응답합니다. 워커가 각 발행을 처리하고 결과를 BulkJob에 기록합니다. 이 방식의 장점: API 서버의 부담이 없습니다. 워커를 수평 확장(horizontal scaling)할 수 있습니다. 서버 재시작 시 처리되지 않은 메시지가 큐에 남아있어 재처리됩니다. at-least-once 전달이 자연스럽게 구현됩니다.

큐 기반 아키텍처의 단점은 복잡성입니다. 큐 인프라가 필요하고, 워커를 별도로 관리해야 하며, 메시지 중복 처리에 대한 멱등성 보장이 더 중요해집니다. 그래서 교육 수준에서는 우리가 구현한 동기 방식으로 개념을 이해하고, 프로덕션 레벨에서는 큐 기반으로 확장하는 것이 현실적인 로드맵입니다. Bull(Redis 기반 Node.js 큐 라이브러리)이나 AWS SQS + Lambda 조합이 Node.js 생태계에서 인기있는 선택입니다.

우리 BulkIssueService 코드 구조가 큐 기반으로 전환하기에도 유리하게 설계되어 있습니다. processChunk 메서드를 큐 워커의 핸들러로 이식하기 쉽습니다. 인터페이스(IBulkJobRepository, IIssuerService)에만 의존하기 때문에 워커 환경에서도 동일한 DI로 주입 가능합니다. 좋은 아키텍처는 이렇게 나중에 다른 실행 환경으로 이식하기 쉬운 형태를 가집니다.

아키텍처 진화 경로: 동기 배치 처리(교육/MVP) → Bull Queue 기반 비동기(프로덕션 소규모) → Kafka/SQS 기반 분산 워커(대규모). 코어 비즈니스 로직(processChunk, issueOne)은 실행 환경이 바뀌어도 재사용 가능하다.

Node.js에서 Bull Queue를 사용한 배치 처리 패턴을 잠깐 보겠습니다. 실습 범위는 아니지만 실무에서 자주 쓰이는 패턴이라 알아두면 좋습니다. const queue = new Bull('issuance-queue', { redis: { host: 'localhost', port: 6379 } }). 배치 요청 시: userIds.forEach(uid => queue.add({ userId: uid, eventType, metadata })). 워커에서: queue.process(async (job) => { const { userId, eventType, metadata } = job.data; await issuerService.issueOne({ userId, eventType, data: metadata }); }). Bull은 실패 시 자동 재시도, 지연 처리, 동시 처리 수 제한 등을 제공합니다. 우리가 직접 구현한 CHUNK_SIZE, retryFailedChunks, PARTIAL_FAILURE 처리가 Bull의 기능들과 많이 겹칩니다. 이렇게 우리가 직접 구현한 것들이 실제로 큐 라이브러리가 제공하는 기능과 동일한 문제를 해결하고 있다는 것을 이해하면, 실무에서 Bull 같은 라이브러리를 쓸 때 "이게 내부적으로 어떻게 동작하는지" 더 잘 이해할 수 있습니다.

tokenId 비트 설계 (1/3)

이제 오늘 세션의 두 번째 큰 주제, tokenId 비트 설계입니다. S28에서 예고한 내용입니다. uint256 tokenId에 어떻게 의미있는 구조를 부여할 수 있을까요?

우리 설계는 이렇습니다. 256비트를 두 구역으로 나눕니다. 상위 64비트(비트 255~192)에는 productCode를 넣습니다. 하위 64비트(비트 63~0)에는 eventCode를 넣습니다. 나머지 128비트(비트 191~64)는 미래 확장을 위해 예약합니다. 이렇게 하면 tokenId = (productCode << 192) | eventCode 같은 방식도 가능하지만, 단순화를 위해 (productCode << 64) | eventCode를 씁니다.

왜 64비트씩 나눌까요? productCode와 eventCode 각각 최대 2^64 - 1 ≈ 1.84×10^19 종류를 표현할 수 있습니다. 현실적으로 충분하고도 넘칩니다. 교보의 상품 코드가 수천 개, 이벤트 코드가 수백 개라면 64비트씩은 극도로 여유롭습니다. 더 작은 비트를 써도 되지만 64비트는 uint64와 잘 맞고 BigInt 연산에서 편리합니다.

tokenId 비트 레이아웃: [비트255~64: productCode(64비트)] [비트63~0: eventCode(64비트)]. 인코딩: tokenId = (BigInt(productCode) << 64n) | BigInt(eventCode). 디코딩: productCode = tokenId >> 64n, eventCode = tokenId & mask.

실제 코드를 보겠습니다. TypeScript에서 tokenId를 인코딩하는 함수입니다. function encodeTokenId(productCode: bigint, eventCode: bigint): bigint { return (productCode << 64n) | eventCode; }. 디코딩 함수: function decodeTokenId(tokenId: bigint): { productCode: bigint; eventCode: bigint } { const MASK = (1n << 64n) - 1n; return { productCode: tokenId >> 64n, eventCode: tokenId & MASK }; }.

주의사항이 있습니다. JavaScript의 Number는 64비트 부동소수점이라 uint256 범위를 정확하게 표현할 수 없습니다. 반드시 BigInt를 사용해야 합니다. BigInt 리터럴은 숫자 뒤에 n을 붙입니다. 1n, 64n, (1n << 64n) 같은 식으로요. BigInt는 Number와 혼용할 수 없습니다. 1n + 1처럼 쓰면 TypeError가 발생합니다. BigInt와 Number를 연산할 때는 명시적으로 변환해야 합니다.

예시로 확인해보겠습니다. productCode = 1n, eventCode = 1n이면 tokenId = (1n << 64n) | 1n = 18446744073709551617n. 이 tokenId를 디코딩하면 productCode = 18446744073709551617n >> 64n = 1n, eventCode = 18446744073709551617n & mask = 1n. 정확하게 복원됩니다. 이것을 단위 테스트로 검증해두세요.

S30 심화 질문 — 자주 나오는 질문들

S30 배치 발행과 tokenId 관련 질문들을 정리했습니다.

Q1: "청크 내에서 Promise.allSettled로 병렬 처리할 때 DB 커넥션이 500개 동시에 열리지 않나요?" 매우 좋은 질문입니다. PostgreSQL 커넥션 풀의 최대 크기가 20이라면 500개의 동시 Promise가 커넥션을 요청할 때 480개는 커넥션 대기 상태가 됩니다. 커넥션 풀이 대기를 지원하면 순서대로 커넥션을 받아서 처리됩니다. 하지만 대기 타임아웃이 발생할 수 있습니다. 이를 방지하려면 청크 크기를 DB 커넥션 풀 크기의 몇 배 수준으로 설정하거나, Semaphore 패턴으로 동시 처리 수를 제한합니다. p-limit 같은 라이브러리가 이 역할을 합니다. const limit = pLimit(50); await Promise.allSettled(batch.map(uid => limit(() => issueOne(uid, eventType, meta)))). 이렇게 하면 최대 50개만 동시에 실행되고 나머지는 큐에서 대기합니다.

Q2: "CHUNK_SIZE가 Gas 한계를 기준으로 결정됐는데, 우리 애플리케이션이 직접 블록체인에 TX를 보내는 게 아니라 Mint 서비스를 통하는 거라면 우리가 Gas를 신경 써야 하나요?" 정확한 관찰입니다. Mint 서비스가 내부적으로 Gas를 관리합니다. 우리는 Mint 서비스에 요청을 보낼 뿐입니다. 그렇다면 CHUNK_SIZE는 왜 Gas 기준으로 결정할까요? Mint 서비스 자체가 너무 많은 요청을 동시에 받으면 블록체인에 너무 많은 트랜잭션을 제출하게 되고, 이는 Gas 가격 급등이나 트랜잭션 큐 포화로 이어질 수 있기 때문입니다. 결국 Mint 서비스의 처리 능력 한계를 고려해서 CHUNK_SIZE를 결정하는 것입니다. 실제로는 Mint 서비스 팀과 협의해서 "초당 최대 몇 건의 요청을 처리할 수 있는지"를 기준으로 설정합니다. Gas 계산은 참고 지표 중 하나입니다.

Q3: "tokenId 비트 인코딩에서 productCode와 eventCode의 최대값이 2^64-1인데, 실제로 그렇게 큰 값이 필요한가요?" 실제로는 필요 없습니다. 교보의 상품 코드가 수천 개, 이벤트 코드가 수백 개 수준이라면 32비트로도 충분합니다. 64비트를 쓰는 이유는 미래 확장성과 단순성 때문입니다. uint64는 일반적인 정수형과 잘 맞고, 비트 연산이 직관적입니다. 32비트로 쓰면 tokenId = (productCode << 32n) | eventCode가 되는데, 32비트 마스크가 32비트인지 64비트인지 실수할 수 있습니다. 64비트를 쓰면 이런 혼동이 없습니다. "충분히 크게 만들되 단순하게"라는 원칙입니다.

Q4: "PARTIAL_FAILURE 상태에서 retryFailedChunks를 자동으로 호출할까요, 수동으로 호출할까요?" 둘 다 가능합니다. 자동 재시도는 배치 완료 직후 일정 지연 후 한 번 자동 재시도합니다. 이후에도 실패가 있으면 알람을 보내고 수동 처리를 기다립니다. 수동 재시도는 운영팀이 판단해서 재시도합니다. 실패 원인이 일시적인 네트워크 문제라면 자동 재시도가 효과적입니다. 실패 원인이 잘못된 지갑 주소나 정책 미스매치 같은 데이터 문제라면 수동으로 원인을 확인하고 수정한 후에 재시도해야 합니다. 둘을 조합하는 것이 일반적입니다. 1회 자동 재시도 후 여전히 실패이면 알람 + 수동 처리.

Q5: "tokenId를 DB에 NUMERIC으로 저장하는데, TypeScript에서 BigInt를 JSON으로 직렬화하면 에러가 나지 않나요?" 맞습니다. JSON.stringify()는 BigInt를 지원하지 않습니다. BigInt를 JSON에 포함하려면 직렬화 전에 string으로 변환해야 합니다. tokenId.toString() 또는 String(tokenId). API 응답에 tokenId를 포함할 때 반드시 string으로 변환해서 반환하세요. 클라이언트에서 받을 때는 BigInt(tokenIdString)으로 변환합니다. 또는 숫자가 안전한 범위(2^53 - 1)를 초과할 가능성이 있으면 API 설계에서 처음부터 string으로 정의하세요. OpenAPI 스펙에 type: string, format: uint256처럼 명시하면 클라이언트가 이를 BigInt나 특수 정수 라이브러리로 처리하도록 안내할 수 있습니다.

internal/apps/issuer-service/src/services/IssuerService.ts
tokenId JSON 직렬화: JSON.stringify({ tokenId: BigInt(100) }); // TypeError! JSON.stringify({ tokenId: BigInt(100).toString() }); // OK: "100" // 클라이언트 역직렬화: const tokenId = BigInt(json.tokenId);

마지막으로 M5 전체에서 배운 패턴들을 다른 도메인에 적용하는 방법을 이야기하겠습니다. 우리가 배운 것들은 NFT 발행 시스템에만 적용되는 것이 아닙니다. DB 기반 정책 테이블 패턴 — 코드에 하드코딩하지 않고 DB로 규칙을 관리하는 것 — 은 결제 수수료 정책, 배달 요금표, 회원 등급별 혜택 등 다양한 도메인에서 사용됩니다. Strategy 패턴으로 조건 검증을 분리하는 것은 로그인 방법(이메일/OAuth/SAML), 결제 수단(카드/계좌이체/암호화폐), 알림 채널(이메일/SMS/푸시) 처리에도 동일하게 적용됩니다. IssuanceRequest 같은 상태 엔티티로 비동기 작업을 추적하는 것은 주문 처리, 파일 변환, 비디오 렌더링 등 어떤 비동기 프로세스에도 적용됩니다. CHUNK_SIZE 기반 배치 처리는 대용량 이메일 발송, 배치 데이터 마이그레이션, 대규모 푸시 알림 발송에도 동일하게 적용됩니다. M5에서 배운 것들이 Web3를 넘어서 일반적인 백엔드 개발의 핵심 패턴들이라는 것을 기억하세요.
