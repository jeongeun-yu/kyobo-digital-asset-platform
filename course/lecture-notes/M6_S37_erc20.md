### ERC-20 탄생 역사

2015년 이전 이더리움에는 토큰 표준이 없었다. 각 프로젝트가 자체 인터페이스로 토큰을 만들었기 때문에 거래소가 토큰을 상장하려면 **각 토큰마다 별도 통합 코드를 작성**해야 했다. Augur의 REP, Golem의 GNT — 모두 인터페이스가 달랐다.

2015년 11월 Fabian Vogelsteller(독일 개발자, 나이 25세)가 GitHub 이슈 #20에 표준안을 올렸다. "ERC"는 Ethereum Request for Comments의 약자. 이슈 번호가 20이었기 때문에 ERC-20이 됐다. 2017년 9월 EIP-20으로 공식화.

**ERC-20이 가져온 변화:**
- 거래소는 단 하나의 ERC-20 통합 코드로 모든 토큰 상장 가능
- ICO 붐(2017): 수천 개의 ERC-20 토큰이 발행됨. 당시 이더리움 네트워크 트래픽의 70% 이상이 ERC-20 전송
- 현재도 이더리움 상위 100개 토큰의 대부분이 ERC-20 기반

### approve + transferFrom 공격 패턴 완전 분석

이것은 ERC-20에서 가장 유명한 취약점이다. **경쟁 조건(race condition)** 공격이다.

**공격 시나리오:**

```
① Alice가 Bob(DEX)에게 100 토큰 허용
   approve(Bob, 100) → allowance[Alice][Bob] = 100

② Bob이 50 토큰 사용
   transferFrom(Alice, Bob, 50)
   → allowance[Alice][Bob] = 50 (남은 한도)

③ Alice가 한도를 200으로 올리려고 시도
   approve(Bob, 200) → 이 트랜잭션이 멤풀에 들어옴

④ 공격자 Bob이 멤풀을 모니터링
   → Alice의 approve(Bob, 200) 트랜잭션 발견
   → 더 높은 가스로 자신의 트랜잭션 먼저 실행
   → transferFrom(Alice, Bob, 50) 으로 남은 50 소비

⑤ Alice의 approve(Bob, 200)이 실행됨
   → allowance[Alice][Bob] = 200 (새로 설정)

⑥ Bob이 또 200 소비
   → Bob은 총 50 + 50 + 200 = 300 소비 (Alice 의도는 200이었음)
```

**왜 이게 가능한가:**  
`approve`는 "현재값에 더하는" 게 아니라 "새 값으로 덮어쓰는" 방식으로 동작한다. 덮어쓰기 직전 남은 한도를 공격자가 소진하면, 덮어쓴 새 한도도 추가로 사용할 수 있다.

**방어법 세 가지:**

```solidity
// 방법 1: approve(0) 후 approve(N)
approve(Bob, 0);      // 먼저 0으로 초기화
approve(Bob, 200);    // 그 후 새 한도 설정
// → 0으로 초기화와 새 설정 사이에 아직 경쟁 조건 존재하지만,
//   최악의 경우 Bob은 0 + 200 = 200만 사용 가능

// 방법 2: increaseAllowance / decreaseAllowance (OpenZeppelin)
increaseAllowance(Bob, 150);  // 50 + 150 = 200
// → 현재값 기준으로 증가. 중간에 50 소비됐어도 200으로 올라감
// 주의: OZ v5에서는 deprecated됨

// 방법 3: ERC-2612 Permit (오프체인 서명)
// 아래 별도 섹션 참조
```

**실제 발생 사례:**  
2017년 Bancor 프로토콜 버그. approve 경쟁 조건으로 사용자 자금이 의도치 않게 이동. 당시 큰 논란이 됐고 increaseAllowance/decreaseAllowance 패턴 도입의 계기가 됐다.

### ERC-20 확장 표준들

**ERC-2612 — Permit (오프체인 서명 approve):**

```
기존 approve 흐름:
  ① Alice → approve 트랜잭션 (가스 비용 발생)
  ② DEX → transferFrom 트랜잭션 (가스 비용 발생)
  = 트랜잭션 2번, 가스 2배

ERC-2612 Permit 흐름:
  ① Alice가 오프체인에서 EIP-712 서명 생성 (가스 없음)
  ② DEX가 서명 포함해서 permit() 호출 → transferFrom까지 1번에 처리
  = 트랜잭션 1번, 가스 절반
```

USDC v2, DAI, Uniswap v2/v3 LP 토큰이 채택. 특히 DeFi에서 UX 개선에 핵심적이다.

**ERC-4626 — Vault 표준 (2022년):**

DeFi yield vault(수익형 금고)의 공통 인터페이스. Aave의 aToken, Compound의 cToken, Yearn Finance — 모두 "토큰을 예치하면 수익 토큰을 받는" 패턴인데 인터페이스가 달랐다. ERC-4626으로 표준화. ERC-20의 확장 표준이다.

### decimals = 18의 이유

ETH의 최소 단위가 wei이고, 1 ETH = 10^18 wei다. ERC-20 토큰에서 `decimals = 18`로 맞추면 **ETH와 동일한 정밀도**를 가지게 된다. 이렇게 하면 DEX에서 ETH ↔ 토큰 비율 계산이 깔끔해진다.

```
decimals = 18:  1 토큰 = 1_000_000_000_000_000_000 (10^18 단위)
decimals = 6:   1 USDC = 1_000_000 (10^6 단위) ← USDC 실제 설정
decimals = 8:   1 WBTC = 100_000_000 (10^8 단위) ← BTC 소수점 맞춤

UI 표시: amount / (10 ** decimals) = 사람이 읽는 숫자
컨트랙트 내부: 항상 정수 연산만
```

decimals를 0으로 설정하면 소수점 없는 토큰 — NFT 티켓 같은 정수 단위 자산에 사용.

### Transfer 이벤트 관례 — mint/burn 신호

ERC-20 표준에 mint/burn 함수는 명세에 없다. 그러나 실무 관례는 확립되어 있다:

```
Transfer(address(0), to, amount)   → mint (from이 0 = "무에서 생성")
Transfer(from, address(0), amount) → burn (to가 0 = "소각")
```

이더스캔, Etherscan은 이 관례를 기반으로 "Token Transfers" 페이지에서 mint를 별도로 필터링한다. The Graph, Dune Analytics도 이 관례를 그대로 따른다. 즉, from/to가 address(0)인지 여부가 온체인 데이터 분석의 기준이 된다.

### 실제 ERC-20 버그 사례

**BEC 토큰 오버플로우 (2018년 4월):**

```solidity
// 취약한 코드 (SafeMath 없이 직접 구현)
function batchTransfer(address[] _receivers, uint256 _value) public {
    uint cnt = _receivers.length;
    uint256 amount = uint256(cnt) * _value;  // ← 오버플로우!
    // cnt=2, _value=2^255+1 이면 amount = 0 (오버플로우로 0이 됨)
    require(_value > 0 && balances[msg.sender] >= amount);
    balances[msg.sender] = balances[msg.sender].sub(amount);
    for (uint i = 0; i < cnt; i++) {
        balances[_receivers[i]] = balances[_receivers[i]].add(_value);
        Transfer(msg.sender, _receivers[i], _value);
    }
}
```

공격자가 `_value = 2^255 + 1`을 넣으면: `amount = 2 × (2^255 + 1) = 2^256 + 2 → 오버플로우로 2`가 된다. 잔액 검사(2 이상 있으면 통과)를 통과하고, 두 명에게 각각 2^255 + 1 개의 토큰이 발행됐다. 시가총액 수천억 원이 증발한 사건. **Solidity 0.8.x부터는 기본으로 오버플로우 체크가 내장되어 이런 버그는 발생하지 않는다.** unchecked 블록 안에서만 오버플로우 가능.

## 0. 코인 vs 토큰 — 먼저 짚고 가기

ERC-20을 배우기 전에 "코인"과 "토큰"이 어떻게 다른지부터 잡아야 한다. 둘을 섞어 쓰는 경우가 많은데, 동작 방식이 근본적으로 다르다.

### 코인(Coin) = 그 블록체인의 "네이티브 화폐"

블록체인이 **태생적으로 갖고 있는** 화폐다. 체인의 프로토콜 레벨에서 직접 관리한다.

```
이더리움  → ETH
비트코인  → BTC
폴리곤    → MATIC(현 POL)
솔라나    → SOL
```

특징:
- **별도 컨트랙트가 없다.** 체인 자체의 규칙(프로토콜)에 잔액이 박혀 있다.
- 가스비(수수료)를 이걸로 낸다. ETH 없이는 이더리움에서 아무 거래도 못 한다.
- 잔액이 "계정(account) 구조"에 직접 기록된다 — 컨트랙트 storage가 아니라.

### 토큰(Token) = 그 블록체인 "위에 얹은" 화폐

블록체인 위에 **스마트컨트랙트로 만들어 올린** 자산이다. 체인 입장에선 "그냥 돌아가는 컨트랙트 하나"일 뿐이다.

```
이더리움 위에서 동작하는 토큰들:
  USDT, USDC (스테이블코인)
  UNI, AAVE (DeFi)
  KyoboToken (우리가 만들 것)
```

특징:
- **컨트랙트가 곧 토큰이다.** USDC 컨트랙트 주소가 USDC의 정체다.
- 잔액이 그 **컨트랙트의 storage(mapping)** 안에 기록된다.
- 가스비는 토큰으로 못 낸다 — 토큰을 옮기려 해도 **ETH(코인)로 가스를 내야** 한다.

### 동작 방식의 핵심 차이

```
코인(ETH) 전송:
  사용자 A → B 에게 1 ETH
  → 체인 프로토콜이 직접 A 잔액 -1, B 잔액 +1
  → 컨트랙트 호출 아님. 체인 기본 기능.

토큰(USDC) 전송:
  사용자 A → B 에게 100 USDC
  → USDC 컨트랙트의 transfer() 함수를 호출
  → 컨트랙트가 자기 storage의 _balances[A] -100, _balances[B] +100
  → 이 호출 자체의 가스비는 ETH로 낸다
```

비유: **코인은 그 나라의 법정화폐, 토큰은 그 나라 안에서 발행되는 상품권**이다. 상품권(토큰)을 주고받을 때도 결국 우표값·수수료는 법정화폐(코인)로 내야 하는 것과 같다.

> **그래서 "잔액이 어디 있나"가 핵심 구분이다.** 코인은 체인 계정에, 토큰은 컨트랙트 storage의 `mapping(address => uint256)`에 있다. ERC-20을 배운다는 건 곧 "이 mapping을 어떻게 관리하는가"를 배우는 것이다.

| | 코인(Coin) | 토큰(Token) |
|---|---|---|
| 예 | ETH, BTC | USDC, KyoboToken |
| 존재 형태 | 체인 프로토콜 내장 | 체인 위의 컨트랙트 |
| 잔액 위치 | 계정 구조에 직접 | 컨트랙트 storage(mapping) |
| 가스비 지불 | 가능 (이걸로 냄) | 불가 (코인으로 내야 함) |
| 전송 방식 | 체인 기본 기능 | 컨트랙트 함수 호출 |

## 1. ERC-20이란 — 대체 가능 토큰 표준

ERC-20은 이더리움 토큰의 최초 표준이다. 2015년 Fabian Vogelsteller가 제안했고, 이후 거의 모든 대체 가능 토큰(Fungible Token)이 이 표준을 따른다.

> **"표준"이란 무슨 뜻인가?** ERC-20은 "토큰이라면 이런 함수들(balanceOf, transfer 등)을 반드시 갖춰라"고 정한 **약속**이다. 강제력이 있는 건 아니지만, 이 약속을 지키면 지갑·거래소·DEX가 별도 작업 없이 그 토큰을 인식한다. 메타마스크가 USDC든 처음 보는 토큰이든 잔액을 표시할 수 있는 이유가, 다들 같은 ERC-20 인터페이스를 따르기 때문이다. **표준 = 호환성의 약속.**

**대체 가능(Fungible)의 의미:**

```
대체 가능 토큰 (ERC-20)          대체 불가능 토큰 (ERC-721)
─────────────────────────       ────────────────────────────
1 ETH = 1 ETH (동일)            토큰 #1 ≠ 토큰 #2 (각각 고유)
1 KRW = 1 KRW (동일)            그림 A ≠ 그림 B
잔액으로 관리                    tokenId로 관리
```

내 1만원과 네 1만원이 똑같은 가치로 교환되는 게 대체 가능. 반면 내 졸업장과 네 졸업장은 못 바꾸는 게 대체 불가능. 돈은 대체 가능, 신분증·자격증은 대체 불가능이다.

**왜 ERC-20을 배우는가?**
KyoboNFT는 ERC-1155다. ERC-1155는 "대체 가능 토큰 + 대체 불가능 토큰을 하나의 컨트랙트에서 동시에 관리"하는 확장 표준이다. ERC-20의 `balanceOf`/`transfer` 개념이 ERC-1155에서도 그대로 등장한다. 표준이 어떻게 설계되는지 이해하는 것이 목적이다.

## 2. ERC-20 표준 6개 함수 + 2개 이벤트

EIP-20 명세에 정의된 최소 인터페이스 (이 외에 name·symbol·decimals는 선택 항목):

```solidity
interface IERC20 {
    // ── 조회 함수 (view) ─────────────────────────────────────────────────
    function totalSupply() external view returns (uint256);                       // 총 발행량
    function balanceOf(address account) external view returns (uint256);          // 잔액 조회
    function allowance(address owner, address spender)                            // 위임 한도 조회
        external view returns (uint256);

    // ── 상태 변경 함수 (트랜잭션) ──────────────────────────────────────────
    function transfer(address to, uint256 amount) external returns (bool);        // 직접 전송 (msg.sender → to)
    function approve(address spender, uint256 amount) external returns (bool);    // 위임 한도 설정
    function transferFrom(address from, address to, uint256 amount)               // 위임 전송 (spender가 from 대신)
        external returns (bool);

    // ── 이벤트 ─────────────────────────────────────────────────────────
    event Transfer(address indexed from, address indexed to, uint256 value);      // 잔액 이동 시
    event Approval(address indexed owner, address indexed spender, uint256 value);// 위임 한도 설정 시
}
```

> 흔히 "ERC-20 함수 6개"로 센다(totalSupply, balanceOf, allowance, transfer, approve, transferFrom). `name`/`symbol`/`decimals`는 사람이 읽기 좋게 하는 **선택(optional) 메타데이터**다. 거의 모든 토큰이 넣지만, 명세상 필수는 아니다.

## 3. approve + transferFrom — 위임 패턴

ERC-20의 핵심이자 가장 헷갈리는 부분이다. **"내 토큰을 남(컨트랙트)이 대신 가져가게 허락"**하는 구조다.

### 왜 이게 필요한가 — transfer만으로 안 되는 이유

`transfer`는 `msg.sender`(부른 사람) 자신의 토큰만 보낼 수 있다. 그런데 DEX(탈중앙 거래소) 같은 컨트랙트는 **사용자 대신** 토큰을 가져가야 한다. 컨트랙트가 멋대로 남의 토큰을 가져가면 안 되니, 사용자가 먼저 "이만큼은 네가 가져가도 돼"라고 **허락(approve)**해야 한다.

```
① 사용자가 DEX에게 100 KyoboToken 사용 허락
   user.approve(DEX_ADDRESS, 100)
   → allowance[user][DEX] = 100    (장부에 "DEX는 user 토큰 100까지 가능" 기록)

② DEX가 사용자 토큰을 가져가서 처리
   DEX.transferFrom(user, DEX, 100)
   → allowance[user][DEX] 100 차감
   → user 잔액 100 감소, DEX 잔액 100 증가
```

비유: **은행 자동이체**. 내가 통신사에 "매달 내 계좌에서 5만원까지 빼가도 돼"라고 등록(approve)하면, 통신사가 매달 알아서 빼간다(transferFrom). 한도(allowance) 안에서만 가능하고, 한도는 내가 정한다.

### allowance — 누가 누구에게 얼마나 허락했나

```solidity
mapping(address => mapping(address => uint256)) _allowances;
//        소유자          위임받는자       한도
//      _allowances[user][DEX] = 100
```

앞에서 본 중첩 mapping이 여기 쓰인다. "user가 → DEX에게 → 100까지 허락"을 두 겹으로 저장한다.

### ⚠️ approve 경쟁 조건(race condition) 취약점

```solidity
// 위험: approve(Bob, 100) 후 approve(Bob, 200)로 변경 시
// Bob이 변경 트랜잭션을 보기 전에 기존 100을 먼저 소비(transferFrom)하고,
// 변경이 반영된 뒤 200을 또 소비 → 총 300 빠져나갈 수 있음 (프론트러닝)

// 안전 패턴: 0으로 리셋 후 새 한도 설정
approve(spender, 0);     // 먼저 0으로
approve(spender, 200);   // 그 다음 새 값
```

> **OZ v5 주의 — `increaseAllowance`/`decreaseAllowance`는 제거됐다.**
> v4까지는 이 문제를 완화하려 `increaseAllowance`(현재값 기준 증감) 함수를 제공했으나, **v5에서 삭제**됐다. 이유: ① EIP-20 표준 함수가 아니고, ② 이 함수를 악용한 피싱(악성 increaseAllowance 서명 유도) 사례가 있었다. 따라서 v5 기반으로 가르칠 때는 "increaseAllowance를 쓰면 된다"고 하면 **틀린다.** 원자적 한도 변경이 필요하면 직접 구현하거나, 더 근본적으로는 아래 ERC-2612(Permit)를 쓴다.

**Phase 1 연관성:**
KyoboNFT(ERC-1155)는 `setApprovalForAll(operator, approved)` 형태로 유사 패턴을 구현한다. ERC-20처럼 "금액 한도"가 아니라 **"전부 허용 / 전부 불허"의 on/off** 방식이다. 사용자가 VASP 서버를 operator로 승인하면 VASP가 그 사용자의 토큰을 대신 전송할 수 있다.

## 4. ERC-20 직접 구현 — 전체 코드

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/access/AccessControl.sol";
import "@openzeppelin/contracts/utils/Pausable.sol";

contract KyoboToken is AccessControl, Pausable {
    // ── 역할 ─────────────────────────────────────────────────────────────
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    // ── 상태변수 ──────────────────────────────────────────────────────────
    string  public name;
    string  public symbol;
    uint8   public decimals;          // 소수점 자릿수. ETH 기준 18
    uint256 public totalSupply;

    mapping(address => uint256)                     private _balances;
    mapping(address => mapping(address => uint256)) private _allowances;

    // ── 이벤트 ───────────────────────────────────────────────────────────
    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    // ── 생성자 ───────────────────────────────────────────────────────────
    constructor(string memory _name, string memory _symbol) {
        name     = _name;
        symbol   = _symbol;
        decimals = 18;
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(MINTER_ROLE, msg.sender);
        _grantRole(PAUSER_ROLE, msg.sender);
    }

    // ── 조회 함수 ─────────────────────────────────────────────────────────
    function balanceOf(address account) public view returns (uint256) {
        return _balances[account];
    }

    function allowance(address owner, address spender) public view returns (uint256) {
        return _allowances[owner][spender];
    }

    // ── 발행 / 소각 ──────────────────────────────────────────────────────
    function mint(address to, uint256 amount) public onlyRole(MINTER_ROLE) whenNotPaused {
        require(to != address(0), "Mint to zero address");
        _balances[to] += amount;
        totalSupply   += amount;
        emit Transfer(address(0), to, amount);  // from=0: mint 관례
    }

    function burn(uint256 amount) public whenNotPaused {
        require(_balances[msg.sender] >= amount, "Insufficient balance");
        _balances[msg.sender] -= amount;
        totalSupply           -= amount;
        emit Transfer(msg.sender, address(0), amount);  // to=0: burn 관례
    }

    // ── 전송 ─────────────────────────────────────────────────────────────
    function transfer(address to, uint256 amount) public whenNotPaused returns (bool) {
        _transfer(msg.sender, to, amount);
        return true;
    }

    function approve(address spender, uint256 amount) public returns (bool) {
        require(spender != address(0), "Approve to zero address");
        _allowances[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount)
        public whenNotPaused returns (bool)
    {
        uint256 currentAllowance = _allowances[from][msg.sender];
        require(currentAllowance >= amount, "Insufficient allowance");
        _allowances[from][msg.sender] = currentAllowance - amount;
        _transfer(from, to, amount);
        return true;
    }

    // ── 내부 함수 ─────────────────────────────────────────────────────────
    function _transfer(address from, address to, uint256 amount) internal {
        require(from != address(0), "Transfer from zero address");
        require(to   != address(0), "Transfer to zero address");
        require(_balances[from] >= amount, "Insufficient balance");
        _balances[from] -= amount;
        _balances[to]   += amount;
        emit Transfer(from, to, amount);
    }

    // ── 긴급 정지 ─────────────────────────────────────────────────────────
    function pause()   public onlyRole(PAUSER_ROLE) { _pause(); }
    function unpause() public onlyRole(PAUSER_ROLE) { _unpause(); }
}
```

## 5. 코드 해부 — 설계 결정 포인트

**① mint에서 `emit Transfer(address(0), to, amount)`:**

ERC-20 표준은 mint를 `address(0)`에서 `to`로의 Transfer 이벤트로 표현한다. from이 0이면 mint, to가 0이면 burn임을 **관례로 약속**한다. 이더스캔이 이 관례를 따라 "Mint"/"Burn"으로 표시한다. (address(0) = `0x000...000` = 존재하지 않는 주소 = "무에서 생성/무로 소멸"의 의미)

**② `_transfer` 내부 함수 분리:**

`transfer`와 `transferFrom` 둘 다 동일한 이동 로직을 쓴다. 중복 방지를 위해 `_transfer` internal 함수로 추출했다. OpenZeppelin도 동일 패턴. (앞에서 본 "modifier로 반복 제거"와 같은 사고 — 공통 로직은 한 곳에)

**③ approve 경쟁 조건 — 위 3절 참고.** v5에서 increaseAllowance가 빠졌으므로 `approve(0)` 후 `approve(N)` 패턴 또는 Permit을 쓴다.

**④ `decimals = 18`:**

```
1 KyoboToken = 10^18 단위 (ETH의 wei 단위와 동일)
표시: 1.0 KBT → 내부 저장: 1_000_000_000_000_000_000

비교: USDC는 decimals=6 → 1 USDC = 1_000_000 단위
      WBTC는 decimals=8 → 비트코인 소수점 8자리에 맞춤
```

**왜 소수점을 안 쓰고 정수로?** Solidity에는 소수(float)가 없다. 부동소수점은 계산 오차가 나서 돈 계산에 부적합하기 때문이다. 그래서 "아주 작은 단위의 정수"로 저장하고, **UI에서 `amount / 10^decimals`로 나눠서** 사람이 보기 좋게 표시한다. 컨트랙트 내부는 항상 정수.

**⑤ Solidity 0.8.x — 오버플로우 기본 방어:**

이 코드가 SafeMath를 import하지 않는 이유: Solidity 0.8.0부터 정수 연산에 오버플로우·언더플로우 검사가 **기본 내장**됐다. 한도를 넘으면 자동 revert된다. 2018년 BEC 토큰 사고(오버플로우로 천문학적 토큰이 발행돼 거래 마비)가 이 기능 도입의 배경이다. 검사를 일부러 끄려면 `unchecked { }` 블록을 쓴다 (루프 카운터 등 오버플로가 불가능한 곳에서 가스 절약용).

> **오버플로우(overflow)란:** uint256은 최대값이 정해져 있다(약 1.15 × 10^77). 거기서 1을 더하면 0으로 한 바퀴 도는 게 오버플로우, 0에서 1을 빼면 최대값으로 가는 게 언더플로우. 잔액 계산에서 이게 터지면 "0 - 1 = 천문학적 숫자"가 돼 무한 발행 사고로 이어진다. 0.8.0의 자동 검사가 이걸 막는다.

## 6. OpenZeppelin ERC20 — 직접 구현 vs OZ 활용

직접 구현을 이해했으니 이제 OZ를 쓸 때의 코드를 보자.

```solidity
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";
import "@openzeppelin/contracts/utils/Pausable.sol";

contract KyoboTokenOZ is ERC20, AccessControl, Pausable {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    constructor() ERC20("KyoboToken", "KBT") {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(MINTER_ROLE, msg.sender);
        _grantRole(PAUSER_ROLE, msg.sender);
    }

    function mint(address to, uint256 amount) public onlyRole(MINTER_ROLE) {
        _mint(to, amount);   // OZ 내부 함수 호출
    }

    function pause()   public onlyRole(PAUSER_ROLE) { _pause(); }
    function unpause() public onlyRole(PAUSER_ROLE) { _unpause(); }

    // Pausable과 ERC20 연결 — 전송(mint/transfer/burn 공통 진입점)에서 pause 확인
    function _update(address from, address to, uint256 value) internal override {
        if (paused()) revert EnforcedPause();
        super._update(from, to, value);
    }
}
```

직접 구현한 코드와 비교:
- `name`·`symbol`·`decimals`·`totalSupply`·`_balances`·`_allowances` → **OZ 내부 처리**
- `transfer`·`approve`·`transferFrom`·`balanceOf`·`allowance` → **OZ 내부 구현**
- 우리가 추가한 것: **역할 제어 + 일시정지 연결만**

> **`_update`가 핵심 연결고리다.** v5에서 mint·transfer·burn이 모두 `_update`를 거치도록 통합됐다(v4의 `_beforeTokenTransfer` 대체). 그래서 여기 한 곳에 pause 검사를 넣으면 모든 토큰 이동이 통제된다. `super._update(...)`로 OZ 원래 로직(잔액 이동)을 먼저 부르고, 그 앞에 우리 검사(paused)를 얹는 구조 — 앞에서 본 `super` 패턴이다.

**이것이 OZ를 쓰는 이유다.** 표준 로직은 수십 번 감사된 코드에 맡기고, 비즈니스 로직(권한·정지)만 추가한다. The DAO·Parity 같은 사고가 "직접 짠 코드"에서 났다는 걸 기억하면, 표준 부분을 직접 구현하지 않는 게 곧 보안이다.

## 7. ERC-20 확장 표준 — 실무에서 자주 만나는 것들

**ERC-2612 (Permit) — 가스리스 승인:**
오프체인 **서명**으로 approve를 대체한다. 사용자가 트랜잭션(가스 듦)을 보내지 않고 서명(가스 0)만 만들면, DEX가 그 서명을 담아 `permit()` 한 번으로 approve + transferFrom을 처리한다. 즉 "approve 트랜잭션 따로, transferFrom 따로" 두 번 → 한 번으로 줄인다. USDC·DAI·Uniswap LP 토큰이 채택. 앞의 approve 경쟁 조건도 근본적으로 완화한다.

**ERC-4626 (Vault) — 수익형 금고 표준:**
"토큰을 예치하면 지분 토큰을 받고, 나중에 수익과 함께 인출"하는 DeFi 금고의 공통 인터페이스. Yearn·Aave v3 등이 채택. ERC-20을 상속해 확장한다.

> 교보 맥락에서는 당장 안 쓰지만, 향후 스테이블코인·VASP 단계로 가면 Permit(가스리스 UX)이 사용자 경험상 중요해진다. NFT 보상 수령 시 사용자가 가스를 안 내게 하는 메타 트랜잭션 설계와 연결되는 지점이다.

## 8. ERC-20과 ERC-1155 비교 — 다음 세션 예고

| | ERC-20 | ERC-1155 |
|---|---|---|
| 토큰 종류 | 1종 (단일 컨트랙트 = 단일 토큰) | N종 (tokenId로 구분) |
| 잔액 조회 | `balanceOf(address)` | `balanceOf(address, tokenId)` |
| 전송 | `transfer(to, amount)` | `safeTransferFrom(from, to, id, amount, data)` |
| 배치 전송 | 없음 | `safeBatchTransferFrom(...)` |
| 승인 방식 | `approve` (금액 한도) | `setApprovalForAll` (전체 on/off) |
| 대체 가능 여부 | 항상 대체 가능 | tokenId에 따라 결정 |
| 표준 연도 | 2015 | 2018 |

**KyoboNFT가 ERC-1155인 이유:** 보험 상품 종류(tokenId)별로 수량을 관리해야 하고, 한 번의 트랜잭션으로 여러 종류를 배치 발행(`mintBatch`)해야 하기 때문이다. ERC-20이었다면 상품 종류마다 컨트랙트를 따로 배포해야 하지만, ERC-1155는 하나의 컨트랙트가 `balanceOf(user, tokenId)`로 여러 종류를 동시에 다룬다.

### KyoboToken 배포 + approve/transferFrom 시나리오

위 `KyoboToken` 코드(직접 구현 버전)를 Remix에서 작성·배포.
생성자 인자: `"KyoboToken"`, `"KBT"`

**시나리오 (5분):**

```
① mint(Account2, 1000) → Transfer(0x0 → Account2, 1000) 이벤트 확인
   totalSupply → 1000, balanceOf(Account2) → 1000

② Account2로 전환
   transfer(Account3, 300) → Transfer(Account2 → Account3, 300) 이벤트
   balanceOf(Account2) → 700, balanceOf(Account3) → 300

③ Account2 → approve(Account1주소, 500) → Approval 이벤트 확인
   allowance(Account2주소, Account1주소) → 500

④ Account1로 전환
   transferFrom(Account2주소, Account3주소, 200)
   → allowance(Account2, Account1) → 300 (500-200)
   → balanceOf(Account2) → 500, balanceOf(Account3) → 500

⑤ Account2 → burn(100)
   → Transfer(Account2 → 0x0, 100) 이벤트
   → totalSupply → 900, balanceOf(Account2) → 400
```

> ④에서 핵심: Account1은 자기 토큰이 없어도, Account2가 허락(approve)한 한도 내에서 Account2의 토큰을 옮길 수 있다. 이게 위임 패턴의 실제 동작이다. 한도(500)를 넘는 transferFrom(600)을 시도하면 "Insufficient allowance"로 revert되는 것도 확인해볼 것.

## 강사 노트

**반드시 짚을 것:**  
`approve + transferFrom` 패턴. DeFi를 처음 접하는 수강생은 "내가 승인(approve)했는데 왜 DEX가 내 토큰을 가져가냐"를 혼동한다. approve는 "최대 한도 위임"이지 즉시 이동이 아님을 명확히 설명할 것.

**approve 경쟁 조건 취약점:**  
강사 배경 섹션의 공격 시나리오(Alice-Bob 예시)를 화이트보드에 단계별로 그려주면 직관적으로 이해된다. "왜 0으로 먼저 리셋해야 하는가"까지 연결할 것. BEC 토큰 오버플로우 사고와 함께 "표준 검증 코드(OZ)를 써야 하는 이유"의 실증 사례로 활용 가능.

**`address(0)` Transfer 이벤트:**  
이더스캔에서 토큰 조회 시 "Mint" 탭이 별도로 표시되는 이유가 바로 `from == address(0)` 필터링이다. 실제 이더스캔 화면을 보여주면 이해가 빠르다.

**OpenZeppelin ERC20 `_update` hook:**  
OZ v5에서는 `_beforeTokenTransfer`가 `_update`로 변경되었다. v4 코드를 검색에서 찾아 그대로 붙이면 컴파일 오류가 난다. 버전 주의.

**decimals 질문 대비:**  
"왜 6이 아닌 18이냐"는 질문이 나올 수 있다. USDC처럼 달러 단위라면 소수점 6자리(센트 이하 4자리)면 충분하다. 18은 ETH와 동일한 정밀도를 맞추기 위한 선택이며, 프로젝트별로 다르다.

**S38 예고:**  
다음 시간 ERC-721. `tokenId`가 고유하고 수량이 1인 NFT. ERC-20의 `balanceOf(address)`가 ERC-721에서 `ownerOf(tokenId)`로 바뀌는 관점 차이를 예고할 것.
