## 0. 왜 통합 검증이 마지막 단계인가

M3에서 구현한 것들:

```
S13  TxStateMachine — 상태 전이 규칙
S14  IBlockchainAdapter — 멀티체인 추상화
S15  EVMAdapter 구현
S16  Idempotency Guard
S17  retryWithBackoff
S18  handleTxRevert
S19~20  handleTimeout / handleReorg
S21  이중 채널 아키텍처
S22  pollStaleRequests
```

이것들을 각자 구현하는 것과, **조합했을 때도 올바르게 동작하는 것**은 다른 문제다.

```
단위 테스트:  handleReorg() 함수가 REORGED → MINED 전이를 올바르게 하는가?
통합 테스트:  pollStaleRequests() → vasp.getStatus() → handleReorg() → DB 저장까지
             전체 흐름이 실제 PostgreSQL + 실제 체인과 맞게 동작하는가?
```

## 2. 각 테스트와 M3 항목 매핑

### 컴포넌트 단독: `tx-status.integration.test.ts`

`TxStateMachineService` + `PgTxRepository`만 올린다. VASP는 `ControlledVaspClient`(테스트 전용 페이크)로 교체.

| 테스트 | M3 검증 항목 |
|---|---|
| `[2]` SUBMITTED → MINED → CONFIRMED → FINALIZED | S13 상태 전이 순서 |
| `[3]` MINED → REORGED → MINED | S19~20 REORG 복구 |
| `[4]` SUBMITTED → FAILED | S18 REVERT |
| `[5]` FINALIZED 이후 전이 → InvalidStatusTransitionError | S13 종단 상태 보호 |
| `[6]` FAILED 이후 전이 → DB 변경 없음 | S13 종단 상태 보호 |
| `[7]` PENDING 30분 초과 → pollStaleRequests | S22 폴링 복구 |
| `[8]` transition 이벤트 발행 확인 | S13 이벤트 설계 |

**핵심**: VASP를 페이크로 교체했기 때문에, 실패 시 "VASP 문제"가 아니라 "상태머신 자체 문제"임을 바로 알 수 있다.

---

### 컴포넌트 단독: `issuance-status.integration.test.ts`

`IssuanceRequestRepository` + `IssuanceConfirmHandler` + `TxTransitionBridge` 조합.

| 테스트 | M3 검증 항목 |
|---|---|
| `[3]` IssuanceConfirmHandler → CONFIRMED | S13 TxStatus↔IssuanceStatus 연결 |
| `[5][6]` 종단 상태 보호 | S13 VALID_TRANSITIONS |
| `[7]` findPending — 중복 발행 방지 | S16 Idempotency |
| `[9]` NFT_ISSUED → 세 레이어 동시 CONFIRMED | M3~M4 전체 연결부 |

`[9]`가 핵심이다. `TxStatus` · `MintStatus` · `IssuanceStatus` 세 레이어가 단일 이벤트로 동시에 CONFIRMED로 전이되어야 한다. 하나라도 엇나가면 DB 불일치.

---

### Hardhat 통합: `issuer-service-mock-vasp.integration.test.ts`

실제 issuer-service 전체 스택 + VASPServer(MockVASP) + PostgreSQL + Redis + Hardhat 로컬 노드.

```
[1] NORMAL        — 정상 발행 전 과정 (웹훅 → CONFIRMED)
[2] REVERT        — TX revert → FAILED + reason 저장
[3] NO_EMIT       — Issued 이벤트 누락 → SUBMITTED 유지
[4] PENDING       — mempool 체류 구간 포착
[5] REORG         — 스냅샷 복구 → 온체인 원복 · DB CONFIRMED 유지
[stream-2] 멱등성  — 동일 requestId 1회만 처리
[stream-3] DLQ    — 3회 실패 → Dead Letter Queue 이동
[stream-4] XAUTOCLAIM — PEL 잔류 메시지 재수신
[poll-1]          — 콜백 차단 → pollStaleRequests → CONFIRMED
```

`[poll-1]`이 S22 핵심 시나리오다. 콜백 없이 SUBMITTED 상태를 30분 초과 방치한 것처럼 DB를 조작한 뒤, `pollStaleRequests()`를 직접 호출해 CONFIRMED로 전이되는 것을 검증한다.

---

### Sepolia 통합: `issuer-service-sepolia.integration.test.ts`

Hardhat 통합과 동일한 9가지 시나리오를 **실제 Ethereum Sepolia 테스트넷**에서 실행.

Hardhat과 다른 점:

| 항목 | Hardhat | Sepolia |
|---|---|---|
| 블록 생성 | 즉시 (evm_mine) | ~12초 대기 |
| TX 대기 | sleep 2초 | `provider.waitForTransaction()` |
| PENDING 포착 | 즉시 채굴 → 불가 → 자연 창(12초) 활용 | 동일 |
| 비용 | 무료 | Sepolia ETH 필요 |
| 격리성 | 완전 격리 | 네트워크 공유 |

Sepolia에서 통과한다는 것은 "실제 이더리움 네트워크 조건에서도 동작한다"는 의미다.

## 3. 실습 순서

### Step 1 — 컴포넌트 단독 (10초)

```bash
npx jest tx-status --runInBand
npx jest issuance-status --runInBand
```

확인 포인트:
- `[5]` FINALIZED → FAILED 시도 시 `InvalidStatusTransitionError` 출력

- `[9]` 세 레이어 동시 CONFIRMED

### Step 2 — Hardhat 통합 (2분)

```bash
npx jest issuer-service-mock-vasp --runInBand
```

각 시나리오 진행 중 콘솔에서 확인할 것:

```
[issuer-service] SUBMITTED txHash=0x...
[TxStateMachine] PENDING → CONFIRMED
[stream] NFT_ISSUED processed requestId=...
[poll] processed=1
```

### Step 3 — 로컬 데모 (5분, 선택)

테스트와 다른 점: **사람이 눈으로 보는 것**이 목적. 로그가 실시간으로 흐르는 것을 확인한다.

```bash
# 터미널 1: 환경 기동
npx ts-node internal/integration/local-demo/start.ts

# 터미널 2: 시나리오 실행
npx ts-node internal/integration/local-demo/scenario.ts poll-stale user-001
npx ts-node internal/integration/local-demo/scenario.ts revert    user-002
npx ts-node internal/integration/local-demo/scenario.ts no-emit   user-003
```

`poll-stale` 흐름:
```
1. NO_EMIT 모드 → 웹훅 전송 → SUBMITTED 대기
2. DB: status='PENDING', created_at=NOW()-11분 강제 설정
3. POST :19870/admin/poll-stale
4. 콘솔: [poll] processed=1
5. issuance_requests.status = CONFIRMED 확인
```

## 5. 실패 시 디버깅 순서

```
통합 테스트 실패
  │
  ├─ 컴포넌트 테스트도 실패?
  │     YES → TxStateMachine 또는 Repository 자체 버그
  │     NO  → 컴포넌트 조합 시 발생하는 버그 (타이밍, 트랜잭션 격리, 이벤트 순서)
  │
  ├─ Hardhat은 통과, Sepolia는 실패?
  │     → 블록 타이밍 의존 버그 (고정 sleep → waitForTransaction으로 교체)
  │     → 가스비 관련 버그 (Alchemy 최소 가스가 Hardhat보다 높음)
  │
  └─ 특정 시나리오만 실패?
        → 해당 시나리오의 상태 전이 규칙 재확인
        → DB beforeEach TRUNCATE가 제대로 되었는지 확인
```
