## 0. 왜 컴포넌트 테스트인가

M3에서 구현한 것들은 TX 상태머신 레이어에 집중돼 있다.

```
S13  TxStateMachine — 상태 전이 규칙
S14  IBlockchainAdapter — 멀티체인 추상화
S15  EVMAdapter 구현
S16  Idempotency Guard
S17  retryWithBackoff
S18  handleTxRevert
S19~20  handleTimeout / handleReorg
S21  이중 채널 아키텍처
S22  pollStaleRequests
```

이 레이어를 검증하는 데 전체 서비스 스택(Redis, 블록체인, WebhookServer)은 필요 없다. `TxStateMachineService` + `PgTxRepository` + 실제 PostgreSQL만 올리면 충분하다.

전체 스택 통합테스트(mock-VASP, Sepolia)는 M3를 넘어 전체 파이프라인이 완성된 이후에 의미가 있다.

## 2. 상태 전이별 담당 메서드 · 클래스

| 전이 | 메서드 | 호출 주체 (클래스) |
|---|---|---|
| REQUESTED → SUBMITTED | `submitMintRequest()` | `IssuerService` |
| SUBMITTED → PENDING | `repo.updateStatus('PENDING')` 직접 | VASP 브로드캐스트 콜백 수신 시 |
| SUBMITTED/PENDING → MINED | `handleMined()` | `ChainEventListener`, `VASPServer` Webhook, `pollStaleRequests` |
| MINED → CONFIRMED | `handleConfirmed()` | `ConsumerGroupWorker` (NFT_ISSUED 처리 후) |
| CONFIRMED → FINALIZED | `handleFinalized()` | `ChainEventListener` (PoS 2/3+ validator 동의 확인 후) |
| MINED → REORGED → MINED/FAILED | `handleReorg()` | `ChainEventListener` (REORG 감지 시) |
| PENDING → FAILED (timeout) | `handleTimeout()` | 크론잡 → gas bump 재전송 후 새 txHash로 PENDING 유지 |
| 어느 상태 → FAILED | `handleFailed()` | REVERT 수신 시 어느 경로에서든 |
| PENDING 체류 → CONFIRMED/FAILED | `pollStaleRequests()` | 크론잡 (10분 초과 PENDING 건 배치) |

> **SUBMITTED → PENDING에 명시적 핸들러가 없는 이유**: VASP가 TX를 mempool에 브로드캐스트한 시점을 서비스가 직접 알 수 없다. VASP 콜백으로 txHash를 수신한 뒤 `repo.updateStatus`로 직접 기록하는 구조다.

모든 전이는 `TxStateMachineService` 내부 `_transition()` 메서드를 거쳐 DB에 기록되고, `transition` 이벤트를 발행한다. `TxTransitionBridge`가 이 이벤트를 구독해 `IssuanceStatus`·`MintStatus` 레이어를 동기화한다.

## 3. 실습

```bash
cd internal/integration
npx jest tx-status --runInBand
```

통과 후 확인할 것:

**`[5]` 종단 상태 보호**
```
InvalidStatusTransitionError: FINALIZED → FAILED is not allowed
```
FINALIZED에서는 어떤 전이도 불가능하다. VALID_TRANSITIONS 맵에서 FINALIZED 키가 빈 배열이어야 한다.

**`[7]` pollStaleRequests**
```
{ processed: 1 }
```
30분 초과 PENDING 건을 VASP에 직접 조회해 CONFIRMED로 전이했다는 뜻. 콜백 없이도 복구된다.

## 3. 컴포넌트 테스트의 가치

통합 테스트(전체 스택)에서 실패했을 때, 원인이 여기서 먼저 잡히면 "TX 상태머신 자체 버그"다. 여기서 통과하고 통합 테스트에서만 실패하면 "컴포넌트 조합 시 발생하는 버그"다. 디버깅 범위가 좁혀진다.
