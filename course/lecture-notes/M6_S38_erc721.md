### ERC-721 탄생 — CryptoKitties와 이더리움 마비

2017년 11월 28일 Dapper Labs가 CryptoKitties를 출시했다. 각 고양이가 고유한 유전자(tokenId에 인코딩)를 가진 NFT였다. 출시 직후 이더리움 전체 트랜잭션의 25%가 CryptoKitties 관련 트랜잭션이었고, 네트워크가 사실상 마비됐다. 가스비가 평소의 수십 배로 치솟았다.

이 사건이 두 가지를 증명했다:
1. NFT라는 개념에 실제 수요가 있다
2. 이더리움의 확장성 문제가 심각하다 (→ 이후 Layer 2 개발의 동력)

CryptoKitties의 표준이 2018년 1월 ERC-721로 공식화됐다. William Entriken, Dieter Shirley, Jacob Evans, Nastassia Sachs 4인이 공동 제안.

**ERC-721이 만든 것들:**
- 2021년 NFT 붐: Bored Ape Yacht Club, CryptoPunks, Art Blocks
- OpenSea 월 거래액 30억 달러 돌파 (2021년 8월)
- NBA Top Shot, 나이키 NFT 스니커즈, 삼성 NFT 마켓

### tokenId 설계 전략 완전 비교

tokenId는 uint256이라 2^256가지 경우의 수가 있다. 어떻게 쓰느냐에 따라 시스템 설계가 달라진다.

**전략 1 — 단순 카운터 (1, 2, 3...):**

```solidity
uint256 private _nextTokenId = 1;  // 0 회피 (0은 "미존재" 혼동 방지)

function mint(address to) public returns (uint256) {
    uint256 id = _nextTokenId++;
    _owners[id] = to;
    emit Transfer(address(0), to, id);
    return id;
}
// 장점: 구현 단순, 순서 추적 가능
// 단점: tokenId만 보고 어떤 자산인지 알 수 없음
// 채택: Bored Ape Yacht Club (#1~#10000), 대부분의 PFP NFT
```

**전략 2 — 비트 인코딩 (상품코드|일련번호):**

```solidity
// tokenId = productCode(32비트) | policyNumber(64비트) | issueDate(32비트)
function encodeTokenId(
    uint32 productCode,
    uint64 policyNumber,
    uint32 issueDate
) public pure returns (uint256) {
    return (uint256(productCode) << 96)
         | (uint256(policyNumber) << 32)
         | uint256(issueDate);
}
// 장점: tokenId만으로 상품 종류, 증권 번호, 발행일 즉시 파악
// 단점: 비트 레이아웃 설계 필요, 실수 시 충돌 위험
// 채택: 교보생명 방식, 게임 아이템 시스템
```

**전략 3 — 해시 기반:**

```solidity
function mintWithHash(address to, bytes memory params) public returns (uint256) {
    uint256 id = uint256(keccak256(params));
    require(_owners[id] == address(0), "Already exists");
    _owners[id] = to;
    emit Transfer(address(0), to, id);
    return id;
}
// 장점: 입력값만 알면 tokenId 사전 계산 가능, 충돌 극히 희박
// 단점: 순번 추적 불가, 연속적이지 않음
// 채택: 일부 DeFi LP NFT, Uniswap v3 포지션 NFT
```

**전략 4 — IPFS CID 기반:**

```solidity
// IPFS CID를 uint256으로 변환해 tokenId로 사용
// tokenId === 메타데이터 해시 → 자체 검증 가능
// 장점: 토큰과 콘텐츠가 동일한 식별자
// 단점: CID 계산 복잡, 온체인 로직에 녹이기 어려움
```

### safeTransferFrom vs transferFrom — NFT 영구 잠김 사고

**transferFrom의 위험:**

스마트 컨트랙트 주소로 NFT를 전송하면, 그 컨트랙트가 NFT를 처리하는 로직이 없으면 **영원히 꺼낼 수 없다.** 컨트랙트는 사람이 아니기 때문에 "이 NFT를 다른 주소로 보내줘"라고 요청할 수 없다.

```
사고 발생 조건:
  transferFrom(userA, someContract, tokenId)
  → someContract에 NFT를 꺼내는 함수가 없음
  → NFT 영구 잠김
  → 소각도 아닌, 영구 접근 불가 상태
```

**실제 사고 사례 (CryptoKitties):**

2017년 CryptoKitties 출시 초기, 일부 게임 컨트랙트가 ERC-721 수신 처리를 구현하지 않았다. 사용자들이 transferFrom으로 게임 컨트랙트에 키티를 보냈는데 게임 컨트랙트에서 꺼낼 방법이 없었다. 수십 마리의 CryptoKitty가 영구 잠겼다. 당시 시가로 수천만 원 상당.

**safeTransferFrom의 동작:**

```solidity
function safeTransferFrom(address from, address to, uint256 tokenId) public {
    transferFrom(from, to, tokenId);  // 먼저 전송
    
    // to가 컨트랙트인지 확인 (코드 크기 > 0)
    if (to.code.length > 0) {
        // IERC721Receiver 콜백 호출
        bytes4 retval = IERC721Receiver(to).onERC721Received(
            msg.sender, from, tokenId, ""
        );
        // 반환값이 매직 바이트와 일치해야 함
        require(
            retval == IERC721Receiver.onERC721Received.selector,
            "ERC721: transfer to non ERC721Receiver implementer"
        );
    }
    // EOA면 검사 없이 통과
}
```

**수신 컨트랙트가 구현해야 하는 것:**

```solidity
// NFT를 받을 수 있는 컨트랙트
contract NFTReceiver is IERC721Receiver {
    function onERC721Received(
        address operator,   // 전송을 실행한 주소
        address from,       // 이전 소유자
        uint256 tokenId,    // 받은 NFT
        bytes calldata data
    ) external pure returns (bytes4) {
        // NFT 수신 처리 로직 작성
        return IERC721Receiver.onERC721Received.selector;
        // = bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))
        // = 0x150b7a02
        // 이 값을 반환해야 "나는 NFT를 처리할 수 있다"고 선언하는 것
    }
}
```

### 메타데이터 저장 방식 비교

tokenURI가 가리키는 곳에 따라 NFT의 영속성이 달라진다.

**방식 1 — 중앙 서버 (https://):**

```
tokenURI: "https://api.myproject.com/nft/1001.json"
→ 장점: 메타데이터 수정 가능 (이미지 변경 등)
→ 단점: 서버 다운 시 메타데이터 消失. NFT는 블록체인에 있지만 이미지/속성은 사라짐
→ 사고 사례: NFT.fi에서 담보로 맡겨진 NFT들의 메타데이터가 서버 종료로 손실
```

**방식 2 — IPFS (ipfs://):**

```
tokenURI: "ipfs://QmXxxxx.../metadata.json"
→ 장점: 내용 기반 주소 (CID). 파일이 바뀌면 CID가 바뀜 → 변조 불가
→ 단점: 핀닝(pinning)을 누군가 유지해야 함. 핀닝 중단 시 가비지 컬렉션
→ OpenSea, 대부분의 NFT 마켓이 기본으로 사용
→ Pinata, NFT.Storage 같은 서비스가 핀닝 담당
```

**방식 3 — Arweave (ar://):**

```
tokenURI: "ar://xxxxx"
→ 장점: 1회 비용으로 영구 저장 보장 (200년+ 스토리지 보장 설계)
→ 단점: 초기 비용 발생
→ Solana NFT의 표준, Nouns DAO
```

**방식 4 — On-chain (완전 온체인):**

```solidity
function tokenURI(uint256 tokenId) public view returns (string memory) {
    // Base64로 인코딩된 JSON을 직접 반환
    return string(abi.encodePacked(
        "data:application/json;base64,",
        Base64.encode(bytes(string(abi.encodePacked(
            '{"name":"NFT #', Strings.toString(tokenId), '",',
            '"image":"data:image/svg+xml;base64,', svgBase64, '"}'
        ))))
    ));
}
// 장점: 외부 의존성 없음. 영구 보존 완전 보장
// 단점: gas 비용 매우 높음 (SVG/JSON을 온체인에 저장)
// 채택: Nouns DAO (완전 온체인 SVG), Art Blocks (생성 알고리즘 온체인)
```

**tokenURI가 빈 문자열("")이면:**  
OpenSea 등의 마켓에서 이미지와 속성이 표시되지 않는다. 블록체인상 토큰은 존재하지만 UI에서는 "No metadata" 상태.

### ERC-721 Enumerable 확장

기본 ERC-721에는 "전체 토큰 목록"이나 "특정 주소의 토큰 목록" 조회 기능이 없다. 이를 추가하는 확장이 ERC-721 Enumerable이다.

```solidity
// ERC-721 Enumerable 추가 함수
function totalSupply() external view returns (uint256);          // 총 발행량
function tokenByIndex(uint256 index) external view returns (uint256);  // 인덱스로 tokenId 조회
function tokenOfOwnerByIndex(address owner, uint256 index) external view returns (uint256);
// 특정 주소의 n번째 토큰
```

**gas 비용 주의:** Enumerable은 내부적으로 배열을 유지한다. mint/transfer 시마다 배열을 업데이트해야 해서 gas가 20-30% 더 든다. 대용량 배치 발행에 부적합. 이것이 ERC-1155를 선택하는 이유 중 하나다.

## 강의 파트 (50분)

### 1. ERC-721이란 — 대체 불가능 토큰

ERC-721은 각 토큰이 고유한 ID를 가지는 대체 불가능 토큰(NFT) 표준이다. 2018년 William Entriken 외 3인이 제안했다.

**ERC-20 vs ERC-721 핵심 차이:**

```
ERC-20 (대체 가능)              ERC-721 (대체 불가능)
────────────────────           ────────────────────────────
잔액으로 관리                  tokenId로 관리
1 KBT = 1 KBT (동일)           token #1 ≠ token #2 (고유)
balanceOf(address) → 수량      ownerOf(tokenId) → 소유자 주소
분할 가능                      분할 불가 (tokenId는 정수)
```

**보험 NFT에서 왜 대체 불가능성이 필요한가?**

```
고객 A의 종신보험 NFT #1001
  → 보험 개시일: 2024-01-15
  → 특약: 암진단비 포함
  → 수익자: 배우자

고객 B의 종신보험 NFT #1002
  → 보험 개시일: 2023-07-22
  → 특약: 없음
  → 수익자: 자녀
```

두 NFT는 같은 보험 상품이지만 내용이 다르다. 교환 불가, 각각 고유하다. 이것이 ERC-721을 사용하는 이유다.

단, KyoboNFT는 최종적으로 ERC-1155를 사용한다. ERC-721을 먼저 배우는 이유는 "tokenId = 고유 식별자"라는 개념을 가장 순수하게 이해할 수 있는 표준이기 때문이다.

### 2. ERC-721 표준 인터페이스

```solidity
interface IERC721 {
    // ── 조회 ───────────────────────────────────────────────────────────

    // 주소가 보유한 NFT 총 개수 (몇 개의 tokenId를 가지는가)
    function balanceOf(address owner) external view returns (uint256);

    // 특정 tokenId의 소유자 주소
    function ownerOf(uint256 tokenId) external view returns (address);

    // spender가 tokenId 하나를 전송할 수 있는지 여부
    function getApproved(uint256 tokenId) external view returns (address);

    // operator가 owner의 전체 NFT를 다룰 수 있는지 여부
    function isApprovedForAll(address owner, address operator) external view returns (bool);

    // ── 전송 ───────────────────────────────────────────────────────────

    // 전송 (수신자 컨트랙트 안전성 검사 없음)
    function transferFrom(address from, address to, uint256 tokenId) external;

    // 전송 (수신자가 컨트랙트이면 onERC721Received 호출해서 확인)
    function safeTransferFrom(address from, address to, uint256 tokenId) external;
    function safeTransferFrom(address from, address to, uint256 tokenId, bytes calldata data) external;

    // ── 승인 ───────────────────────────────────────────────────────────

    // tokenId 하나에 대한 전송 권한 위임
    function approve(address to, uint256 tokenId) external;

    // operator에게 전체 NFT 전송 권한 위임 / 회수
    function setApprovalForAll(address operator, bool approved) external;

    // ── 이벤트 ─────────────────────────────────────────────────────────
    event Transfer(address indexed from, address indexed to, uint256 indexed tokenId);
    event Approval(address indexed owner, address indexed approved, uint256 indexed tokenId);
    event ApprovalForAll(address indexed owner, address indexed operator, bool approved);
}
```

ERC-20과 비교:
- `balanceOf`는 존재하지만 "몇 개의 tokenId를 보유"하는 의미로 쓰인다
- `ownerOf`가 핵심: "이 tokenId의 주인이 누구냐"
- `approve`가 tokenId 단위 (`amount` 없음)
- `setApprovalForAll`로 전체 위임 가능

### 3. tokenId 설계 — 무엇을 담을 것인가

tokenId는 `uint256`이다. 단순 순번으로 쓸 수도 있고, 구조화된 값으로 인코딩할 수도 있다.

**단순 순번 방식:**

```solidity
uint256 private _nextTokenId;

function mint(address to) public returns (uint256) {
    uint256 tokenId = _nextTokenId++;
    _owners[tokenId] = to;
    emit Transfer(address(0), to, tokenId);
    return tokenId;
}
// tokenId: 0, 1, 2, 3, ...
// 장점: 구현 단순
// 단점: tokenId만 보고 어떤 자산인지 알 수 없음
```

**구조화 인코딩 방식:**

```solidity
// tokenId = productCode(32비트) | policyNumber(64비트) | issueDate(32비트)
function encodeTokenId(
    uint32 productCode,
    uint64 policyNumber,
    uint32 issueDate
) public pure returns (uint256) {
    return (uint256(productCode) << 96)
         | (uint256(policyNumber) << 32)
         | uint256(issueDate);
}

function decodeTokenId(uint256 tokenId) public pure returns (
    uint32 productCode,
    uint64 policyNumber,
    uint32 issueDate
) {
    productCode  = uint32(tokenId >> 96);
    policyNumber = uint64(tokenId >> 32);
    issueDate    = uint32(tokenId);
}
```

보험 시스템에서는 구조화 방식이 유용하다. tokenId만 보고 상품 코드·증권 번호·발행일을 바로 추출할 수 있다. 이 전략이 S39에서 배울 KyoboNFT의 ERC-1155 tokenId 설계로 이어진다.

### 4. ERC-721 직접 구현 — 핵심 코드

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/access/AccessControl.sol";
import "@openzeppelin/contracts/utils/Pausable.sol";

contract KyoboPolicyNFT is AccessControl, Pausable {

    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    // ── 핵심 상태변수 ──────────────────────────────────────────────────
    mapping(uint256 => address) private _owners;        // tokenId → 소유자
    mapping(address => uint256) private _balances;      // 주소 → 보유 토큰 수
    mapping(uint256 => address) private _tokenApprovals; // tokenId → 승인 주소
    mapping(address => mapping(address => bool)) private _operatorApprovals;

    uint256 private _totalSupply;

    // ── 이벤트 ────────────────────────────────────────────────────────
    event Transfer(address indexed from, address indexed to, uint256 indexed tokenId);
    event Approval(address indexed owner, address indexed approved, uint256 indexed tokenId);
    event ApprovalForAll(address indexed owner, address indexed operator, bool approved);

    // ── 생성자 ────────────────────────────────────────────────────────
    constructor() {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(MINTER_ROLE, msg.sender);
        _grantRole(PAUSER_ROLE, msg.sender);
    }

    // ── ERC-721 조회 ──────────────────────────────────────────────────
    function balanceOf(address owner) public view returns (uint256) {
        require(owner != address(0), "Zero address");
        return _balances[owner];
    }

    function ownerOf(uint256 tokenId) public view returns (address) {
        address owner = _owners[tokenId];
        require(owner != address(0), "Token does not exist");
        return owner;
    }

    function getApproved(uint256 tokenId) public view returns (address) {
        require(_owners[tokenId] != address(0), "Token does not exist");
        return _tokenApprovals[tokenId];
    }

    function isApprovedForAll(address owner, address operator) public view returns (bool) {
        return _operatorApprovals[owner][operator];
    }

    function totalSupply() public view returns (uint256) {
        return _totalSupply;
    }

    // ── 발행 / 소각 ───────────────────────────────────────────────────
    function mint(address to, uint256 tokenId)
        public onlyRole(MINTER_ROLE) whenNotPaused
    {
        require(to != address(0), "Mint to zero address");
        require(_owners[tokenId] == address(0), "Token already exists");
        _owners[tokenId]  = to;
        _balances[to]    += 1;
        _totalSupply     += 1;
        emit Transfer(address(0), to, tokenId);
    }

    function burn(uint256 tokenId) public whenNotPaused {
        address owner = ownerOf(tokenId);
        require(
            msg.sender == owner
            || msg.sender == _tokenApprovals[tokenId]
            || _operatorApprovals[owner][msg.sender],
            "Not authorized"
        );
        delete _tokenApprovals[tokenId];  // 승인 초기화
        _balances[owner] -= 1;
        _totalSupply     -= 1;
        delete _owners[tokenId];
        emit Transfer(owner, address(0), tokenId);
    }

    // ── 전송 ─────────────────────────────────────────────────────────
    function transferFrom(address from, address to, uint256 tokenId)
        public whenNotPaused
    {
        require(_isApprovedOrOwner(msg.sender, tokenId), "Not authorized");
        _transfer(from, to, tokenId);
    }

    function safeTransferFrom(address from, address to, uint256 tokenId)
        public whenNotPaused
    {
        transferFrom(from, to, tokenId);
        // 실제 구현에서는 to가 컨트랙트이면 onERC721Received 호출 필요
        // 학습 목적으로 생략
    }

    // ── 승인 ─────────────────────────────────────────────────────────
    function approve(address to, uint256 tokenId) public {
        address owner = ownerOf(tokenId);
        require(
            msg.sender == owner || _operatorApprovals[owner][msg.sender],
            "Not owner or operator"
        );
        _tokenApprovals[tokenId] = to;
        emit Approval(owner, to, tokenId);
    }

    function setApprovalForAll(address operator, bool approved) public {
        require(operator != msg.sender, "Approve to caller");
        _operatorApprovals[msg.sender][operator] = approved;
        emit ApprovalForAll(msg.sender, operator, approved);
    }

    // ── 내부 함수 ─────────────────────────────────────────────────────
    function _transfer(address from, address to, uint256 tokenId) internal {
        require(ownerOf(tokenId) == from, "Not owner");
        require(to != address(0), "Transfer to zero address");
        delete _tokenApprovals[tokenId];  // 전송 시 개별 승인 초기화
        _balances[from] -= 1;
        _balances[to]   += 1;
        _owners[tokenId] = to;
        emit Transfer(from, to, tokenId);
    }

    function _isApprovedOrOwner(address spender, uint256 tokenId)
        internal view returns (bool)
    {
        address owner = ownerOf(tokenId);
        return (
            spender == owner
            || spender == _tokenApprovals[tokenId]
            || _operatorApprovals[owner][spender]
        );
    }

    // ── 긴급 정지 ─────────────────────────────────────────────────────
    function pause()   public onlyRole(PAUSER_ROLE) { _pause(); }
    function unpause() public onlyRole(PAUSER_ROLE) { _unpause(); }
}
```

### 5. 코드 해부 — 설계 결정 포인트

**① `_owners[tokenId] == address(0)` = 존재하지 않는 토큰:**

ERC-721에서 `address(0)`은 "소유자 없음 = 미발행 또는 소각됨"을 의미한다. `ownerOf`에서 0이면 revert하는 이유가 이것이다. mapping의 기본값이 0이기 때문에, 별도 "존재 여부" 변수 없이 소유자 주소만으로 존재 여부를 판단할 수 있다.

**② 전송 시 `delete _tokenApprovals[tokenId]` — 보안 필수 항목:**

개별 승인(`approve`)은 1회용이다. 전송이 완료되면 즉시 초기화한다. 이 줄을 빠뜨리면 발생하는 버그:

```
시나리오:
① Alice가 NFT #1001 소유
② Alice → approve(Bob, 1001)  (Bob에게 전송 권한 위임)
③ 어떤 이유로 Bob이 아직 전송 안 함
④ Alice → transferFrom(Alice, Carol, 1001)  (직접 Carol에게 전송)
⑤ _tokenApprovals[1001]에 Bob이 그대로 남아 있음 (초기화 안 했을 경우)
⑥ Bob → transferFrom(Carol, Bob, 1001)  (새 소유자 Carol의 NFT를 Bob이 가져감!)
```

전송 시 개별 승인을 초기화하지 않으면, 이전 소유자가 승인한 제3자가 새 소유자의 NFT를 탈취할 수 있다. **보안 상 매우 중요.**

**③ `approve` vs `setApprovalForAll`:**

```
approve(spender, tokenId)          → tokenId 하나만 위임
setApprovalForAll(operator, true)  → 보유한 모든 tokenId 위임
```

마켓플레이스 컨트랙트는 `setApprovalForAll`을 사용한다. 사용자가 한 번만 승인하면 마켓플레이스가 보유한 모든 NFT를 판매할 수 있다.

**`setApprovalForAll` 취약점 주의:**  
`setApprovalForAll(phishingContract, true)`를 실수로 서명하면 보유한 모든 NFT를 탈취당한다. 2022년 OpenSea 피싱 공격에서 수백 명이 이 방식으로 피해. "무엇에 서명하는지 항상 확인하라"는 NFT 보안의 기본 원칙.

**④ `safeTransferFrom` — ERC721Receiver 안전 검사:**

```
to가 EOA(일반 지갑)    → 바로 전송
to가 컨트랙트         → IERC721Receiver.onERC721Received() 호출
                       → 컨트랙트가 NFT를 처리할 수 있는지 확인
                       → 응답 없거나 잘못된 값 반환 → revert (NFT 영구 잠금 방지)
```

OpenZeppelin 구현체에는 이 검사가 포함되어 있다. 우리 구현에서는 학습 목적으로 생략했다.

### 6. tokenURI — 메타데이터 연결

ERC-721의 선택적 확장인 ERC-721 Metadata가 `tokenURI`를 정의한다.

```solidity
// ERC-721 Metadata 확장
function tokenURI(uint256 tokenId) public view returns (string memory) {
    require(_owners[tokenId] != address(0), "Token does not exist");
    return string.concat(
        "https://api.kyobo.com/nft/policy/",
        _toString(tokenId),
        ".json"
    );
}
```

tokenURI가 가리키는 JSON 파일 예시:

```json
{
  "name": "교보생명 종신보험 NFT #1001",
  "description": "교보생명 종신보험 증권 NFT",
  "image": "https://api.kyobo.com/nft/images/1001.png",
  "attributes": [
    { "trait_type": "상품코드", "value": "LI-001" },
    { "trait_type": "발행일",   "value": "2024-01-15" },
    { "trait_type": "보험기간", "value": "종신" }
  ]
}
```

이더스캔·OpenSea 등이 이 URI를 fetch해서 NFT 이미지와 속성을 표시한다.

**tokenURI가 빈 문자열("")이면:**  
블록체인상 NFT는 존재하지만 OpenSea 등에서 이미지와 속성이 표시되지 않는다. "No metadata" 상태로 표시됨. 교보생명 시스템에서는 tokenURI가 교보 API 서버를 가리키므로, 서버가 유지되는 한 메타데이터가 표시된다.

### 7. OpenZeppelin ERC721 활용

직접 구현을 이해했으니 OZ 버전을 보자.

```solidity
import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";
import "@openzeppelin/contracts/utils/Pausable.sol";

contract KyoboPolicyNFT_OZ is ERC721, AccessControl, Pausable {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    uint256 private _nextTokenId;
    string  private _baseTokenURI;

    constructor(string memory baseURI) ERC721("KyoboPolicyNFT", "KPNFT") {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(MINTER_ROLE, msg.sender);
        _grantRole(PAUSER_ROLE, msg.sender);
        _baseTokenURI = baseURI;
    }

    function mint(address to) public onlyRole(MINTER_ROLE) returns (uint256) {
        uint256 tokenId = _nextTokenId++;
        _safeMint(to, tokenId);   // safeTransferFrom과 동일한 receiver 검사
        return tokenId;
    }

    function _baseURI() internal view override returns (string memory) {
        return _baseTokenURI;
    }

    // Pausable 연결 (OZ v5 방식)
    function _update(address to, uint256 tokenId, address auth)
        internal override returns (address)
    {
        if (paused()) revert EnforcedPause();
        return super._update(to, tokenId, auth);
    }

    function pause()   public onlyRole(PAUSER_ROLE) { _pause(); }
    function unpause() public onlyRole(PAUSER_ROLE) { _unpause(); }
}
```

직접 구현 대비 우리가 추가한 것: 역할 제어 + URI 설정 + 일시정지 연결만. 나머지는 OZ `ERC721`이 처리.

**`_safeMint` vs `_mint`:**

```
_mint(to, tokenId):      receiver 검사 없음 (EOA, 컨트랙트 구분 안 함)
_safeMint(to, tokenId):  receiver가 컨트랙트면 onERC721Received 확인
                          → 수신 불가 컨트랙트에 발행 시 revert
```

실무에서는 `_safeMint`를 권장한다. 단, to가 항상 EOA임이 보장되는 시스템(KYC로 검증된 지갑 주소)이면 `_mint`도 안전하다.

### 8. ERC-20 / ERC-721 / ERC-1155 비교 — S39 예고

| | ERC-20 | ERC-721 | ERC-1155 |
|---|---|---|---|
| 토큰 종류 | 1종 | 1종 (고유 ID) | N종 |
| 수량 | 분할 가능 | 항상 1개 | tokenId당 수량 |
| 잔액 조회 | `balanceOf(addr)` | `balanceOf(addr)` (개수) | `balanceOf(addr, id)` |
| 소유자 | — | `ownerOf(tokenId)` | — |
| 배치 전송 | 없음 | 없음 | `safeBatchTransferFrom` |
| 메타데이터 | 없음 | `tokenURI(tokenId)` | `uri(tokenId)` |
| Gas (배치) | N번 트랜잭션 | N번 트랜잭션 | 1번 트랜잭션 |
| NFT 잠금 방지 | — | `safeTransferFrom` | `safeTransferFrom` |

KyoboNFT가 ERC-1155를 선택한 이유:
- 보험 상품 종류(tokenId)가 여러 개
- 동일 상품을 여러 고객에게 한 번에 발행(`mintBatch`) 가능
- ERC-721보다 배치 처리 gas 비용이 낮음
- ERC-721 Enumerable의 gas 오버헤드 없이 `balanceOf(addr, id)`로 직접 조회 가능

```
⑥ Account2 → burn(1002)
   → Transfer(Account2 → 0x0, 1002)
   → ownerOf(1002) → revert: "Token does not exist"
```

## 강사 노트

**반드시 짚을 것:**  
`_owners[tokenId] == address(0)` = 존재하지 않는 토큰. 이 패턴이 ERC-721의 "존재 여부 확인" 기준이다. `ownerOf`에서 0 반환이 아닌 revert인 이유가 이것이다.

**전송 시 approve 초기화 — 보안 시나리오:**  
강사 배경 섹션의 Alice-Bob-Carol 시나리오를 화이트보드에 그려주면 직관적이다. `delete _tokenApprovals[tokenId]`를 빠뜨리면 이전 소유자가 승인한 주소가 새 소유자의 NFT도 전송할 수 있는 버그. 코드에서 직접 짚어줄 것.

**safeTransferFrom receiver 검사 생략 이유:**  
학습 코드에서 `IERC721Receiver.onERC721Received` 검사를 생략했다고 명시적으로 언급할 것. 실제 운영 코드에서는 OZ `ERC721._safeMint` / `_safeTransfer`가 이를 처리한다. CryptoKitties NFT 잠김 사고를 실제 사례로 활용할 것.

**setApprovalForAll 피싱 경고:**  
"setApprovalForAll에 서명할 때는 항상 어떤 컨트랙트에 승인하는지 확인하라"는 실용적 보안 팁을 전달할 것. 2022년 OpenSea 피싱 사고(수십억 원 피해)의 직접적 원인.

**tokenURI 메타데이터 저장 방식 질문 대비:**  
"NFT를 IPFS에 올리면 영구 보존되는가"라는 질문이 자주 나온다. IPFS는 핀닝을 유지해야 하며, 핀닝 서비스가 종료되면 데이터가 사라질 수 있다. 완전한 영구 보존은 Arweave만 보장한다.

**S39 예고:**  
ERC-1155는 `balanceOf(address, tokenId)` — 주소와 tokenId 두 인자가 모두 필요하다. ERC-20과 ERC-721을 하나로 합친 구조. KyoboNFT 코드를 처음 해부하는 세션이다.
