01

표지 — 지갑 프로비저닝 & 매핑 설계

~3분
자, S27 시작하겠습니다. 이번 세션의 주제는 지갑 프로비저닝과 매핑 설계입니다.
M5 전체를 관통하는 핵심 질문이 하나 있습니다. "NFT를 누구의 지갑에 발행할 것인가?" 이 질문에 답하려면 교보생명 시스템이 사용자를 식별하는 방식과, 블록체인이 수신자를 식별하는 방식이 근본적으로 다르다는 사실부터 이해해야 합니다.
교보생명 내부에서 사용자는 userId로 식별됩니다. 예를 들어 "K-00123" 같은 내부 식별자죠. 반면 블록체인에서 수신자는 walletAddr, 즉 "0x742d..." 형태의 이더리움 주소로만 식별됩니다. 이 두 식별자 공간을 어떻게 연결하느냐가 바로 이번 세션의 핵심입니다.
프로비저닝(Provisioning)이란? 사용자 계정 생성 시 필요한 리소스를 미리 준비하고 할당하는 과정. 이번 세션에서는 "사용자가 NFT를 받을 수 있는 지갑 주소를 준비하는 것"을 의미합니다.
02

전체 아키텍처맵 — S27이 담당하는 영역

~5분
M5 전체 아키텍처를 보겠습니다. 슬라이드에 큰 그림이 있는데, S27이 어디에 위치하는지부터 짚고 가겠습니다.
전체 흐름은 이렇습니다. 사용자가 이벤트를 발생시키면 — 예를 들어 걷기 챌린지를 달성했다면 — 시스템은 이 사용자에게 NFT를 발행해야 합니다. 그 발행 과정은 크게 세 단계로 나뉩니다. 첫째, 이 사용자에게 어떤 NFT를 발행할지 정책을 확인하고, 둘째, 발행 조건을 충족했는지 검증하고, 셋째, 실제 지갑 주소를 찾아서 VASP에 발행을 위탁합니다.
S27은 세 번째 단계의 기반을 담당합니다. 즉, "이 userId에게 대응되는 지갑 주소가 무엇인가?"라는 질문에 답하는 인프라를 구축하는 것입니다. 이게 없으면 S28에서 정책을 아무리 잘 세워도, S29에서 조건을 아무리 완벽하게 체크해도, 실제로 NFT를 어디로 보낼지를 모르게 됩니다.
아키텍처맵에서 S27은 가장 아래 인프라 레이어에 해당합니다. WalletProvisioningService가 WalletMappingService를 통해 DB에 접근하고, 필요 시 ExternalVaspClient를 통해 외부 VASP에서 지갑을 생성합니다.
S27의 역할 요약 userId → walletAddr 변환을 담당하는 인프라 레이어. S28~S30이 "무엇을 발행할지", "조건이 충족됐는지", "어떻게 배치 처리할지"를 다룬다면, S27은 "누구에게 발행할지"의 물리적 주소를 확보하는 역할입니다.
03

두 개의 식별자 공간 — userId vs walletAddr

~6분
이 슬라이드가 이번 세션의 핵심 개념입니다. 두 개의 식별자 공간이 존재합니다.
왼쪽이 교보생명 내부 세계입니다. 여기서는 모든 사용자가 userId로 식별됩니다. "K-00123", "K-99999" 이런 형태죠. 이 식별자는 교보생명 DB 어딘가에 있고, 사용자의 보험 계약 정보, 건강 데이터, 이벤트 참여 기록 등 모든 것이 이 userId에 연결돼 있습니다.
오른쪽이 블록체인 세계입니다. 여기서는 모든 수신자가 walletAddr로 식별됩니다. "0x742d35Cc6634C0532925a3b844Bc454e4438f44e" 이런 형태의 이더리움 주소입니다. 블록체인은 userId 같은 개념이 없습니다. 오직 지갑 주소만 알 뿐이에요.
이 두 식별자 공간 사이에 브릿지가 필요합니다. "K-00123 → 0x742d..." 이 매핑 정보를 어딘가에 저장해둬야 하는 거죠. 그것이 바로 user_wallet_mapping 테이블입니다.
식별자 공간 분리의 원칙 두 공간을 절대 혼용하지 않습니다. 교보생명 내부 시스템에 walletAddr를 직접 넣지 않고, 블록체인 TX에 userId를 직접 넣지 않습니다. 브릿지 테이블이 유일한 연결 고리입니다.
04

userId를 블록체인에 저장하면 안 되는 이유

~7분
"그냥 블록체인 TX의 메타데이터 필드에 userId를 함께 기록하면 되지 않나요?" 라는 질문을 하실 수 있습니다. 이 슬라이드가 그 질문에 답합니다.
첫 번째 이유: 개인정보보호법 위반 위험입니다. 교보생명의 내부 식별자 K-00123은 해당 사람이 교보 고객임을 나타내는 정보입니다. 이것이 블록체인에 올라가면 — 블록체인은 기본적으로 공개 원장이므로 — 전 세계 누구나 "이 지갑 주소는 교보생명 고객이다"라는 사실을 알 수 있게 됩니다. 이는 개인정보 노출입니다.
두 번째 이유: 영구성과 수정 불가입니다. 블록체인에 올린 데이터는 수정할 수 없습니다. 만약 교보생명이 내부 userId 체계를 바꾸거나, 사용자가 개인정보 삭제를 요청하면 어떻게 될까요? 블록체인에 이미 올라간 데이터는 지울 수가 없습니다.
세 번째 이유: 시스템 결합도 증가입니다. 블록체인에 교보 내부 식별자가 박혀버리면, 블록체인과 교보 내부 시스템이 강하게 결합됩니다. 향후 시스템 변경 시 블록체인 데이터와의 호환성을 평생 유지해야 하는 짐이 생깁니다.
실제 사례의 교훈 초기 블록체인 프로젝트들 중 내부 ID를 온체인에 올렸다가 나중에 GDPR 대응, 시스템 마이그레이션 시 심각한 문제가 발생한 사례가 다수 있습니다. 두 식별자 공간의 분리는 설계 초기에 반드시 결정해야 할 원칙입니다.
05

앱이 먼저, 서버가 나중 — 프로비저닝 타이밍

~5분
지갑 프로비저닝은 언제 해야 할까요? 이 슬라이드가 타이밍에 대한 설계 결정을 설명합니다.
두 가지 선택지가 있습니다. 첫 번째는 이벤트 발생 시점에 즉석에서 지갑을 만드는 것입니다. NFT 발행이 필요한 순간에 "이 사용자 지갑이 없네, 지금 만들자"라고 하는 거죠. 두 번째는 사전에 미리 프로비저닝 해두는 것입니다.
교보생명 설계에서는 두 번째 방식을 선택했습니다. 그 이유는 간단합니다. 지갑 생성은 VASP 외부 API를 호출해야 하는 비동기 작업이고, 네트워크 지연이 발생할 수 있습니다. NFT 발행 파이프라인 한가운데에서 지갑 생성이 실패하면 전체 발행이 실패합니다.
그래서 프로비저닝 흐름은 이렇습니다. 사용자가 교보생명 앱에 처음 로그인하거나, 블록체인 관련 서비스에 처음 동의할 때 앱이 먼저 프로비저닝 API를 호출합니다. 서버는 VASP에서 지갑을 생성하고 user_wallet_mapping에 저장합니다. 이후 이벤트가 발생해서 NFT를 발행할 때는 이미 지갑이 준비돼 있으므로 DB에서 주소만 조회하면 됩니다.
프로비저닝 타이밍 원칙 NFT 발행 파이프라인 외부에서 미리 처리한다. 발행 시점에는 DB 조회(findByUserId)만 하고, 없으면 FAILED 처리한다. "없으면 그때 만들자" 패턴은 발행 지연·이중 생성 등 복잡한 race condition을 유발한다.
06

user_wallet_mapping 테이블 DDL — 1/2

~8분
이제 실제 코드입니다. user_wallet_mapping 테이블의 DDL을 봅시다.
CREATE TABLE IF NOT EXISTS user_wallet_mapping ( id BIGSERIAL PRIMARY KEY, user_id VARCHAR(64) NOT NULL UNIQUE, wallet_addr VARCHAR(42) NOT NULL, vasp_type VARCHAR(16) NOT NULL CHECK (vasp_type IN ('EXTERNAL', 'KYOBO')), verified BOOLEAN NOT NULL DEFAULT false, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() );
📁 infrastructure/docker/postgres/initdb.d/01-dmz-schema.sql
컬럼을 하나씩 읽겠습니다. id는 BIGSERIAL, 즉 자동 증가하는 정수형 기본 키입니다. 단순한 내부 레코드 식별자입니다.
user_id는 VARCHAR(64)이고 UNIQUE 제약이 있습니다. 교보생명 내부 사용자 식별자입니다. 64자면 충분히 긴 식별자를 수용할 수 있습니다. 그리고 UNIQUE가 핵심입니다. 한 사용자는 하나의 지갑 매핑만 가질 수 있다는 제약을 DB 수준에서 강제하는 거죠.
wallet_addr는 VARCHAR(42)입니다. 이더리움 주소는 "0x" + 40자리 16진수로 정확히 42자입니다. 이 사이즈는 이더리움 표준에서 나온 숫자입니다.
vasp_type은 VARCHAR(16)이고 CHECK 제약으로 'EXTERNAL' 또는 'KYOBO'만 허용합니다. EXTERNAL은 현재 교보생명이 계약한 외부 VASP(예: 월렛원)을 통해 생성한 수탁 지갑이고, KYOBO는 향후 교보생명이 자체적으로 운영하는 VASP를 의미합니다. Phase 1에서는 EXTERNAL만 사용합니다.
verified는 BOOLEAN이고 DEFAULT false입니다. Phase 1의 수탁 지갑은 VASP가 관리하므로 검증이 불필요하지만, Phase 2에서 사용자가 자가관리 지갑을 가져오면 검증이 필요합니다. 이 컬럼이 그 상태를 추적합니다.
UNIQUE(user_id)의 의미 한 사용자 = 한 지갑이라는 Phase 1 설계 결정을 DB 레벨에서 강제합니다. 만약 같은 userId로 두 번 INSERT를 시도하면 DB가 에러를 냅니다. 애플리케이션에서 중복 체크를 해도 되지만, DB 제약이 최후의 방어선 역할을 합니다.
07

테이블 설계 2/2 — 인덱스 & 코멘트

~4분
DDL 두 번째 부분입니다.
CREATE INDEX IF NOT EXISTS idx_wallet_mapping_user_id ON user_wallet_mapping(user_id); CREATE INDEX IF NOT EXISTS idx_wallet_mapping_addr ON user_wallet_mapping(wallet_addr); COMMENT ON TABLE user_wallet_mapping IS 'M5 실습: userId ↔ walletAddr 매핑 (S27)';
인덱스가 두 개 있습니다. user_id 인덱스는 "이 사용자의 지갑 주소를 알고 싶다" — 즉 발행 전 주소 조회 시 사용됩니다. 가장 빈번한 쿼리 패턴이므로 반드시 필요합니다.
wallet_addr 인덱스는 역방향 조회, 즉 "이 지갑 주소의 소유자가 누구인가"를 빠르게 찾기 위한 것입니다. 감사 로그나 분쟁 처리 시 사용합니다. 일반적인 발행 흐름에서는 잘 쓰이지 않지만, 운영 중에 갑자기 특정 지갑에서 이상한 활동이 감지됐을 때 "이 지갑이 누구 것인지"를 빨리 찾아야 하는 상황이 있습니다. 그때 이 인덱스가 없으면 전체 테이블 스캔을 해야 합니다.
COMMENT는 DBA나 나중에 이 테이블을 보는 사람이 "이게 뭔 테이블이지?"라는 질문에 바로 답할 수 있도록 남겨두는 메모입니다. 코드 주석과 같은 역할이지만 DB 딕셔너리에 저장됩니다.
08

전체 의존관계 다이어그램

~6분
구현에 들어가기 전에, 우리가 만들 컴포넌트들의 관계를 전체적으로 봅시다.
슬라이드의 의존관계 다이어그램을 보면 다음과 같은 구조입니다. 최상위에 WalletProvisioningService가 있습니다. 이게 이번 세션의 진입점이자 외부에서 호출하는 주요 서비스입니다.
WalletProvisioningService는 두 가지에 의존합니다. 하나는 ExternalVaspClient, 다른 하나는 WalletMappingService입니다. ExternalVaspClient는 외부 VASP API를 호출해서 실제 지갑을 생성하는 역할이고, WalletMappingService는 그 결과를 DB에 저장하고 조회하는 역할입니다.
WalletMappingService는 WalletMappingRepository 인터페이스에 의존합니다. 그리고 그 인터페이스의 실제 구현체가 PgWalletMappingRepository입니다. Pg는 PostgreSQL의 약자입니다.
이 구조에서 중요한 것은 화살표의 방향입니다. 상위 컴포넌트가 하위 컴포넌트를 알지만, 하위 컴포넌트는 상위를 모릅니다. 그리고 서비스들은 구체 구현체가 아닌 인터페이스에 의존합니다. 이것이 DIP입니다.
09

DIP — 의존성 역전 원칙

~8분
DIP, 의존성 역전 원칙을 이 프로젝트에 어떻게 적용했는지 구체적으로 봅시다.
DIP의 핵심 문장은 이겁니다: "고수준 모듈은 저수준 모듈에 의존해서는 안 된다. 둘 다 추상화에 의존해야 한다." 이게 무슨 의미인지 예시로 설명하겠습니다.
DIP 없이 만들면 이렇게 됩니다. WalletMappingService 내부에 `new PgWalletMappingRepository(pool)`이 직접 들어갑니다. WalletMappingService가 PgWalletMappingRepository를 직접 생성하고 알고 있는 거죠. 이 경우 문제는 테스트할 때 실제 PostgreSQL이 반드시 필요하다는 겁니다.
DIP를 적용하면 이렇게 됩니다. WalletMappingService의 생성자 파라미터로 `repo: WalletMappingRepository` 인터페이스를 받습니다. 이제 WalletMappingService는 PgWalletMappingRepository를 전혀 모릅니다. 인터페이스만 압니다. 운영 환경에서는 PgWalletMappingRepository를 주입하고, 테스트 환경에서는 InMemoryWalletMappingRepository를 주입하면 됩니다.
이게 왜 중요한가요? 이 코드를 나중에 PostgreSQL이 아닌 다른 DB로 마이그레이션한다고 가정해 봅시다. DIP가 적용돼 있으면 WalletMappingRepository를 구현하는 새 클래스만 만들면 됩니다. WalletMappingService 코드는 단 한 줄도 바꾸지 않아도 됩니다.
DIP (Dependency Inversion Principle) SOLID 원칙의 D. 고수준 모듈이 저수준 모듈의 구체 구현이 아닌 인터페이스(추상화)에 의존하게 한다. TypeScript에서는 interface 키워드로 추상화를 정의하고, 생성자 주입으로 구현체를 교체한다.

이제 실제 코드입니다. WalletMappingService를 4개 슬라이드에 걸쳐 설명합니다. 첫 번째는 이 서비스가 의존하는 리포지토리 인터페이스입니다.

WalletMappingService 2/4 — getWalletAddr

~7분
WalletMappingService의 두 번째 메서드인 getWalletAddr입니다. NFT 발행 직전에 호출하는 핵심 메서드입니다.
async getWalletAddr(userId: string): Promise<string> { const existing = await this.repo.findByUserId(userId); if (!existing) throw new WalletNotFoundError(userId); if (!existing.verified) throw new WalletNotVerifiedError(userId); return existing.walletAddr; }
로직이 단순합니다. DB를 조회해서 매핑이 없으면 WalletNotFoundError를 던집니다. 매핑은 있는데 verified가 false이면 WalletNotVerifiedError를 던집니다. 둘 다 통과하면 walletAddr를 반환합니다.
두 에러 경로가 다른 이유를 이해하는 게 중요합니다. WalletNotFoundError는 "아직 프로비저닝이 안 됐다"는 의미입니다. HTTP로 매핑하면 404 Not Found입니다. WalletNotVerifiedError는 "매핑은 있는데 아직 검증 전이다"는 의미입니다. Phase 2에서 사용자가 자가관리 지갑을 가져온 경우 서명 검증을 해야 하는데 아직 안 된 상태입니다. HTTP로는 403 Forbidden에 해당합니다.
중요한 설계 결정: getWalletAddr가 지갑을 자동으로 생성하지 않는다는 것입니다. 없으면 에러를 던집니다. 왜냐하면 지갑 생성은 명시적 provision() 호출을 통해서만 이루어져야 하기 때문입니다. 운영자 모르게 새 지갑이 생기면 감사 추적이 불가능해집니다.
자동 프로비저닝 패턴의 위험성 "없으면 그때 만들자" 패턴은 동시 요청 시 같은 사용자에게 지갑이 두 개 생성될 수 있는 race condition을 만들 수 있습니다. 또한 언제, 왜 지갑이 생성됐는지 추적이 어려워집니다. 명시적 프로비저닝 흐름을 유지하는 것이 감사 가능성을 보장합니다.

WalletMappingService 3/4 — getMapping (멱등성 체크)

~5분
세 번째 메서드인 getMapping입니다. 이름만 보면 단순한 조회처럼 보이지만, 역할이 중요합니다.
async getMapping(userId: string): Promise<WalletMapping | null> { return this.repo.findByUserId(userId); }
코드 자체는 아주 단순합니다. 그냥 리포지토리에 위임하는 거죠. 하지만 이 메서드가 호출되는 맥락이 중요합니다.
provision() 함수의 가장 첫 번째 단계에서 이 메서드를 호출합니다. "이 userId에 대한 매핑이 이미 있나?"를 먼저 확인하는 거죠. 결과에 따라 분기합니다. null이 반환되면, 즉 매핑이 없으면 VASP를 호출해서 새로 만듭니다. WalletMapping이 반환되면, 이미 프로비저닝된 것이므로 즉시 그걸 반환합니다. VASP 호출도 없고, DB 저장도 없습니다.
이것이 바로 멱등성 구현입니다. 같은 userId로 provision()을 10번 호출해도 VASP는 1번만 호출되고, DB에는 1행만 저장됩니다. 멱등성이 왜 중요하냐면, 네트워크 오류 등으로 retry가 발생했을 때 안전하게 재시도할 수 있어야 하기 때문입니다.
멱등성(Idempotency) 같은 연산을 여러 번 수행해도 결과가 동일한 성질. f(f(x)) = f(x). provision()에 멱등성이 있으면 네트워크 타임아웃 후 retry해도 "지갑이 두 개 생기는" 사고가 발생하지 않습니다.

PgWalletMappingRepository 2/5 — findByUserId

~7분
async findByUserId(userId: string): Promise<WalletMapping | null> { const { rows } = await this.pool.query( 'SELECT * FROM user_wallet_mapping WHERE user_id = $1', [userId], ); return rows[0] ? this._toModel(rows[0]) : null; }
SQL 쿼리를 봅시다. WHERE user_id = $1에서 $1은 플레이스홀더입니다. 실제 값은 두 번째 파라미터 배열 [userId]에 들어갑니다. 이것이 파라미터화된 쿼리(Parameterized Query)입니다.
왜 문자열 연결 대신 파라미터화된 쿼리를 써야 하는가? SQL Injection 방지 때문입니다. 만약 `SELECT * FROM ... WHERE user_id = '${userId}'` 처럼 직접 넣으면, userId에 ' OR '1'='1 같은 값이 들어올 때 전체 테이블이 반환될 수 있습니다. 파라미터화된 쿼리에서는 드라이버가 값을 이스케이프 처리하므로 이런 공격이 불가능합니다.
rows[0] 존재 여부로 null 처리합니다. 없으면 null을 반환하고, 에러를 throw하지 않습니다. 에러를 던질지 여부는 호출자(getWalletAddr)가 결정합니다. 리포지토리는 "데이터가 없다"는 사실만 전달하고, 그게 에러인지 아닌지의 판단은 하지 않습니다. 이것이 책임 분리입니다.
조회 결과가 있으면 _toModel(rows[0])을 호출합니다. DB row의 snake_case 컬럼을 camelCase 도메인 모델로 변환하는 메서드인데, 슬라이드 18에서 자세히 보겠습니다.
파라미터화된 쿼리는 선택이 아닌 필수 SQL Injection은 OWASP Top 10에서 오랜 기간 1위를 차지해온 취약점입니다. 금융 서비스에서 이 취약점이 발생하면 전체 고객 데이터가 노출될 수 있습니다. 파라미터화된 쿼리는 한 줄로 이를 완전히 방어합니다.

PgWalletMappingRepository 3/5 — save (UPSERT)

~9分
async save(mapping: WalletMapping): Promise<void> { await this.pool.query( `INSERT INTO user_wallet_mapping (user_id, wallet_addr, vasp_type, verified, created_at) VALUES ($1, $2, $3, $4, $5) ON CONFLICT (user_id) DO UPDATE SET wallet_addr = $2, vasp_type = $3, verified = $4`, [ mapping.userId, mapping.walletAddr, mapping.vaspType, mapping.verified, mapping.createdAt, ], ); }
UPSERT 쿼리입니다. ON CONFLICT (user_id) DO UPDATE SET ... 이 부분이 핵심입니다.
동작 방식입니다. INSERT를 시도합니다. user_id 컬럼에 UNIQUE 제약이 있으므로, 같은 user_id가 이미 있으면 충돌이 발생합니다. 충돌이 없으면 새 행이 삽입됩니다. 충돌이 발생하면 DO UPDATE SET으로 기존 행의 wallet_addr, vasp_type, verified 컬럼을 업데이트합니다.
왜 UPSERT인가? Phase 1에서는 한 사람이 지갑을 바꾸는 시나리오가 없습니다. 하지만 Phase 2 이상에서 사용자가 "새 지갑으로 바꾸고 싶다"고 요청할 수 있습니다. UPSERT로 구현해두면 그 시나리오도 자연스럽게 처리됩니다. 코드를 바꿀 필요가 없습니다.
또한 SELECT + UPDATE 두 번의 DB 왕복이 필요 없습니다. "지금 있는지 확인한 다음 없으면 INSERT, 있으면 UPDATE" 이 논리를 DB 한 번의 왕복으로 처리합니다. TOCTOU(Time Of Check To Time Of Use) 문제도 없습니다. SELECT와 INSERT 사이에 다른 요청이 끼어들어 동시에 두 번 INSERT되는 상황을 DB가 원자적으로 방지합니다.
TOCTOU (Time Of Check To Time Of Use) "확인 시점"과 "사용 시점" 사이에 상태가 바뀔 수 있는 동시성 버그. "없는 것 확인 후 INSERT" 패턴은 두 요청이 동시에 "없음"을 확인하고 둘 다 INSERT를 시도해 중복이 생길 수 있다. UPSERT는 이를 원자적으로 해결한다.

PgWalletMappingRepository 5/5 — _toModel

~6분
private _toModel(row: Record<string, unknown>): WalletMapping { return { userId: row['user_id'] as string, walletAddr: row['wallet_addr'] as string, vaspType: row['vasp_type'] as VaspType, verified: row['verified'] as boolean, createdAt: new Date(row['created_at'] as string), }; }
_toModel 메서드입니다. 이 메서드가 하는 일은 세 가지입니다.
첫째, snake_case에서 camelCase로 변환합니다. DB는 snake_case 컬럼명(user_id, wallet_addr, vasp_type)을 쓰고, TypeScript 모델은 camelCase(userId, walletAddr, vaspType)를 씁니다. 이 변환이 여기서 이루어집니다.

셋째, 도메인 모델 분리입니다. DB 스키마가 변경되더라도 — 예를 들어 테이블 컬럼명이 바뀌더라도 — 이 _toModel 메서드만 수정하면 됩니다. 상위 레이어의 WalletMapping 인터페이스는 건드리지 않아도 됩니다.
private 접근제한자를 주목하세요. 외부에서 직접 호출하는 메서드가 아닙니다. 인터페이스에도 없습니다. 리포지토리 내부 구현 세부사항입니다.

WalletProvisioningService 1/4 — 나쁜 설계 vs 좋은 설계

~8분
이제 이번 세션의 핵심 서비스인 WalletProvisioningService입니다. 먼저 나쁜 설계를 보고, 왜 나쁜지 이해한 다음, 좋은 설계를 봅시다.
나쁜 설계에서는 컨트롤러가 이렇게 생겼습니다.
// ❌ 나쁜 설계 — 컨트롤러에 VASP 분기 로직 app.post('/api/wallet/provision', async (req, res) => { if (req.body.vaspType === 'EXTERNAL') { // VASP A 전용 로직... } else if (req.body.vaspType === 'KYOBO') { // VASP B 전용 로직... } // VASP 추가할 때마다 여기를 수정 });
이게 왜 나쁜가요? VASP가 추가될 때마다 컨트롤러를 수정해야 합니다. 컨트롤러는 HTTP 요청을 파싱하고 응답을 반환하는 역할만 해야 하는데, 비즈니스 로직이 들어가 버렸습니다. 테스트하려면 컨트롤러를 직접 테스트해야 하고, 그 안의 VASP 로직도 함께 테스트해야 합니다.
좋은 설계에서는 이렇습니다.
// ✅ 좋은 설계 — 컨트롤러는 위임만 app.post('/api/wallet/provision', async (req, res) => { const { userId, vaspType } = req.body; const result = await walletProvisioningService.provision(userId, vaspType); res.status(200).json(result); });
컨트롤러는 파싱과 위임만 합니다. 모든 VASP 분기 로직은 WalletProvisioningService.provision() 내부로 숨겨집니다. VASP가 추가되거나 교체돼도 컨트롤러 코드는 바뀌지 않습니다.

async provision(userId: string, vaspType: VaspType | string): Promise<ProvisionResult> { // ① 멱등성 체크 — 이미 프로비저닝된 경우 즉시 반환 const existing = await this.walletMapping.getMapping(userId); if (existing) { return { walletAddress: existing.walletAddr, isNew: false, }; } // ② VASP 분기 — vaspType에 따라 다른 방식으로 지갑 생성 let walletAddr: string; if (vaspType === 'EXTERNAL') { const result = await this.vaspClient.createWallet({ userId }); walletAddr = result.address; } else if (vaspType === 'KYOBO') { // Phase 2: 교보 자체 VASP 로직 throw new Error('KYOBO VASP not yet implemented'); } else { throw new UnsupportedVaspTypeError(vaspType); } ... }

~7분
ExternalVaspClient 인터페이스를 봅시다. 이게 WalletProvisioningService와 외부 VASP API 사이의 계약입니다.
export interface ExternalVaspClient { createWallet(params: { userId: string; }): Promise<{ address: string; // 생성된 지갑 주소 vaspRefId: string; // VASP 내부 참조 ID }>; }

여기서 중요한 질문: "왜 인터페이스인가?" 교보생명이 지금 계약한 VASP는 월렛원이라고 가정합시다. 월렛원의 API를 직접 WalletProvisioningService에 하드코딩하면 어떻게 될까요? 나중에 다른 VASP로 교체할 때 WalletProvisioningService 코드를 수정해야 합니다.
인터페이스를 중간에 두면 다릅니다. WalletProvider이 WalletOneVaspClient를 사용하고 싶으면 WalletOneVaspClient가 ExternalVaspClient 인터페이스를 구현하면 됩니다. VASP가 교체돼도 WalletProvisioningService는 건드리지 않아도 됩니다. 인터페이스의 구현체만 교체하면 됩니다.
인터페이스를 통한 외부 서비스 격리 외부 서비스(VASP, 결제사, SMS 발송사 등)는 언제든 바뀔 수 있다. 인터페이스를 통해 격리하면 변경의 영향 범위가 구현체 클래스 하나로 한정된다. 이를 어댑터 패턴(Adapter Pattern)이라고 한다.

에러 타입 설계 — 도메인 에러 vs 일반 에러

~7분
에러 타입 설계에 대해 이야기합시다. 이번 세션에서 세 가지 에러 타입을 새로 정의합니다.
// 지갑 매핑 없음 — HTTP 404에 대응 export class WalletNotFoundError extends Error { constructor(userId: string) { super(`지갑 미등록: ${userId}`); this.name = 'WalletNotFoundError'; } } // 지갑 미검증 — HTTP 403에 대응 export class WalletNotVerifiedError extends Error { constructor(userId: string) { super(`지갑 미검증: ${userId}`); this.name = 'WalletNotVerifiedError'; } } // 지원하지 않는 VASP 타입 — HTTP 400에 대응 export class UnsupportedVaspTypeError extends Error { constructor(vaspType: string) { super(`미지원 VASP 타입: ${vaspType}`); this.name = 'UnsupportedVaspTypeError'; } }
왜 Error를 직접 던지지 않고 커스텀 에러 클래스를 만드는가? 두 가지 이유입니다.
첫째, catch에서 타입으로 분기할 수 있습니다. if (err instanceof WalletNotFoundError)처럼 어떤 종류의 에러인지 코드로 판별할 수 있습니다. 일반 Error를 쓰면 메시지 문자열로 판별해야 하는데, 이건 너무 취약합니다.
둘째, HTTP 상태 코드와의 매핑이 명확해집니다. WalletNotFoundError → 404, WalletNotVerifiedError → 403, UnsupportedVaspTypeError → 400. 컨트롤러에서 instanceof 체크만 하면 올바른 HTTP 응답을 만들 수 있습니다.
this.name = 'WalletNotFoundError'는 에러의 name 프로퍼티를 설정합니다. 로그에서 에러 타입을 쉽게 식별하기 위함입니다. JavaScript에서 클래스 이름이 자동으로 name에 들어가지 않는 경우가 있어서 명시적으로 설정하는 것이 좋습니다.

provision() 완전한 흐름 정리

~8분
지금까지 설명한 provision() 전체 흐름을 한 장에 정리합니다.
흐름의 시작은 클라이언트(앱)가 POST /api/wallets/provision을 호출하는 것입니다. userId와 vaspType이 전달됩니다.
① 멱등성 체크: WalletMappingService.getMapping(userId)를 호출합니다. DB에 user_wallet_mapping 테이블을 조회합니다. 결과가 있으면 즉시 반환(isNew: false). 없으면 다음 단계로.
② VASP 분기: vaspType을 보고 어느 클라이언트를 쓸지 결정합니다. EXTERNAL이면 ExternalVaspClient.createWallet() 호출. 이 호출이 외부 VASP API로 나갑니다.
③ 지갑 생성: VASP API가 성공하면 새 지갑 주소(0x...)가 반환됩니다. VASP 내부 참조 ID도 함께 옵니다.
④ 매핑 저장: 성공한 경우에만 WalletMappingService.saveMapping()을 호출합니다. 이 메서드가 리포지토리의 save()를 통해 DB UPSERT를 실행합니다.
⑤ 감사 로그: auditLog가 주입된 경우 WALLET_PROVISIONED 이벤트를 기록합니다.
⑥ 반환: walletAddress와 isNew: true를 클라이언트에게 반환합니다.
어느 단계든 실패하면? VASP 호출 실패이면 saveMapping이 실행되지 않으므로 DB는 이전 상태 그대로입니다. 다음 retry에서 멱등성 체크를 통과해도 매핑이 없으므로 VASP를 다시 호출합니다. 만약 VASP가 지갑을 만들었는데 응답 반환 중 네트워크 오류가 났다면, 다음 retry에서 VASP가 같은 userId로 지갑을 또 만들 수 있습니다. 이것이 이중 지갑 문제인데, VASP 계약 시 외부 사용자 ID(externalUserId) 기반 멱등성을 지원하도록 요구하거나, VASP 내부에서 중복 생성을 방지하는 메커니즘이 필요합니다.
분산 시스템에서의 "딱 한 번" 보장 VASP API 호출과 DB 저장은 서로 다른 시스템입니다. 둘 사이에 네트워크 실패가 발생하면 "VASP에는 생성됐는데 DB에는 없는" 상황이 생길 수 있습니다. 완전한 해결은 SAGA 패턴이나 보상 트랜잭션(Compensating Transaction)이 필요합니다. Phase 1에서는 VASP의 externalUserId 기반 중복 방지로 대응합니다.

S28·02

왜 발행 정책을 DB에 저장하는가 — 하드코딩의 문제

~8분
가장 단순한 방법은 이렇게 하는 겁니다. 코드 안에 "걷기 챌린지 NFT의 tokenId는 1001이다"라고 직접 써버리는 거죠. 이것이 하드코딩입니다.
하드코딩의 문제는 무엇인가요? 교보생명이 새로운 이벤트 — 예를 들어 "보험 갱신 NFT"를 추가하고 싶다고 합시다. 하드코딩이면 반드시 개발자가 코드를 수정해야 합니다. 코드를 수정하면 빌드, 테스트, 배포 사이클이 돌아야 합니다. 야간에 긴급으로 새 NFT 이벤트를 추가해야 한다면? 개발자를 깨워야 합니다.
또 다른 문제: 기간 제한. "이 이벤트는 2026년 1월 1일부터 1월 31일까지만 유효하다"라는 조건은 코드로 관리하기가 번거롭습니다. 날짜가 지나면 다시 코드를 수정하고 배포해야 합니다.
세 번째 문제: 발행 한도. "사용자당 최대 1개", "전체 1000개 한도"와 같은 수량 제한도 코드 안에 숫자로 박혀 있으면 변경할 때마다 배포가 필요합니다.
해결책은 간단합니다. 이 모든 정책 정보를 DB 테이블에 저장하는 겁니다. 새 이벤트 추가? DB에 행 하나 INSERT. 기간 변경? UPDATE. 한도 조정? UPDATE. 코드 변경 없이 운영 중에 실시간으로 정책을 바꿀 수 있습니다.
정책의 DB화가 주는 세 가지 이점 1. 운영자가 코드 없이 정책 추가·변경·삭제 가능
2. 발행 이력과 함께 정책 이력도 추적 가능 (어떤 정책 버전으로 발행됐는가)
3. A/B 테스트나 이벤트 pilot 운영이 쉬워짐
S28·03

두 서비스의 역할 분리 — SRP 관점

~6분
앞 슬라이드에서 두 가지 질문을 나눴습니다. 이제 왜 이 두 질문을 별개의 서비스로 분리하는지 설명합니다.
단일 책임 원칙(SRP): 변경 이유가 다르면 분리하라. IssuancePolicyService와 EventConditionService는 변경 이유가 다릅니다.
IssuancePolicyService가 변경되는 경우: 운영팀이 새 이벤트 정책을 추가하거나 기간을 변경할 때. DB 행 하나를 추가하면 됩니다. 코드 수정이 필요하지 않습니다.
EventConditionService가 변경되는 경우: 새 이벤트 타입이 추가될 때. 개발자가 새 Checker 클래스를 작성해야 합니다. 코드를 수정해야 합니다.
두 변경 이유가 독립적입니다. IssuancePolicyService는 DB 관리자나 기획자가 변경하는 반면, EventConditionService는 개발자가 변경합니다. 이 두 책임을 하나의 클래스에 넣으면, 하나를 바꿀 때 다른 쪽에 영향을 줄 위험이 생깁니다.
두 서비스 비교표
| | IssuancePolicyService | EventConditionService |
|질문|발행 가능한가?|조건을 충족하는가?|
|데이터|DB (issuance_policy)|이벤트 payload|
|변경 주체|운영팀·기획자|개발자|
|실패 시|NoPolicyError|false 반환|
S28·04

안티패턴 — 정책을 코드에 하드코딩

~6분
DB 기반 정책 관리를 도입하기 전에, 흔히 볼 수 있는 안티패턴을 먼저 보겠습니다.
// ❌ 안티패턴 — 정책이 코드에 박혀 있다 if (eventType === 'WALKING_10000') { tokenId = 1001n; maxPerUser = 1; } else if (eventType === 'HEALTH_CHECK') { tokenId = 1002n; maxPerUser = 1; } else if (eventType === 'COUPON_SUMMER') { tokenId = 1003n; maxPerUser = 3; }
이렇게 하면 무슨 문제가 생길까요? 네 가지입니다.
첫째: 정책 변경 = 코드 수정 + 배포. 여름 쿠폰 한도를 3개에서 5개로 바꾸려면 개발자가 코드를 고치고 배포해야 합니다.
둘째: 조건 추가 시 분기 폭발. 기간 조건, 총 발행량 한도, is_active 플래그 같은 것을 추가할수록 if-else가 걷잡을 수 없이 커집니다.
셋째: 운영팀이 직접 수정 불가. 기획자가 새 이벤트를 추가하고 싶어도 반드시 개발자를 거쳐야 합니다.
넷째: 테스트에서 정책을 독립 제어 불가. "이 tokenId 조건만 바꿔서 테스트하고 싶은데" — 코드가 하드코딩돼 있으면 어렵습니다.
해결책: 이 모든 정보를 issuance_policy 테이블로 옮깁니다. 코드는 DB에서 읽어올 뿐입니다.
배포 없이 정책을 바꿀 수 없다
운영 중인 서비스에서 이벤트 정책 하나를 바꾸려고 배포를 하는 것은 위험합니다. 오전 2시에 이벤트를 긴급 중단해야 할 때, DB의 is_active를 false로 바꾸는 것과 코드를 수정해 배포하는 것 — 어느 쪽이 안전한가?
S28·05

issuance_policies DDL — 발행 정책 테이블

~10분
issuance_policies 테이블 DDL을 봅시다.
CREATE TABLE IF NOT EXISTS issuance_policies ( id BIGSERIAL PRIMARY KEY, event_type VARCHAR(64) NOT NULL UNIQUE, token_id NUMERIC NOT NULL, name VARCHAR(128), max_per_user INT DEFAULT 1, total_supply INT, -- NULL = 무제한 start_date TIMESTAMPTZ, end_date TIMESTAMPTZ, metadata_uri VARCHAR(512), is_active BOOLEAN NOT NULL DEFAULT true, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() );
컬럼을 하나씩 설명합니다.
event_type은 VARCHAR(64)이고 UNIQUE입니다. 하나의 이벤트 타입에는 하나의 정책만 존재합니다. "WALKING_10000"이라는 이벤트 타입은 이 테이블에서 단 한 행만 가질 수 있습니다. 중복 정책이 생기면 어떤 것이 맞는지 알 수 없으므로 DB가 막아줍니다.
token_id는 NUMERIC입니다. ERC-1155 표준에서 tokenId는 uint256, 즉 최대 2의 256승까지의 숫자입니다. JavaScript의 number 타입은 53비트까지만 정확하게 표현할 수 있어서 bigint를 써야 합니다. DB에서는 NUMERIC 타입이 임의 정밀도를 지원하므로 uint256도 수용할 수 있습니다.
max_per_user는 사용자당 최대 발행 수입니다. DEFAULT 1로, 대부분의 이벤트에서 한 사람이 같은 NFT를 여러 개 받을 수 없습니다.
total_supply는 전체 발행 한도입니다. NULL이면 무제한입니다. 예를 들어 "선착순 1000명에게만" 같은 이벤트를 만들 수 있습니다.
start_date / end_date는 이벤트 유효 기간입니다. NULL이면 기간 제한 없음입니다.
is_active는 이 정책이 현재 활성 상태인지를 나타냅니다. false로 설정하면 event_type이 있어도 발행이 거부됩니다. 소프트 비활성화입니다. 행을 삭제하지 않아도 정책을 중단할 수 있습니다.
소프트 비활성화 (Soft Deactivation) 레코드를 삭제하지 않고 is_active = false로 비활성화하는 패턴. 이렇게 하면 "이 정책이 과거에 존재했었다"는 이력이 보존된다. 발행 이력과 정책 이력을 연결해서 감사할 수 있다.

실습용 DDL 파일 위치입니다. 실제 프로덕션 issuance_policies 테이블은 컬럼이 더 단순합니다. token_id, amount, valid_from, valid_to, created_at만 있습니다. is_active, max_per_user, total_supply, metadata_uri는 강의 설명을 위해 추가한 컬럼입니다. 실제 운영 환경에서는 필요에 따라 마이그레이션으로 추가합니다.
S28·06

issuance_policy 컬럼 설계 이유

~6분
각 컬럼의 설계 의도를 짚겠습니다. 컬럼 하나하나에 이유가 있습니다.
token_id BIGINT UNIQUE: ERC-1155에서 토큰 타입을 식별하는 숫자입니다. 정책 1개 = NFT 타입 1개입니다. UNIQUE 제약으로 서로 다른 이벤트가 같은 tokenId를 쓰는 실수를 방지합니다.
event_type VARCHAR UNIQUE: EventConditionService의 라우팅 키입니다. 이 값으로 어떤 Checker를 쓸지 결정합니다.
max_per_user INT DEFAULT 1: 사용자당 최대 보유 수입니다. 1로 설정하면 중복 발행을 방지합니다. 서비스 레이어에서 이 값을 체크해야 합니다.
total_supply INT NULLABLE: NULL이면 무제한입니다. "선착순 1000명"처럼 한정판 이벤트에만 설정합니다.
start_date / end_date TIMESTAMPTZ: 이벤트 유효 기간입니다. 서버 시각 기준으로 판단합니다.
is_active BOOLEAN: 긴급 비활성화 플래그입니다. false로 바꾸면 배포 없이 즉시 이벤트를 중단할 수 있습니다.
is_active + 기간 검증을 서비스 레이어에서 하는 이유
WHERE is_active = true로 DB에서 필터링해도 되지만, 실패 이유를 구분해야 할 때는 코드에서 분기합니다. "정책이 없다"와 "비활성화됐다"와 "기간이 지났다"는 로그에서 서로 다르게 추적해야 할 수 있습니다.

PgIssuancePolicyRepository — 조회 쿼리

~8분
실제 DB 조회 구현입니다. findByEventType()과 getPolicy()의 차이를 구분하는 것이 핵심입니다.
// Repository 레이어: DB 조회만 담당 async findByEventType(eventType: string): Promise<IssuancePolicy | null> { const res = await this.pool.query( `SELECT id, token_id, event_type, name, max_per_user, total_supply, start_date, end_date, metadata_uri, is_active FROM issuance_policy WHERE event_type = $1`, [eventType], ); if (!res.rowCount) return null; return this._toModel(res.rows[0]); }
findByEventType()은 Repository의 메서드입니다. 단순하게 DB를 조회하고 행이 없으면 null을 반환합니다. 비즈니스 로직이 없습니다.
// Service 레이어: 비즈니스 로직 (is_active + 기간 검증) async getPolicy(eventType: string): Promise<IssuancePolicy> { const p = await this.repo.findByEventType(eventType); if (!p || !p.isActive) throw new NoPolicyError(eventType); const now = new Date(); if (now < p.startDate || now > p.endDate) throw new NoPolicyError(eventType); return p; }
getPolicy()는 Service의 메서드입니다. is_active 확인, 기간 검증을 합니다. Repository가 데이터를 가져오고, Service가 비즈니스 규칙을 적용합니다. 이 분리가 레이어드 아키텍처의 핵심입니다.
Repository는 "DB에서 이 데이터를 가져와"라는 역할만 합니다. Service는 "이 데이터가 현재 비즈니스 맥락에서 유효한가"를 판단합니다. 두 역할이 섞이면 둘 다 테스트하기 어려워집니다.
DIP (Dependency Inversion Principle)
Service는 PgIssuancePolicyRepository(구체 클래스)를 직접 알지 않습니다. IssuancePolicyRepository(인터페이스)만 압니다. 테스트에서는 InMemoryIssuancePolicyRepository를 주입합니다. 구현체를 바꾸어도 Service 코드는 변경하지 않아도 됩니다.

~10분
IssuancePolicyService의 핵심 메서드인 getPolicy()를 봅시다.

세 가지 실패 경로가 있습니다. 모두 NoPolicyError를 던집니다.
첫 번째: DB에 정책이 없는 경우. findByEventType()이 null을 반환합니다. 정의되지 않은 이벤트 타입이거나, 타이포가 있거나, 아직 정책이 등록되지 않은 경우입니다.
두 번째: is_active가 false인 경우. 정책은 있지만 비활성화됐습니다. 이벤트가 종료됐거나, 운영자가 긴급 중단시킨 경우입니다.
세 번째: 유효 기간을 벗어난 경우. start_date 이전이거나 end_date 이후입니다. 이벤트 기간이 아닌 시점에 발행 시도가 들어온 경우입니다.
왜 세 가지 모두 NoPolicyError로 처리하는가? 호출자 입장에서는 "이 이벤트에 대해 발행할 정책이 있는가"만 알면 됩니다. 세부 이유(없는지, 비활성인지, 기간 외인지)는 호출자가 알 필요 없습니다. 단, 로그와 모니터링에서는 세부 이유를 구분하기 위해 NoPolicyError에 reason 필드를 추가할 수 있습니다.

BIGINT는 JS에서 string으로 온다
node-postgres(pg 패키지)는 PostgreSQL의 bigint 타입을 JavaScript string으로 반환합니다. Number()로 파싱하면 2^53 이상에서 정밀도 손실이 생깁니다. 반드시 BigInt()를 사용하세요.

// ❌ 안티패턴 async function checkCondition( userId: string, eventType: string, payload: unknown, ): Promise<boolean> { if (eventType === 'WALKING_10000') { const { stepCount } = payload as any; return stepCount >= 10_000; } if (eventType === 'HEALTH_CHECK_ANNUAL') { const { checkDate } = payload as any; return isWithinCurrentYear(checkDate); } if (eventType.startsWith('COUPON_')) { const { couponCode } = payload as any; return externalApi.validateCoupon(userId, couponCode); // ⚠ 외부 의존성 하드와이어드 — 테스트에서 교체 불가 } return false; // 조용히 false — 위험! }
이 구조의 문제점 네 가지입니다.
첫째: SRP 위반. 이벤트 추가 = 이 파일 수정. 하나의 함수에 모든 이벤트 로직이 집중됩니다.
둘째: 테스트 불가. externalApi가 하드와이어드돼 있어서 테스트에서 Mock으로 교체할 방법이 없습니다.
셋째: 조용한 false. 지원하지 않는 eventType이 들어오면 그냥 false를 반환합니다. 이건 버그가 조용히 숨겨지는 것입니다.
넷째: 파일 팽창. 이벤트가 늘어날수록 if 블록이 수백 줄이 됩니다.
Strategy 패턴이 이 모든 문제를 해결합니다. 각 이벤트의 판단 로직을 독립 클래스(Checker)로 분리합니다.
OCP 위반 — 수정에 열려 있다
새 이벤트를 추가할 때마다 기존 함수를 수정해야 합니다. 이 함수는 확장에 닫혀 있고 수정에 열려 있습니다. Strategy 패턴을 적용하면 새 이벤트 추가 = 새 클래스 파일 하나 추가로 바뀝니다.

문제부터 정의합시다. 교보생명에는 다양한 이벤트 타입이 있습니다. 걷기 챌린지(WALKING_10000), 건강검진(HEALTH_CHECK_ANNUAL), 쿠폰(COUPON_SUMMER_2025), 보험 신규 가입(INSURANCE_NEW)... 그리고 앞으로 더 추가될 겁니다. 각 이벤트 타입마다 조건 판단 로직이 다릅니다. 걷기는 걸음 수를 보고, 건강검진은 검진 날짜를 보고, 쿠폰은 외부 쿠폰 API를 호출해야 합니다.

이 설계의 문제점이 보이시나요? 세 가지입니다.
첫째, OCP(개방-폐쇄 원칙) 위반입니다. 새 이벤트 타입을 추가할 때마다 이 함수를 수정해야 합니다. 함수는 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 하는데, 그 반대입니다.
둘째, 테스트 어려움입니다. CouponConditionChecker처럼 외부 API를 직접 호출하는 로직이 함수 안에 하드코딩돼 있으면, 이 함수를 테스트할 때 실제 외부 API가 필요합니다. Mock으로 교체할 방법이 없습니다.
셋째, 파일 팽창입니다. 이벤트가 10개, 20개가 되면 이 파일이 끝없이 커집니다.
Strategy 패턴이 해결책입니다. 각 이벤트 타입의 조건 판단 로직을 독립된 클래스로 분리합니다.
Strategy 패턴 (Strategy Pattern) 알고리즘 군을 정의하고, 각각을 캡슐화하여, 서로 교환할 수 있게 하는 디자인 패턴. 클라이언트(EventConditionService)는 구체적인 알고리즘(각 Checker)을 몰라도 된다. 인터페이스(EventConditionChecker)만 알면 된다.

// 이벤트 평가에 필요한 컨텍스트 정보 interface EvaluationContext { userId: string; eventType: string; payload: unknown; // Checker가 자신이 아는 타입으로 캐스팅 } // 모든 Checker가 구현하는 계약 interface EventConditionChecker { /** 이 Checker가 eventType을 처리할 수 있는가 */ supports(eventType: string): boolean; /** 조건 충족 여부 반환 */ check(ctx: EvaluationContext): Promise<boolean>; }
두 메서드의 역할이 명확히 분리됩니다. supports(): 라우팅 담당. "내가 이 이벤트를 처리할 수 있나?" check(): 실제 조건 평가.

payload: unknown인 이유를 설명합니다. 각 이벤트 타입마다 payload 형태가 다릅니다. 걷기 챌린지는 stepCount, 건강검진은 checkDate, 쿠폰은 couponCode. 인터페이스 레벨에서 이 모든 것을 알 수는 없으니 unknown으로 선언하고, 각 Checker가 자신이 처리할 타입으로 캐스팅합니다.
Strategy Pattern 구조
Context (EventConditionService): 어떤 Strategy(Checker)를 쓸지 결정
Strategy Interface (EventConditionChecker): supports() + check()
Concrete Strategy (WalkingConditionChecker, ...): 실제 구현체
→ 새 이벤트 = 새 Concrete Strategy 추가. Context와 Interface는 변경 없음.

export interface EventConditionChecker { supports(eventType: string): boolean; check(ctx: EvaluationContext): Promise<boolean>; } export interface EvaluationContext { userId: string; eventType: string; payload: unknown; }
Strategy 패턴의 핵심 인터페이스입니다. 메서드가 두 개입니다.
supports(eventType): "이 Checker가 이 eventType을 처리할 수 있는가?"를 묻습니다. true이면 담당, false이면 다른 Checker가 처리합니다. EventConditionService가 Checker 배열에서 이 메서드로 적합한 Checker를 찾습니다.
check(ctx): 실제 조건 판단을 합니다. EvaluationContext에는 userId, eventType, payload가 담겨 있습니다. payload는 이벤트 데이터입니다. 걷기 챌린지라면 stepCount가, 건강검진이라면 checkDate가 payload에 들어있습니다.
반환값이 boolean입니다. true이면 조건 충족, false이면 미충족입니다. 예외적인 경우 — 예를 들어 외부 API 호출이 실패한 경우 — 는 false를 반환하지 않고 에러를 throw합니다. 왜냐하면 API 오류로 인한 미판단과, 실제 조건 미충족을 구분해야 하기 때문입니다.
EvaluationContext가 별도 인터페이스인 이유는 응집도 때문입니다. userId, eventType, payload 세 가지는 항상 함께 다닙니다. 세 개를 함수 파라미터로 나열하는 것보다 하나의 객체로 묶는 것이 확장성이 좋습니다. 나중에 필드를 추가해도 인터페이스 시그니처를 바꾸지 않아도 됩니다.

export class EventConditionService { constructor(private readonly checkers: EventConditionChecker[]) {} async evaluate(ctx: EvaluationContext): Promise<boolean> { const checker = this.checkers.find(c => c.supports(ctx.eventType)); if (!checker) { throw new UnsupportedEventTypeError(ctx.eventType); } return checker.check(ctx); } }

첫째, checkers.find(c => c.supports(ctx.eventType))로 이 eventType을 처리할 수 있는 Checker를 찾습니다. 못 찾으면 UnsupportedEventTypeError를 던집니다. 찾으면 그 Checker의 check()에 위임합니다.
이게 Strategy 패턴의 진수입니다. EventConditionService는 어떤 Checker가 있는지, 각 Checker의 로직이 뭔지 전혀 모릅니다. 그저 "이 eventType 처리할 수 있는 거 찾아서 실행해줘"라고 위임합니다. 새 Checker가 추가되면 EventConditionService 코드는 한 줄도 바뀌지 않습니다.
UnsupportedEventTypeError를 주목하세요. 이걸 false로 처리하면 안 됩니다. "알 수 없는 이벤트 타입"과 "조건 미충족"은 완전히 다른 상황입니다. 전자는 시스템 설정 오류이고, 후자는 정상적인 비즈니스 흐름입니다. 에러를 throw해야 모니터링에서 즉시 감지할 수 있습니다.
UnsupportedEventTypeError를 false로 처리하면 안 되는 이유 등록되지 않은 이벤트 타입이 들어왔다는 건 호출자 쪽에 버그가 있다는 신호입니다. 이를 false로 조용히 처리하면 버그가 숨겨집니다. 에러로 throw해야 알림이 가고 즉시 수정할 수 있습니다.

false positive vs false negative — 조건 판단 오류의 두 방향

~8분
조건 판단 로직을 만들 때 반드시 이해해야 하는 개념입니다.
false positive: 조건을 충족하지 않은 사람에게 NFT를 발행하는 오류입니다. 예를 들어 실제로는 9,500보 걸었는데 "10,000보 달성"으로 판단해버리는 경우입니다. 결과: NFT가 발행됩니다. 블록체인에 영구적으로 기록됩니다.
false negative: 조건을 충족한 사람에게 NFT를 발행하지 않는 오류입니다. 실제로 10,000보를 걸었는데 "미달성"으로 판단하는 경우입니다. 결과: NFT가 발행되지 않습니다. 사용자 불만이 생기지만, 나중에 다시 발행할 수 있습니다.
어느 쪽이 더 위험한가요? false positive가 훨씬 위험합니다. 이유는 세 가지입니다.
첫째, 블록체인 발행은 되돌릴 수 없습니다. burn이 가능하긴 하지만, 이미 사용자에게 배포된 NFT를 회수하는 건 법적, 기술적으로 매우 복잡합니다. false negative는 재발행으로 해결할 수 있지만 false positive는 그럴 수 없습니다.
둘째, 공정성 훼손입니다. 조건을 달성하지 못한 사람이 NFT를 받으면 제대로 달성한 다른 사용자에 대한 불공정입니다. 특히 한정판 NFT라면 더 심각합니다.
셋째, 규제 위험입니다. 금융 상품과 연계된 NFT에서 오발행은 금융 당국의 감사 대상이 될 수 있습니다.
결론: check() 구현 시 애매한 경우는 false를 반환하세요. 외부 API 오류 같은 예외적 상황은 false가 아닌 throw를 하세요. 모르면 발행하지 않습니다.
false positive 방지 원칙 조건 판단은 보수적으로. 애매하면 false. 외부 의존성(API) 오류 → false가 아닌 throw로 처리하여 재시도 기회를 확보. false는 "정상적으로 판단했더니 미충족"이고, throw는 "판단 자체를 못 했으니 다시 해야 함"입니다.

tokenId는 Strategy가 아닌 IssuancePolicyService에서 온다

~6분
중요한 설계 결정 하나를 짚고 가겠습니다.
"조건을 확인하는 Checker가 어떤 tokenId를 발행할지도 결정하면 어떨까요?" 이렇게 생각할 수 있습니다. WalkingConditionChecker.check()가 true를 반환하면서 "tokenId: 1001"도 같이 반환하는 거죠.
이렇게 하면 안 됩니다. 이유: 단일 책임 원칙(SRP) 위반입니다. Checker의 책임은 "조건을 충족했는가" 판단입니다. tokenId를 결정하는 것은 "이 이벤트에 어떤 NFT를 발행할지"라는 별개의 책임입니다.
두 책임을 Checker에 합치면: 새 이벤트 추가 시 Checker에 tokenId도 하드코딩해야 합니다. tokenId를 바꾸려면 코드를 수정하고 배포해야 합니다. 우리가 DB 정책화를 도입한 이유가 사라집니다.
올바른 흐름: IssuancePolicyService.getPolicy(eventType)가 tokenId를 반환합니다. 이 값은 issuance_policies 테이블에서 옵니다. EventConditionService는 조건 판단만 하고, tokenId는 모릅니다. IssuerService(S29)가 두 결과를 받아서 조합합니다.
SRP (Single Responsibility Principle) 적용 IssuancePolicyService: "무엇을 발행하는가" (tokenId, amount, 기간, 한도)
EventConditionService: "발행할 자격이 있는가" (true/false)
IssuerService (S29): "두 결과를 조합해서 발행을 실행하는가" (오케스트레이션)
세 서비스가 각자의 한 가지 책임만 갖는다.

IssuanceRequest — 상태 흐름 (4개 상태)

~8분
IssuanceRequest의 상태 전이 다이어그램을 보겠습니다. 상태가 4개뿐이라 단순합니다.
REQUESTED → SUBMITTED: IssuerService.issueOne()이 VASP에 발행 요청을 성공적으로 전달하면 전이합니다.
SUBMITTED → CONFIRMED: VASP Webhook으로 'confirmed'를 수신하면 전이합니다. txHash가 채워집니다. 종단 상태입니다.
REQUESTED 또는 SUBMITTED → FAILED: 어느 단계에서든 실패하면 FAILED로 전이합니다. failReason이 채워집니다. 종단 상태입니다. REQUESTED에서 FAILED로 가는 경우는 지갑 미등록이나 VASP 연결 오류입니다. SUBMITTED에서 FAILED는 Webhook으로 'failed'를 수신한 경우입니다.
상태 전이 규칙
REQUESTED: IssuerService.issueOne() ③단계에서 INSERT (walletAddr=null)
SUBMITTED: IssuerService.issueOne() ⑤단계에서 갱신 (walletAddr 채워짐)
CONFIRMED: WebhookHandler에서 갱신 (txHash 채워짐) — 종단
FAILED: IssuerService 또는 WebhookHandler에서 갱신 (failReason 채워짐) — 종단
→ CONFIRMED/FAILED에서 다른 상태로 전이 불가 (상태 불변성)
중요한 설계 결정: 재시도는 새 IssuanceRequest를 생성합니다. 기존 IssuanceRequest의 상태를 REQUESTED로 되돌리지 않습니다. FAILED가 종단 상태인 이유입니다. 이 설계가 감사 이력을 단순하게 만듭니다. "이 요청은 왜 실패했고, 재시도는 어떻게 됐는가"를 별도 레코드로 추적할 수 있습니다.
상태 불변성 (CONFIRMED/FAILED는 종단)
CONFIRMED나 FAILED 상태에서 updateStatus()를 호출하면 에러를 던져야 합니다. 이미 완료된 요청의 상태를 바꾸는 것은 데이터 무결성을 해칩니다. 블록체인에 이미 발행된 기록을 취소할 수 없듯이, DB 레코드도 종단 상태를 되돌릴 수 없어야 합니다.

선행 개념 — TxStatus / MintStatus / IssuanceStatus 세 레이어

~15분
M3, M4를 수강하셨다면 TxStatus와 MintStatus를 이미 알고 있을 겁니다. S29에서 새로 추가되는 IssuanceStatus와 어떻게 다른지 비교합니다. 이 비교가 어렵게 느껴질 수 있지만, 핵심을 먼저 파악하면 됩니다: 같은 사건을 세 다른 관점에서 바라보는 것입니다.
TxStatus: 체인 TX 레이어. "블록체인 TX가 지금 어디 있는가?" mempool에 있는가, 블록에 포함됐는가, finality를 확보했는가. TxStateMachineService(@kyobo/vasp 패키지)가 관리합니다. 상태: REQUESTED → SUBMITTED → PENDING → MINED → CONFIRMED → FINALIZED / FAILED / REORGED. 8개 상태입니다.
MintStatus: 원장 레이어. "DB 원장이 체인 상태와 일치하는가?" LedgerService(M4에서 구현)가 관리합니다. PENDING이 없습니다. mempool 대기 상태에는 관심이 없기 때문입니다. 상태: REQUESTED → SUBMITTED → MINED → CONFIRMED → FINALIZED / FAILED / REORGED. 7개 상태입니다.
IssuanceStatus: 비즈니스 레이어. "이 발행 요청이 완료됐는가?" IssuerService(S29에서 구현)가 관리합니다. PENDING도, MINED도, FINALIZED도, REORGED도 없습니다. 4개 상태뿐입니다.
왜 IssuanceStatus가 이렇게 단순한가? VASP를 통해 발행을 위탁하기 때문입니다. VASP가 TX 관리의 복잡성을 추상화해줍니다. PENDING(mempool), MINED, REORGED 같은 체인 세부 상태는 VASP 내부에서 처리됩니다. 우리는 VASP가 Webhook으로 "confirmed"나 "failed"를 알려줄 때만 상태를 바꿉니다.
레이어 추상화의 원칙 위로 올라갈수록 상태가 단순해진다. TxStatus(8개) → MintStatus(7개) → IssuanceStatus(4개). 하위 레이어가 복잡성을 흡수하고 상위 레이어는 단순한 인터페이스만 본다. 이것이 레이어드 아키텍처의 핵심 이점이다.
상태 대응표를 읽겠습니다. REQUESTED: 세 레이어 모두 있지만 의미가 다릅니다. IssuanceStatus REQUESTED는 지갑 주소 조회 전입니다. MintStatus/TxStatus REQUESTED는 지갑 확보 후입니다.
PENDING: TxStatus에만 있습니다. mempool 대기 상태는 체인 TX 레이어만 추적합니다.
MINED: TxStatus와 MintStatus에 있지만 IssuanceStatus에는 없습니다. VASP가 이 단계를 추상화해주기 때문입니다.
CONFIRMED: TxStatus와 MintStatus는 "아직 FINALIZED 전 중간 단계"를 의미합니다. IssuanceStatus CONFIRMED는 VASP Webhook의 'confirmed'를 수신한 시점입니다. 이 시점이면 내부적으로 이미 FINALIZED 수준이므로 IssuanceStatus CONFIRMED가 MintStatus CONFIRMED + FINALIZED를 흡수합니다.
REORGED: TxStatus와 MintStatus에 있지만 IssuanceStatus에는 없습니다. 블록 재편(REORG)은 VASP가 감지하고 재처리합니다. 결과만 Webhook으로 통보해줍니다.

~6분
TxStatus의 8개 상태를 정리합니다. TxStateMachineService가 전이를 관리합니다.
TxStatus 상태 전이표
REQUESTED: 발행 요청 생성됨, VASP 전송 전 (IssuerService)
SUBMITTED: VASP에 전송됨, TX hash 아직 없음
PENDING: TX 전송됨, mempool 대기 중 ← IssuanceStatus에 없는 상태
MINED: 블록에 포함됨, finality 미확보
CONFIRMED: 충분한 블록 확인 완료
FINALIZED: PoS 2/3+ validator 동의, 절대 불변 — 종단
FAILED: REVERT 또는 최종 실패 — 종단
REORGED: MINED 후 블록 재편으로 소실, 재처리 대기
PENDING이 있는 이유: mempool은 불안정합니다. 가스비가 낮으면 오래 대기합니다. 오래된 PENDING TX를 찾아서 가스비를 올리거나 타임아웃 처리해야 합니다. findPendingOlderThan()이 바로 이 용도입니다. MintStatus와 IssuanceStatus에는 PENDING이 없습니다. 이 두 레이어는 mempool 관리에 관심이 없기 때문입니다.

MINED: 블록에 포함됨, finality 미확보 ← ReconcileService 대상
CONFIRMED: 원장 확정 허용, token_id 채워짐
FINALIZED: PoS finality 확보, 절대 불변 — 종단
FAILED: 최종 실패 — 종단
REORGED: 블록 재편으로 소실, 재채굴 대기
MINED가 있는 이유: ReconcileService(S25)가 "MINED이지만 CONFIRMED 미달" 요청을 찾아 체인과 대조합니다. MINED와 CONFIRMED를 구분하지 않으면 이 조회가 불가능합니다. IssuanceStatus에는 MINED가 없습니다. VASP가 이 단계를 추상화해주기 때문입니다.

선행 개념 (7/9) — IssuanceStatus 4개 상태 + FAILED 범위

~6분
IssuanceStatus 4개 상태와 누가 전이시키는지 정리합니다.
IssuanceStatus 상태 전이표
REQUESTED: IssuerService.issueOne() ③단계에서 INSERT (walletAddr=null)
SUBMITTED: IssuerService.issueOne() ⑤단계 — VASP 접수 완료 (walletAddr 채워짐)
CONFIRMED: WebhookHandler — Webhook 수신, txHash 채워짐 — 종단
FAILED: IssuerService 또는 WebhookHandler — failReason 채워짐 — 종단
FAILED의 범위가 MintStatus보다 넓습니다. MintStatus FAILED는 체인 실패만을 의미합니다. IssuanceStatus FAILED는 세 가지를 포함합니다.
첫째: 지갑 미등록(WalletNotFoundError). 체인에 도달하기 전에 실패합니다. 둘째: VASP 오류(submitIssuance() 실패). TX도 생성되지 않은 채로 실패합니다. 셋째: 체인 실패(Webhook으로 'failed' 수신). 이 경우만 MintStatus FAILED와 대응합니다.
FAILED 범위 확인 중요
IssuanceStatus FAILED 레코드를 분석할 때 fail_reason을 확인해야 합니다. "지갑 미등록"이면 사용자에게 지갑 등록을 안내해야 합니다. "VASP 오류"면 VASP 서비스 상태를 확인해야 합니다. "체인 실패"면 스마트 컨트랙트나 가스비 문제일 수 있습니다.

선행 개념 (8/9) — 세 Status를 한 흐름으로

~8분
세 Status의 시간적 흐름을 한 눈에 봅니다.
시간 t1: IssuerService가 발행을 시작합니다. IssuanceStatus = REQUESTED (INSERT).
시간 t2: IssuerService가 submitIssuance()를 호출합니다. VASP 내부에서 MintStatus REQUESTED와 TxStatus REQUESTED가 동시에 생성됩니다. IssuanceStatus는 아직 REQUESTED입니다.
시간 t3: TX hash가 반환됩니다. IssuanceStatus = SUBMITTED. MintStatus = SUBMITTED. TxStatus = SUBMITTED.
t4~t6: TX가 mempool(TxStatus PENDING), 블록 포함(MINED), 충분한 확인(CONFIRMED)을 거칩니다. 이 구간에서 IssuanceStatus는 여전히 SUBMITTED입니다. VASP가 내부적으로 처리하는 중입니다.
t7: TxStatus와 MintStatus가 FINALIZED됩니다. VASP가 Webhook을 발송합니다.
t8: WebhookHandler가 Webhook을 수신합니다. IssuanceStatus = CONFIRMED. txHash가 기록됩니다.
이 흐름에서 IssuanceStatus가 SUBMITTED에서 CONFIRMED로 건너뛰는 이유가 보입니다. t3~t7 사이의 체인 세부 단계는 IssuanceStatus 관점에서는 "VASP가 처리 중인 상태"로 뭉뚱그려집니다.
핵심 인사이트: 위임과 추상화
IssuanceStatus가 단순한 이유: 복잡한 상태(PENDING, MINED, REORGED)를 VASP에 위임했기 때문
레이어를 추가하면 복잡성이 숨겨지는 것이 아니라, 적절한 레이어가 적절한 복잡성을 관리하게 됩니다.
비즈니스는 결과만 보고, TxLayer가 체인을 보고, 원장은 감사 이력을 추적합니다.

선행 개념 (9/9) — 전체 상태 대응표

~6분
같은 이름이라도 레이어마다 의미가 다릅니다. 대응표를 읽겠습니다.
REQUESTED: 세 레이어 모두 있지만 의미가 다릅니다. IssuanceStatus REQUESTED는 지갑 주소 조회 전이고 walletAddr=null입니다. MintStatus/TxStatus REQUESTED는 지갑이 확보된 후 생성됩니다.
PENDING: TxStatus에만 있습니다. mempool 상태는 체인 TX 레이어만 추적합니다.
MINED: TxStatus와 MintStatus에 있지만 IssuanceStatus에는 없습니다. VASP가 추상화해주기 때문입니다.
CONFIRMED: TxStatus/MintStatus에서는 아직 FINALIZED 전 중간 단계. IssuanceStatus에서는 Webhook 'confirmed' 수신 시점으로, FINALIZED 수준을 흡수합니다.
REORGED: TxStatus와 MintStatus에 있지만 IssuanceStatus에는 없습니다. 블록 재편은 VASP가 감지하고 재처리합니다. 결과만 Webhook으로 통보합니다.
FAILED: 세 레이어 모두 있지만 범위가 다릅니다. TxStatus/MintStatus FAILED는 체인 실패만. IssuanceStatus FAILED는 지갑 미등록, VASP 오류, 체인 실패를 모두 포함합니다.
레이어별 FAILED 범위 차이
TxStatus FAILED: TX가 체인에서 REVERT됨
MintStatus FAILED: 체인 실패 → 원장 기록
IssuanceStatus FAILED: 지갑 미등록 + VASP 오류 + 체인 실패 모두 포함
→ 비즈니스 레이어는 실패 경로를 가장 넓게 봅니다. 사용자에게 "발행 실패"를 알려야 하기 때문입니다.

ERC-1155 — 멀티 토큰 표준 (1/3)

~5분
S30을 시작합니다. 주제는 배치 발행입니다. S29에서 issueOne()으로 단건 발행을 구현했습니다. 이번엔 15만 명에게 한 번에 발행해야 하는 시나리오입니다. 그 전에 교보생명이 왜 ERC-1155를 쓰는지 먼저 이해해야 합니다.
ERC-20, ERC-721, ERC-1155 세 표준을 비교합니다. ERC-20은 1종류 토큰 대량 발행. USDT 같은 것입니다. ERC-721은 tokenId마다 고유합니다. 소유자 1명, 수량 1개. 이 세상에 하나뿐인 NFT입니다. ERC-1155는 tokenId별로 종류를 구분합니다. 여러 명이 같은 tokenId를 보유할 수 있습니다.
교보생명 케이스: 이벤트 타입별로 여러 종류의 NFT를 1개 컨트랙트로 관리합니다. tokenId 1<<64 = 걷기 챌린지 NFT. tokenId 2<<64 = 건강검진 NFT. tokenId 3<<64 = 보험료 납입 NFT. 같은 걷기 챌린지 NFT를 15만 명이 각자 보유합니다. ERC-1155가 가장 적합합니다.
ERC-1155가 필요한 이유 — 같은 이벤트의 NFT를 여러 명이 보유 가능. 토큰 종류 추가 = 새 컨트랙트 배포 불필요. 1개 컨트랙트로 전체 이벤트 타입 관리. 배치 발행에 최적화된 mintBatch() 함수 제공.

// 단일 발행: 1명에게 1종류 function mint( address to, // 수신자 1명 uint256 id, // 토큰 종류 ID uint256 amount, // 수량 (교보: 항상 1) bytes data ) external; // 배치 발행: 1명에게 여러 종류 function mintBatch( address to, // 수신자 1명 ← 핵심! uint256[] ids, // 토큰 종류 여러 개 uint256[] amounts, // 각 종류별 수량 bytes data ) external;
ERC-1155의 핵심 함수들입니다. mint()는 1명에게 1종류를 발행합니다. mintBatch()는 1명에게 여러 종류를 발행합니다. mintBatch()의 첫 번째 파라미터가 address to, 즉 수신자 1명입니다.
잔액 조회는 balanceOf(account, id)입니다. 어떤 주소가 어떤 tokenId를 몇 개 가지고 있는지 조회합니다. safeTransferFrom()으로 단일 전송, safeBatchTransferFrom()으로 여러 종류를 동시에 전송합니다.
ERC-1155 설계 포인트 — 1 컨트랙트가 여러 토큰 종류를 관리합니다. 토큰 종류 추가 = 새 컨트랙트 배포 불필요. 이것만으로 운영 비용이 크게 절감됩니다.

~5분
mintBatch()의 흔한 오해가 있습니다. "mintBatch()를 쓰면 15만 명에게 한 TX로 발행 가능하다"는 것입니다. 틀렸습니다.
mintBatch(address to, uint256[] ids, ...)에서 to는 수신자 1명입니다. 1명에게 여러 종류를 발행하는 것이지, 여러 명에게 발행하는 게 아닙니다. 다중 수신자 발행은 ERC-1155 표준에 없습니다. 커스텀 컨트랙트가 필요합니다.

결론 — 단건 발행 로직(issueOne)을 그대로 쓰는 건 규모 문제를 해결하지 못합니다. 배치 전용 서비스가 필요합니다.

왜 배치 발행인가 (2/2)

~4분
배치 발행의 두 가지 이유입니다. 이유 ①: 처리 시간 단축. 15만 명을 청크(500명 단위)로 분할합니다. 청크 내 500건은 동시(병렬) 처리합니다. 300청크 × 10초 = 약 50분. 3.5일 대비 약 100배 단축입니다.
이유 ②: 가스 효율. VASP가 커스텀 배치 컨트랙트를 지원하면, 청크당 1 TX → TX 수가 1/500로 감소합니다. 가스비가 대폭 절감됩니다.
배치 처리 전략 구조: 15만 명 userIds[] → _chunk(500) → 300개 청크. 청크 간은 순차 처리입니다. Rate Limit 보호와 Nonce 보장을 위해서입니다. 청크 내는 병렬 처리입니다. Promise.all로 500건 동시 → 청크당 약 10초. 진행 상태는 BulkJob에 기록하고, 실패 청크는 chunkErrors에 저장하며, retryFailedChunks()로 재처리합니다.

블록체인 Gas — 왜 한 번에 무한히 담을 수 없는가

~6분
Gas를 이해해야 CHUNK_SIZE가 왜 500인지 알 수 있습니다. Gas는 블록체인의 모든 연산이 소비하는 비용 단위입니다. "블록체인 연산 단위"라고 생각하면 됩니다.
현실 세계 비유를 들겠습니다. 블록 하나 = 트럭 한 대. 적재 용량 한계가 있습니다. TX 하나 = 화물. 각각 다른 무게, 즉 Gas 소비량이 있습니다. Block Gas Limit = 트럭 최대 적재 무게. 무게 초과 화물은 트럭에 실을 수 없습니다. TX가 거절됩니다.
1,000건을 한 TX에 담으면: 1,000 × 50,000 gas = 50,000,000 gas. Block Gas Limit은 약 30,000,000 gas입니다. 50M이 30M을 초과합니다. TX 자체가 실패합니다. 1건도 발행되지 않습니다.
Gas ≠ 가스비(ETH) — Gas는 연산 복잡도의 단위로 고정된 기준입니다. 가스비 = Gas × gasPrice (ETH 단위, 시장에서 결정). Block Gas Limit은 블록에 담을 수 있는 총 Gas의 상한선입니다. 현재 이더리움 메인넷 Block Gas Limit은 약 30M gas입니다.

EVM Block Gas Limit — CHUNK_SIZE = 500의 근거

~5분
CHUNK_SIZE = 500이 어디서 나왔는지 계산해봅니다. Block Gas Limit 최대값: 약 30,000,000 gas. NFT mint 1건의 가스 추정: 약 50,000 gas. 이론적 최대 mint 수: 30M ÷ 50k = 600건. 안전 버퍼 17% 적용: 600 × 0.83 ≈ 500건.
500건 → 안전: 500 × 50,000 = 25,000,000 gas. Block Gas Limit 내에 포함됩니다. 17% 버퍼는 컨트랙트 로직 변화를 흡수합니다. 안정적 발행이 보장됩니다.
50,000 gas/건은 추정치 — 컨트랙트 로직 복잡도, Solidity 버전, EVM 업그레이드에 따라 달라집니다. 운영 배포 전 반드시 실제 가스 측정을 재실행해야 합니다. CHUNK_SIZE = 500은 규칙이 아니라 Gas 물리적 한계에서 역산한 상한값입니다. 컨트랙트가 바뀌면 이 숫자도 바뀝니다.

청크 분할 알고리즘 — _chunk()

~6분
_chunk<T>( arr: T[], size: number ): T[][] { const result: T[][] = []; for (let i = 0; i < arr.length; i += size) { result.push(arr.slice(i, i + size)); } return result; }
📁 internal/apps/issuer-service/src/services/BulkIssueService.ts
실제 프로덕션 BulkIssueService.ts에도 동일한 _chunk() 구현이 있습니다. private 메서드가 아니라 테스트 가능성을 위해 public으로 선언했습니다. 강의 슬라이드의 구현과 한 줄도 다르지 않습니다.
_chunk() 함수입니다. 배열을 size 단위로 나눠서 이중 배열을 반환합니다. 구현이 놀라울 정도로 단순합니다. for 루프와 slice 하나뿐입니다.
slice(i, i+size)는 배열 끝을 넘어도 에러 없이 있는 만큼만 반환합니다. 마지막 청크가 500 미만이어도 자동으로 처리됩니다. 별도의 나머지 처리 코드가 필요 없습니다.
동작 예시: size=3, arr=['u0'~'u9']. i=0: slice(0,3) → ['u0','u1','u2']. i=3: slice(3,6) → ['u3','u4','u5']. i=6: slice(6,9) → ['u6','u7','u8']. i=9: slice(9,12) → ['u9'] ← 1개만, 정상. 경계값 케이스: 빈 배열 → [] 반환. 딱 500명 → 1개 청크. 501명 → 2개 청크 (500명 + 1명).
왜 public 메서드인가 — 독립 단위 테스트가 가능해야 합니다. 경계값(1001명, 빈 배열, 딱 500명) 검증이 중요합니다. S30 실습 [1]에서 직접 테스트합니다.

부분 실패 허용 정책 (1/2)

~6분
청크 하나가 실패하면 어떻게 해야 할까요? 두 가지 정책이 있습니다. 전체 롤백 vs 부분 커밋.
전체 롤백 정책: 청크 0 성공(500명 발행 완료). 청크 1 실패(WalletNotFoundError). → 청크 0의 500명 NFT를 burn TX로 취소. → 처음부터 재실행. 문제점: 성공한 500명까지 재처리 필요. 멱등성 체크 없으면 이중 발행 위험. 15만 명 중 1명 실패로 전체 취소, 완전 비효율입니다.
부분 커밋 정책: 청크 0 성공 → 그대로 유지. 청크 1 실패 → chunkErrors에 기록. → 나중에 retryFailedChunks()로 재처리. BulkJob 상태: PARTIAL_FAILURE. 장점: 성공한 청크는 확정 — 재처리 불필요. 실패 원인 기록 → 선택적 재처리 가능. 운영자가 실패 청크만 확인 후 대응합니다.
두 정책의 핵심 차이 — 성공한 작업을 취소(롤백)하느냐, 아니면 실패한 작업만 기록하고 분리하느냐. 교보생명처럼 사용자별 독립 권리가 발생하는 케이스는 부분 커밋이 정답입니다.

부분 실패 허용 정책 (2/2)

~4분
교보생명 케이스에서 부분 커밋이 맞는 세 가지 이유입니다.
① 사용자별 독립 건: 사용자 A의 지갑이 미등록됐다고 사용자 B의 발행을 막을 이유가 없습니다. 보험 이벤트는 개인별 달성 조건을 각각 충족한 독립적 권리 발생입니다.
② 재처리 가능: 실패 청크는 chunkErrors에 기록됩니다. retryFailedChunks()로 나중에 선택적 재처리합니다. 지갑 미등록 → 사용자가 지갑 등록 후 해당 청크만 재실행하면 됩니다.
③ 운영 현실: 15만 명 중 100명의 지갑 미등록으로 15만 건 전체를 취소하는 건 비효율입니다. 실패 100명만 별도로 처리하는 게 운영 비용과 리스크 모두 낮습니다.
PARTIAL_FAILURE → COMPLETED 경로 — retryFailedChunks() 후 모든 실패 청크가 성공하면 COMPLETED로 전환됩니다. COMPLETED와 FAILED는 되돌릴 수 없습니다. 재실행이 필요하면 새 BulkJob을 생성합니다.

BulkJob 상태 전이 — RUNNING → COMPLETED / PARTIAL_FAILURE / FAILED

~5분
BulkJob의 상태 전이를 설명합니다. executeBulkIssue()가 호출되면 BulkJob이 RUNNING 상태로 생성됩니다. 모든 청크 처리가 끝나면 결과에 따라 세 가지 중 하나가 됩니다.

상태 결정 로직 — failedCount === 0 → COMPLETED. failedCount === totalChunks → FAILED. 그 외 → PARTIAL_FAILURE. 이 로직이 executeBulkIssue() 마지막에 실행됩니다.

tokenId 비트 설계입니다. uint256 = 256비트입니다. 이 큰 숫자 공간에 하나의 숫자가 아니라 여러 정보를 담을 수 있습니다.
현재 설계: 상위 64비트에 이벤트 타입 코드를 저장합니다. BigInt(1) << BigInt(64) = WALK_CHALLENGE tokenId. BigInt(2) << BigInt(64) = HEALTH_CHECK tokenId. BigInt(3) << BigInt(64) = PREMIUM_PAYMENT tokenId. 하위 192비트는 비어 있습니다. 향후 확장 공간입니다.
왜 단순 순번(1, 2, 3)이 아닌가? 단순 순번을 쓰면 이벤트 타입 vs 인스턴스 ID를 구분할 수 없습니다. 나중에 필드를 추가할 때 기존 ID와 충돌이 발생합니다. 비트 분할을 사용하면 필드 확장을 처음부터 설계에 내장할 수 있습니다.
향후 확장 레이아웃 예시 — 상위 64비트: 이벤트 타입. 다음 32비트: 발행 연도. 다음 32비트: 캠페인 코드. 나머지 128비트: 시리얼 번호/등급/미래 필드. 이 모든 정보가 tokenId 하나에 담깁니다.

// tokenId 생성 — 이벤트 코드를 상위 64비트 위치로 밀어 올림 const WALK = BigInt(1) << BigInt(64); // = 18446744073709551616n (= 2^64) const HEALTH = BigInt(2) << BigInt(64); // = 36893488147419103232n (= 2 × 2^64) const PREMIUM = BigInt(3) << BigInt(64); // = 55340232221128654848n (= 3 × 2^64) // tokenIdToEventType() — 역변환 function tokenIdToEventType(tokenId: bigint): string { const MAP: Record<string, string> = { '1': 'WALK_CHALLENGE', '2': 'HEALTH_CHECK', '3': 'PREMIUM_PAYMENT', }; // 상위 64비트 추출: 오른쪽으로 64비트 시프트 const code = String(tokenId >> BigInt(64)); const type = MAP[code]; if (!type) throw new Error(`알 수 없는 tokenId: ${tokenId}`); return type; } // 사용 예 tokenIdToEventType(WALK); // 'WALK_CHALLENGE' tokenIdToEventType(HEALTH); // 'HEALTH_CHECK'
📁 internal/apps/issuer-service/src/services/BulkIssueService.ts
tokenId 비트 설계와 tokenIdToEventType() 함수도 BulkIssueService.ts 또는 연결된 유틸리티 파일에 있습니다. BigInt(1) << BigInt(64) 패턴은 실제 프로덕션에서도 동일하게 쓰입니다. >> BigInt(64) 역변환도 동일합니다.
tokenId 생성입니다. BigInt(1) << BigInt(64)는 숫자 1을 왼쪽으로 64비트 밀어 올립니다. 결과: ...00000001 [64개의 0]. 2의 64제곱 = 18446744073709551616n입니다. 이것이 걷기 챌린지 tokenId입니다. BigInt(2) << BigInt(64)는 건강검진. BigInt(3) << BigInt(64)는 보험료 납입입니다.
tokenIdToEventType()은 역변환입니다. tokenId를 오른쪽으로 64비트 시프트합니다. 18446744073709551616n >> 64n = 1n. String(1n) = '1'. MAP['1'] = 'WALK_CHALLENGE'. 비트 시프트 하나로 역변환이 됩니다.
이 함수가 IssuerServiceSubmitter 내부에서 사용됩니다. BulkIssueService가 tokenId(bigint)를 전달하면, IssuerServiceSubmitter가 tokenIdToEventType(tokenId)로 eventType(string)으로 변환하여 issuerSvc.issueOne({ eventType })을 호출합니다.

남은 192비트로 무엇을 더 만들 수 있는가? 네 가지 예시입니다.
① 발행 연도: 빈티지 NFT입니다. 2026년 NFT vs 2027년 NFT → tokenId가 다릅니다. "2026 오리지널 참여자" 진위 검증이 가능합니다. 초기 참여자에게 희소 토큰을 부여할 수 있습니다.
② 캠페인 코드: 동일 걷기 챌린지라도 어느 캠페인인지, DB 조회 없이 tokenId 하나로 식별합니다. Etherscan에서 즉시 읽힙니다. ③ 개인별 시리얼 번호: "당신은 1번 참여자입니다"를 온체인에서 증명합니다. ERC-1155 위의 진짜 "1 of 1" 구현입니다. ④ 등급(Tier) 인코딩: Bronze/Silver/Gold를 tokenId에 내장합니다. 컨트랙트가 tokenId만 보고 혜택을 자동으로 분기합니다.
온체인 데이터의 진짜 가치 — 일반 설계: tokenId → 백엔드 API → DB 조회 → 결과. 비트 설계: tokenId >> 64 → 이벤트 타입 즉시 추출. 서드파티 DeFi, 다른 컨트랙트, 지갑 앱 등 어떤 주체도 교보생명 서버에 의존하지 않고 tokenId 하나로 토큰의 모든 의미를 읽습니다. 토큰이 자기 자신의 의미를 설명합니다(Self-describing). 이것이 온체인 데이터의 진짜 가치입니다.
