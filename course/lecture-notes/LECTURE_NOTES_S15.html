Slide 3 — ethers.js Provider vs Wallet

JsonRpcProvider와 Wallet은 메서드가 아니라 ethers.js가 제공하는 클래스다. new로 인스턴스를 만들어 쓴다.

JsonRpcProvider 블록체인 노드에 RPC로 연결하는 객체 — private key 없이 읽기만 한다

블록 조회, 이벤트 구독, TX 상태 조회가 가능하다. TX 서명·전송은 불가 — private key가 없으니 서명 자체가 안 된다.

Wallet JsonRpcProvider + private key를 합친 객체 — Provider 기능 전부 + 서명 능력 추가

Provider의 모든 기능(읽기) 위에 TX 서명·브로드캐스트 능력을 얹은 것이다. new Wallet(privateKey, provider) 형태로 생성한다 — "이 provider 위에서 이 key로 서명한다"는 의미다.

EVMAdapter 생성자에서 두 객체가 어떻게 쓰이는지 보면 바로 이해된다:

constructor(config: { rpcUrl: string; chainId: string; privateKey?: string }) {
  this.provider = new JsonRpcProvider(config.rpcUrl);  // 항상 생성 — 읽기 전용
  this.wallet   = config.privateKey
    ? new Wallet(config.privateKey, this.provider)     // privateKey 있으면 쓰기 가능
    : null;                                            // 없으면 read-only 모드
}

privateKey가 없으면 this.wallet은 null이다. sendTransaction()을 호출하면 "read-only mode, no private key" 에러가 난다. ChainEventListener처럼 이벤트 구독만 하는 용도라면 private key 없이 provider만으로 충분하다.

JsonRpcProviderWallet
생성new JsonRpcProvider(rpcUrl)new Wallet(privateKey, provider)
읽기가능가능 (Provider 기능 포함)
TX 서명·전송불가가능
사용 시점이벤트 구독, 조회 전용mintNFT, burnNFT 등 쓰기 작업

Slide 5 — 생성자 — 3가지 보안 원칙

슬라이드에 "privateKey 환경변수 주입"이 보안 원칙으로 나온다. 이게 "환경변수가 안전하다"는 뜻이 아니다. "코드에 하드코딩하는 것보다 낫다"는 최소 원칙이다.

왜 환경변수인가 git 이력 유출 방지 — 코드에 키를 박으면 커밋 이후 영원히 이력에 남는다 
// 절대 금지 — git에 올라가는 순간 이력에 영원히 남음
const privateKey = '0xabc123...';

// 환경변수 주입 — 코드엔 없음, git 이력에 키가 안 남음
const privateKey = process.env['EVM_SIGNER_KEY'];

환경변수도 완전한 해법이 아니다. 서버 접근권한이 있으면 printenv로 볼 수 있고, 컨테이너 로그에 찍히면 유출된다. 메모리 덤프로도 추출 가능하다.

실제 프로덕션 키 보안 환경변수는 개발·교육 수준 — 프로덕션은 별도 키 관리 시스템이 필요하다
수준방식특징
개발/교육환경변수 (EVM_SIGNER_KEY)git 하드코딩만 막음
스테이징AWS Secrets Manager, HashiCorp Vault접근 제어·감사 로그
프로덕션 CustodyHSM (Hardware Security Module)키가 하드웨어 밖으로 절대 나오지 않음

슬라이드의 "환경변수 주입" 원칙은 git 하드코딩 금지를 설명하는 것이다. Phase 3에서 직접 Custody로 전환하면 환경변수가 아닌 HSM이나 KMS가 필요하다 — 이 슬라이드는 그 출발점을 설명하는 것이지 완전한 키 보안 해법이 아니다.

Slide 6 — Private RPC를 써야 하는 이유 (1/4)

"공개 RPC 대신 Private RPC를 써야 한다"는 말이 나오면 자주 나오는 질문이 있다 — "유료 공개 RPC(Alchemy, QuickNode 등)는 괜찮지 않나?" 4가지 이유별로 답이 다르다.

이유유료 공개 RPC로 해결되나설명
① Rate limit ✓ 해결됨 유료 플랜은 수백만 req/day. 한도 문제 없음.
② WebSocket 안정성 ✓ 대체로 해결됨 Alchemy, QuickNode 유료 플랜은 안정적 WebSocket 지원.
③ SLA △ 조건부 Enterprise 등급은 SLA 계약 가능. 단 Alchemy·Infura는 미국 회사 — 국내 금융 규제·내부 통제 요건 충족 여부는 별도 검토 필요.
④ 쿼리 프라이버시 ✗ 해결 안 됨 돈을 내도 Alchemy 서버가 우리 쿼리를 본다. 교보 고객 지갑 주소 패턴이 미국 회사 서버 로그에 쌓임 — 금융 데이터 프라이버시·데이터 주권 문제.

Rate limit·WebSocket·SLA는 유료 공개 RPC로 해결 가능하다. 하지만 쿼리 프라이버시와 데이터 주권은 해결이 안 된다. 금융기관 수준에서는 이 마지막 이유 하나만으로도 전용 RPC(또는 자체 노드)가 필요하다.

Phase 1에서 "Private RPC"는 노드를 직접 운영하는 게 아니라 월렛원이 BaaS로 제공하는 전용 인증 엔드포인트를 쓰는 것이다. 쿼리가 월렛원 내부망에서만 처리되므로 외부 노출이 없다.

Slide 9 — Private RPC를 써야 하는 이유 (4/4)

"어차피 블록체인은 모든 노드가 동일한 데이터를 공유하는데 프라이버시가 무슨 의미냐"는 질문이 나올 수 있다. 블록체인 데이터와 RPC 쿼리를 구분해야 한다.

블록체인 데이터 모든 노드가 동일하게 갖고 있고 누구나 조회 가능 — 이미 공개, 숨길 수 없음

TX 내용, 컨트랙트 상태, 이벤트 로그는 전 세계 모든 노드가 동일하게 보유한다. 이건 맞다.

쿼리 프라이버시 "누가 뭘 물어봤는가" — 블록체인 데이터가 아닌 쿼리 행위 자체의 노출 문제

Alchemy 서버를 통해 쿼리하면 Alchemy 서버 로그에 이런 정보가 남는다:

IP:   교보 서버 IP
시각: 2026-05-26 14:32:11
쿼리: getBalance(contractAddr=0xKyoboNFT, owner=0xAlice)
쿼리: getBalance(contractAddr=0xKyoboNFT, owner=0xBob)
이벤트 구독: NFTIssued on 0xKyoboNFT

블록체인에 올라간 데이터가 아니라 "교보가 어떤 주소를 얼마나 자주 조회하는지"가 Alchemy에 노출된다.

이게 왜 문제인가 — 교보가 모니터링하는 고객 지갑 주소 목록이 드러나고, 쿼리 빈도로 사용자 수·거래량 추정이 가능하며, 어떤 이벤트를 구독하는지로 서비스 구조 파악이 가능하다. 블록체인 데이터는 공개지만 "교보가 구체적으로 어떤 주소를 언제 얼마나 자주 들여다보는지"는 공개된 정보가 아니다. 그 쿼리 패턴 자체가 금융기관의 영업 정보이고 고객 데이터다.

블록체인 데이터의 프라이버시가 아니라 쿼리 행위 자체의 프라이버시다. 전용 RPC(월렛원 내부망)를 쓰면 쿼리가 외부 서버 로그에 남지 않는다.

Slide 10 — ABI란 무엇인가

핵심 전제 EVM은 Solidity를 모른다 — 바이트코드만 실행한다

Solidity는 사람이 읽을 수 있는 언어일 뿐이고 EVM은 이를 직접 실행하지 못한다. solc 컴파일러가 Solidity를 두 가지로 변환한다:

Solidity (.sol)
    ↓ solc 컴파일러
바이트코드 (0x608060405234801561001057...)   ← EVM이 실행하는 것 (체인에 올라감)
ABI (JSON)                                  ← 외부 호출을 위한 명세 (개발자가 보관)
EVM 스택 기반 가상머신 — opcode를 하나씩 순서대로 실행

EVM은 Java의 JVM, Python의 CPython과 같은 개념이다. 플랫폼 무관하게 동일하게 실행되도록 추상화된 가상 컴퓨터다. 전 세계 수만 개 노드가 동일한 코드를 실행해서 동일한 결과를 내야 한다 — x86이든 ARM이든 EVM 위에서 돌리면 결과가 같아야 탈중앙화가 성립한다.

PUSH1 0x60   → 스택에 0x60 올림
PUSH1 0x40   → 스택에 0x40 올림
MSTORE       → 메모리에 저장
...          → 이런 opcode 수백~수천 개가 바이트코드 안에 들어있음
왜 ABI가 필요한가 바이트코드만 보고는 어떤 함수가 있고 파라미터가 뭔지 알 수 없다

컨트랙트가 배포되면 체인에 바이트코드 덩어리만 올라간다. 외부에서 mint(address, uint256, uint256)을 호출하려면 TX의 data 필드에 이렇게 넣어야 한다:

0xa9059cbb                                  ← 함수 선택자 (4바이트)
000000000000000000000000Alice주소           ← 첫 번째 파라미터 (32바이트)
0000000000000000000000000000000000003E9    ← tokenId = 1001
0000000000000000000000000000000000000001   ← amount = 1

함수 선택자는 keccak256("mint(address,uint256,uint256)")의 앞 4바이트다. EVM은 이 4바이트를 보고 어떤 함수를 호출하는지 판단한다. ABI가 없으면 이 시그니처 문자열을 알 수 없고, 파라미터를 32바이트 단위로 어떻게 인코딩해야 하는지도 알 수 없다.

ethers.js가 하는 일이 정확히 이것이다 — ABI를 읽고 calldata를 자동으로 만들어준다:

// 개발자가 이렇게 쓰면
contract.mint("0xAlice", 1001n, 1n)

// ethers.js가 ABI 기반으로 calldata를 만들어 TX data 필드에 삽입
data: 0xa9059cbb000...Alice000...3E9000...1

ABI는 바이트코드와 사람(또는 라이브러리) 사이의 번역 규칙이다. 컨트랙트 소스코드를 잃어버려도 ABI만 있으면 호출할 수 있다. ABI도 없으면 raw 바이트코드를 직접 인코딩해야 한다 — 사실상 불가능한 수준의 작업이다.

// 전체 흐름 요약
Solidity → [컴파일] → 바이트코드 (체인에 올라감)
                    → ABI       (개발자가 보관, 외부 호출 시 사용)

외부 호출 시:
  ABI로 calldata 인코딩 → TX data 필드에 삽입 → EVM이 바이트코드 실행

Slide 11 — ABI란 무엇인가 — Bytecode 경로

사실 ABI는 Solidity만의 개념이 아니다. 비슷한 패턴이 다른 곳에도 있다.

기술ABI 역할을 하는 것용도
C 라이브러리헤더 파일 (.h)바이너리만 있을 때 함수 시그니처 공개
gRPCProtobuf (.proto)서버 바이너리의 RPC 명세 공유
REST APIOpenAPI (Swagger)엔드포인트·파라미터 명세
Solidity/EVMABI (JSON)컨트랙트 바이트코드의 함수 명세

ABI 자체는 어디서나 있는 개념이다. EVM이 특별한 게 아니다.

그러면 왜 EVM에서 ABI가 더 두드러지는가
이유 1 EVM 바이트코드는 리플렉션이 없다

Java JAR는 리플렉션으로 런타임에 "이 클래스에 어떤 메서드가 있는지" 조회할 수 있다. EVM 바이트코드는 그게 안 된다. ABI 없이 바이트코드만 보면 함수가 뭔지 알아낼 방법이 없다.

이유 2 caller와 callee가 절대 같이 컴파일되지 않는다

일반 소프트웨어는 링커가 caller와 callee를 엮어준다. 블록체인은 컨트랙트가 체인에 배포된 이후, 전혀 관계없는 지갑·dApp·스크립트가 네트워크를 통해 함수를 호출한다. 링커가 없으니 ABI라는 명세를 별도로 공유해야 한다.

ABI는 Solidity만의 특수한 개념이 아니라, "바이트코드만 있는 상황에서 외부 caller가 함수를 호출해야 할 때" 필요한 범용 패턴이다. EVM에서 이게 더 명시적으로 드러나는 이유는 리플렉션도 없고 링커도 없는 환경이기 때문이다.

Slide 12 — ABI란 무엇인가 — ABI 경로

ABI를 개발자가 각자 들고 있어야 하는 게 불편해 보이지만, 실제로는 공개 저장소에 올려두고 다운받아 쓰는 방식이 이미 표준화되어 있다.

Etherscan verify 가장 일반적인 방식 — 배포 시 소스를 제출하면 ABI가 공개 저장소에 올라감

컨트랙트를 배포할 때 소스코드를 Etherscan에 제출(verify)하면, Etherscan이 직접 컴파일해서 체인에 올라간 바이트코드와 일치하는지 확인한다. 일치하면 ABI를 공개한다. 이후 누구나 컨트랙트 주소로 검색해서 ABI를 다운받을 수 있다.

배포자: 컨트랙트 주소 0xKyoboNFT → Etherscan에 소스 제출
Etherscan: 컴파일 → 바이트코드 일치 확인 → ABI 공개

사용자: etherscan.io/address/0xKyoboNFT → ABI 다운로드
방식설명
Etherscan verify가장 일반적. 오픈소스 컨트랙트는 거의 다 이렇게 함
npm 패키지프로젝트가 직접 ABI를 패키지로 배포 (@uniswap/v3-core 등)

Slide 26 — subscribeEvents (1/2)

_fromBlock이 파라미터에 있지만 무시되는 이유

IBlockchainAdapter.subscribeEvents() 시그니처에는 _fromBlock: number가 있다. 그런데 EVMAdapter 구현을 보면 이 값을 전혀 쓰지 않고 변수명 앞에 언더스코어(_)가 붙어 있다. TypeScript에서 _ 접두사는 "의도적으로 사용하지 않는 파라미터"를 나타내는 관례다.

이유는 WebSocket 방식의 근본적인 한계에 있다. ethers.js의 contract.on()은 내부적으로 Ethereum JSON-RPC의 eth_subscribe 프로토콜을 사용한다. eth_subscribe는 "지금 이 순간부터 이벤트를 스트리밍해줘"라는 명령이다. 과거 블록에서 시작하는 fromBlock 파라미터 자체가 존재하지 않는다.

방식APIfromBlock 지정용도
WebSocket (contract.on())eth_subscribe불가 — 연결 시점부터실시간 이벤트 수신
HTTP (contract.queryFilter())eth_getLogs가능 (fromBlock~toBlock)과거 이벤트 조회

따라서 subscribeEvents()가 WebSocket으로 구독을 시작하기 전에 놓친 이벤트(missed events)는 subscribeEvents()가 직접 복구할 수 없다. 이 역할은 별도로 존재하는 queryEvents()가 담당한다. 서비스 재시작 시 queryEvents(lastKnownBlock, currentBlock)로 공백 구간을 채운 뒤, subscribeEvents()로 실시간 구독을 연결하는 순서로 동작한다.

그런데 왜 _fromBlock을 아예 지우지 않고 인터페이스에 남겨뒀을까? IBlockchainAdapter는 EVM·XRPL 등 여러 체인의 어댑터가 공유하는 공통 인터페이스다. XRPL 어댑터나 미래의 HTTP polling 기반 어댑터는 fromBlock을 실제로 사용할 수 있다. 인터페이스의 파라미터를 맞추되, EVM WebSocket 구현에서만 무시하는 구조다.

클로저 패턴 — 왜 이렇게 짰는가

클로저(closure)는 함수가 자신이 선언된 시점의 주변 변수를 "기억"하는 기능이다. JavaScript/TypeScript에서는 함수 안에서 함수를 만들면 바깥 함수의 변수를 자동으로 캡처한다.

이 코드를 단계별로 보자:

for (const eventName of eventNames) {            // ① 이벤트 이름마다 반복
  const listener = async (...args) => { ... };   // ② 이 이벤트의 핸들러 함수 생성
  contract.on(eventName, listener);               // ③ 구독 등록
  listeners.push(() => contract.off(eventName, listener));  // ④ 해제 클로저 저장
}
return () => listeners.forEach(off => off());    // ⑤ 단일 unsubscribe 함수 반환

핵심은 ④번이다. () => contract.off(eventName, listener)는 클로저다. 이 화살표 함수는 이 루프 회차의 eventName과 listener를 캡처해서 기억한다. 나중에 이 함수를 호출하면, 당시 캡처했던 정확한 이벤트 이름과 핸들러를 가지고 contract.off()를 실행한다.

만약 클로저를 쓰지 않고 contract.off()를 바로 호출하면 어떻게 될까? 그 순간 즉시 해제되어 버린다 — 구독 등록 직후에. 클로저로 "나중에 호출할 함수"를 만들어 배열에 저장하기 때문에 원하는 타이밍(서비스 종료 시)에 정확히 해제할 수 있다.

⑤번의 () => listeners.forEach(off => off())도 클로저다. listeners 배열을 캡처하고 있다. 이 함수를 호출하는 시점에 배열 안의 클로저들을 하나씩 실행해서 모든 이벤트 구독을 한 번에 해제한다.

결과적으로 호출자는 이벤트 종류가 몇 개든, 어떤 이벤트인지 몰라도 반환받은 함수 하나만 실행하면 전부 정리된다. GracefulShutdown 처리나 테스트 cleanup이 단순해지는 이유다.

EVMAdapter.ts 181~192줄 — 코드 흐름 상세

const listeners: Array<() => void> = [];           // ①

for (const eventName of eventNames) {
  const listener = async (...args: unknown[]) => {  // ②
    const payload = args[args.length - 1]            // ③
      as { log?: EventLog } & EventLog;
    const log = payload.log ?? payload;              // ④
    await handler(
      this._toChainEvent(eventName, contractAddr, log, args)
    );
  };
  contract.on(eventName, listener);                  // ⑤
  listeners.push(() => contract.off(eventName, listener)); // ⑥
}

① listeners 배열
나중에 구독을 해제할 함수들을 모아두는 빈 배열. 타입은 Array<() => void> — "인자 없이 호출되고 반환값 없는 함수"의 배열이다.

② async (...args: unknown[]) — rest parameter
ethers.js가 이벤트를 발생시킬 때 넘겨주는 인자 개수가 이벤트마다 다르다. NFTIssued는 (to, tokenId, amount, payload) 4개, 다른 이벤트는 3개일 수도 있다. ...args로 개수에 상관없이 전부 배열로 받아 처리한다.

③ args[args.length - 1] — 마지막 인자
ethers.js v6에서 contract.on() 핸들러의 마지막 인자는 항상 ContractEventPayload다. 이벤트 파라미터가 3개면 args = [param1, param2, param3, ContractEventPayload], 4개면 args = [param1, param2, param3, param4, ContractEventPayload]. 마지막 위치가 고정이므로 args[args.length - 1]로 꺼낸다.

④ payload.log ?? payload — ethers v6 이중 구조 대응
ethers.js v6의 ContractEventPayload는 내부에 log 필드를 갖는다. 이 log가 실제 EventLog 객체이며 transactionHash, blockNumber 등이 들어있다.

경우구조결과
일반적인 경우payload = { log: EventLog, ... }payload.log 사용
일부 버전/환경payload 자체가 EventLogpayload.log가 undefined → payload 자체 사용

??는 null-coalescing 연산자 — 왼쪽이 null이나 undefined일 때만 오른쪽을 쓴다. 즉 "payload.log가 있으면 그걸 쓰고, 없으면 payload 자체를 EventLog로 간주"하는 방어 코드다. ethers.js 버전별 미세한 차이를 흡수하기 위한 처리다.

⑤ contract.on(eventName, listener)
실제 WebSocket 구독 등록. 이 시점부터 해당 이벤트가 발생하면 listener가 호출된다.

⑥ listeners.push(() => contract.off(eventName, listener))
구독 해제 클로저를 배열에 저장. contract.off()에는 반드시 등록할 때 쓴 동일한 listener 참조를 넘겨야 한다. JavaScript에서 함수 동등성은 참조 비교이기 때문에, 새로운 함수를 만들어 넘기면 ethers.js가 "모르는 리스너"로 인식해 해제에 실패한다. 클로저가 listener 변수를 캡처해서 기억하는 것이 핵심이다.

슬라이드 예시 코드와 실제 운영 코드의 관계

슬라이드의 예시 코드는 subscribeEvents()가 어떻게 쓰이는지 원리만 뽑아 단순화한 것이다. 실제 운영 코드는 3개 파일에 역할이 나뉘어 있다.

슬라이드 예시실제 운영 코드파일
adapter.subscribeEvents() 직접 호출ChainEventListener.start() 안에서 호출ChainEventListener.ts:55
const unsubscribe = ...this.unsubscribers.push(unsub) — 배열로 관리ChainEventListener.ts:65
unsubscribe()ChainEventListener.stop() → unsubscribers.forEach(unsub => unsub())ChainEventListener.ts:71
process.on('SIGTERM', ...)process.on('SIGTERM', shutdown) → shutdown()이 eventListener.stop() 호출issuer-service/index.ts:249,254

왜 ChainEventListener로 감쌌는가

슬라이드 예시처럼 adapter.subscribeEvents()를 직접 노출하면 호출하는 쪽이 unsubscribe 참조를 직접 들고 다녀야 한다. 실제 운영에서는 두 가지 문제가 있다.

  • 감시할 컨트랙트·이벤트가 여러 개 — unsubscribe도 여러 개가 생긴다
  • 재시작 시 missed event 복구(queryEvents)를 구독 전에 먼저 실행해야 한다

ChainEventListener가 이 복잡도를 캡슐화해서 외부(issuer-service)에서는 start() / stop() 두 개만 보인다. 슬라이드의 unsubscribe()가 실제로는 eventListener.stop()이고, 그 안에서 배열에 저장된 클로저들을 일괄 실행하는 구조다. 

// issuer-service/index.ts — 실제 종료 처리
const shutdown = async () => {
  pool.stop();
  await eventListener.stop();   // ← 이 한 줄이 슬라이드의 unsubscribe() + server.close()
  await webhookServer.close();
  await redis.quit();
  process.exit(0);
};
process.on('SIGTERM', shutdown);
process.on('SIGINT',  shutdown);

Slide 31 — _toChainEvent (2/2) — fragment.inputs 역할

EventLog가 어떤 형태로 들어오는가

ethers.js는 체인에서 받은 raw 로그(Log)를 ABI로 디코딩해서 EventLog를 만든다. 두 계층으로 나뉜다.

Log — 체인에서 그대로 온 raw 데이터

transactionHash  "0xabc..."        // TX 해시
blockNumber      18_542_301        // 포함된 블록 번호
index            3                 // 이 블록 내 로그 순서
data             "0x000000..."     // ABI 인코딩된 raw bytes (non-indexed 파라미터)
topics           ["0x1234...",     // [0]: 이벤트 시그니처 해시 (keccak256)
                  "0x0000..."]     // [1~]: indexed 파라미터
address          "0x6B2e..."       // 컨트랙트 주소

EventLog — Log + ABI 디코딩 결과

fragment         EventFragment     // ABI에서 읽어온 이벤트 정의
  .name          "NFTIssued"
  .inputs        [{ name: "to",      type: "address" },
                  { name: "tokenId", type: "uint256" },
                  { name: "amount",  type: "uint256" }, ...]
args             Result            // 디코딩된 파라미터 값 (배열)
  [0]            "0x91ff..."       // to 주소
  [1]            42n               // tokenId (BigInt)
  [2]            1n                // amount

fragment.inputs는 ABI에 정의된 파라미터 메타데이터(이름·타입)고, log.args는 실제 디코딩된 값 배열이다. 둘 다 같은 인덱스 순서로 정렬되어 있기 때문에 인덱스 i로 묶을 수 있다.

_toChainEvent()가 이걸 어떻게 쓰는가

const named: Record<string, unknown> = {};
log.fragment.inputs.forEach((input, i) => {
  named[input.name] = log.args?.[i];
});
// → named = { to: "0x91ff...", tokenId: 42n, amount: 1n }

log.args만 쓰면 [0], [1] 숫자 인덱스로만 접근 가능하다. fragment.inputs[i].name을 붙여 딕셔너리로 변환하면 이후 코드에서 named.to, named.tokenId처럼 이름으로 접근할 수 있다. 이게 fragment.inputs가 필요한 이유다.

fragment가 없는 경우(ABI 없이 raw 로그만 수신된 상황)엔 { raw: args }로 폴백한다. named가 비어 있으면 Object.keys(named).length === 0 → 폴백 조건 충족.

접근 방식예시
log.args만 사용숫자 인덱스log.args[1] → 42n
fragment.inputs 결합이름 키named.tokenId → 42n

Slide 33 — XRPLAdapter — 교체 시뮬레이션

XRPL_WS_URL과 XRPL_SEED — EVM 설정값과 대응

XRPL_WS_URL — XRPL 노드 WebSocket 주소

XRPL은 HTTP가 아니라 WebSocket으로 통신한다. EVM의 RPC_URL에 해당하지만 프로토콜이 wss:// 고정이다. 현재 .env에 XRPL_WS_URL=wss://xrplcluster.com으로 설정돼 있다.

XRPL_SEED — XRPL 계정 서명 키

EVM의 OPERATOR_PRIVATE_KEY에 해당한다. XRPL에서는 private key를 직접 쓰지 않고 seed라는 형태로 관리한다. seed에서 key pair(공개키 + 비밀키)를 파생시켜 트랜잭션 서명에 사용한다. 형식은 s로 시작하는 Base58 문자열이다 (예: sEdTM1uX8pu2do5XvTnutH6HsouMaM2). 현재 .env에 XRPL_SEED=로 비어있다 — XRPL 실습 시 채워야 한다.
