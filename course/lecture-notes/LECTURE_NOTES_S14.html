Slide 4 — EVM 고착화 리스크 1/2

비유로 시작한다 — USB-C(표준) vs 전용 케이블(고착화). 소프트웨어도 같다. EVM 전용 개념이 비즈니스 코드에 들어가는 순간 체인 교체 비용이 폭증한다.

케이블 얘기를 먼저 한다. A사 전용 케이블을 쓰는 노트북을 바꾸면 케이블만 바꾸면 될 것 같지만, 가방 포켓 사이즈, 차량 거치대, 멀티탭까지 연쇄적으로 바꿔야 한다. 교체 비용이 노트북 한 대를 훌쩍 넘는다.

USB-C가 표준화된 이후에는 노트북을 바꿔도 케이블 그대로 쓴다. 교체 비용 = 노트북 한 대뿐이다.

소프트웨어도 똑같다. ethers.js, gasUsed, topics 같은 EVM 전용 개념이 비즈니스 로직 안에 직접 들어가면, 나중에 XRPL이나 Circle로 체인을 바꿀 때 비즈니스 코드까지 전부 수정해야 한다.

여기서 topics가 낯설 수 있다. 이더리움 이벤트 로그는 topics 배열로 이벤트를 식별한다. topics[0]은 이벤트 시그니처 해시, topics[1]부터는 indexed 파라미터다. XRPL에는 이 개념 자체가 없다. 그래서 topics가 비즈니스 코드에 박혀 있으면 체인 교체 시 그 줄을 전부 다시 짜야 한다.

Vendor Lock-in특정 기술·벤더의 개념이 비즈니스 코드 깊숙이 침투해, 교체 시 비즈니스 코드까지 전부 수정해야 하는 상황
topicsEVM 이벤트 로그 전용 필드. topics[0] = 이벤트 시그니처 해시, topics[1]~ = indexed 파라미터. XRPL·Circle에는 없는 개념

Slide 6 — IBlockchainAdapter 설계 원칙 1/3

설계 원칙을 설명하기 전에 GoF가 무엇인지 짚고 넘어간다. IBlockchainAdapter의 설계는 GoF 패턴 여러 개를 동시에 적용한 결과물이다.

GoF는 Gang of Four의 약자다. 1994년 Gamma, Helm, Johnson, Vlissides 네 명이 쓴 책 Design Patterns: Elements of Reusable Object-Oriented Software에서 나온 말이다. 이 책에서 소프트웨어 설계에 반복적으로 등장하는 23개의 패턴을 정리했고, 30년이 지난 지금도 설계의 기본 교재로 쓰인다.

패턴은 세 가지로 분류된다. 생성 패턴은 객체를 어떻게 만드는가, 구조 패턴은 객체를 어떻게 조합하는가, 행위 패턴은 객체가 어떻게 협력하는가를 다룬다.

우리 프로젝트에서 이미 쓰인 GoF 패턴을 정리하면 이렇다.

분류패턴우리 코드세션
생성FactoryChainAdapterFactoryS14
구조DecoratorLoggingAdapterDecorator, RetryAdapterDecoratorS17
구조AdapterIBlockchainAdapter — 체인별 인터페이스 통일S14
행위ObserverTxStateMachineService EventEmitterS13
행위StrategyIConditionStrategy—
행위Template MethodChainVASPAdapterBase—

"GoF 원칙"이라는 표현은 틀렸다. GoF는 원칙이 아닌 패턴이다. 원칙은 SOLID(단일책임·개방폐쇄·리스코프·인터페이스분리·의존역전)가 따로 있고, GoF 패턴은 그 원칙을 구현하는 구체적인 방법이다.

Slide 7 — IBlockchainAdapter 설계 원칙 2/3

DI(의존성 주입) — 객체가 스스로 의존성을 만들지 않고 외부에서 주입받는 패턴. IBlockchainAdapter 설계의 핵심 연결 고리다.

DI가 없으면 어떻게 되는지부터 본다. IssuerService 내부에서 new EVMAdapter()를 직접 생성하면, IssuerService는 EVMAdapter에 고착된다. XRPL로 교체하려면 클래스 내부를 수정해야 한다.

DI를 적용하면 생성자에서 IBlockchainAdapter 타입으로 받는다. 어떤 구현체가 들어오는지는 호출 측에서 결정한다. new IssuerService(new EVMAdapter())도 되고, new IssuerService(new XRPLAdapter())도 되고, 테스트에서는 new IssuerService(new MockAdapter())로 주입한다.

IssuerService 코드는 한 줄도 바뀌지 않는다.

DIDependency Injection. 객체가 필요한 의존성을 스스로 생성하지 않고 생성자·메서드·프로퍼티를 통해 외부에서 주입받는 설계 기법
// ❌ DI 없이 — EVMAdapter에 고착
class IssuerService {
  private adapter = new EVMAdapter();
}

// ✅ DI 적용 — 인터페이스에만 의존
class IssuerService {
  constructor(private adapter: IBlockchainAdapter) {}
}

new IssuerService(new EVMAdapter());   // 운영
new IssuerService(new XRPLAdapter());  // 체인 교체 시 이 줄만
new IssuerService(new MockAdapter());  // 테스트

핵심 효과 3가지 — ① 구현체 교체 시 IssuerService 코드 무변경  ② Mock 주입으로 단위 테스트 가능  ③ DIP(의존 역전 원칙) 실현 수단

DI는 GoF 패턴이 아니라 설계 기법이다. Factory·Strategy 패턴과 함께 쓰이는 경우가 많다. 우리 프로젝트에서는 ChainAdapterFactory.create(config)가 DI의 주입 지점 역할을 한다.

이 슬라이드는 ChainAdapterFactory 내부 구조를 설명한다. 두 가지를 본다.

왼쪽 코드 — 어떤 어댑터를 만들지 결정하는 곳. config.chainType이 'EVM'이면 EVMAdapter, 'XRPL'이면 XRPLAdapter를 만들어 반환한다. 반환 타입은 IBlockchainAdapter — 호출자는 구체 클래스가 뭔지 모른다.

오른쪽 — default: never 패턴. ChainType = 'EVM' | 'XRPL' 유니온 타입에 나중에 'UTXO'를 추가했다고 하자. switch에 case 'UTXO'가 없으므로 default로 빠진다. 거기서 const _: never = config.chainType을 만나는데, 'UTXO'는 never에 할당 불가 → 컴파일 에러, 빌드 실패. 사람이 잊어버려도 타입 시스템이 강제로 잡아준다.

이 switch 분기가 ChainAdapterFactory 안에만 있다는 게 핵심. index.ts도, IssuerService도 "EVM인지 XRPL인지" 판단하는 코드가 없다. 체인 추가 시 Factory 한 곳만 고치면 된다.

Slide 21 — 파라미터 인터페이스 — 왜 별도로 분리하는가

MintParams, MintBatchParams, ContractCallParams는 모두 IBlockchainAdapter.ts에 정의된 파라미터 인터페이스다. 이걸 왜 별도 타입으로 빼는지 두 가지 이유로 설명한다.

이유 1 Named parameters — 순서 실수 방지

파라미터를 인터페이스로 묶지 않으면 메서드 시그니처가 이렇게 된다:

mintNFT(contractAddr: string, to: string, tokenId: bigint, amount: bigint, requestId: string)

파라미터가 5개다. 호출하는 쪽에서 순서를 헷갈리면 컴파일러가 잡지 못한다 — tokenId와 amount가 둘 다 bigint라 타입은 맞아도 값이 뒤바뀐다. 반면 인터페이스로 묶으면:

mintNFT(params: MintParams)

// 호출 시
adapter.mintNFT({
  contractAddr: '0x...',
  to: '0x...',
  tokenId: 1n,
  amount: 1n,
  requestId: uuid,
})

이름으로 전달하므로 순서가 없다. 필드 이름이 틀리면 컴파일 에러가 난다.

이유 2 메서드 시그니처 변경 없이 필드 확장 가능

나중에 gasLimit를 옵셔널로 추가해야 한다고 하자. 인터페이스 없이 positional params였다면 mintNFT() 시그니처 자체를 바꿔야 하고, 이 메서드를 호출하는 모든 곳을 다 고쳐야 한다. 인터페이스를 쓰면:

interface MintParams {
  contractAddr: string;
  to:           string;
  tokenId:      bigint;
  amount:       bigint;
  requestId:    string;
  gasLimit?:    bigint;  // ← 옵셔널 추가
}

mintNFT(params: MintParams) 시그니처는 그대로다. 기존 호출 코드는 gasLimit를 안 넘겨도 되고, 필요한 곳만 선택적으로 넘긴다. 호출 측 코드 변경이 없다.

이 두 인터페이스는 체인마다 다른 게 아니다 — EVMAdapter도 XRPLAdapter도 동일한 MintParams를 받아서 각자의 방식으로 내부에서 변환한다. 호출 측은 체인이 뭔지 몰라도 된다.

Slide 23 — 공통 데이터 추상화 1/2

체인마다 이벤트나 TX 결과를 표현하는 데이터 구조가 다르다. EVM은 gasUsed, blockHash, logIndex 같은 개념이 있고, XRPL은 가스라는 개념 자체가 없고 이벤트 구조도 완전히 다르다. 그런데 IssuerService나 TxStateMachineService 같은 비즈니스 로직은 "지금 EVM이야 XRPL이야"를 알면 안 된다. 그래서 체인 무관하게 쓸 수 있는 공통 데이터 타입을 정의한 것이 이 슬라이드의 주제다.

TransactionReceipt TX 실행 결과를 담는 공통 타입 
interface TransactionReceipt {
  txHash:      string;
  blockNumber: number;
  blockHash:   string;
  status:      'success' | 'failed' | 'pending';
  gasUsed?:    bigint;   // EVM만 유효, XRPL은 undefined
  timestamp:   number;
}

gasUsed가 옵셔널인 이유가 핵심이다. EVM은 가스 사용량이 있고, XRPL은 없다. 그래서 ?로 선언하고 어댑터가 체인에 맞게 채우거나 안 채운다. 상위 레이어(IssuerService, TxStateMachineService)는 gasUsed에 의존하면 안 된다 — 의존하는 순간 체인 종속이 생긴다.

TxStateMachineService는 getReceipt(txHash)가 null을 반환하면 TX가 아직 PENDING이라고 판단한다. receipt 자체가 없다는 것이 PENDING의 신호다.

ethers.js의 TransactionReceipt와 이름이 같지만 다른 타입이다. ethers.js에서는 gasUsed가 필수 필드다. 우리 코드의 TransactionReceipt는 XRPL 수용을 위해 옵셔널로 설계된 것이다. 혼동 주의.

Slide 24 — 공통 데이터 추상화 2/2

ChainEvent 이벤트 구독/조회로 올라오는 이벤트의 공통 타입 
interface ChainEvent {
  eventName:    string;
  contractAddr: string;
  txHash:       string;
  blockNumber:  number;
  logIndex:     number;
  args:  Record<string, unknown>;  // 체인 무관 공통 필드
  raw:   unknown;                  // 체인별 원본 데이터
}

args와 raw 두 필드가 핵심이다. args는 어댑터가 체인 원본을 파싱해서 공통 포맷으로 변환한 것이다. raw는 체인에서 올라온 원본 데이터를 버리지 않고 그대로 보존한 것이다.

흐름으로 보면 이렇다. 체인에서 이벤트가 올라오면 EVMAdapter._toChainEvent()가 ABI를 기반으로 원본을 파싱해서 named args로 변환한다. 그 결과로 ChainEvent { args, raw }가 만들어지고, 이게 IssuanceConfirmHandler나 ledgerService.record()로 전달된다.

raw는 어댑터 내부에서만 다뤄야 한다. IssuerService나 핸들러가 raw를 직접 파싱하기 시작하면 그 순간 EVM 종속 코드가 된다. raw에 의존하는 로직은 반드시 어댑터 안으로 넣어야 한다.

정리하면 — TransactionReceipt는 TX 실행 결과의 공통 포맷, ChainEvent는 온체인 이벤트의 공통 포맷. 둘 다 어댑터가 체인 원본을 이 구조로 변환해서 올려준다. 상위 레이어는 이 두 타입만 알면 어떤 체인이든 동일하게 처리할 수 있다.

Slide 25 — EVM vs XRPL vs Circle ARC 패러다임 비교

이 슬라이드는 왜 추상화가 필요한지를 체인별 패러다임 차이로 보여준다. 세 체인이 근본적으로 다른 방식으로 동작하기 때문에 공통 인터페이스 없이는 상위 레이어가 체인마다 분기 처리를 해야 한다는 것이 요점이다.

개념EVM (Ethereum)XRPLCircle ARC
스마트컨트랙트 Solidity로 작성. 튜링 완전 — 어떤 로직이든 온체인에 올릴 수 있다. 스마트컨트랙트 없음. Hooks라는 실험적 기능이 있지만 아직 미성숙. 컨트랙트 대신 프로그래머블 월렛으로 로직을 처리. Circle이 인프라를 운영.
NFT 표준 ERC-1155 — tokenId와 amount로 다수량 NFT 표현. 컨트랙트에 직접 mint. XLS-20 — Offer 기반 전송 모델. NFT 전송이 CreateOffer + AcceptOffer 두 단계로 분리됨. ERC-1155를 Circle 인프라 위에 래핑. 직접 체인에 쓰지 않고 Circle이 중간에서 처리.
가스 체계 Gas × GasPrice = ETH. TX마다 가스 비용 계산 필요. EIP-1559 이후 BaseFee + Priority Fee 구조. 가스 개념 없음. 대신 계정에 XRP를 Reserve(잠금)해야 하고, TX당 고정 Fee가 있음. 가스를 Circle이 추상화해서 처리. 호출자는 가스를 신경 쓰지 않아도 됨.
이벤트 ABI-encoded Log. topics 필드에 이벤트 시그니처 해시 + 인덱싱된 파라미터가 들어감. Transaction Metadata에 변경 내역이 포함. 이벤트 로그 개념이 아닌 상태 변화 diff 형태. WebHook 또는 SDK 이벤트. 체인 레벨 이벤트가 아닌 Circle 플랫폼 이벤트.
Finality PoS Checkpoint 기반. 약 12분 후 절대 불변 (2/3+ validator 동의). 그 전까지는 REORG 가능. BFT 합의 — 3~5초 안에 최종 확정. REORG 없음. 블록 확인 수를 기다릴 필요가 없다. 의존하는 체인에 따라 다름.

EVM ↔ XRPL 1:1 매핑 불가 사례 — XRPL에서 NFT 전송은 CreateOffer + AcceptOffer 두 TX가 필요하다. 그런데 IssuerService는 adapter.mintNFT(params) 한 번만 호출한다. XRPLAdapter가 내부적으로 두 TX를 묶어서 하나의 mintNFT()로 표현하는 것이다. 이게 어댑터 패턴의 존재 이유다 — 체인별 복잡성을 어댑터 안에 가둔다.

XRPL의 Finality가 3~5초로 빠른 것은 REORG 처리 로직이 불필요하다는 뜻이다. 하지만 IBlockchainAdapter는 그 차이를 노출하지 않는다 — getReceipt()가 status: 'success'를 반환하면 상위 레이어는 체인 무관하게 확정으로 처리한다.

Circle ARC — "프로그래머블 월렛으로 로직을 처리한다"는 게 무슨 뜻인가

EVM은 로직이 블록체인 위에 올라간다. Solidity 컨트랙트에 mint 조건, whitelist 체크, 잔액 업데이트 코드가 있고, 체인이 직접 실행한다.

Circle은 다르다. 로직이 Circle 서버 위에 올라간다. Solidity 컨트랙트를 작성하는 게 아니라 Circle 대시보드/API에서 "이 월렛은 이런 조건에서만 송금 가능" 같은 정책(Policy)을 설정하면, Circle 서버가 그 정책을 집행한다. 실제 체인에는 최종 결과 TX만 기록된다.

EVMCircle ARC
로직 위치블록체인 위 (on-chain Solidity)Circle 서버 위 (off-chain Policy)
실행 주체EVM 노드 (체인)Circle 서버
체인에 올라가는 것컨트랙트 코드 + TX최종 TX 결과만
설정 방법Solidity 코드 작성 + 배포Circle API/대시보드에서 정책 설정

따라서 CircleAdapter.mintNFT()는 내부적으로 Solidity 컨트랙트를 호출하는 게 아니라 Circle REST API를 호출하는 형태가 된다. IssuerService는 그걸 모른다 — adapter.mintNFT(params)만 호출할 뿐이다. 이게 어댑터가 체인별 구현 방식의 차이를 숨기는 실제 사례다.

Slide 29 — 멀티체인 동시 운영 3/4

이 슬라이드는 여러 체인이 동시에 운영될 때 어느 체인으로 발행할지 결정하는 방식을 보여준다. 핵심은 코드가 결정하는 게 아니라 정책 DB(Policy DB)가 결정한다는 것이다.

정책 기반 라우팅 발행 요청이 들어오면 productId로 정책을 조회하고, 정책에 있는 chainId로 어댑터를 선택한다 
async issue(req: IssuanceRequest) {
  const policy = await this.policyService.get(req.productId);
  // policy.chainId = 'sepolia' | 'xrpl-mainnet' | ...

  const adapter = this.registry.get(policy.chainId);

  return adapter.mintNFT({
    contractAddr: policy.contractAddr,
    to: req.walletAddr, tokenId: req.tokenId,
    amount: 1n, requestId: req.requestId,
  });
}

흐름을 보면: 발행 요청(productId='KRW-BOND') → policyService.get()로 정책 조회 → policy.chainId = 'xrpl-mainnet' → registry.get('xrpl-mainnet')로 XRPLAdapter 선택 → adapter.mintNFT() 호출 → XRPL에 발행.

내일 정책 DB에서 KRW-BOND의 chainId를 'sepolia'로 바꾸면? 코드 한 줄 안 건드리고 Ethereum으로 라우팅된다. 이게 정책 기반 라우팅의 핵심이다.

IssuerService는 체인을 모른다. policy.chainId가 뭔지 신경 쓰지 않는다. registry에서 어댑터를 꺼내서 mintNFT()를 호출할 뿐이다. 체인 선택 로직이 비즈니스 코드 밖으로 완전히 빠져 있다.

이 슬라이드의 IssuerService는 Phase 2+ 버전이다. Phase 1의 현재 코드는 registry가 아닌 단일 chainAdapter를 주입받는다. ChainAdapterRegistry는 운영 코드에 추가해 두었지만 Phase 2 전까지는 사용하지 않는다.
