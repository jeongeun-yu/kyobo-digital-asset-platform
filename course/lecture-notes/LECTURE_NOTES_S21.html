Travel Rule — 왜 transfer()에 포함되는가

트래블룰(Travel Rule)은 금융정보분석원(KoFIU)이 특금법 §8의4에 근거해 가상자산사업자(VASP)에게 부과한 의무다. 100만원 이상의 가상자산을 이체할 때 송신자(originator)와 수신자(beneficiary) 정보를 수취 VASP에 함께 전달해야 한다.

쉽게 말하면 은행 송금의 "보내는 사람 이름·계좌" 같은 정보를 가상자산에도 붙이는 것이다. SWIFT 전문에서 온 개념이라 "Travel Rule"이라고 부른다 — 돈과 함께 정보가 "여행"한다는 뜻.

항목내용
적용 기준100만원(약 $1,000 FATF 기준) 이상 이체
전달 정보originator: 이름·계좌ID·VASP / beneficiary: 이름·계좌ID·VASP
전달 방식수취 VASP API에 암호화 전송 (VASP 간 직접 통신)
미이행 시과태료 + 영업정지 리스크

코드상으로는 TransferRequest 안의 travelRuleData 필드에 담긴다. 100만원 미만이면 travelRuleData를 생략할 수 있고, 이상이면 VASP가 이 필드 없이 전송을 거부한다.

AML / screenAddress — 블랙리스트 체크가 왜 필요한가

AML(Anti-Money Laundering, 자금세탁방지)은 범죄 수익이 금융 시스템을 통해 세탁되는 것을 막는 규제 체계다. 가상자산은 익명성이 높아 자금세탁에 악용될 수 있기 때문에 VASP는 거래 전 상대방 주소를 검증할 의무가 있다.

screenAddress(address)는 해당 지갑 주소가 제재 대상(OFAC SDN 리스트), 다크넷 마켓, 해킹 관련 주소 등 블랙리스트에 포함되어 있는지 체크한다. 내부적으로는 Chainalysis, Elliptic 같은 온체인 분석 업체의 API를 VASP가 호출한다.

Chainalysis란

블록체인 분석 전문 회사다. 모든 블록체인 TX는 공개되어 있지만, 지갑 주소만 보고는 그게 누구 것인지·어디서 온 돈인지 알 수 없다. Chainalysis는 이걸 추적·분석하는 것을 사업으로 한다.

하는 일

  • 수백만 개의 지갑 주소를 클러스터링해서 "이 주소들은 바이낸스 것", "이건 실크로드 관련" 등으로 레이블링
  • 특정 지갑의 자금 출처를 소급 추적 (믹서, 다크넷, 해킹 연루 여부)
  • OFAC 제재 대상 주소 데이터베이스 유지

VASP는 규제상 고객이 보내거나 받는 주소가 제재·범죄 연루 지갑인지 확인할 의무가 있다. 자체적으로 이 DB를 구축하기 어려우니 Chainalysis 같은 업체 API를 구독해서 쓴다. screenAddress() 내부에서 실제로 호출되는 게 이 API다.

업체국가
Chainalysis미국 (시장 1위)
Elliptic영국
TRM Labs미국
람다256 (두나무), CAMS국내

요약하면 "블록체인판 신용조회 기관"에 가깝다. 

// 반환값
{ flagged: boolean; reason?: string }

// flagged: true  → 이체 차단
// flagged: false → 정상 처리 가능
// reason: "OFAC_SANCTIONED" | "DARKNET_MARKET" | ...

IssuerService에서는 transfer() 호출 전에 수신자 주소를 screenAddress()로 먼저 검증하고, flagged: true이면 이체를 중단한다. 이 두 단계(AML 스크리닝 → Travel Rule 포함 전송)가 VASP 규제 준수의 핵심 흐름이다.

TravelRuleData 타입 — 각 필드가 의미하는 것

슬라이드의 TravelRuleData는 Travel Rule 이행에 필요한 최소 정보다. originator(보내는 쪽)와 beneficiary(받는 쪽) 각각 3개 필드를 담는다. 

interface TravelRuleData {
  originator:  { name: string; accountId: string; vasp: string; };
  beneficiary: { name: string; accountId: string; vasp: string; };
}
필드예시의미
name"홍길동"실명 — KYC 인증된 법적 이름
accountId"kyobo-user-0042"해당 VASP 내 계정 식별자
vasp"KYOBO-VASP-KR"VASP 식별 코드 (FATF 등록 명칭)

수취 VASP는 이 정보를 받아 자체 AML 정책으로 검증한 뒤 이체를 수락하거나 거부한다. 전달 시 평문으로 보내지 않고 VASP 간 암호화 채널(TRISA, VerifyVASP 등 프로토콜)을 통해 전송한다.

idempotencyKey — 왜 필수인가

네트워크 장애로 응답이 없을 때 같은 요청을 재시도하면 TX가 두 번 전송될 수 있다. VASP는 idempotencyKey를 캐시해두고 같은 키로 두 번째 요청이 오면 새 TX를 만들지 않고 첫 번째 결과를 그대로 반환한다. 값으로는 비즈니스 고유 키(activityId, requestId 등)를 쓴다 — UUID면 충분하다.

VASPTransactionReceipt — status 상태어 주의점

status: 'pending' | 'submitted' | 'confirmed' | 'failed'는 VASP가 정의한 외부 상태어다. 우리 내부 상태머신(TxStateMachineService)의 상태어와 이름이 다를 수 있다.

VASP 상태어 (외부)내부 TxStatus의미
pendingPENDINGTX mempool에 있음, 블록 미채굴
submittedSUBMITTEDVASP가 TX를 RPC에 전송함
confirmedCONFIRMED블록 채굴 확인 완료
failedFAILED실패 — 종단 상태

주의 — 내부 TxStatus에는 REQUESTED가 따로 있다. "요청 생성, VASP 전송 전" 상태로, 외부 VASP 응답에는 대응 상태어가 없다. VASP의 'pending'은 REQUESTED와 전혀 다른 개념 — 이미 TX가 mempool에 들어간 상태다. REQUESTED를 'pending'이라고 불렀을 때 의미가 불명확해서 바꾼 것이고, VASP의 'pending'은 블록체인 업계 표준 용어라 수정 대상이 아니다.

파트너 VASP가 바뀌면 상태어 매핑이 달라질 수 있다. VaspTxClientAdapter가 이 변환을 담당하기 때문에 상태어가 바뀌어도 내부 로직은 수정하지 않는다.

슬라이드에서 생략된 코드 — transfer() / screenAddress()

슬라이드 오른쪽 callout의 AML·Travel Rule 설명은 공간 부족으로 요약만 했다. 실제 구현은 ExternalVASPAdapter.ts에 있다.

transfer() — Travel Rule 포함 이체 (ExternalVASPAdapter.ts:72)

async transfer(req: TransferRequest): Promise<TransferResult> {
  const payload = {
    from: req.from, to: req.to,
    amount: req.amount.toString(),
    tokenAddr: req.tokenAddr,
  };

  // Travel Rule — 특금법 의무 (100만원 상당 이상 이체)
  if (req.travelRuleData) {
    payload['travelRule'] = req.travelRuleData;  // VASP가 수취 VASP에 전달
  }

  const res = await this._request('POST', '/transfers', payload);
  return { txHash: res['txHash'], status: res['status'], fee: BigInt(res['fee']) };
}

travelRuleData가 있을 때만 payload에 포함한다. 100만원 미만 이체는 travelRuleData 없이 그냥 전송하면 되고, VASP가 금액을 판단해서 필요 시 거부한다.

screenAddress() — AML 블랙리스트 체크 (ExternalVASPAdapter.ts:103)

async screenAddress(address: string): Promise<{ flagged: boolean; reason?: string }> {
  const res = await this._request('GET', `/aml/screen/${address}`);
  return { flagged: res['flagged'], reason: res['reason'] };
}

VASP가 내부적으로 Chainalysis 등 외부 AML API를 호출한다. 우리 코드는 주소만 넘기고 결과(flagged)만 받는다. flagged: true면 IssuerService에서 이체·발행을 중단한다.

Phase 1에서 transfer()는 실제로 호출하지 않는다 — NFT 발행(mint)은 이체가 아니기 때문. screenAddress()도 현재는 선택적이고, Phase 2+ 실제 이체가 들어올 때 필수화된다.

Slide 7 — VaspTxClientAdapter (1/2) — 왜 필요한가

왜 두 단계 추상화인가

레이어가 두 개인 이유는 사용하는 주체가 다르기 때문이다. 

IssuerService
    ↓ IVASPAdapter          (비즈니스 언어)
ExternalVASPAdapter
    ↓ VaspTxClient          (TX 기계 언어) ← VaspTxClientAdapter가 번역
TxStateMachineService

IVASPAdapter — IssuerService가 쓰는 비즈니스 언어

submitTransaction, transfer, createWallet, screenAddress — "VASP가 제공하는 서비스 전체"를 표현한다. IssuerService는 이 인터페이스만 알면 VASP 파트너가 누구인지 몰라도 된다.

VaspTxClient — TxStateMachineService가 쓰는 TX 기계 언어

submitMint, getStatus, resubmitWithGasBump — TX 하나의 생명주기 관리에만 집중한다.

둘을 합치면 안 되는 이유

TxStateMachineService에 IVASPAdapter를 직접 주입하면 TX 상태 추적기가 createWallet, screenAddress, transfer까지 알아야 한다. TX 생명주기와 전혀 관계없는 것들이다 — SRP 위반.

VaspTxClientAdapter가 하는 번역

TxStateMachine 언어IVASPAdapter 언어
submitMint(to, tokenId, ...)submitTransaction({ method: 'mint', args: [...] })
getStatus() → 'confirmed'getTransferStatus() → 'completed' 번역
resubmitWithGasBump()Phase 3 구현 예정

Phase 3 교체 시 실용적 이유

ExternalVASPAdapter → KyoboVASPAdapter로 교체되면 상태어가 완전히 달라질 수 있다. VaspTxClientAdapter가 그 번역을 혼자 흡수하기 때문에 TxStateMachineService는 손댈 필요가 없다.

정리하면: IVASPAdapter는 VASP 파트너 교체를 흡수, VaspTxClientAdapter는 언어 차이를 흡수 — 두 가지 변경 이유가 독립적이기 때문에 레이어가 분리된 것이다.

그럼 IssuanceStatus는 뭔가

IssuanceStatus는 이 레이어들보다 한 단계 더 위의 순수 비즈니스 도메인 상태다. "교보 발행 요청이 어디까지 왔는가"를 나타내며 issuance_requests 테이블에 저장된다. 

IssuanceStatus   → 발행 요청의 비즈니스 상태  (issuance_requests 테이블)
TxStatus         → 블록체인 TX의 기술 상태    (mint_requests 테이블)
VaspTxClient     → TX 실행 인터페이스
IVASPAdapter     → VASP 서비스 인터페이스

각 레이어의 상태는 서로 다른 관점을 표현한다.

상태 타입관점예시
IssuanceStatus비즈니스 — 발행 요청이 완료됐는가REQUESTED → SUBMITTED → CONFIRMED
TxStatus기술 — TX가 블록체인 어디에 있는가PENDING → MINED → CONFIRMED
TransferResult.statusVASP 외부 — VASP API 응답 상태어pending → completed → failed

이 세 상태는 TxTransitionBridge가 동기화시킨다. TX가 CONFIRMED되면 발행 요청(IssuanceStatus)도 CONFIRMED로 전이시키는 역할이다. IVASPAdapter를 "비즈니스 인터페이스"라고 한 건 VaspTxClient(TX 기계어)보다 상위 레벨이라는 의미였고, IssuanceStatus는 그보다 한 단계 더 위다.

Slide 9 — 레이어 전체 조립도

다이어그램이 두 개로 나뉜다. ① TX 제출 경로와 ② 확정 수신 경로다.

① TX 제출 경로 — NFT 발행 요청이 체인에 전달되는 흐름

유저가 NFT 발행을 요청하면 IssuerService가 TxStateMachineService.submitMintRequest()를 호출한다. 이 순간부터 아래로 내려가면서 각 레이어를 통과한다.

  1. TxStateMachineService — "mint 요청이 들어왔다. VASP에 TX를 보내야 한다." VaspTxClient.submitMint()를 호출한다.
  2. VaspTxClientAdapter (변환 브릿지) — submitMint(to, tokenId, amount)를 IVASPAdapter.submitTransaction({ method: 'mint', args: [...] })로 번역한다. TxStateMachineService는 이 번역 과정을 모른다.
  3. IVASPAdapter → ExternalVASPAdapter — 인터페이스를 통해 실제 구현체인 ExternalVASPAdapter.submitTransaction()이 호출된다.
  4. ExternalVASPAdapter → VASP REST API — POST /transactions를 외부 VASP 서버에 전송한다. VASP가 실제로 TX에 서명하고 블록체인 노드에 브로드캐스트한다.
  5. VASP REST API → txHash 반환 — VASP가 TX를 mempool에 넣은 뒤 txHash를 응답으로 돌려준다.
  6. TxStateMachineService (맨 아래 박스) — txHash를 받아 DB에 저장하고 상태를 SUBMITTED로 전이한다. "TX를 VASP에 위탁했고 txHash를 알고 있다"는 상태다.

① 경로에서 TxStatus 전이: REQUESTED (요청 생성) → SUBMITTED (txHash 확보, VASP 위탁 완료). 이 시점까지가 ① 경로의 전부다. 블록 채굴 여부는 아직 모른다.

② 확정 수신 경로 — 블록에 실제로 채굴됐다는 것을 어떻게 아는가

TX를 보낸 것과 그 TX가 블록에 확정됐다는 것은 별개다. Phase 1에서 확정을 수신하는 경로는 두 가지다.

정상 경로 — NFT_ISSUED Webhook

  1. VASP가 TX를 브로드캐스트한 뒤 블록에 채굴되면 NFT_ISSUED Webhook을 우리 서버로 콜백한다.
  2. WebhookServer가 이를 수신해서 Redis Streams에 메시지를 적재한다. 바로 처리하지 않고 큐에 넣는 이유는 처리 실패 시 재시도가 가능해야 하기 때문이다.
  3. NFTIssuedProcessor가 Redis Stream에서 메시지를 꺼내 처리한다.
  4. LedgerService가 두 가지를 동시에 처리한다.
    • creditNFT() — user_nft_holdings 테이블에 NFT 보유량 기록.
    • updateMintRequestConfirmed() — TxStateMachineService.handleMined() → handleConfirmed() 호출 → TxStatus SUBMITTED → MINED → CONFIRMED 전이. TxTransitionBridge가 연쇄적으로 MintStatus·IssuanceStatus도 CONFIRMED로 동기화한다.

Webhook 경로 TxStatus 전이: SUBMITTED → MINED → CONFIRMED — NFTIssuedProcessor 내부에서 완결. ChainEventListener 불필요.

폴백 경로 — ChainEventListener (Webhook 누락 시)

VASP Webhook이 네트워크 장애로 안 오거나 누락될 수 있다. 이 경우를 대비해 ChainEventListener가 RPC 노드를 직접 폴링하면서 이벤트를 감지한다.

  1. ChainEventListener — ethers.js WebSocket으로 블록체인 이벤트를 실시간 구독한다. Issued 이벤트가 감지되면 핸들러를 호출한다.
  2. IssuanceConfirmHandler — 이벤트를 받아 TxStateMachineService.handleMined() → handleConfirmed()를 순서대로 호출한다.
  3. TxStateMachineService — TxStatus를 SUBMITTED → MINED → CONFIRMED로 전이시킨다. TxTransitionBridge가 이 전이 이벤트를 수신해서 MintStatus·IssuanceStatus도 CONFIRMED로 동기화한다.

폴백 경로 TxStatus 전이: SUBMITTED → MINED → CONFIRMED — Webhook 경로와 동일한 결과. 어느 경로든 수렴점이 같다.

정상 경로와 폴백 경로가 둘 다 동시에 동작한다

Phase 1에서 두 경로는 공존한다. Webhook이 정상으로 오면 LedgerService가 먼저 원장을 업데이트하고, ChainEventListener는 멱등성 처리로 중복을 걸러낸다. Webhook이 누락되면 ChainEventListener가 폴백으로 커버한다. 어느 쪽이든 결국 원장과 issuance_requests 상태가 CONFIRMED로 수렴한다.

슬라이드에 나오는 상태값은 모두 TxStatus 기준이다

다이어그램에서 보이는 SUBMITTED, MINED, CONFIRMED는 전부 TxStatus — 블록체인 TX 추적용 기술 상태다. 그런데 실제 시스템에는 상태 레이어가 세 개다.

  • TxStatus — TX가 체인에서 어디까지 왔는가 (기술 레이어)
  • MintStatus — NFT가 원장에 기록됐는가 (원장 레이어)
  • IssuanceStatus — 발행 요청 비즈니스가 끝났는가 (도메인 레이어)

이 세 레이어를 동기화시키는 컴포넌트가 TxTransitionBridge다. TxStatus가 전이될 때마다 TxTransitionBridge가 MintStatus와 IssuanceStatus를 따라 업데이트한다. 단, IssuanceStatus는 모든 전이마다 동기화되지 않는다 — CONFIRMED와 FAILED일 때만 반영된다.

TxStatus MintStatus IssuanceStatus
SUBMITTED SUBMITTED — (변경 없음)
MINED MINED — (변경 없음)
CONFIRMED CONFIRMED CONFIRMED ✓
FINALIZED FINALIZED — (변경 없음)
FAILED FAILED FAILED ✓
PENDING — (skip) — (변경 없음)

비즈니스 레이어(IssuanceStatus)는 중간 과정에는 관심 없다 — "발행이 확정됐냐, 실패했냐" 두 가지만 본다. 그래서 SUBMITTED·MINED·FINALIZED 전이는 IssuanceStatus를 건드리지 않는다.
