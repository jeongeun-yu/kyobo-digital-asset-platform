Slide 4 — 콜백 누락 경로 전체 분석

이 표는 Webhook이 유실될 수 있는 원인을 위치별로 분해한 겁니다. 각 행을 하나씩 짚어보겠습니다.
  • 네트워크 단절 — VASP가 발송했지만 KYOBO 서버까지 오는 구간에서 패킷이 유실됩니다. 우리 서버에는 아무것도 도착하지 않으므로 감지 자체가 불가합니다.
  • KYOBO 서버 재시작 — "수신 직후 처리 전" — Webhook HTTP 요청이 소켓까지는 도착했지만, 애플리케이션이 파싱·검증·Redis 적재를 실행하기 전에 서버 프로세스가 크래시된 경우입니다. TCP 레벨에서는 수신이 됐지만 DB나 Redis에 기록이 전혀 남지 않습니다. 그래서 영향이 "수신 기록 없음"입니다.
  • VASP 발송 버그 — VASP 내부에서 Webhook 자체를 발송하지 않은 경우입니다. KYOBO 입장에서는 아무 신호도 오지 않으니 감지가 불가합니다.
  • 처리 큐 포화 — 수신은 됐지만 Redis Stream이나 처리 큐가 꽉 차서 메시지 적재에 실패하는 경우입니다. 큐 길이를 모니터링하면 조건부로 감지할 수 있습니다.
  • DB 트랜잭션 실패 — 처리는 진행됐지만 마지막 상태 업데이트 DB 쓰기가 실패해 롤백된 경우입니다. PENDING이 유지되므로 폴링이 결국 잡아냅니다.
  • 파트너사 SLA 미달 — VASP 처리 자체가 지연돼 Webhook 발송이 늦어지는 경우입니다. 우리가 10분 초과 PENDING을 폴링 대상으로 설정해두면 감지 가능합니다.

공통 패턴 — 원인이 어디에 있든 KYOBO DB에는 항상 PENDING 상태가 남습니다. 이 상태가 임계 시간 이상 지속되면 "누락"으로 판단할 수 있고, 그게 폴링 채널의 존재 이유입니다.

Slide 9 — pollStaleRequests 알고리즘 설계 (1/2)

queryEvents()와 pollStaleRequests()가 비슷해 보일 수 있는데, 완전히 다른 함수입니다.
  • queryEvents() — IBlockchainAdapter 인터페이스 메서드입니다. ChainEventListener가 서비스 재시작 시 호출해서 특정 블록 범위의 온체인 이벤트(Issued 등)를 RPC로 직접 조회합니다. 방향은 블록체인 → 우리 시스템이고, 목적은 서비스 다운 중 놓친 온체인 이벤트 복구입니다.
  • pollStaleRequests() — TxStateMachineService 메서드입니다. DB에서 10분 초과 PENDING/SUBMITTED TX를 꺼내 VASP REST API에 상태를 직접 조회합니다. 방향은 우리 시스템 → VASP이고, 목적은 Webhook 누락된 TX 상태 동기화입니다.

조회 대상이 다릅니다 — queryEvents()는 블록체인 RPC, pollStaleRequests()는 VASP REST API. 트리거도 다릅니다 — queryEvents()는 재시작 시 1회, pollStaleRequests()는 스케줄러 5분 주기.

헷갈리면 택배 비유로 생각하세요.
  • pollStaleRequests() — "내가 보낸 택배 잘 도착했어?" — 택배사(VASP)에 전화해서 내 운송장 번호로 배송 상태 확인. 우리 DB에 있는 미완성 TX 목록에서 출발해서 VASP에 "이 TX 어떻게 됐어?" 질문합니다. DB에 PENDING TX가 없으면 아무것도 안 합니다.
  • queryEvents() — "오늘 우리 집에 배달된 택배가 있어?" — 블록체인에 직접 물어봅니다. "X블록~Y블록 사이에 우리 컨트랙트에서 Issued 이벤트 발생한 거 다 줘." TX 기준이 아니라 블록 범위 기준입니다. 서비스가 꺼져 있던 1시간 동안 TX를 하나도 제출 안 했어도, 그 시간에 온체인에서 발생한 이벤트를 다 가져옵니다.

queryEvents() 블록 범위와 컨트랙트 필터링

그러면 어디 블록부터 어디 블록까지 뒤지는지, 그리고 전체 블록체인 중 어떻게 우리 것만 골라내는지 설명하겠습니다.
  • 블록 범위 — fromBlock은 stateStore.getLastProcessedBlock(), 즉 마지막으로 처리한 블록입니다. toBlock은 adapter.getBlockNumber(), 현재 블록입니다. 서비스가 꺼져 있던 구간이 그대로 범위가 됩니다. RPC 과부하 방지를 위해 1000블록씩 청크로 나눠서 조회합니다.
  • 우리 트랜잭션 식별 — contract.addr(우리 NFT 컨트랙트 주소)와 eventName('Issued')으로 필터링합니다. 블록체인 전체를 뒤지는 게 아니라 RPC 레벨에서 이 컨트랙트 주소 + 이벤트 시그니처로 좁혀서 조회합니다. 이 두 값은 index.ts에서 ChainEventListener 생성 시 NFT_CONTRACT_ADDR와 ['Issued']로 주입됩니다.

_dispatch()에서 한 번 더 h.contractAddr === event.contractAddr로 핸들러 레벨 필터링도 합니다. RPC + 핸들러 두 단계로 우리 이벤트만 처리합니다.

Slide 10 — pollStaleRequests 알고리즘 설계 (2/2)

폴링 대상 조건에 PENDING뿐만 아니라 SUBMITTED도 포함되어 있습니다. SUBMITTED에서 고착되는 시나리오를 설명하겠습니다.
  • SUBMITTED 상태의 의미 — submitMint()가 성공해서 VASP로부터 txHash를 받고 DB에 SUBMITTED로 저장까지 완료된 상태입니다. 즉, 우리 시스템은 요청을 넘겼고 txHash도 알고 있습니다.
  • 고착 시나리오 — VASP가 txHash는 발급했지만 실제 mempool 브로드캐스트에 실패하거나, 브로드캐스트는 했지만 PENDING 콜백을 보내지 못한 경우입니다. 이 경우 우리 DB는 SUBMITTED에 멈춰 있고 아무 후속 콜백도 오지 않습니다.
  • 코드 상 증거 — handleMined()가 PENDING뿐 아니라 SUBMITTED도 허용하는 이유가 여기 있습니다. PENDING 콜백이 누락된 채 MINED 콜백만 오는 경우 SUBMITTED → MINED 직행을 처리해야 하기 때문입니다.
  • 폴링의 역할 — 10분 초과 SUBMITTED를 폴링이 잡아 VASP에 직접 상태를 조회하고, confirmed면 MINED → CONFIRMED로 밀어줍니다.

PENDING 고착은 "TX가 mempool에 있는데 콜백이 안 온" 경우, SUBMITTED 고착은 "TX가 mempool에 들어갔는지조차 모르는" 더 불확실한 경우입니다. 폴링이 두 케이스를 모두 커버합니다.

부록 — issuance-status 통합 테스트 beforeAll 상세 해석

경로: internal/integration/__tests__/issuance-status.integration.test.ts

beforeAll(() => {
  pool = new Pool({ connectionString: getPgUrl() });          // ①
  repo = new PgIssuanceRequestRepository(pool);               // ②

  txRepo = new PgTxRepository(pool);                         // ③
  const stubVasp = {                                         // ④
    async submitMint()          { return { txHash: '0x0' }; },
    async getStatus()           { return { status: 'pending' as const }; },
    async resubmitWithGasBump() { return { txHash: '0x0' }; },
  };
  txStateMachine = new TxStateMachineService(txRepo, stubVasp);  // ⑤

  const ledgerService = new LedgerService(                   // ⑥
    new PgDatabaseClient(pool),
    new StubCoreBankingAdapter(),
  );
  const bridge = new TxTransitionBridge(ledgerService, repo); // ⑦
  bridge.attach(txStateMachine);                              // ⑧

  handler = new IssuanceConfirmHandler(                       // ⑨
    '0xCONTRACT', txRepo, txStateMachine,
  );
});

① Pool — 단일 커넥션 풀 공유

getPgUrl()는 globalSetup이 띄운 Testcontainers PostgreSQL 컨테이너 URL을 읽어온다. 이 pool 하나를 아래 모든 Repository·Client가 공유한다. 테스트 종료 후 afterAll에서 pool.end()로 연결을 닫는다.

② PgIssuanceRequestRepository — issuance_requests 테이블 담당

비즈니스 레이어 상태(REQUESTED → SUBMITTED → CONFIRMED/FAILED)를 issuance_requests 테이블에 기록하는 Repository다. 이 테스트의 주된 검증 대상이다.

③ PgTxRepository — tx_mint_requests 테이블 담당

TX 상태머신 레이어(SUBMITTED → PENDING → MINED → CONFIRMED → FINALIZED)를 tx_mint_requests 테이블에 기록하는 Repository다. IssuanceConfirmHandler가 온체인 이벤트를 받으면 이 repo에서 txHash로 요청을 조회한다.

④ stubVasp — 인라인 페이크 VASP

블록체인에 실제 TX를 보내지 않는다. submitMint()는 0x0을 반환하고, getStatus()는 항상 pending을 반환한다. 이 테스트에서 VASP는 단지 TxStateMachineService를 초기화하는 데 필요한 의존성일 뿐, 실제로 호출되지 않는다.

tx-status 테스트의 ControlledVaspClient와 역할이 같다. 둘 다 "VASP를 테스트 범위 밖으로 격리"하는 패턴.

⑤ TxStateMachineService — TX 상태 전이 엔진

txRepo(PgTxRepository)와 stubVasp를 주입해 생성한다. 상태 전이가 발생할 때마다 transition 이벤트를 발행(EventEmitter)한다. 아래 TxTransitionBridge가 이 이벤트를 구독한다.

⑥ LedgerService — 원장 기록 담당

PgDatabaseClient(pool): PostgreSQL에 직접 쓰는 DB 클라이언트.
StubCoreBankingAdapter: 코어뱅킹 시스템 연동을 빈 구현체로 대체. 이 테스트에서 코어뱅킹 잔액 차감은 검증하지 않는다.

CONFIRMED 전이 시 user_nft_holdings 테이블에 보유 수량을 기록하는 것이 LedgerService의 역할이다.

⑦ TxTransitionBridge — TX 전이 → Issuance 동기화 연결부

TxStateMachine의 상태 전이 이벤트를 받아 issuance_requests 상태를 동기화하는 브릿지다. 두 Repository를 알고 있다:

  • ledgerService: CONFIRMED 전이 시 원장 기록
  • repo(PgIssuanceRequestRepository): IssuanceStatus 업데이트

⑧ bridge.attach(txStateMachine) — Observer 연결

txStateMachine의 EventEmitter에 TxTransitionBridge를 구독자로 등록한다. 이 한 줄로 TX 레이어 전이가 자동으로 Issuance 레이어에 전파된다.

txStateMachine 전이bridge가 자동으로 수행하는 것
→ CONFIRMEDissuance_requests CONFIRMED + user_nft_holdings 기록
→ FAILEDissuance_requests FAILED

[9] 테스트에서 TxStatus·MintStatus·IssuanceStatus 세 레이어가 동시에 CONFIRMED로 전이되는 것이 가능한 이유가 바로 이 attach() 한 줄이다.

⑨ IssuanceConfirmHandler — 온체인 Issued 이벤트 수신

컨트랙트 주소('0xCONTRACT'), txRepo, txStateMachine을 주입받는다. 실제 운영에서는 ChainEventListener가 온체인 Issued 이벤트를 감지하면 이 핸들러를 호출한다. 테스트에서는 handler.handle(event)를 직접 호출해 시뮬레이션한다.

핸들러 내부 흐름: txHash로 txRepo 조회 → txStateMachine.handleMined() 또는 handleConfirmed() 호출 → TxTransitionBridge를 통해 Issuance 레이어 동기화.

전체 객체 연결 구조

Pool (PostgreSQL)
 ├── PgIssuanceRequestRepository (repo)  ─────────────────────┐
 ├── PgTxRepository (txRepo)                                  │
 │    └── TxStateMachineService (txStateMachine)              │
 │         │  EventEmitter: 'transition' 이벤트 발행           │
 │         └── [attach] ──→ TxTransitionBridge ──────────────┘
 │                           │  transition 구독
 │                           ├── LedgerService (원장 기록)
 │                           │    └── PgDatabaseClient
 │                           │    └── StubCoreBankingAdapter
 │                           └── repo.updateStatus() (IssuanceStatus 동기화)
 │
 └── IssuanceConfirmHandler
      └── txRepo.findByTxHash() → txStateMachine.handleMined/Confirmed()

beforeAll은 동기(async 없음)다. Pool·Repository 생성은 연결이 아닌 설정만 하므로 비동기가 필요 없다. 실제 DB 연결은 첫 쿼리 실행 시 맺어진다.

테스트 케이스 [1]~[9] — 무엇을 검증하려는가

코드 레벨이 아닌 의도 중심으로 읽는다. beforeEach에서 매 테스트마다 테이블 전체를 TRUNCATE하므로 각 케이스는 완전히 독립적이다.

케이스검증 목표왜 중요한가
[1] 생성 repo.create() 호출 시 issuance_requests에 REQUESTED 행이 실제로 생성되는가 Repository가 DB에 올바르게 INSERT하는지 가장 기초 검증. 이게 안 되면 이후 모든 테스트 전제가 무너진다.
[2] REQUESTED → SUBMITTED updateStatus()가 txHash를 함께 기록하는가 VASP에 TX를 제출한 뒤 txHash를 DB에 기록해야 이후 콜백·폴링에서 이 TX를 추적할 수 있다. txHash 누락 시 CONFIRMED 경로가 완전히 막힌다.
[3] IssuanceConfirmHandler 온체인 Issued 이벤트(txHash + blockNumber)를 받으면 issuance_requests가 CONFIRMED로 전이되는가 IssuanceConfirmHandler는 TX 레이어(tx_mint_requests)와 Issuance 레이어(issuance_requests) 사이의 연결 고리다. 이 핸들러가 없으면 블록체인 이벤트가 비즈니스 레이어에 도달하지 못한다.
[3-b] 멱등성(핸들러) 해당 txHash를 가진 tx_mint_requests가 없을 때 핸들러가 에러 없이 조용히 종료하는가 온체인 이벤트는 중복 수신될 수 있다. 대응하는 레코드가 없을 때 예외를 던지면 컨슈머 전체가 멈춘다. 조용한 종료가 맞다.
[4] SUBMITTED → FAILED VASP TX 실패 콜백(VASP_TX_FAILED) 수신 시 txHash로 요청을 찾아 FAILED로 전이하고 사유를 기록하는가 실패 경로의 DB 기록이 완전한지 검증. failReason이 없으면 운영자가 실패 원인을 알 수 없다.
[5] 종단 보호 — CONFIRMED CONFIRMED 이후 다시 FAILED로 전이 시도하면 예외가 발생하는가 이미 원장에 반영된 NFT 발행을 FAILED로 되돌리면 user_nft_holdings와 issuance_requests가 불일치한다. DB 레벨에서 막아야 한다.
[6] 종단 보호 — FAILED FAILED 이후 SUBMITTED로 전이 시도하면 예외가 발생하는가 실패한 요청을 다시 진행 중 상태로 되돌리면 중복 발행이 발생할 수 있다. 종단 상태에서 어떤 전이도 허용하지 않아야 한다.
[7] findPending 멱등성 동일 사용자·이벤트·토큰에 대해 진행 중인 요청(REQUESTED/SUBMITTED)이 있으면 감지되고, CONFIRMED 이후엔 감지되지 않는가 동일 사용자가 동시에 두 번 요청을 보냈을 때 중복 발행을 방지하는 핵심 로직이다. findPending이 CONFIRMED 이후에도 반환하면 정상 완료된 요청이 "진행 중"으로 오인된다.
[8] findByTxHash txHash가 없는 요청(REQUESTED 상태)은 조회되지 않고, txHash가 기록된 요청(SUBMITTED 이후)은 정확히 조회되는가 VASP 콜백·폴링은 txHash를 키로 요청을 찾는다. txHash 미설정 행이 잘못 반환되면 엉뚱한 요청이 CONFIRMED/FAILED로 전이된다.
[9] NFT_ISSUED → 3레이어 동시 CONFIRMED Redis Stream의 NFT_ISSUED 메시지를 NFTIssuedProcessor가 처리했을 때, tx_mint_requests·mint_requests·issuance_requests 세 테이블이 동시에 CONFIRMED로 전이되고 user_nft_holdings에 잔액이 반영되는가 이 테스트 전체에서 가장 복잡한 케이스. NFTIssuedProcessor → PgNFTLedgerService → TxStateMachineService → TxTransitionBridge → issuance_requests까지 이어지는 전체 연결 고리가 한 번에 작동하는지 검증한다. 세 레이어 중 하나라도 CONFIRMED가 안 되면 원장 불일치 장애다.

[9] 데이터 준비가 복잡한 이유

[9]는 테스트 시작 전 4개 테이블에 데이터를 직접 INSERT한다. 각각의 이유:

  • user_wallet_mapping — NFTIssuedProcessor가 walletAddr → userId 역방향 조회를 하기 때문
  • tx_mint_requests — TxStateMachineService가 txHash로 상태 전이 대상을 찾기 때문
  • mint_requests — TxTransitionBridge가 MintStatus를 동기화하기 때문
  • issuance_requests — TxTransitionBridge가 IssuanceStatus를 동기화하기 때문

네 테이블이 모두 같은 txHash로 연결되어 있어야 하나의 이벤트가 전체 레이어를 관통한다.

await new Promise(r => setTimeout(r, 300))가 [3]과 [9]에 있는 이유: TxTransitionBridge는 EventEmitter를 통해 비동기로 issuance_requests를 업데이트한다. 300ms를 기다리지 않으면 아직 전이가 완료되기 전에 DB를 조회해 SUBMITTED가 나온다.
