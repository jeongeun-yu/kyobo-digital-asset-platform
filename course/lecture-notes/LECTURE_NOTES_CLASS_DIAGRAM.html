Kyobo DAP — 클래스 다이어그램 해설

6개 패키지 · Phase 1 구현 기준 · 각 클래스의 존재 이유와 관계

0다이어그램 읽는 법

관계 표기법

클래스 다이어그램에서 선의 종류가 관계의 의미를 결정합니다. 네 가지만 기억하면 됩니다.

표기관계의미예시
◁|..구현 (implements)인터페이스를 구체 클래스가 구현IVASPAdapter ◁|.. ExternalVASPAdapter
◁|—상속 (extends)부모 클래스를 자식이 확장AdapterDecorator ◁|— LoggingAdapterDecorator
◆—컴포지션 (has-a)생성자에서 주입받아 소유TxStateMachineService ◆— TxRepository
..>의존 (uses)메서드 내에서 일시적으로 사용TokenIssuerFactory ..> IssuerService

이 다이어그램의 범위

다이어그램에 있는 클래스는 모두 Phase 1에서 실제로 인스턴스가 생성되거나 주입되는 클래스입니다. 파일은 존재하지만 현재 wiring되지 않은 클래스(XRPLAdapter, KyoboVASPAdapter 등)는 제거했습니다.

또한 다이어그램의 메서드 목록은 외부에서 호출되는 핵심 public 메서드만 표시합니다. 실제 구현에는 private 메서드가 더 있습니다.

다이어그램의 목적 = 관계와 역할 파악. 완전한 API 레퍼런스가 아님

레이어 의존 방향

전체 구조를 보면 의존 방향이 한 방향입니다.

issuer-service (앱)
  └─ depends on ──▶ event-engine, vasp, core-banking, chain-adapters, compliance (패키지)
                         └─ 패키지끼리는 원칙상 서로 의존하지 않음

issuer-service가 모든 패키지를 알지만, 패키지들은 issuer-service를 모름 — 단방향 의존

1chain-adapters

IBlockchainAdapter — 블록체인 추상화 인터페이스

IBlockchainAdapter는 이 시스템이 블록체인에 대해 아는 전부입니다. EVM이든 XRPL이든 상관없이 이 인터페이스만 보고 코드를 작성합니다.

핵심 메서드는 세 가지입니다. mintNFT()는 NFT를 발행하고, queryEvents()는 컨트랙트 이벤트를 조회하고, getBlockNumber()는 현재 블록 높이를 반환합니다. Phase 1에서는 TX 실행을 VASP에 위탁하기 때문에 EVMAdapter의 mintNFT()는 직접 호출되지 않습니다. queryEvents()와 getBlockNumber()만 ChainEventListener가 폴링용으로 사용합니다.

인터페이스 분리 원칙 상위 레이어(issuer-service, event-engine)는 IBlockchainAdapter만 알면 됨 — 구체 체인 교체 시 상위 코드 수정 없음

EVMAdapter — EVM 구현체

Phase 1의 유일한 구현체입니다. 생성자에서 rpcUrl, chainId, privateKey를 받습니다. 내부적으로 ethers.js의 JsonRpcProvider와 Wallet을 사용합니다.

주목할 점은 Phase 1에서 EVMAdapter를 읽기 전용으로만 씁니다. TX 브로드캐스트는 ExternalVASPAdapter(외부 VASP)가 담당하고, EVMAdapter는 ChainEventListener가 블록을 폴링할 때만 씁니다.

Phase 3에서 KyoboVASPAdapter로 전환 시 EVMAdapter.sendTransaction()이 활성화됨 — 현재는 호출 안 됨

Decorator 패턴 — LoggingAdapterDecorator / RetryAdapterDecorator

Decorator 패턴은 기존 객체를 감싸서 기능을 추가합니다. AdapterDecorator가 추상 기반 클래스이고, 여기서 LoggingAdapterDecorator와 RetryAdapterDecorator가 파생됩니다.

실제 생성 순서는 이렇습니다. 안쪽부터 바깥쪽 순서입니다.

new LoggingAdapterDecorator(
  new RetryAdapterDecorator(
    new EVMAdapter({ rpcUrl, chainId, privateKey })
  )
)

이렇게 하면 호출이 들어올 때 Logging → Retry → EVMAdapter 순으로 통과합니다. EVMAdapter를 전혀 수정하지 않고 로깅과 재시도를 붙인 겁니다.

IBlockchainAdapter <|.. AdapterDecorator — Decorator도 IBlockchainAdapter를 구현하므로 상위 코드는 래핑 여부를 알 수 없음

2vasp

IVASPAdapter — VASP 추상화

IVASPAdapter는 VASP(Virtual Asset Service Provider)와 통신하는 인터페이스입니다. Phase 1에서는 외부 VASP에 TX 실행을 위탁합니다. 인터페이스를 사이에 두기 때문에 Phase 3에서 KyoboVASPAdapter로 교체해도 상위 코드는 그대로입니다.

submitTransaction()이 핵심입니다. NFT 민팅 TX를 VASP에 넘기면 VASP가 서명·브로드캐스트를 처리하고 txHash를 돌려줍니다.

TxStateMachineService — TX 상태머신

이 시스템에서 가장 중요한 클래스 중 하나입니다. tx_mint_requests 테이블의 상태를 관리하며, TX가 SUBMITTED → MINED → CONFIRMED → FINALIZED로 전이될 때마다 'transition' 이벤트를 emit합니다.

Node.js EventEmitter를 상속하기 때문에 TxTransitionBridge가 .on('transition', handler)로 구독할 수 있습니다. 이것이 두 테이블(mint_requests, issuance_requests) cascade 업데이트의 핵심입니다.

pollStaleRequests()는 STALE_MINUTES 이상 SUBMITTED 상태로 머문 TX를 찾아 PENDING으로 전이시킵니다. 스케줄러 또는 Admin HTTP로 호출됩니다.

메서드역할호출 시점
submitMintRequest()DB INSERT → VASP 브로드캐스트 → SUBMITTED 전이IssuerService.issueActivityNFT() 내부
handleMined()SUBMITTED/PENDING → MINED 전이IssuanceConfirmHandler, NFTIssuedProcessor
handleConfirmed()MINED → CONFIRMED 전이 + emithandleMined() 직후 연속 호출
pollStaleRequests()장기 미채굴 TX → PENDING 전이스케줄러 / Admin /admin/poll-stale

TxStateMachineService는 tx_mint_requests만 관리 — mint_requests·issuance_requests는 TxTransitionBridge가 cascade로 처리

VaspTxClientAdapter — TX 제출 어댑터

VaspTxClient 인터페이스의 구현체입니다. IVASPAdapter를 내부에 갖고, TX 제출에 특화된 메서드(submitMint, getStatus, resubmitWithGasBump)를 노출합니다.

왜 IVASPAdapter를 직접 쓰지 않고 VaspTxClientAdapter로 한 번 더 감쌌냐면, IVASPAdapter는 VASP의 전체 기능(지갑 생성, 이체 등)을 포함하는 넓은 인터페이스고, TxStateMachineService는 그 중 TX 제출 기능만 필요하기 때문입니다. 인터페이스 분리 원칙 적용입니다.

TxRepository / PgTxRepository

TxRepository 인터페이스를 통해 TxStateMachineService가 DB에 접근합니다. 구현체인 PgTxRepository는 PostgreSQL의 tx_mint_requests 테이블을 직접 다룹니다.

인터페이스를 사이에 두는 이유는 테스트 때 DB 없이 메모리 구현체로 교체할 수 있기 때문입니다.

3event-engine

WebhookServer

외부에서 들어오는 Webhook을 수신하는 HTTP 서버입니다. 세 가지 책임을 갖습니다. 첫째, HMAC-SHA256 서명 검증으로 위변조된 요청을 차단합니다. 둘째, 검증 통과 즉시 202를 응답해 발신자 timeout을 방지합니다. 셋째, 등록된 핸들러에 비동기로 위임합니다.

on(eventType, handler)가 this를 반환하기 때문에 체이닝 패턴으로 등록합니다.

webhookServer
  .on('ACTIVITY_ACHIEVED', webhookPublisher.createHandler())
  .on('NFT_ISSUED',        webhookPublisher.createHandler())
  .on('VASP_TX_FAILED',    async (payload) => { ... });

같은 eventType에 핸들러를 여러 개 등록할 수 있음 — 내부적으로 Map<string, Handler[]>로 관리, Promise.allSettled()로 병렬 실행

IdempotencyGuard / IdempotencyStore

중복 이벤트가 두 번 처리되지 않도록 막는 장치입니다. run(key, fn)을 호출하면 먼저 Redis에 key가 있는지 확인합니다. 이미 있으면 fn을 실행하지 않고 반환합니다. 없으면 key를 등록하고 fn을 실행합니다.

IdempotencyStore는 인터페이스이고 RedisIdempotencyStore가 구현체입니다. Redis의 SET key NX EX ttl 명령을 씁니다. NX(Not eXists) 옵션 덕분에 동시 요청이 와도 한 번만 처리됩니다.

SET NX EX key가 없을 때만 설정(NX) + TTL 자동 만료(EX) — 원자적 연산이라 race condition 없음

RedisStreamPublisher

Webhook 수신 후 Redis Streams에 이벤트를 적재합니다. 내부적으로 RedisStreamClient 인터페이스를 통해 XADD를 호출합니다.

WebhookPublishHandler는 RedisStreamPublisher와 IdempotencyGuard를 묶어서 "검증된 이벤트만 스트림에 넣는" 단일 핸들러 팩토리 역할을 합니다. createHandler()가 반환하는 함수를 WebhookServer에 등록합니다.

ConsumerGroupPool / ConsumerGroupWorker

ConsumerGroupWorker는 Redis Streams의 Consumer Group에서 메시지를 꺼내 처리하는 단위입니다. XREADGROUP으로 메시지를 가져오고, 처리 후 XACK로 확인합니다. 처리 실패 시 재시도하고, 재시도 횟수 초과 시 DLQ로 이동합니다.

ConsumerGroupPool은 여러 ConsumerGroupWorker를 관리하는 컨테이너입니다. Phase 1에서는 nft-consumers와 activity-consumers 두 그룹을 운영합니다. 같은 스트림을 두 그룹이 독립적으로 읽기 때문에 NFT_ISSUED 이벤트와 ACTIVITY_ACHIEVED 이벤트가 서로 간섭하지 않습니다.

Consumer Group처리 Processor대상 이벤트
nft-consumersNFTIssuedProcessorNFT_ISSUED
activity-consumersActivityProcessorACTIVITY_ACHIEVED

NFTIssuedProcessor / ActivityProcessor

두 클래스 모두 EventProcessor 인터페이스를 구현합니다. 인터페이스는 단 두 가지입니다. eventTypes는 이 Processor가 처리할 이벤트 타입 목록이고, process(msg)가 실제 처리 로직입니다.

NFTIssuedProcessor는 NFT_ISSUED 이벤트를 받아 NFTLedgerService를 호출해 민팅 결과를 원장에 기록합니다. ActivityProcessor는 ACTIVITY_ACHIEVED 이벤트를 받아 IActivityIssuer(=IssuerService)를 호출해 NFT 발행 파이프라인을 시작합니다.

ActivityProcessor → IActivityIssuer → IssuerService.issueActivityNFT() — 이것이 발행 파이프라인의 실제 진입점

DLQHandler

Dead Letter Queue 핸들러입니다. 재시도 횟수(retryCount ≥ 3)를 초과한 메시지를 kyobo:events:dlq 스트림으로 이동시킵니다. DLQ에 들어간 메시지는 자동으로 재처리되지 않으며 운영자가 수동으로 검토해야 합니다.

ChainEventListener

블록체인을 직접 폴링해 온체인 이벤트를 감지합니다. VASP 콜백(NFT_ISSUED Webhook)이 누락됐을 때의 폴백 경로입니다.

IBlockchainAdapter를 주입받아 블록체인 종류에 무관하게 동작합니다. 감지된 이벤트는 등록된 IEventHandler[]에 순서대로 전달됩니다. Phase 1에서는 IssuanceConfirmHandler와 ProcessedEventHandler 두 핸들러가 등록됩니다.

ChainEventListener는 Phase 1부터 항상 구동됨 — VASP 경로(Phase 2A)와 체인 직접 폴링(Phase 2B)이 동시에 작동하며, 둘 다 멱등 처리로 중복 실행 안전

4core-banking

ICoreBankingAdapter

Core Banking 시스템(Java 내부원장)과 통신하는 인터페이스입니다. getUserAccount()로 사용자 계좌 정보를 조회하고, notifyReward()로 NFT 발행 완료를 알리고, recordNftHolding()으로 NFT 보유 현황을 기록하고, recordAuditLog()로 감사 로그를 남깁니다.

Phase 1 구현체는 KyoboCoreBankingAdapter입니다. 내부적으로 InternalGatewayClient를 통해 Java 서비스의 HTTP API를 호출합니다.

InternalGatewayClient

Java 내부원장 서버에 HTTP 요청을 보내는 클라이언트입니다. baseUrl과 secret(HMAC 서명용)을 생성자에서 받습니다.

내부에 CircuitBreaker를 갖고 있어서 Java 서버가 연속으로 실패하면 회로를 열어 추가 요청을 차단합니다. Java 서버 장애가 Node.js 서비스까지 cascading failure로 번지는 것을 방지합니다.

CircuitBreaker

세 가지 상태를 순환합니다.

상태동작전이 조건
CLOSED정상 통과실패 누적 → OPEN
OPEN즉시 차단, 에러 반환timeout 경과 → HALF_OPEN
HALF_OPEN소수 요청만 통과 (탐색)성공 → CLOSED / 실패 → OPEN

CircuitBreaker는 core-banking 패키지 내부에 있어 InternalGatewayClient만 사용 — 외부에 노출 안 됨

LedgerService

mint_requests 테이블 단일 진입점입니다. createMintRequest(userId, policyId)로 새 발행 요청 레코드를 생성하고, updateMintRequest(id, patch)로 상태를 업데이트합니다. findByTxHash()로 txHash 기반 조회를 지원하고, recordProcessedEvent()로 온체인 이벤트 중복 처리를 방지합니다.

상태 전이 가드(VALID_TRANSITIONS)를 이 레이어에서 강제합니다. 잘못된 전이 시도 시 InvalidStateTransitionError를 throw합니다. DB 레벨이 아닌 애플리케이션 레벨에서 상태 무결성을 보장합니다.

ICoreBankingAdapter를 주입받아 상태 변경마다 recordAuditLog()를 호출합니다. audit_log는 이 경로로만 기록됩니다.

AuditLogService / ReconcileService

AuditLogService는 audit_log 테이블을 읽기 전용으로 조회하는 서비스입니다. verifyIntegrity()로 SHA-256 체인 체크섬을 검증하고, queryByResource() / queryByActor()로 감사 이력을 조회합니다. 쓰기는 Node.js에서 하지 않습니다.

audit_log 쓰기 경로는 단 하나입니다. Node.js → ICoreBankingAdapter.recordAuditLog() → KyoboCoreBankingAdapter → InternalGatewayClient(X-Internal-Secret 인증) → Java internal-ledger → DB. Java가 SHA-256 체인 체크섬을 계산해 append-only로 기록합니다. Node.js가 직접 audit_log 테이블에 쓰면 체크섬 체인이 깨집니다.

ReconcileService는 온체인 NFT 잔액과 DB user_nft_holdings가 일치하는지 주기적으로 검증합니다. 불일치 발견 시 알림을 보냅니다.

audit_log는 Java만 씀 — Node.js가 직접 INSERT하면 prev_checksum 체인이 깨져 감사 추적 무결성 파괴

5compliance

IKYCProvider

KYC(Know Your Customer) 상태를 조회하는 인터페이스입니다. getStatus(userId)와 verify(userId)를 노출합니다. Phase 1에서는 직접 wiring되지 않고, ISMSChecklist가 참조합니다.

ISMSChecklist — 정보보호 관리체계 자동 점검

금융회사의 ISMS(Information Security Management System) 요구사항을 자동으로 점검하는 클래스입니다. Phase 1에서 실제로 인스턴스가 생성되어 1시간마다 runAll()이 실행됩니다.

점검 항목은 온체인 컨트랙트 상태(contractCall), 감사 로그 최신성(queryLatestAuditLog) 등입니다. 실패 항목이 있으면 콘솔 에러로 출력합니다. Phase 2에서 DB 연동으로 고도화됩니다.

ISMSChecklist는 비즈니스 로직이 아닌 규제 대응 컴포넌트 — 실패해도 발행 파이프라인은 중단 안 됨

6issuer-service

TokenIssuerFactory

의존성 조립을 담당하는 팩토리입니다. chainAdapter, vaspAdapter, coreBanking, pool을 받아서 IssuerService, IssuanceConfirmHandler, TxStateMachineService, TxTransitionBridge, LedgerService를 한꺼번에 생성하고 연결합니다.

왜 팩토리가 필요한가? 이 클래스들 사이의 의존 관계가 복잡해서 index.ts에서 직접 조립하면 코드가 지저분해지기 때문입니다. 팩토리가 "이 모듈을 쓰려면 이렇게 조립하세요"를 캡슐화합니다.

factory.createNFTIssuer(nftIssuerAddr, conditionService) → { issuerService, confirmHandler, txStateMachine, txRepo, ledgerService }

IssuerService

NFT 발행 파이프라인의 오케스트레이터입니다. IActivityIssuer 인터페이스를 구현해서 ActivityProcessor에서 인터페이스로 호출됩니다.

issueActivityNFT()가 Phase 1 동기 구간 전체를 담당합니다. issuance_requests REQUESTED 생성 → mint_requests REQUESTED 생성 → TxStateMachineService.submitMintRequest() 호출 → SUBMITTED 직접 기록 → 반환. 이 시점 이후부터는 TxStateMachineService의 이벤트로 상태가 전이됩니다.

handleVaspTxFailed()는 VASP_TX_FAILED 웹훅 수신 시 직접 처리합니다. Redis Stream을 우회해서 즉시 issuance_requests를 FAILED로 전이합니다.

IssuancePolicyService발행 정책 조회 (tokenId, amount, 유효 기간)
EventConditionService이벤트 조건 충족 여부 판단 (걸음수 등)

IssuancePolicyService

이벤트 타입별 발행 정책을 DB에서 읽어오는 서비스입니다. 정책은 { tokenId, amount, validFrom, validTo } 형태입니다. 정책이 없으면 NoPolicyError를 던지고 발행이 거부됩니다.

EventConditionService

이벤트가 발행 조건을 만족하는지 판단합니다. Strategy 패턴을 씁니다. ActivityConditionStrategy는 걸음수 달성을 검사합니다. 추후 CouponConditionStrategy, PremiumConditionStrategy 등을 추가할 수 있습니다.

conditionService.evaluate(event, policy) → true/false — 조건 불충족 시 발행 요청 자체가 생성 안 됨

PgIssuanceRequestRepository

issuance_requests 테이블을 담당하는 리포지토리입니다. IIssuanceRequestRepository 인터페이스를 구현합니다. create(), findByTxHash(), updateStatus()가 핵심 메서드입니다.

TxTransitionBridge가 CONFIRMED/FAILED 전이 시 findByTxHash()로 해당 발행 요청을 찾아서 상태를 동기화합니다.

PgNFTLedgerService

NFTLedgerService 인터페이스의 구현체입니다. NFTIssuedProcessor로부터 호출받아 온체인 NFT 전송 이벤트를 처리합니다.

내부적으로 ICoreBankingAdapter를 주입받습니다. creditNFT() 호출 시 coreBanking.recordNftHolding()으로 Java internal-ledger에 보유 현황을 기록합니다. user_nft_holdings 테이블에 Node.js가 직접 쓰지 않습니다. Java가 소유하는 테이블입니다.

PgNFTLedgerService → coreBanking.recordNftHolding() → Java → user_nft_holdings — Node.js는 Java를 경유해야만 이 테이블에 쓸 수 있음

TxTransitionBridge

TxStateMachineService의 'transition' 이벤트를 구독해서 tx_mint_requests 상태 변화를 mint_requests(LedgerService)와 issuance_requests(IIssuanceRequestRepository)에 cascade 반영합니다. attach(txStateMachine)으로 구독을 등록합니다.

내부의 TX_TO_MINT 매핑이 핵심입니다. TxStatus → MintStatus 매핑인데, PENDING이 매핑에 없습니다. TX가 PENDING으로 전이되면 mint_requests와 issuance_requests는 SUBMITTED 그대로 유지됩니다.

CONFIRMED / FAILED 전이 시 ICoreBankingAdapter.recordAuditLog()를 호출합니다. coreBanking은 optional로 주입되지만, 프로덕션에서는 항상 주입됩니다.

TxStatus (emit)mint_requestsissuance_requests
SUBMITTED→ SUBMITTED (IssuerService 직접)— (IssuerService 직접)
PENDINGskip (매핑 없음)불변
MINED→ MINED불변
CONFIRMED→ CONFIRMED→ CONFIRMED ✅
FAILED→ FAILED→ FAILED
FINALIZED→ FINALIZED불변

SUBMITTED는 TxTransitionBridge가 아닌 IssuerService가 직접 씀 — submitMintRequest() 반환 전에는 txHash가 mint_requests에 없어서 Bridge의 findByTxHash()가 탐지 못하기 때문

IssuanceConfirmHandler

IEventHandler 인터페이스를 구현합니다. ChainEventListener가 온체인에서 Issued 이벤트를 감지하면 이 핸들러의 handle()이 호출됩니다.

내부에서 PgTxRepository로 txHash에 해당하는 tx_mint_request를 찾고, TxStateMachineService.updateStatus()로 MINED → CONFIRMED 전이를 트리거합니다. 이 전이 이벤트를 TxTransitionBridge가 수신해 mint_requests와 issuance_requests를 cascade 업데이트합니다. 이것이 Phase 2B(ChainEventListener 폴백) 경로입니다.

Phase 2A(VASP 콜백)와 Phase 2B(체인 직접 폴링) 모두 TxStateMachineService → TxTransitionBridge cascade로 수렴 — 중복 전이는 InvalidStateTransitionError catch로 멱등 처리

7Bootstrap — 모든 것이 어떻게 연결되는가

index.ts의 bootstrap()은 이 시스템의 모든 클래스를 한 곳에서 조립합니다. 조립 순서는 의존성 방향과 반대입니다. 내가 의존하는 것이 먼저 만들어져야 나를 만들 수 있습니다. 그래서 인프라 → 어댑터 → 유틸 → 서비스 → 파이프라인 순서로 생성됩니다.

이 섹션에서는 각 클래스가 어떤 관계로 연결되는지를 중심으로 봅니다. 단순히 "A를 B에 넘긴다"가 아니라 그 관계가 컴포지션인지, 구현인지, 이벤트 구독인지를 구분하는 것이 핵심입니다.

STEP 1 — 인프라 레이어

가장 먼저 만들어지는 것은 외부 시스템과의 연결 객체입니다. Redis(ioredis 인스턴스)와 Pool(pg.Pool 인스턴스)은 클래스가 아니라 그냥 생성된 연결 객체입니다. 이들은 여러 클래스에 주입(inject)됩니다.

const redis = new Redis(REDIS_URL);          // ioredis 연결
const pool  = new Pool({ connectionString: DATABASE_URL }); // pg 연결 풀

Redis와 Pool은 싱글턴처럼 하나만 만들어서 공유 — 각 서비스가 별도로 연결을 열면 DB 연결 수가 폭발함

STEP 2 — 어댑터 레이어: 외부 시스템 추상화

세 개의 어댑터가 생성됩니다. 모두 인터페이스를 구현(implements)하는 구체 클래스입니다. 상위 레이어는 이 인터페이스만 알면 됩니다.

클래스구현 인터페이스컴포지션 (has-a)주입받는 환경변수
EVMAdapter IBlockchainAdapter 내부: JsonRpcProvider, Wallet (ethers.js) RPC_URL, CHAIN_ID, OPERATOR_PRIVATE_KEY
ExternalVASPAdapter IVASPAdapter — VASP_API_URL, VASP_API_KEY
InternalGatewayClient — CircuitBreaker (컴포지션) CORE_BANKING_URL, CORE_BANKING_SECRET
KyoboCoreBankingAdapter ICoreBankingAdapter InternalGatewayClient (컴포지션) —

InternalGatewayClient는 KyoboCoreBankingAdapter에 컴포지션으로 들어갑니다. ICoreBankingAdapter를 구현하는 건 KyoboCoreBankingAdapter고, 실제 HTTP 호출을 담당하는 건 내부의 InternalGatewayClient입니다. 역할 분리입니다.

CircuitBreaker는 InternalGatewayClient 안에 컴포지션으로 숨어 있습니다. 외부에서는 Circuit Breaker의 존재를 모릅니다. Java 서버가 다운됐을 때 InternalGatewayClient.execute()가 내부적으로 차단합니다.

컴포지션 *-- 생성자에서 받아 필드에 저장 — 외부에서 교체 불가, 생명주기를 소유자가 관리

STEP 3 — 공통 유틸: DB 클라이언트 · 멱등성

PgDatabaseClient는 DatabaseClient 인터페이스를 구현합니다. Pool을 주입받아 query()와 transaction()을 wrapping합니다. LedgerService가 이 인터페이스를 통해 DB에 접근하므로, 테스트에서 인메모리 구현체로 교체할 수 있습니다.

멱등성 체계는 두 클래스로 구성됩니다. RedisIdempotencyStore가 IdempotencyStore 인터페이스를 구현하고, IdempotencyGuard가 이 인터페이스를 컴포지션으로 소유합니다. 상위 코드는 IdempotencyGuard.run(key, fn)만 호출하면 됩니다. Redis를 쓰는지 메모리를 쓰는지 몰라도 됩니다.

DatabaseClient <|.. PgDatabaseClient         ← 구현(implements)
IdempotencyStore <|.. RedisIdempotencyStore  ← 구현(implements)
IdempotencyGuard *-- IdempotencyStore        ← 컴포지션(has-a)

// 생성 순서
const pgDb      = new PgDatabaseClient(pool);
const idpStore  = new RedisIdempotencyStore(redis);
const idpGuard  = new IdempotencyGuard(idpStore, ttlSeconds=300);

STEP 4 — 조건 서비스: Strategy 패턴

이벤트 발행 조건 판단 로직은 Strategy 패턴으로 분리되어 있습니다. IConditionStrategy 인터페이스를 ActivityConditionStrategy가 구현하고, EventConditionService가 이 전략들을 컴포지션으로 관리합니다.

EventConditionService.registerStrategy(strategy)로 런타임에 전략을 추가할 수 있습니다. Phase 1에서는 ActivityConditionStrategy(걸음수 달성) 하나만 등록됩니다. 나중에 CouponConditionStrategy를 추가해도 IssuerService 코드를 전혀 수정하지 않습니다.

IConditionStrategy <|.. ActivityConditionStrategy  ← 구현
IConditionStrategy <|.. CouponConditionStrategy    ← 구현 (추후 추가)
EventConditionService *-- IConditionStrategy       ← 컴포지션 (전략 배열)

const conditionService = new EventConditionService();
conditionService.registerStrategy(new ActivityConditionStrategy());

Strategy 패턴: 알고리즘(조건 판단 방식)을 인터페이스 뒤에 캡슐화 — 새 이벤트 타입 추가 시 새 전략 클래스만 작성하면 됨

STEP 5 — TokenIssuerFactory: 발행 서비스 조립

이 시스템에서 가장 복잡한 조립이 여기서 일어납니다. TokenIssuerFactory는 IBlockchainAdapter, IVASPAdapter, ICoreBankingAdapter를 컴포지션으로 소유하고, createNFTIssuer() 호출 시 여러 서비스를 생성해서 내부적으로 연결한 뒤 반환합니다.

Factory가 생성하는 클래스들과 그 관계를 단계별로 따라가 보겠습니다.

5-1. 리포지토리 계층 — DB 직접 접근 담당

5-2. 서비스 계층 — 비즈니스 로직 담당

IssuancePolicyService는 IIssuancePolicyRepository를 컴포지션으로 소유합니다. 정책 조회가 필요하면 리포지토리에 위임합니다.

LedgerService는 DatabaseClient와 ICoreBankingAdapter를 컴포지션으로 소유합니다. mint_requests 테이블에 직접 쓰고, 상태 변경마다 ICoreBankingAdapter.recordAuditLog()를 호출해서 Java 내부원장에 감사 로그를 남깁니다.

5-3. TX 상태머신 — TxStateMachineService · VaspTxClientAdapter

VaspTxClientAdapter는 VaspTxClient 인터페이스를 구현하고, IVASPAdapter를 컴포지션으로 소유합니다. 왜 IVASPAdapter를 직접 쓰지 않고 한 번 더 감쌌냐면, TxStateMachineService가 필요한 기능은 TX 제출·조회뿐인데 IVASPAdapter는 지갑 생성·이체 등 더 넓은 기능을 포함하기 때문입니다. 인터페이스 분리 원칙입니다.

TxStateMachineService는 Node.js EventEmitter를 상속합니다. 이게 핵심입니다. 상태가 바뀔 때마다 emit('transition', { requestId, from, to })를 발생시킵니다. 다른 클래스는 이 이벤트를 구독(subscribe)해서 후속 처리를 합니다.

VaspTxClient    <|.. VaspTxClientAdapter  ← 구현
VaspTxClientAdapter *-- IVASPAdapter      ← 컴포지션

TxStateMachineService *-- TxRepository   ← 컴포지션 (tx_mint_requests CRUD)
TxStateMachineService *-- VaspTxClient   ← 컴포지션 (TX 제출·조회)
TxStateMachineService o-- WalletResolver ← 선택적 컴포지션 (지갑 주소 조회)

// TxStateMachineService extends EventEmitter
txStateMachine.emit('transition', { requestId, from: 'MINED', to: 'CONFIRMED' });
extends EventEmitter TxStateMachineService는 Node.js 이벤트 버스 역할 — 상태 전이마다 'transition' 이벤트를 발행, 구독자가 후속 처리
5-4. TxTransitionBridge — 이벤트 구독자

TxTransitionBridge는 LedgerService, IIssuanceRequestRepository, ICoreBankingAdapter를 컴포지션으로 소유합니다.

.attach(txStateMachine)을 호출하면 txStateMachine.on('transition', this._handler)로 이벤트를 구독합니다. 이후부터는 TxStateMachineService가 상태 전이를 emit할 때마다 Bridge가 자동으로 반응합니다.

Bridge의 역할은 tx_mint_requests 상태 변화를 mint_requests와 issuance_requests 두 테이블에 cascade 반영하는 것입니다. CONFIRMED 전이 시에는 ICoreBankingAdapter.recordNftHolding()도 추가로 호출합니다.

TxTransitionBridge *-- IIssuanceRequestRepository ← 컴포지션
TxTransitionBridge *-- ICoreBankingAdapter        ← 컴포지션
TxTransitionBridge ..> TxStateMachineService      ← attach()로 이벤트 구독

5-5. IssuerService — 발행 오케스트레이터

IssuerService가 소유하는 의존성은 7개입니다. 모두 컴포지션입니다. 이 클래스가 이 시스템에서 가장 많은 의존성을 가집니다.

5-6. IssuanceConfirmHandler — 체인 이벤트 → TX 상태 전이

IssuanceConfirmHandler는 IEventHandler 인터페이스를 구현합니다. ChainEventListener가 온체인 Issued 이벤트를 감지하면 이 핸들러의 handle()을 호출합니다.

내부에 TxStateMachineService와 TxRepository를 컴포지션으로 소유합니다. 이 두 가지가 필요한 이유는 명확합니다. txHash로 tx_mint_request를 찾아야 하고(TxRepository), 찾은 뒤 MINED → CONFIRMED 전이를 수행해야 하기 때문(TxStateMachineService)입니다. 이 전이가 emit을 발생시키고, Bridge가 받아서 cascade 업데이트합니다.

IEventHandler <|.. IssuanceConfirmHandler  ← 구현
IssuanceConfirmHandler *-- TxStateMachineService ← 컴포지션
IssuanceConfirmHandler *-- TxRepository          ← 컴포지션

// Phase 2B 호출 흐름
ChainEventListener.poll()
  → IssuanceConfirmHandler.handle({ txHash, blockNumber })  ← 호출
    → TxRepository.findByTxHash(txHash)                     ← 조회
    → TxStateMachineService.handleMined(requestId)          ← 호출
    → TxStateMachineService.handleConfirmed(requestId)      ← 호출
    → emit('transition', { from:'MINED', to:'CONFIRMED' })  ← 이벤트 발행
    → TxTransitionBridge._handler()                         ← 구독 수신
    → LedgerService.updateMintRequest()                     ← cascade
    → IIssuanceRequestRepository.updateStatus('CONFIRMED')  ← cascade

STEP 6 — NFT 원장 · Reconcile 서비스

PgNFTLedgerService는 Factory 밖에서 별도로 생성됩니다. NFT_CONTRACT_ADDR과 CHAIN_ID 환경변수를 받기 때문에 Factory 내부보다 index.ts 레벨에서 생성하는 것이 더 자연스럽습니다.

NFTLedgerService 인터페이스를 구현하고, ICoreBankingAdapter를 컴포지션으로 소유합니다. creditNFT()가 호출되면 로컬 DB를 직접 쓰지 않고 ICoreBankingAdapter.recordNftHolding()을 통해 Java 내부원장에 전달합니다. Java가 user_nft_holdings 테이블을 소유합니다.

NFTLedgerService <|.. PgNFTLedgerService   ← 구현
PgNFTLedgerService *-- ICoreBankingAdapter  ← 컴포지션

// creditNFT() 호출 경로 (Phase 2A — NFTIssuedProcessor 경유)
NFTIssuedProcessor.process(msg)
  → PgNFTLedgerService.creditNFT(wallet, tokenId, amount, txHash)  ← 호출
  → ICoreBankingAdapter.recordNftHolding(params)                   ← 위임
  → InternalGatewayClient HTTP POST /api/internal/users/nft-holdings
  → Java InternalLedgerService → user_nft_holdings INSERT

PgNFTLedgerService는 user_nft_holdings에 직접 INSERT하지 않음 — Node.js가 이 테이블에 직접 쓰면 Java의 NftHolding.addAmount() 중복 방지 로직이 우회됨

ReconcileService는 IReconcileService 인터페이스를 구현합니다. ICoreBankingAdapter와 PgNftHoldingRepository를 컴포지션으로 소유합니다. Reconcile은 두 데이터 소스를 비교합니다. 온체인 잔액(EVM 직접 조회)과 DB 보유 현황(PgNftHoldingRepository)입니다. 불일치 시 NotifierAdapter로 알림을 보냅니다.

ReconcileAdminService는 ReconcileService를 컴포지션으로 소유하며 Admin HTTP 엔드포인트를 노출합니다. ReconcileService를 직접 index.ts에 노출하지 않고 Admin 서비스로 한 번 더 감싸서 Admin 전용 기능(스케줄 실행, 이력 조회)을 추가할 수 있게 합니다.

클래스관계구성 요소역할
PgNftHoldingRepositoryPool 주입pooluser_nft_holdings 읽기 전용 조회
ReconcileServiceIReconcileService 구현, 컴포지션ICoreBankingAdapter, PgNftHoldingRepository온체인 vs DB 잔액 대조
ReconcileAdminService컴포지션ReconcileService, ICoreBankingAdapter, NotifierAdapterAdmin HTTP 인터페이스 제공

ReconcileService는 발행 파이프라인과 완전히 독립 — Admin 요청 또는 스케줄러가 직접 호출. 실패해도 발행 파이프라인에 영향 없음

STEP 7 — 스트림 파이프라인 조립

스트림 파이프라인은 Webhook 수신 → Redis 적재 → Consumer 처리 순서로 흐릅니다. 각 클래스의 관계를 따라가면 이 흐름이 보입니다.

7-1. Webhook 수신 → Redis 적재

WebhookPublishHandler는 RedisStreamPublisher와 IdempotencyGuard를 컴포지션으로 소유합니다. createHandler()가 반환하는 함수는 "멱등 체크 후 Redis에 적재"를 하나로 묶은 클로저입니다.

WebhookServer는 WebhookPublishHandler를 직접 소유하지 않습니다. on(eventType, handler)로 핸들러 함수를 등록받을 뿐입니다. 이 핸들러가 webhookPublishHandler.createHandler()가 반환한 함수입니다. 느슨한 연결입니다.

ProcessedEventHandler는 LedgerService를 컴포지션으로 소유합니다. ChainEventListener에 등록되어 온체인 이벤트가 이미 처리됐는지 확인하고 중복 처리를 막습니다.

WebhookPublishHandler *-- RedisStreamPublisher  ← 컴포지션
WebhookPublishHandler *-- IdempotencyGuard      ← 컴포지션
RedisStreamPublisher  *-- RedisStreamClient     ← 컴포지션

WebhookServer --> WebhookPublishHandler         ← .on()으로 핸들러 등록 (약한 참조)

ProcessedEventHandler *-- LedgerService         ← 컴포지션
IEventHandler <|.. ProcessedEventHandler        ← 구현
IEventHandler <|.. IssuanceConfirmHandler       ← 구현
7-2. Redis Consumer → Processor

ConsumerGroupWorker는 RedisConsumerClient, EventProcessor[], DLQHandler를 컴포지션으로 소유합니다. XREADGROUP으로 메시지를 꺼내 EventProcessor.process()를 호출합니다.

NFTIssuedProcessor와 ActivityProcessor는 모두 EventProcessor 인터페이스를 구현합니다. ConsumerGroupWorker는 어떤 Processor인지 모릅니다. 인터페이스를 통해서만 호출합니다.

Consumer GroupProcessor구현 인터페이스컴포지션 의존성최종 호출
nft-consumers NFTIssuedProcessor EventProcessor IdempotencyGuard, NFTLedgerService PgNFTLedgerService.creditNFT()
activity-consumers ActivityProcessor EventProcessor IdempotencyGuard, IActivityIssuer IssuerService.issueActivityNFT() 
EventProcessor <|.. NFTIssuedProcessor    ← 구현
EventProcessor <|.. ActivityProcessor     ← 구현
NFTIssuedProcessor *-- IdempotencyGuard   ← 컴포지션
NFTIssuedProcessor *-- NFTLedgerService   ← 컴포지션 (인터페이스로 주입)
ActivityProcessor  *-- IdempotencyGuard   ← 컴포지션
ActivityProcessor  *-- IActivityIssuer    ← 컴포지션 (인터페이스로 주입)

ConsumerGroupPool   *-- ConsumerGroupWorker ← 컴포지션 (Worker 배열 관리)
ConsumerGroupWorker *-- EventProcessor      ← 컴포지션 (인터페이스로 주입)
ConsumerGroupWorker *-- DLQHandler          ← 컴포지션
ConsumerGroupWorker *-- RedisConsumerClient ← 컴포지션

DLQHandler *-- DLQRedisClient  ← 컴포지션
DLQHandler *-- DLQNotifier     ← 컴포지션

STEP 8 — 이벤트 수신 서버 기동

마지막으로 두 이벤트 수신 채널이 기동됩니다.

ChainEventListener는 IBlockchainAdapter와 IEventHandler[]를 컴포지션으로 소유합니다. 폴링 루프를 돌면서 새 블록을 감지하면 등록된 핸들러의 handle()을 순서대로 호출합니다. Phase 1에서는 IssuanceConfirmHandler와 ProcessedEventHandler 두 핸들러가 등록됩니다.

WebhookServer는 .on(eventType, handler)로 세 가지 이벤트 타입을 처리합니다. ACTIVITY_ACHIEVED와 NFT_ISSUED는 Redis Stream에 적재되는 경로이고, VASP_TX_FAILED는 Redis를 우회해 IssuerService.handleVaspTxFailed()를 즉시 호출합니다. TX 실패는 재시도 대기 없이 즉각 처리해야 하기 때문입니다.

ChainEventListener *-- IBlockchainAdapter  ← 컴포지션 (EVMAdapter 주입)
ChainEventListener *-- IEventHandler       ← 컴포지션 (핸들러 배열)

// 핸들러 등록 (ChainEventListener)
listener.addHandler(issuanceConfirmHandler);  // IEventHandler 구현체
listener.addHandler(processedEventHandler);   // IEventHandler 구현체

// 핸들러 등록 (WebhookServer)
webhookServer
  .on('ACTIVITY_ACHIEVED', webhookPublishHandler.createHandler())
  //   → IdempotencyGuard.run() → RedisStreamPublisher.publish() → XADD
  .on('NFT_ISSUED',        webhookPublishHandler.createHandler())
  //   → 동일 경로 → Redis → NFTIssuedProcessor → PgNFTLedgerService
  .on('VASP_TX_FAILED',    issuerService.handleVaspTxFailed)
  //   → IssuerService 직접 호출 (Redis 우회)

VASP_TX_FAILED만 Redis를 우회 — TX 실패 알림은 지연 없이 issuance_requests를 즉시 FAILED로 전이해야 하기 때문

세 경로 — 클래스 연결 전체 조망

Bootstrap이 완료되면 발행·확인 경로가 세 개 작동합니다. 어떤 클래스가 어떤 관계로 연결되어 있는지를 경로별로 따라가 보겠습니다.

경로 1 — Phase 1: 동기 발행 구간 (ActivityProcessor → issuance_requests SUBMITTED)
ActivityProcessor.process(msg)            ← EventProcessor 구현, ConsumerGroupWorker가 호출
  → IActivityIssuer.issueActivityNFT()     ← 인터페이스 호출 (IssuerService가 구현)
    → IssuancePolicyService.getPolicy()    ← 컴포지션 호출
    → EventConditionService.evaluate()    ← 컴포지션 호출
    → IVASPAdapter.screenAddress()        ← 컴포지션 호출 (AML)
    → ICoreBankingAdapter.getUserAccount()← 컴포지션 호출
    → IIssuanceRequestRepository.create() ← 컴포지션 호출 → issuance_requests INSERT
    → LedgerService.createMintRequest()   ← 컴포지션 호출 → mint_requests INSERT
    → TxStateMachineService.submitMintRequest()  ← 컴포지션 호출
      → VaspTxClient.submitMint()         ← 컴포지션 호출
        → VaspTxClientAdapter             ← VaspTxClient 구현
          → IVASPAdapter.submitTransaction() ← 컴포지션 호출
            → ExternalVASPAdapter         ← IVASPAdapter 구현, HTTP POST /transactions
      → TxRepository.save(SUBMITTED)      ← 컴포지션 호출

이 구간이 끝나면 제어권이 TxStateMachineService로 넘어감 — 이후 상태 전이는 이벤트 기반(Phase 2A/2B)으로 진행

경로 2 — Phase 2A: VASP 콜백 → NFT 원장 갱신
ExternalVASP → HTTP POST /webhook (NFT_ISSUED)
  → WebhookServer HMAC 검증 → 202 즉시 응답
  → WebhookPublishHandler.createHandler()() 비동기 실행
    → IdempotencyGuard.run()              ← 컴포지션 호출 (중복 방지)
    → RedisStreamPublisher.publish()      ← 컴포지션 호출
      → RedisStreamClient.xadd()         ← 컴포지션 호출 → Redis XADD

ConsumerGroupWorker (nft-consumers)
  → NFTIssuedProcessor.process(msg)      ← EventProcessor 구현 호출
    → IdempotencyGuard.run()             ← 컴포지션 호출 (2차 중복 방지)
    → NFTLedgerService.creditNFT()       ← 인터페이스 호출 (PgNFTLedgerService가 구현)
      → ICoreBankingAdapter.recordNftHolding() ← 컴포지션 호출
        → InternalGatewayClient HTTP POST → Java → user_nft_holdings INSERT
경로 3 — Phase 2B: 체인 직접 폴링 → issuance_requests CONFIRMED
ChainEventListener.poll() 루프
  → IBlockchainAdapter.queryEvents()     ← 컴포지션 호출 (EVMAdapter가 구현)
    → 온체인 Issued 이벤트 감지
  → IssuanceConfirmHandler.handle()      ← IEventHandler 구현 호출
    → TxRepository.findByTxHash()        ← 컴포지션 호출
    → TxStateMachineService.handleMined()← 컴포지션 호출
      → TxRepository.updateStatus(MINED) ← 컴포지션 호출
      → emit('transition', MINED)        ← EventEmitter 이벤트 발행
    → TxStateMachineService.handleConfirmed()
      → TxRepository.updateStatus(CONFIRMED)
      → emit('transition', CONFIRMED)
        → TxTransitionBridge._handler()  ← .on() 구독 수신
          → LedgerService.updateMintRequest(CONFIRMED) ← 컴포지션 호출
          → IIssuanceRequestRepository.updateStatus(CONFIRMED) ← 컴포지션 호출
          → ICoreBankingAdapter.recordNftHolding() ← 컴포지션 호출 (CONFIRMED 시 추가)
          → ICoreBankingAdapter.recordAuditLog()   ← 컴포지션 호출

  → ProcessedEventHandler.handle()       ← IEventHandler 구현 호출
    → LedgerService.recordProcessedEvent() ← 컴포지션 호출 (중복 처리 방지 마킹)

Phase 2A와 Phase 2B가 모두 완주하더라도 안전 — TxStateMachineService의 상태 전이 가드가 이미 CONFIRMED된 요청에 대한 재전이를 InvalidStateTransitionError로 차단. Bridge는 이 예외를 catch하고 무시함
