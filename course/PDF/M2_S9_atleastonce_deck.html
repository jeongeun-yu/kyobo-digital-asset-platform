두 저장소 문제 — 핵심 질문

THE TWO-STORAGE PROBLEM

저장소 A — Redis (PEL)

  • XACK → PEL에서 메시지 제거
  • "이 메시지를 내가 책임지고 처리했다"
  • 큐 시스템의 영수증

저장소 B — DB (원장)

  • COMMIT → user_nft_holdings +1
  • "실제 비즈니스 처리가 완료됐다"
  • 데이터 변경의 원자적 확정
문제 — 두 저장소는 독립적이다. DB 커밋과 Redis XACK를 하나의 트랜잭션으로 묶을 수 없다. Redis는 XA 프로토콜(2PC)을 지원하지 않는다.
선택 — 두 저장소 중 하나가 반드시 "뒤처지는 순간"이 존재한다. 어느 쪽을 뒤처지게 할 것인가? → 이것이 설계의 핵심이다.

Exactly-once는 왜 불가능한가

WHY EXACTLY-ONCE IS IMPRACTICAL

방식문제결과판정
XACK → DB
ACK 먼저		 ACK 후 DB 실패 → PEL 없음 → 재수신 불가 데이터 영구 유실 ❌ 치명적
DB → XACK
커밋 먼저		 DB 커밋 후 XACK 실패 → PEL 재수신 → 중복 처리 가능 중복 (복구 가능) △ 멱등성 필요
2PC
분산 트랜잭션		 Redis가 XA 미지원 · 구현 복잡도 폭발 · 성능 저하 현실적 불가 ❌ 비현실
At-least-once
+ 멱등성		 DB 커밋 먼저, XACK 나중. 중복 수신 시 멱등성이 차단 정합성 보장 ✅ 현실 해법
결론 — Exactly-once = 이상  /  At-least-once + 멱등성 = 현실적 정답

올바른 처리 순서 — 4단계 불변 규칙

THE FOUR-STEP INVARIANT

4단계 순서 (절대 불변)

  • Step 1 — 멱등성 확인 → 이미 처리됐으면 XACK + 종료
  • Step 2 — DB 트랜잭션 시작 (원장 업데이트)
  • Step 3 — 트랜잭션 커밋 (원자적 완료)
  • Step 4 — XACK (PEL 제거, "처리 완료" 선언)

각 단계가 그 위치에 있는 이유

  • 멱등성 먼저 — 중복 수신 시 DB 접근 없이 차단
  • DB 원자성 — 원장+상태 전이 중 장애 시 전체 롤백
  • XACK 마지막 — ACK 전 장애 → PEL 재수신 → 멱등성 차단
XREADGROUP (메시지 수신 + PEL 등록) │ ├─ Step 1: 멱등성 확인 ── 이미 처리? → XACK만 실행 후 종료 │ ├─ Step 2+3: DB 트랜잭션 커밋 │ └─ Step 4: XACK ← 절대 마지막 (XACK 전 크래시 = PEL 잔류 = 재수신 가능)
위반 시 — XACK를 Step 1보다 먼저 하면 DB 실패 후 재수신 불가 → 원장 누락 → 감사 실패
