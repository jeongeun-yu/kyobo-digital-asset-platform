무한 재시도는 왜 위험한가

THE PROBLEM WITH INFINITE RETRY

재시도가 유효한 경우 (일시적 장애)

  • DB 연결 오류 (일시적) → 재시도 → 성공 ✅
  • 외부 API 타임아웃 → 재시도 → 성공 ✅

재시도해도 소용없는 경우 (영구 장애)

  • 코드 버그 → 항상 같은 위치에서 throw → 재시도 → 또 실패 ❌
  • 스키마 불일치 → payload 파싱 오류 → 재시도 → 또 오류 ❌
  • 비즈니스 규칙 위반 → 데이터 자체가 잘못됨 → 재시도 → 또 실패 ❌

재시도만 있을 때 발생하는 4가지 문제

msg-bug → 처리 실패 → retryCount+1 → PEL 잔류 msg-bug → 처리 실패 → retryCount+1 → PEL 잔류 msg-bug → 처리 실패 → retryCount+1 → PEL 잔류 ... 결과: ① PEL이 계속 쌓임 → Redis 메모리 압박 ② Consumer가 계속 처리 시도 → 정상 메시지 지연 ③ 운영자가 장애를 인지하지 못함 ④ 코드 버그가 있어도 아무도 알 수 없음
결론 — 영구 실패 메시지를 재시도 큐에서 격리해야 정상 메시지 처리가 막히지 않는다.

DLQ — 불량품 격리 창고 비유

DLQ IS NOT A GRAVEYARD — IT IS A TEMPORARY ISOLATION WARD

공장 생산 라인 비유

일반 라인: 상품 검사 → 합격 → 출하 불량 발견: 상품 검사 → 불합격 → 즉시 격리 불량품을 격리하지 않으면: → 계속 같은 라인 돌면서 기계 막힘 → 합격 상품 처리 지연 → 불량 원인 파악 안 됨 DLQ = 불량품 격리 창고 처리 실패 N회 → 원 스트림에서 격리 → DLQ로 → 원 스트림은 정상 메시지만 처리 (막힘 없음) → 운영자가 DLQ에서 불량 원인 분석 → 원인 수정 후 → 재투입 (requeueMessage)

DLQ 전체 생명주기

정상 처리: Streams → Consumer → 성공 → XACK ✅ DLQ 진입: Consumer 실패 → retryCount+1 → PEL (3회 누적) → dlq.move() — dlq 스트림에 XADD → 운영팀 알림 발송 → 원 스트림 XACK (PEL 정리) DLQ 탈출: listPending() → 실패 메시지 확인 → 원인 분석 (코드/데이터/외부서비스) → 원인 수정 (배포 or 데이터 정정) → requeueMessage(dlqMessageId) → Consumer가 재처리 → XACK ✅

requeueMessage() — 6단계 흐름

REQUEUE — THE RESCUE OPERATION (DLQHandler.ts:116)

async requeueMessage( dlqMessageId: string, targetStreamKey?: string, // 선택적 — 다른 스트림으로 라우팅 가능 ): Promise<{ newMessageId: string }> { // ① DLQ에서 메시지 조회 (start=end=id → 1건만) const [entry] = await this.redis.xrange( dlqStreamKey, dlqMessageId, dlqMessageId, 1 ); if (!entry) throw new DLQMessageNotFoundError(dlqMessageId); // ② // ③ 목적지 스트림: 인자 → 원본 메타 → 기본값 const targetKey = targetStreamKey ?? entry.fields['_originalStream'] ?? 'kyobo:events'; // ④ _ 시작 DLQ 메타 필드 제거 → 비즈니스 필드만 추출 const requeueFields: Record<string, string> = {}; for (const [k, v] of Object.entries(entry.fields)) { if (!k.startsWith('_')) requeueFields[k] = v; } // ⑤ 재투입 추적 메타 추가 requeueFields['_requeuedFrom'] = dlqMessageId; requeueFields['_requeuedAt'] = new Date().toISOString(); const newMessageId = await this.redis.xadd(targetKey, requeueFields); // ⑥ 원 스트림 적재 await this.redis.xdel(this.dlqStreamKey, dlqMessageId); // ⑦ DLQ 삭제 return { newMessageId }; }

6단계 흐름 요약

① DLQ에서 메시지 조회 (xrange start=end=id) ② 존재 확인 → 없으면 커스텀 에러 throw ③ 목적지 결정: 인자 → 원본 메타 → 기본값 ④ _ 메타 필드 제거 → 비즈니스 필드만 ⑤ 추적 메타 추가 (_requeuedFrom, _requeuedAt) ⑥ 원 스트림에 XADD (새 messageId 발급) ⑦ DLQ에서 XDEL (영구 제거)
⑤ 추적 메타 용도 — 감사 로그 추적, 무한 루프 감지 (_requeuedFrom 체인 분석), Consumer가 재처리 케이스 인지.
⑥→⑦ 사이 크래시 — xadd 성공 + xdel 실패 → 원 스트림과 DLQ 양쪽에 메시지 존재. 멱등성 또는 Lua로 보완.

메타 필드 _ prefix 컨벤션의 힘

UNDERSCORE PREFIX CONVENTION — AUTO FILTERING METADATA

필드 구분 원칙

분류필드 예시처리
비즈니스eventType, payload, txHash, requestId재투입 시 그대로 전달
DLQ 메타_originalStream, _reason, _failedAt재투입 시 제거
재투입 메타_requeuedFrom, _requeuedAt추적용으로 신규 추가
핵심 코드 한 줄 — if (!k.startsWith('_')) requeueFields[k] = v;
_ prefix 컨벤션 덕에 자동 필터링. 새 메타 필드 추가 시 코드 변경 없음.

왜 이 컨벤션이 강력한가

  • 새 메타 필드 추가 시 자동 처리 (코드 변경 X)
  • Consumer가 메타와 비즈니스 데이터 한눈에 구분
  • 디버깅 시 "이건 시스템이 추가한 거" 즉시 인지

xrange 단건 조회 패턴

// start = end = dlqMessageId → 정확히 1건만 xrange(dlqStreamKey, dlqMessageId, dlqMessageId, 1) // count=1 → 안전장치 // Redis Streams는 messageId 중복 없지만 방어적 코드
방어적 코딩 — count 없으면 모든 매칭 반환. 정상 Redis라도 "혹시 모를 중복" 대비해 count=1 명시.

⑥⑦ 사이의 위험 — xadd + xdel은 원자적이지 않다

NON-ATOMIC XADD + XDEL — PARTIAL FAILURE MITIGATION

부분 실패 시나리오

T+0: ⑥ xadd 성공 (원 스트림에 새 메시지 적재됨) T+1: 네트워크 끊김 또는 프로세스 죽음 T+2: ⑦ xdel 못 함 (DLQ에 원본 그대로) 결과: 같은 메시지가 원 스트림 + DLQ 양쪽에 존재 운영자가 같은 ID로 또 requeue 호출 → 추가 중복
왜 문제인가? — Consumer가 원 스트림에서 처리 완료 후 운영자가 DLQ에서 또 requeueMessage 호출 → 2중 처리 위험.

실무 해법 3가지

해법 1: Lua 스크립트 (원자적)

-- Redis에서 xadd + xdel을 원자적으로 실행 local newId = redis.call('XADD', targetKey, ...) redis.call('XDEL', dlqKey, dlqId) return newId

해법 2: Consumer 측 멱등성

_requeuedFrom 체크 → 이미 처리한 dlqMessageId면 무시. 항상 멱등하게 만드는 것이 황금률.

해법 3: 트랜잭션 + 보상 작업

xadd 성공 → DB에 "requeue 진행 중" 기록 → xdel 실패 시 별도 cleanup 워커가 처리.

현실 — 운영 도구는 보통 해법 2(멱등성)에 의존. 운영자가 같은 ID로 재호출해도 첫 번째 한 번만 효과.

왜 requeueMessage는 수동 호출인가

WHY MANUAL REQUEUE — AUTOMATIC REQUEUE IS DANGEROUS

자동 재투입 안 하는 3가지 이유

  • ① 영구 실패 메시지의 무한 루프
DLQ 도착 → 자동 재투입 → 또 실패 → 또 DLQ → 자동 재투입 → ... 코드 버그가 원인이면 영원히 반복 = 시스템 리소스 낭비
  • ② 원인 파악 없는 재투입은 위험

데이터 문제? 외부 의존성? 코드 버그? 사람이 분석 후 결정해야 함.

  • ③ 부분 처리된 데이터 정리 필요

외부 API 호출, 이메일 발송 등 사이드 이펙트. 재투입 전 cleanup 필요할 수 있음.

올바른 DLQ 운영 패턴

DLQ 도착 → 알림 (Slack/Email) ↓ listPending() → 실패 메시지 목록 확인 ↓ 원인 파악 버그? → 코드 수정 + 배포 데이터? → 데이터 정정 외부서비스? → 복구 확인 ↓ requeueMessage(dlqMessageId) ← 이 함수 ↓ Consumer가 재처리 → 성공 → XACK ✅ ↓ 실패 시 → 또 DLQ 진입 → 즉시 알림 (2회 DLQ = 비즈니스 로직 버그 강력 의심)
핵심 — requeueMessage는 운영자의 "구조 작업". 분석 → 수정 → 구조의 마지막 단계. 자동화는 루프를 만들 뿐.

이 세션에서 새로 등장한 TypeScript 문법

NEW TYPESCRIPT PATTERNS IN S11

선택적 매개변수 ?:

targetStreamKey?: string
생략 가능 → 함수 안에서 undefined. string | undefined와 동일. 점진적 기능 추가에 유리.

인라인 반환 타입

Promise<{newMessageId: string}>
별도 interface 없이 즉석 타입 명시. 호출자가 result.newMessageId로 접근.

배열 구조 분해

const [entry] = await xrange(...)
xrange는 배열 반환 → 첫 요소만 entry로. 비어있으면 entry = undefined.

커스텀 에러 클래스

throw new DLQMessageNotFoundError(id)
호출자가 instanceof로 잡을 수 있음. 일반 Error보다 의미 명확. 에러 타입별 분기 처리 가능.

?? 연쇄 (fallback chain)

a ?? b ?? c
왼쪽부터 차례로: 인자 → 원본 메타 → 기본값. 셋 다 nullish면 마지막 사용. 우선순위 명시적 표현.

Record<string, string>

키와 값이 모두 string인 객체 타입. {} 빈 객체로 시작해서 동적으로 채움. Redis Streams의 fields 타입.

Object.entries(obj)

{a:1, b:2} → [['a',1],['b',2]]
객체를 [key,value] 쌍 배열로. for...of 루프 가능. 모던 객체 순회 패턴.

for...of + 구조 분해

for (const [k, v] of Object.entries(...))
각 entry가 [key, value] → 즉석에서 k, v로 분해. 일반 for 루프보다 깔끔.

startsWith('_')

문자열 prefix 검사. _ 로 시작 = DLQ 메타 필드 표식. 한 줄 코드로 자동 필터링.

new Date().toISOString()

ISO 8601 형식 반환. 예: 2026-05-13T09:00:00.000Z. 로그/DB 저장 표준 형식.

강의 강조 포인트 — 핵심 암기

KEY TAKEAWAYS — MUST REMEMBER

설계 원칙

  • DLQ는 무덤이 아니라 임시 격리 — requeue로 살려낼 수 있어야 완전한 시스템
  • 운영자 수동 호출이 핵심 — 자동화 = 무한 루프 위험
  • 알림 비동기 처리 — .catch() 패턴. 알림 실패가 DLQ 이동을 차단하면 안 됨
  • DLQ 이동 후 반드시 XACK — 안 하면 원 스트림 PEL에 계속 잔류

구현 세부

  • _ prefix 컨벤션 — 메타와 비즈니스 데이터 자동 분리. 새 메타 추가 시 코드 변경 없음
  • fallback 체인 ?? — 인자 → 원본 메타 → 기본값. 우선순위 명시
  • xrange start=end+count=1 — 단건 조회 방어적 패턴
  • xadd+xdel 비원자성 — 부분 실패 대비 멱등성 또는 Lua 필요
  • _requeuedFrom 체인 — 메시지 추적성 보존, 무한 루프 감지
  • 커스텀 에러 클래스 — DLQMessageNotFoundError → 호출자 친화적 분기
한 줄 정리 — requeueMessage는 DLQ 격리 메시지를 운영자가 분석 후 원 스트림으로 되돌리는 6단계 함수. 수동 호출이 원칙. 핵심은 _ 컨벤션과 멱등성 — 부분 실패에도 정합성 유지.
