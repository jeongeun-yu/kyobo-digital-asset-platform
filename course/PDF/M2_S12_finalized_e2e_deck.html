왜 Finalized 블록 기준인가 — 블록 확정 단계

WHY FINALIZED — BLOCKCHAIN REORG AND FINALITY

블록 확정 3단계

단계상태안전성
PENDING아직 마이닝 안 됨처리 금지
CONFIRMED마이닝됨, but Reorg 가능위험
FINALIZEDPoS Checkpoint 통과, 절대 불변처리 가능
Ethereum PoS Finality — 블록 생성 후 2 epochs(약 12분) 뒤 Finalized. 약 64블록 이상.

Reorg(체인 재편)가 일어나면

블록 #100에 NFT 발행 TX 포함 → 원장 업데이트 완료 (CONFIRMED에서 처리) → 체인 재편: 블록 #100이 고아 블록(Orphan) → TX가 없던 일이 됨 → 원장에는 NFT 발행 기록 남음 (불일치!) Finalized 이전에 처리하면: = 존재하지 않는 NFT 발행 기록 = 회계 불일치 = 감사 실패
금융 시스템에서 Finalized 검증은 필수 — 미확정 블록 처리 = 잠재적 손실. Phase 1: IBlockchainAdapter.getReceipt()로 read-only 조회 방식.

process() — 3단계 처리 라인별 해부

THREE-STEP PROCESSING: FINALITY → IDEMPOTENCY → LEDGER

async process(message: StreamMessage): Promise<void> { const payload = JSON.parse(message.fields['payload'] ?? '{}'); const requestId = message.fields['requestId'] ?? message.id; // requestId fallback: 명시적 ID → Redis messageId // Step 1: Finalized 블록 검증 if (this.finalizedBlockProvider && payload.blockNumber != null) { const finalized = await this.finalizedBlockProvider .getFinalizedBlockNumber(); if (payload.blockNumber > finalized) { throw new DeferredProcessingError( `block ${payload.blockNumber} not yet finalized` ); // retryCount 증가 없음 — "실패"가 아닌 "지연" } } // Step 2+3: 멱등성 확인 → 원장 업데이트 await this.idempotency.run(`NFTIssued:${requestId}`, async () => { await this.ledger.creditNFT(payload.to, payload.tokenId); }); }

DeferredProcessingError — "실패"와 "지연"의 구분

DEFERRED vs ERROR — CRITICAL DESIGN DISTINCTION

throw 방식별 Worker 반응

상황throw 방식retryCount결과
DB 연결 실패new Error(...)+13회 후 DLQ
외부 API 타임아웃new Error(...)+13회 후 DLQ
블록 미확정new DeferredProcessingError유지PEL 잔류 → 자동 처리
왜 return이 아닌 throw? — return하면 Worker가 성공으로 간주 → XACK 호출 → 메시지 영구 소실. throw DeferredProcessingError → Worker가 특수 분기 진입 → PEL 잔류.

Worker 측 처리 (추정 코드)

try { await processor.process(msg); await xack(...); // 성공 } catch (err) { if (err instanceof DeferredProcessingError) { // 카운트 안 올림, XACK 안 함 // 시간 지나면 _reclaimPending()이 재수신 return; } // 일반 에러 → retryCount 증가 msg.fields['_retryCount'] = String(retryCount + 1); }
핵심 통찰 — DB 실패 = 시스템 문제 → 빨리 알아채야 함 → DLQ. 블록 미확정 = 시간 지나면 해결 → 기다리면 됨. 같은 throw지만 의미가 다르다.

FinalizedBlockProvider — 블록체인 finalized 블록 번호 반환. 이 번호 이하 블록은 "절대 뒤집히지 않음" 보장.

이 세션에서 새로 등장한 TypeScript 문법

NEW TYPESCRIPT PATTERNS IN S12

implements EventProcessor

클래스가 인터페이스를 만족함을 명시. 필드/메서드 모두 구현해야 컴파일 통과. 단순 형태 맞추기가 아닌 명시적 약속.

readonly eventTypes

한 번 정해지면 변경 불가. 외부에서 processor.eventTypes = [...] 시도 → 컴파일 에러. 사실상 상수.

private readonly 생성자

별도 필드 선언 없이 생성자 매개변수에서 바로 this.x = x 처리. TS 보일러플레이트 절약.

선택적 의존성 ?:

finalizedBlockProvider?: FinalizedBlockProvider
없으면 undefined. Finalized 검증 없이도 동작. 점진적 기능 활성화.

!= null 관용

payload.blockNumber != null
느슨한 비교로 null과 undefined 둘 다 검사. !== null && !== undefined의 단축형. 의도적 예외.

throw new DeferredProcessingError

커스텀 에러 클래스. Worker가 instanceof로 잡아 특별 처리. 일반 Error와 의미 구분. "실패"와 "지연" 분리.

idempotency.run(key, callback)

함수를 인자로 넘기는 콜백 패턴. run()이 키 체크 후 신규일 때만 콜백 실행. 멱등성 로직 캡슐화.

JSON.parse(str ?? '{}')

payload 없으면 빈 객체 JSON. 파싱 결과는 {} → undefined 접근 안전. 잘못된 JSON이면 throw → DLQ.

requestId ?? message.id

우선순위 fallback. 비즈니스 ID → 큐 자동 생성 ID. Redis messageId는 고유 보장. 멱등성 키로 충분.

멱등성 키 네임스페이스

NFTIssued:${requestId} — 이벤트 타입 접두사로 충돌 방지. NFTBurned와 NFTIssued는 같은 requestId도 별도 키.

Consumer 장애 복구 실습 시나리오 + CLI 검증

CONSUMER CRASH RECOVERY — XAUTOCLAIM IN ACTION

장애 복구 시나리오 8단계

1. ConsumerGroupWorker 실행 중 2. 메시지 XREADGROUP으로 소유 (PEL 등록) 3. 처리 중 Ctrl+C (강제 종료) 4. XACK 안 됨 → PEL에 메시지 잔류 5. minIdleMs(30초) 경과 6. Consumer 재시작 7. _reclaimPending() → XAUTOCLAIM으로 재수신 8. 정상 처리 + XACK ✅ 멱등성 덕에 재처리해도 원장 중복 없음

M2 모듈 완료 기준 체크리스트 + 강의 강조 포인트

M2 COMPLETION CRITERIA & KEY TAKEAWAYS

M2 완료 기준 (6가지)

  • At-least-once + 멱등성 — 동일 이벤트 2회 → 원장 1회만 반영
  • 장애 복구 — Consumer 강제 종료 → 재시작 후 미ACK 자동 재수신
  • DLQ — 3회 실패 → DLQ 이동 + 알림
  • Finalized 체크 — 미확정 이벤트 → 처리 보류 (XACK 안 함)
  • E2E — Webhook → Stream → Consumer → 원장 1건 완주
  • 수평 확장 — Consumer 2개 동시 → 중복 처리 없음

S12 강의 강조 포인트

  • implements로 명시적 계약 — 시그니처 어긋나면 컴파일 에러
  • readonly 클래스 필드 — 인스턴스 생성 후 변경 불가
  • DeferredProcessingError 패턴 — "재시도 실패"와 "지연"을 구분
  • 블록체인 reorg 인식 — 금융 시스템에서 Finalized 검증 필수
  • 멱등성 키 네임스페이스 — EventType:requestId 형식으로 충돌 방지
  • 인터페이스 의존 = 미래 교체 비용 0 — M4에서 LedgerService 교체해도 그대로
  • 3단계의 미묘한 차이 — Finalized=사전 조건, 멱등성=중복 방지, 원장=실제 효과

THREE RELIABILITY PRINCIPLES OF M2 EVENT PIPELINE

원칙 1

At-least-once + 멱등성

"최소 1회 처리 보장 + 중복 발행 차단" DB unique constraint + ON CONFLICT DO NOTHING → 중복 수신해도 원장은 1회만 반영
S9에서 설계 → S10에서 구현
원칙 2

PEL + XAUTOCLAIM

"Consumer 장애 시 미처리 메시지 자동 복구" XACK를 마지막 단계로 → PEL에 잔류 → 30초 후 재수신 멱등성이 중복 차단 → 재처리해도 안전
S7 CLI 실습 → S10 코드 구현
원칙 3

DLQ + 알림

"3회 실패 메시지 격리 + 운영자 개입 유도" 무한 재시도 대신 격리 → 원인 파악 → 수동 requeueMessage 큐 막힘 없음 운영자가 즉시 인지
S11 DLQ 설계 → S10 연결
M3 예고 — M2: "이벤트가 도착했을 때 어떻게 안전하게 처리하는가" → M3: "TX를 보냈을 때 블록체인이 어떤 경로로 실패하는가, 각각 어떻게 복구하는가" (TxStateMachineService 7-상태 머신)
