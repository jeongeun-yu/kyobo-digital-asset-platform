THE FOUR-BRANCH DISPATCHER (ConsumerGroupWorker.ts:164)

const eventType = msg.fields['eventType'] ?? ''; const retryCount = parseInt(msg.fields['_retryCount'] ?? '0', 10); // 분기 ①: 3회 초과 → DLQ if (retryCount >= this.MAX_RETRIES) { await this.dlq.move({ messageId: msg.id, event: msg.fields, reason: `max retries exceeded`, failedAt: new Date(), ... }); await this.redis.xack(streamKey, groupName, msg.id); // DLQ 이동 후 반드시 XACK return; } const processors = this.processors.filter(p => p.eventTypes.includes(eventType)); // 분기 ②: 처리자 없음 → 무시 if (processors.length === 0) { await this.redis.xack(streamKey, groupName, msg.id); return; } try { // 분기 ③: 처리 성공 → XACK await Promise.all(processors.map(p => p.process(msg))); await this.redis.xack(streamKey, groupName, msg.id); } catch (err) { // 분기 ④: 처리 실패 → XACK 없음 → PEL 잔류 msg.fields['_retryCount'] = String(retryCount + 1); }

_handleWithRetry() — 5가지 책임과 분기 세부 설명

FIVE RESPONSIBILITIES — BRANCH ANALYSIS

5가지 책임 (단일 진입점)

  • ① 메시지 메타데이터 추출 (eventType, retryCount)
  • ② 재시도 한도 체크 → 초과 시 DLQ 이동 + XACK
  • ③ 처리자 매칭 → 없으면 XACK + 무시
  • ④ 실제 처리 실행 (Promise.all 병렬)
  • ⑤ 결과에 따른 ACK 결정 (성공 → XACK, 실패 → PEL 잔류)
분기 ② DLQ 이동 후 XACK 필수 — DLQ만 하고 XACK 안 하면 무한 재수신. XACK만 하고 DLQ 안 하면 메시지 소실.

분기 ③ 처리자 없음 — 왜 무시하나

  • 새 이벤트 타입이 추가됐는데 이 워커는 옛 버전
  • "모르는 건 그냥 통과 → 큐 막힘 방지"
  • 주의 진짜 처리해야 할 이벤트인데 eventType 오타면 소실 → 모니터링 필수

분기 ④ 실패 시 주의점

  • _retryCount는 메모리 객체에만 변경됨
  • PEL 원본 fields는 변경 안 됨 (Redis Streams는 fields 불변)
  • 워커 재시작 또는 다른 워커 인계 시 → 카운트 리셋 (실무 한계)
실무 해법 — DB나 Redis Hash에 messageId → retryCount 별도 영속화

Promise.all 동작 정밀 분석

PROMISE.ALL — "ALL SUCCEED OR ALL RETRY"

병렬 실행 동작

await Promise.all([ ledgerProcessor.process(msg), auditProcessor.process(msg), notificationProcessor.process(msg), ]); // 셋 다 동시 시작 → 가장 오래 걸리는 것까지 대기 // 한 개라도 reject → Promise.all 즉시 reject // 다른 둘은 취소 안 됨 (이미 실행 중)
한 개 실패 → 메시지 전체 재시도 — 성공한 processor도 재시도 시 다시 실행됨. 모든 processor가 멱등해야 안전한 이유.

Promise.all vs Promise.allSettled

방식동작이 코드
Promise.all하나라도 실패 → 전체 reject사용
Promise.allSettled실패해도 나머지 계속 + 개별 결과미사용
설계 의도 — "전부 성공 아니면 전부 재시도" 정책. 부분 성공 허용 안 함 → 일관성 보장이 더 중요.

TS 문법 — 이 함수의 핵심 패턴

  • · parseInt(str, 10) — 10진수 명시 (관례)
  • · String(retryCount + 1) — Redis는 모든 field가 string
  • · array.filter(...).includes(...) — processor 매칭
  • · new Date() — Date 객체 (DLQ 타임스탬프)

재시도 메커니즘의 미묘한 함정 — _retryCount는 메모리 카운터

THE RETRY COUNT TRAP — MEMORY-ONLY COUNTER

무슨 일이 일어나는가

// 이 변경은 메모리 객체에만 적용됨 msg.fields['_retryCount'] = String(retryCount + 1); // Redis Streams는 적재 후 fields 변경 불가 // PEL은 messageId만 추적 (fields는 스트림 원본) // 다음 _reclaimPending이 PEL에서 가져오면 // → 원본 fields → _retryCount 다시 0?
결과 — 같은 워커 내 즉시 재처리 시 카운트 누적. 워커 재시작 또는 다른 워커 인계 시 카운트 리셋. MAX_RETRIES 보장 불완전.

실무 해법 3가지

  • ① DB 영속화
  • DB에 messageId → retryCount 저장
    _handleWithRetry 진입 시 외부에서 조회
  • ② Redis Hash 영속화
  • HSET retry-counts:{messageId} count {n}
  • ③ 시간 기반 DLQ 정책
  • idle 1시간 이상 PEL 메시지 → DLQ 이동
    재시도 횟수 대신 시간으로 판단
실습 수준에서는 — 메모리 카운터로도 충분. 구조를 이해하는 게 목적. 실무에서 보완 포인트를 알고 있으면 된다.

이 세션에서 새로 등장한 TypeScript 문법

NEW TYPESCRIPT PATTERNS IN S10

parseInt(str, 10)

문자열을 정수로 변환. 두 번째 인자 10 = 10진수 명시. 옛 환경에서 '08'을 8진수로 오해 방지 관례.

String(값)

어떤 타입이든 문자열로 변환. Redis Streams는 모든 field가 string. (n).toString()과 동일.

new Date()

현재 시각 Date 객체. Date.now()는 숫자(ms), new Date()는 객체. DLQ 기록에 객체가 더 유용(포맷팅 가능).

array.filter(p => p.includes(v))

조건 만족하는 것만 남김. includes(value)는 배열에 값 존재 여부 boolean. 한 줄로 "처리 가능한 processor만 추출".

Promise.all(arr.map(...))

배열을 각 Promise로 변환 후 병렬 실행. 하나라도 reject → 전체 reject. 부분 성공 허용 안 하는 "모두 또는 재시도" 정책.

msg.fields['key'] = value

객체 필드 동적 수정. 메모리 객체에만 적용, PEL 원본은 불변. 주의 포인트.

?? 연산자 (Nullish Coalescing)

msg.fields['x'] ?? '0' — x가 null/undefined이면 '0' 사용. 빈 문자열('')은 통과 (falsy 아님). ||와 차이.

try / catch 구조

start()의 try/catch = 워커 자체 보호. _handleWithRetry()의 try/catch = 메시지 단위 실패 처리. 계층적 오류 처리.

return으로 조기 종료

분기마다 명시적 return → 이후 코드 실행 안 함. 의도를 명확하게. else 중첩 없이 가독성 높임.

강의 강조 포인트 — 핵심 암기

KEY TAKEAWAYS — MUST REMEMBER

설계 원칙

  • 모든 메시지는 4분기 중 하나로 종결 — 누락 없는 결정 트리
  • XACK = 처리 끝 영수증 / DLQ = 포기 선언 — 둘 다 PEL 정리에 사용
  • Promise.all = "모두 성공 or 전부 재시도" — 부분 성공 없음
  • try/catch 위치가 전략 — start()는 워커 보호, _handleWithRetry()는 메시지 단위
  • DLQ 이동 후 반드시 XACK — 안 하면 무한 재수신

운영 관련

  • _retryCount는 메모리 카운터 — 분산/재시작 환경에선 불완전, 실무는 영속화
  • new Date()로 타임스탬프 — DLQ 운영자가 "언제 실패했는지" 추적
  • eventType 누락 방어 — ?? ''로 자동으로 처리자 없음 분기
  • DLQ도 멱등성 필요 — dlq.move 자체가 실패할 수 있음
  • 모니터링 지표 — DLQ 건수, 처리자 없음 무시 건수, 평균 retry 횟수 모두 알람 대상
한 줄 정리 — _handleWithRetry는 메시지 1건의 운명을 결정하는 4분기 디스패처. retry 한도면 DLQ, 처리자 없으면 무시, 처리 성공이면 XACK, 처리 실패면 PEL 잔류. 유일하게 XACK 안 하는 경우 = 처리 실패.

구현체 패턴

class NFTIssuedProcessor implements EventProcessor { readonly eventTypes = ['NFTIssued']; async process(msg: StreamMessage): Promise<void> { const event = JSON.parse(msg.fields['payload'] ?? '{}'); const key = `NFTIssued:${event.txHash}:${event.logIndex}`; await this.idempotencyGuard.run(key, async () => { await this.ledgerService.db.transaction(async trx => { await trx('mint_requests').where({...}) .update({ status: 'CONFIRMED' }); await trx('user_nft_holdings') .insert({...}).onConflict().merge(); }); }); } }

완료 기준 (4가지 시나리오 검증)

  • 시나리오 1 — retryCount ≥ MAX_RETRIES → DLQ 이동 ✅ + XACK ✅
  • 시나리오 2 — processor 없음 → XACK ✅ (호출 없음)
  • 시나리오 3 — 처리 성공 → XACK ✅
